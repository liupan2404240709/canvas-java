# 05 · 逻辑删除与回收站

## 一、一句话定位

`@TableLogic` 让删除变成 `UPDATE deleted=1`，好处是不丢数据，代价是**它会偷偷改掉你的所有 SQL**——回收站的两个接口必须手写。

## 二、完整代码

```java
// 删除：走内置方法，自动变成 UPDATE deleted=1
@Override
@Transactional(rollbackFor = Exception.class)
public void delete(Long userId, Long projectId) {
    requireProject(userId, projectId);
    projectMapper.deleteById(projectId);
}

// 回收站：手写 SQL 才能看到已删除的行
List<CanvasProject> selectTrash(@Param("userId") Long userId);

// 恢复：手写 UPDATE 才能改到已删除的行
int restore(@Param("id") Long id, @Param("userId") Long userId);
```

```xml
<select id="selectTrash" resultType="com.infinitecanvas.canvas.entity.CanvasProject">
    SELECT <include refid="columns"/>
    FROM t_canvas_project
    WHERE user_id = #{userId} AND deleted = 1
    ORDER BY updated_at DESC
</select>

<update id="restore">
    UPDATE t_canvas_project
    SET deleted = 0, updated_at = CURRENT_TIMESTAMP
    WHERE id = #{id} AND user_id = #{userId} AND deleted = 1
</update>
```

## 三、`@TableLogic` 到底改了哪些 SQL

| 你写的 | 实际执行的 |
| --- | --- |
| `selectById(id)` | `SELECT ... WHERE id=? AND deleted=0` |
| `selectList(wrapper)` | `SELECT ... WHERE (你的条件) AND deleted=0` |
| `updateById(entity)` | `UPDATE ... WHERE id=? AND deleted=0`（+ version 条件） |
| `update(entity, wrapper)` | `UPDATE ... WHERE (你的条件) AND deleted=0` |
| `deleteById(id)` | `UPDATE ... SET deleted=1 WHERE id=? AND deleted=0` |
| `delete(wrapper)` | `UPDATE ... SET deleted=1 WHERE (你的条件) AND deleted=0` |

**它只改内置方法**。手写的 XML / `@Select` 不受影响——这既是坑（要自己记得加 `deleted=0`），也是解法（回收站就是用这一点绕开它的）。

## 四、为什么删除时不清空节点

```java
projectMapper.deleteById(projectId);   // 只有这一行，节点和连线都没动
```

如果把节点也删了，回收站恢复出来的就是一张空画布——这比不提供回收站更糟。

反过来说，节点表**没有** `deleted` 列：它是附属数据，只有"跟随项目存在"和"跟随快照替换"两种状态，不需要独立的删除标记。

## 五、实测结果

```
删除                HTTP 200 code=0 "success"
删除后查详情         HTTP 404 code=40410 "画布不存在或已被删除"
回收站              HTTP 200 条数=1 含本画布=True
恢复                HTTP 200 code=0 "success"
恢复后详情          HTTP 200 nodes=1（节点应还在）
再次恢复            HTTP 404 code=40410 "画布不存在或已被删除"
```

四个关键点：

1. **删除后查详情返回 404 而不是 200 + null**——因为 `selectById` 自动加了 `deleted=0`，查不到就是 null，`requireProject` 抛 40410。
2. **回收站能看到**——手写 SQL 显式 `deleted=1`。
3. **恢复后节点还在**——删除时没动附属表。
4. **重复恢复返回 404**——`restore` 的 `WHERE ... AND deleted=1` 匹配 0 行。

## 六、为什么不给回收站加自动清理

真实产品会有"30 天后永久删除"。这里没做，原因：

- 需要定时任务（阶段 8 才有调度基础设施）；
- 永久删除要连带删节点、删素材文件（阶段 3）、删对象存储，跨模块；
- 演示阶段数据量小，不清也没影响。

写进 `docs` 的"已知取舍"里，而不是假装做了。

## 七、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 删除方式 | 逻辑删除 | 物理删除 | 用户创作内容，误删成本高 |
| 节点是否逻辑删除 | 否 | 是 | 附属数据，跟随项目/快照 |
| 回收站查询 | 手写 SQL | 关掉 `@TableLogic` 全局开关 | 全局关掉等于放弃逻辑删除的便利 |
| 自动清理 | 不做 | 定时任务 | 阶段 8 有调度后再做 |

## 八、面试考察点

### 基础题

**Q1：逻辑删除的优缺点？**

优点：可恢复、可审计、不会因为外键/引用导致数据不一致。
缺点：① 所有查询都要带条件，忘一次就是数据泄漏；② 唯一索引会冲突（删除后不能再用同名）；③ 表会越来越大，需要归档策略。

**Q2：`@TableLogic` 是怎么实现的？**

MP 在 SQL 注入阶段给 `select`/`update`/`delete` 方法追加条件。它作用在**内置方法**上，手写 SQL 不受影响。

### 进阶题

**Q3：唯一索引和逻辑删除冲突怎么办？**

经典问题：`username` 唯一，用户注销后 `deleted=1`，新用户就不能再注册同名了。三种解法：
1. 唯一索引改成 `(username, deleted)`——但 `deleted` 只有 0/1，第二次删除同一用户名还是冲突；
2. 删除时把唯一列改名（`username = username + '_deleted_' + id`）；
3. 用 `deleted` 存删除时间戳（`0` 表示未删），唯一索引 `(username, deleted)` 就天然不冲突。

本项目 `t_canvas_project` 没有唯一索引（标题允许重复），所以没这个问题。但 `t_user.username` 有，阶段 1 也没做注销功能——**如果以后要做，必须按上面第 3 种方案改**。

**Q4：为什么恢复必须手写 SQL？**

因为 `updateById` 会被追加 `deleted=0`，而恢复的对象恰恰是 `deleted=1` 的行，条件永远不成立。`update(null, wrapper)` 也一样。

### 陷阱题

**Q5：手写 SQL 忘了加 `deleted=0` 会怎样？**

已删除的数据会出现在正常列表里。表现在用户侧就是"删掉的画布又回来了"。这是逻辑删除方案最常见的事故。本项目的 `selectTrash` 是唯一手写查询，且它就是要查 `deleted=1` 的，所以风险可控。

## 九、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 恢复用 `updateById` | 永远 0 行 | 手写 UPDATE |
| 回收站用 `selectList` | 永远空 | 手写 SELECT，显式 `deleted=1` |
| 删除时清了附属表 | 恢复出空画布 | 附属表不动 |
| 唯一索引没考虑逻辑删除 | 注销后无法复用用户名 | `deleted` 存时间戳 |
| 统计没排除已删除 | 数量偏大 | 内置方法会自动排除，手写 SQL 要自己加 |
