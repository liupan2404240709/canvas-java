# 11 · 自动填充与时间戳

## 一、一句话定位

`createdAt` / `updatedAt` 由 `MetaObjectHandler` 自动填，业务代码不用管。但这个"自动"有一个**只在更新时才会暴露的坑**，本阶段实现时踩到了。

## 二、完整代码

```java
public class AuditMetaObjectHandler implements MetaObjectHandler {

    @Override
    public void insertFill(MetaObject metaObject) {
        LocalDateTime now = LocalDateTime.now();
        strictInsertFill(metaObject, "createdAt", LocalDateTime.class, now);
        strictInsertFill(metaObject, "updatedAt", LocalDateTime.class, now);
    }

    @Override
    public void updateFill(MetaObject metaObject) {
        // 这里刻意不用 strictUpdateFill：它只在字段为 null 时才填充。
        // 而 updateById(entity) 的 entity 通常是从数据库读出来的，updatedAt 已经有旧值，
        // 结果就是 SQL 里显式写回旧时间，MySQL 的 ON UPDATE CURRENT_TIMESTAMP 也不会触发
        // （列被显式赋值时它不生效），updated_at 永远停在第一次保存的时间。
        if (metaObject.hasSetter("updatedAt")) {
            setFieldValByName("updatedAt", LocalDateTime.now(), metaObject);
        }
    }
}
```

## 三、`strictUpdateFill` 到底做了什么

MyBatis-Plus 的 `strictFillStrategy` 逻辑：

```java
// 简化后的源码语义
if (metaObject.getValue(fieldName) == null) {
    metaObject.setValue(fieldName, 新值);
}
```

**只在字段为 null 时填充。**

现在看 `saveSnapshot` 的更新路径：

```java
CanvasProject project = projectMapper.selectById(projectId);  // updatedAt = 17:18:50（有值）
project.setNodeCount(30);
projectMapper.updateById(project);                            // strictUpdateFill 发现不为 null，跳过
```

生成的 SQL：

```sql
UPDATE t_canvas_project
SET node_count=?, ..., updated_at=?, ...   -- ← 写回了 17:18:50 这个旧值
WHERE id=? AND version=? AND deleted=0
```

### 为什么数据库的 `ON UPDATE CURRENT_TIMESTAMP` 没救回来

`updated_at` 列的定义是：

```sql
updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

`ON UPDATE` 的触发条件是"**该列没有在 SET 中被显式赋值**"。这里既然 `SET updated_at = 17:18:50` 出现了，MySQL 就认为"你自己管，我不插手"。

结果是：**画布内容变了，列表页的"最后更新时间"却一直显示第一次保存的时间**。

这个 bug 的特点：
- 不会报错；
- 不会影响功能；
- 只影响"按更新时间排序"和列表页展示；
- 测试时如果不刻意看时间戳，根本发现不了。

## 四、修法对比

| 修法 | 代码 | 评价 |
| --- | --- | --- |
| ① 业务代码手动 set | `project.setUpdatedAt(LocalDateTime.now())` | 能用，但每个 update 都要记得写 |
| ② 全局用 `setFieldValByName` 强制覆盖 | 本项目采用 | 一次修好，所有实体受益 |
| ③ 把列改成只在 DB 侧维护 | 去掉 fill 注解，全靠 `ON UPDATE` | **不可行**：`updateById` 仍会带上旧的 `updated_at` |

② 的实现有一个细节：

```java
if (metaObject.hasSetter("updatedAt")) {
    setFieldValByName("updatedAt", LocalDateTime.now(), metaObject);
}
```

`hasSetter` 是必要的防御——`updateFill` 只对"声明了 update 填充的实体"调用，理论上一定有 setter，但 `CanvasNode` 这种没有该字段的实体一旦被扫到，`setFieldValByName` 会抛异常。

## 五、实测验证

```python
创建      createdAt = 2026-11-14T17:19:41
保存后    updatedAt = 2026-11-14T17:19:42   ← +1s，说明 updateById 刷新了
改名后    updatedAt = 2026-11-14T17:19:43   ← +1s，说明 wrapper 更新也刷新了
```

两条路径都刷新的原因不同，值得分清：

| 路径 | 谁在刷新 `updated_at` |
| --- | --- |
| `saveSnapshot` → `updateById(entity)` | **`AuditMetaObjectHandler.updateFill`**（本篇修的那个） |
| `update` → `update(null, wrapper)` | **MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`**（wrapper 方式没有实体，不触发 fill，所以列没被显式赋值） |

**同一个字段，两种更新方式，两个不同的刷新机制**——这是最容易混乱的地方。想复现第一行的坑：把 `updateFill` 换回 `strictUpdateFill`，再跑一次保存，`updatedAt` 就会停在创建时间。

## 六、时间精度：为什么只到秒

实体是 `LocalDateTime`，序列化出来是 `2026-11-14T17:19:42`（秒级），数据库列是 `DATETIME`（精度 0）。

三个后果：

1. **同一秒内的多次更新，`updated_at` 完全相同**——所以列表排序必须加 `id DESC` 兜底（见 07 篇）；
2. **前端做"几秒前"的相对时间显示会不准**——最多差 1 秒，可接受；
3. **想要毫秒**：列改 `DATETIME(3)`，Jackson 配置里加毫秒格式。本项目不需要。

## 七、为什么节点表不加这两个字段

```java
@TableName("t_canvas_node")
public class CanvasNode {
    // 没有 createdAt / updatedAt
}
```

| 理由 | 说明 |
| --- | --- |
| 批量插入 | 每行填充两个时间 = 多两次反射 + 多两个 SQL 参数 × N 行 |
| 无业务含义 | 节点每次保存都是"删除 + 重新插入"，创建时间永远是本次保存时间，没有信息量 |
| 数据库兜底 | 列上有 `DEFAULT CURRENT_TIMESTAMP`，需要查的时候仍然有值 |

**"表里有列"和"实体里有字段"是两件事**——不需要读写的列不必映射，这也是减少映射负担的常用手段。

## 八、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| update 填充 | `setFieldValByName` 强制 | `strictUpdateFill` | 后者在 update 时几乎不生效 |
| 节点表时间字段 | 不映射 | 全部映射 | 批量插入成本、无业务含义 |
| 时间精度 | 秒 | 毫秒 | 画布场景不需要，且能省 3 字节 |
| 时区 | 全局 `GMT+8` + `LocalDateTime` | `Instant` + UTC | 单地域部署，简单优先 |

## 九、面试考察点

### 基础题

**Q1：MyBatis-Plus 的自动填充怎么用？**

三步：① 实体字段加 `@TableField(fill = FieldFill.INSERT / INSERT_UPDATE)`；② 实现 `MetaObjectHandler`；③ 注册成 Bean。填充逻辑里用 `strictInsertFill` / `setFieldValByName`。

**Q2：`INSERT` 和 `INSERT_UPDATE` 的区别？**

前者只在 insert 时填，后者 insert 和 update 都填。`createdAt` 用 INSERT，`updatedAt` 用 INSERT_UPDATE。

### 进阶题

**Q3：`strictUpdateFill` 和 `setFieldValByName` 的区别？**

`strictXxxFill` 有"只在 null 时填充"的保护，避免覆盖业务手动设的值；`setFieldValByName` 是无条件覆盖。更新场景下实体通常已有旧值，所以前者会跳过——这是它的设计意图（"别覆盖用户设的值"），但对"自动更新时间戳"这个需求恰好是反的。

**Q4：数据库的 `ON UPDATE CURRENT_TIMESTAMP` 什么时候不生效？**

当该列在 UPDATE 语句的 SET 里被显式赋值时。另外如果 UPDATE 的值和原值完全相同（没有实际变更），InnoDB 也不会更新时间戳。

**Q5：分布式部署时 `LocalDateTime.now()` 会有问题吗？**

会。多台机器的时钟不同步，`updated_at` 会出现"时间倒流"。解决：① NTP 同步；② 用数据库时间（`NOW()`）；③ 用雪花 id 里的时间戳。本项目单机部署，`LocalDateTime.now()` 够用，但要知道这个限制。

### 陷阱题

**Q6：为什么 `update(null, wrapper)` 不需要处理 fill？**

因为 `MetaObjectHandler` 的入参是实体对象，`update(null, wrapper)` 传的是 null 实体，MP 不会调用 `updateFill`。此时 `updated_at` 靠数据库的 `ON UPDATE` 兜底。

**Q7：`createdAt` 能在 update 时被改掉吗？**

如果标了 `FieldFill.INSERT_UPDATE` 就会。本项目 `createdAt` 只标 `INSERT`，所以 update 不会碰它。但如果实体从库里读出来、`created_at` 有值，`updateById` 仍会把它写回去（值相同，无影响）。

## 十、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 用 `strictUpdateFill` 更新 | `updated_at` 永远是创建时间 | 改 `setFieldValByName` |
| 实体没有对应字段 | `setFieldValByName` 抛异常 | 先 `hasSetter` 判断 |
| 只靠 `ON UPDATE` | `updateById` 时失效 | 应用侧也要填 |
| 用 `DATETIME` 做毫秒排序 | 同秒数据顺序随机 | 加 id 兜底或改 `DATETIME(3)` |
| 多实例时钟不同步 | 时间倒流 | NTP 或数据库时间 |
