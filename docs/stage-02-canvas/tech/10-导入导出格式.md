# 10 · 导入导出格式设计

## 一、一句话定位

导出文件是**唯一离开系统控制的数据**——一旦用户下载了，你就再也改不动它。所以格式必须自带"身份"和"版本"。

## 二、完整代码

```java
public record ProjectExportVO(
        String app,              // "infinite-canvas"
        Integer formatVersion,   // 1
        LocalDateTime exportedAt,
        String title,
        String backgroundMode,
        Boolean showImageInfo,
        CanvasViewportVO viewport,
        List<CanvasNodeVO> nodes,
        List<CanvasConnectionVO> connections
) {
    public static final String APP_NAME = "infinite-canvas";
    public static final int FORMAT_VERSION = 1;
}
```

导入端：

```java
if (request.formatVersion() != null && request.formatVersion() > ProjectExportVO.FORMAT_VERSION) {
    throw new BizException(ResultCode.BAD_REQUEST,
            "导入文件版本过高（" + request.formatVersion() + "），当前最多支持 " + ProjectExportVO.FORMAT_VERSION);
}
```

## 三、为什么有 `app` 字段

用户导入时可能选错文件（拿了个别的产品的 JSON）。检查 `app` 能立刻给出"这不是本产品的文件"，而不是解析到一半报一个莫名其妙的字段错误。

```java
if (request.app() != null && !ProjectExportVO.APP_NAME.equals(request.app())) { ... }
```

本项目只在校验版本时做了严格判断，`app` 目前是"写进导出但不强制校验"——因为要兼容"手工拼一个最小 JSON"的测试场景。生产环境应该加上。

## 四、为什么有 `formatVersion`

这是**前向兼容**的关键。

场景：v2 版本把 `nodes[].position` 从 `{x, y}` 改成了缩放的 `{x, y, z}`。用户拿 v2 导出的文件到 v1 的服务上导入：

- **不检查版本**：v1 读到 `position` 里的 `x`、`y` 能对上，`z` 被静默忽略，画布导入成功但**高度丢失**。用户以为导入成功了，实际上数据丢了。
- **检查版本**：直接报"文件版本过高"，用户知道要用新版本。

实测：

```
formatVersion=99    HTTP 400 code=40000 "导入文件版本过高（99），当前最多支持 1"
```

### 为什么只拒绝"更高"的版本

```java
request.formatVersion() > FORMAT_VERSION
```

低版本要能读（向后兼容），高版本要拒绝（前向不兼容）。这是所有序列化格式的通用原则。

## 五、导出格式 vs 内部 VO：为什么要分开

```java
// 导出用独立 VO，即使字段看起来和 ProjectDetailVO 很像
```

| | `ProjectDetailVO` | `ProjectExportVO` |
| --- | --- | --- |
| 面向 | 前端运行时 | 文件、跨系统 |
| 加字段的影响 | 无（前端忽略未知字段） | 所有解析方都要兼容 |
| 含 `version` | 是（保存需要） | 否（导出的是内容，不是并发状态） |
| 含 `id` | 是（路由需要） | 否（导入一定生成新 id） |
| 含 `formatVersion` | 否 | 是 |

**核心区别**：`ProjectDetailVO` 是"内部协议"，可以随时改；`ProjectExportVO` 是"对外契约"，改了就要考虑存量文件。

多写一个类，换来的是"内部重构不会破坏用户手里的文件"。

## 六、导出为什么不带 files

前端原始实现（`web/src/lib/canvas/canvas-export.ts`）导出的是 **ZIP**：

```ts
const data: CanvasExportFile = {
    app: "infinite-canvas",
    version: 3,
    exportedAt: new Date().toISOString(),
    projects: exportedProjects,   // [{ project, files: [...] }]
};
const zip = await createZip([{ name: "projects.json", data: JSON.stringify(data) }, ...zipFiles]);
```

里面除了 `projects.json`，还有所有图片/视频的二进制文件，路径写在 `files[].path` 里。

本阶段**只导出 JSON**，不带媒体文件。原因：媒体存储是阶段 3 的内容（对象存储、URL 生成、秒传）。现在导出，节点里的 `storageKey` 指向的还是浏览器 IndexedDB 的 key，后端根本没有对应的文件。

**所以导出的 JSON 里，图片节点只有 `storageKey`（一个字符串），没有真实图片。** 这是阶段性限制，写进"已知取舍"，不假装完整。

等到阶段 3 之后，导出应该变成：后端生成一个 ZIP（JSON + 媒体文件），前端直接下载。

## 七、`import` 为什么复用导出结构

```java
public record ImportProjectRequest(
        String app,
        Integer formatVersion,
        String title,
        ...
```

字段名和 `ProjectExportVO` 完全一致。这样"导出 → 改标题 → 导入"能直接跑通，实测：

```
导出  app=infinite-canvas formatVersion=1 title=改过名的画布 nodes=1
导入  id=... nodes=1 title=从文件导入的画布 backgroundMode=dots
```

注意 `backgroundMode=dots` 也带过来了——**视口、背景、显示设置都属于"画布内容"**，导入应该完整还原。

导出文件里多出来的 `exportedAt`、`id` 在导入时被忽略（Spring Boot 默认 `FAIL_ON_UNKNOWN_PROPERTIES=false`）。这是有意的宽松：文件里多几个字段不该导致导入失败。

## 八、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 导出载体 | JSON | ZIP（含媒体） | 媒体存储还没做（阶段 3） |
| 格式版本 | `formatVersion` 整数 | 无版本 | 见第四节 |
| 版本检查 | 只拒绝更高版本 | 全等才通过 | 向后兼容 |
| 未知字段 | 忽略 | 严格报错 | 宽容读取，严格写入 |
| 导入结果 | 新画布（完整详情） | 只返回 id | 前端导入后直接跳进画布，省一次请求 |

## 九、面试考察点

### 基础题

**Q1：什么是序列化格式的向后兼容和向前兼容？**

向后兼容：新版本能读旧数据。向前兼容：旧版本能读新数据。导出文件只能保证后者里的"旧读新会明确失败"，前者必须严格保证。

**Q2：为什么要给导出文件加版本号？**

数据一旦离开系统就无法更新，格式演进时必须有办法判断"这份文件我能不能正确解析"。没有版本号就只能靠猜字段。

### 进阶题

**Q3：JSON 里的 `unknown properties` 应该报错还是忽略？**

**读的时候忽略，写的时候严格**。读宽松是为了兼容（对方多加字段不该让我们失败），写严格是为了契约（我们不乱加字段）。

Jackson 对应：`FAIL_ON_UNKNOWN_PROPERTIES=false`（Spring Boot 默认）+ 出参用明确的 record（不会多写字段）。

**Q4：如果要做 ZIP 导出，后端怎么设计？**

1. 生成 `projects.json` 写入 `ZipOutputStream`；
2. 遍历节点收集 `storageKey`，从对象存储拉流写入 zip 内的 `files/` 目录；
3. 大文件要流式处理，不能全读进内存（`ZipOutputStream` + `InputStream.transferTo`）；
4. 响应设 `Content-Type: application/zip` + `Content-Disposition: attachment`。

**Q5：导入 5 万个节点怎么办？**

当前 `@Size(max=500)` 会直接拒绝。真要支持，得改成异步任务：上传文件 → 落临时存储 → 返回 taskId → 后台解析入库 → 前端轮询进度。这是阶段 6（任务队列）的模式。

### 陷阱题

**Q6：导入时 `nodes` 里的 `id` 会和已有画布冲突吗？**

不会。导入一定创建**新项目**，`(project_id, node_key)` 的唯一约束是按项目隔离的。所以同一个文件可以重复导入多次，得到多张独立画布。

**Q7：导出时要不要带 `version`？**

不要。`version` 是"这份内容的并发状态"，导入是创建全新内容，版本从 0 开始。带上反而会误导——用户会以为导入后还能用原来的 version 保存。

## 十、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 没有版本号 | 格式演进后静默丢数据 | 加 `formatVersion` |
| 严格校验未知字段 | 对方加个字段就导入失败 | 关闭 `FAIL_ON_UNKNOWN_PROPERTIES` |
| 导出复用内部 VO | 内部加字段污染对外契约 | 独立 VO |
| 导入不校验图结构 | 库里出现悬空连线 | 复用 `validateGraph` |
| 导入带 `version` | 用户拿旧 version 保存成功，覆盖新内容 | 不带 |
