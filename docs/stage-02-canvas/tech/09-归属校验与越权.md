# 09 · 归属校验与越权防护

## 一、一句话定位

`/v1/projects/{id}` 这个路径里出现了用户可控的 id——**只要 URL 能传 id，就有越权风险**。防护只有一处：`requireProject`。

## 二、完整代码

```java
/** 查项目并校验归属。查不到和不是自己的都返回 404，避免用 403 泄露"这个 id 存在"。 */
private CanvasProject requireProject(Long userId, Long projectId) {
    CanvasProject project = projectMapper.selectById(projectId);
    if (project == null || !Objects.equals(project.getUserId(), userId)) {
        throw new BizException(ResultCode.PROJECT_NOT_FOUND);
    }
    return project;
}
```

十一个接口全部先调它（或它的变体），没有例外：

| 接口 | 是否调用 | 说明 |
| --- | --- | --- |
| 详情 / 更新 / 删除 / 复制 / 保存快照 / 导出 | ✅ | 都需要归属 |
| 恢复 | ✅（在 SQL 里） | `WHERE id=? AND user_id=? AND deleted=1` |
| 回收站 / 列表 / 创建 / 导入 | — | 本身就是按 `userId` 过滤的 |

## 三、为什么返回 404 而不是 403

| 返回 | 泄露的信息 | 攻击者能做什么 |
| --- | --- | --- |
| 403 没权限 | **这个 id 存在**，只是不是你的 | 遍历 id 探测系统里有多少画布、什么时候创建（配合时间侧信道） |
| 404 不存在 | 什么都没有 | 无法区分"不存在"和"别人的" |

实测：

```
他人访问详情    HTTP 404 code=40410 "画布不存在或已被删除"
他人删除        HTTP 404 code=40410
他人保存快照    HTTP 404 code=40410
```

三个接口返回完全一致的响应，攻击者拿不到任何额外信息。

**代价**：真实用户如果手误输错 id，看到的是"不存在"而不是"没权限"，体验略差。这是安全优先的取舍，也是行业惯例（GitHub 私有仓库、Notion 页面都是 404）。

## 四、`Objects.equals` 而不是 `==`

```java
!Objects.equals(project.getUserId(), userId)
```

两个 `Long`：

- `==` 比较的是引用（对 `Long` 而言，`-128~127` 以外都是不同对象）；
- 直接 `project.getUserId().equals(userId)` 在当前代码里能用，但 `userId` 为 null 时会 NPE；
- `Objects.equals` 两个方向都安全。

**这是 `Long` 比较的经典坑**：`Long a = 128L; Long b = 128L; a == b` 是 `false`。用户 id 是雪花生成的，早就超出缓存范围，用 `==` 会**必然**导致所有请求 404。这种 bug 一旦写出来，本地测小 id 可能恰好通过，上线就全挂。

## 五、越权有两种，别只防一种

### 5.1 水平越权（横向）

A 用户访问 B 用户的资源。防护就是 `requireProject` 里的 `userId` 比对。

### 5.2 垂直越权（纵向）

普通用户调用管理员接口。本项目阶段 2 还没有角色体系，所以：

- 所有 `/v1/projects/**` 只要求"登录"，不区分角色；
- 阶段 8 或后续加 `@PreAuthorize("hasRole('ADMIN')")` 时，`RestAccessDeniedHandler` 已经能返回统一的 40300。

`SecurityConfig` 里所有 projects 路径都在 `authenticated()` 之下，未登录直接 40100：

```
未登录访问 /v1/projects      → 401 / 40100
```

### 5.3 参数越权（第三种，容易漏）

即使 `projectId` 校验了，如果请求体里还能传 `userId`，攻击者就能把画布"送"给别人或者伪造归属。本项目的 `SaveSnapshotRequest` / `CreateProjectRequest` **都没有 `userId` 字段**——归属只从 `SecurityUtils.currentUserId()` 来。

**原则：归属字段永远不进 DTO。**

## 六、为什么把校验放在 Service 而不是 Controller

```java
// Controller：只传 userId，不做判断
projectService.detail(SecurityUtils.currentUserId(), id);

// Service：在这里校验
return toDetail(requireProject(userId, projectId), ...);
```

三个理由：

1. **复用**：以后加"分享链接访问"（按 token 授权而非 userId），改 Service 一处；
2. **不会漏**：新增接口时如果忘了校验，写测试能发现；如果校验散在 Controller，新增接口很容易复制粘贴时漏掉；
3. **可测**：Service 是纯 Java，单测不需要起 MVC。

## 七、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 越权响应 | 404 | 403 | 不泄露资源存在性 |
| 校验位置 | Service | Controller | 复用、不易漏 |
| 归属来源 | `SecurityUtils` | 请求参数 | 参数可伪造 |
| 比较方式 | `Objects.equals` | `==` | Long 缓存坑 |

## 八、面试考察点

### 基础题

**Q1：什么是水平越权和垂直越权？**

水平：同级用户之间互相访问（A 看 B 的订单）。垂直：低权限用户访问高权限功能（普通用户调管理接口）。防护分别是"数据归属校验"和"角色/权限校验"。

**Q2：为什么不能靠前端隐藏按钮来防越权？**

前端只是 UI，攻击者可以直接构造 HTTP 请求。**所有权限判断必须在服务端**，前端隐藏只是体验优化。

### 进阶题

**Q3：为什么 404 比 403 安全？**

403 确认了资源存在，可以用来枚举。404 把"不存在"和"无权限"合并，攻击者无法区分。代价是正常用户的错误提示变模糊。

**Q4：`Long` 用 `==` 比较会怎样？**

`Long` 有 `-128~127` 的缓存，超出范围后 `==` 比引用，两个值相等的 `Long` 会返回 `false`。用户 id 是雪花 id，必然超出缓存，所以用 `==` 会导致**所有请求都判定为越权**。

**Q5：如果要做"分享链接"，归属校验怎么改？**

分享是一种"授权代理"：链接里带一个 `shareToken`，服务端校验 token 有效且未过期，然后以**画布所有者**的身份读数据，但只允许读。这时 `requireProject(userId, id)` 要拆成两个入口：`requireOwnedProject(userId, id)` 和 `requireSharedProject(token, id)`。

### 陷阱题

**Q6：`selectById` 会不会因为逻辑删除而返回 null？**

会。它自动加 `deleted=0`，所以已删除的画布查出来是 null，直接走 404 分支。这正好符合"删除后不可访问"的预期。

**Q7：批量接口怎么防越权？**

比如"批量删除 10 个画布"，必须对**每个 id** 校验归属，不能只校验第一个。更好的做法是 SQL 里直接带上 `user_id`：`UPDATE ... WHERE id IN (...) AND user_id = ?`，然后检查影响行数是否等于传入数量。

## 九、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| `Long` 用 `==` | 全部 404 | `Objects.equals` |
| 只校验列表接口 | 详情接口能越权 | 每个带 id 的接口都要校验 |
| DTO 里有 `userId` | 可伪造归属 | 归属只从 token 取 |
| 返回 403 | 泄露资源存在性 | 统一 404 |
| 校验写在 Controller | 新增接口容易漏 | 收口到 Service |
