# 12 · 一次保存请求的完整链路

## 一、一句话定位

面试官最爱问"讲讲你这个接口是怎么走的"。这一篇用**真实的日志**把 `PUT /v1/projects/{id}/snapshot` 从字节流到 SQL 走一遍。

## 三、分层走过一遍

### 3.1 Tomcat 线程

```
[http-nio-8082-exec-9]
```

请求由 Tomcat 的 worker 线程处理。线程名里的 `exec-9` 说明这是第 9 个执行线程——**同一个线程会服务多个请求**，所以任何存到 `ThreadLocal` 的状态都必须在 finally 里清理（`TraceIdFilter` 就是这么做）。

### 3.2 Filter 链

```
TraceIdFilter → JwtAuthenticationFilter → (Spring Security 其余)
```

`TraceIdFilter` 先跑，为这次请求生成 `92c6af3c...`，放进 MDC。所以后面每一行日志都带这个 id，包括 MyBatis 的 SQL——**这就是阶段 2 把 `StdOutImpl` 换成 `Slf4jImpl` 的价值**：用 StdOutImpl 时 SQL 直接 `System.out`，不经过 Logback，日志里既没有 traceId 也没有文件落盘。

`JwtAuthenticationFilter` 解析 `Authorization`，把 `LoginUser` 放进 `SecurityContext`。失败也不拦截，只记原因（阶段 1 的设计）。

### 3.3 Controller

```java
@PutMapping("/{id}/snapshot")
public Result<SaveSnapshotVO> saveSnapshot(@PathVariable Long id,
                                           @Valid @RequestBody SaveSnapshotRequest request) {
    return Result.ok(projectService.saveSnapshot(SecurityUtils.currentUserId(), id, request));
}
```

三件事：路径变量绑定、`@Valid` 触发校验、从 `SecurityContext` 取 userId。

**注意顺序**：`@Valid` 在进入方法体之前就执行完了。如果 `nodes[0].position` 缺失，根本不会进方法，直接由 `GlobalExceptionHandler` 返回 400——实测：

```
节点缺 position   HTTP 400 code=40000 "nodes[0].position: 节点缺少 position"
```

### 3.4 Service（事务开始）

`@Transactional` 由代理拦截，方法进入时从连接池拿连接、关闭自动提交。

```
1. requireProject        → SELECT ... WHERE id=? AND deleted=0
2. 版本校验（内存）
3. validateGraph         → 纯内存，30 个节点建 Set 去重 + 29 条连线查引用
4. 删除旧节点/连线       → 两条 DELETE
5. 批量插入              → 两条多值 INSERT
6. updateById            → 带 version 条件的 UPDATE
7. 返回 VO
```

第 3 步值得强调：**图结构校验是纯内存的**，没有查库。因为它要验证的是"请求内部是否自洽"（连线引用的节点是否在本次请求的 nodes 里），不需要和数据库比对。

### 3.5 Mapper → SQL

`CanvasNodeMapper.insertBatch` 是手写 XML（见 06 篇），其它都是 `BaseMapper` 的内置方法。

MyBatis 在这一层做三件事：
1. 把 `#{item.nodeKey}` 替换成 `?`，参数按顺序排列（30 × 10 = 300 个）；
2. 拦截器改写 SQL（乐观锁加 `version` 条件、逻辑删除加 `deleted=0`、分页加 `LIMIT`）；
3. 把 `ResultSet` 映射回实体（`map-underscore-to-camel-case` 负责 `node_key → nodeKey`）。

### 3.6 响应

```json
{
  "code": 0,
  "message": "success",
  "data": { "id": "2121533114450456578", "version": 1, "nodeCount": 30,
            "connectionCount": 29, "updatedAt": "2026-11-14T17:18:05" },
  "traceId": "92c6af3cd9ae4ed9961a1e2fb91c88be"
}
```

`Result.ok()` 包一层，`traceId` 由全局切面/过滤器补上。前端只需要 `data.version`。

## 四、这条链路上每个环节可能出错的位置

| 环节 | 可能的错误 | 返回 |
| --- | --- | --- |
| 路径变量 | `id=abc` 无法转 `Long` | 400 `参数格式错误: id` |
| 请求体 | JSON 语法错 | 400 `请求体格式错误` |
| `@Valid` | 字段缺失/超长/为负 | 400 带字段路径 |
| 认证 | 无 token / 过期 / 已撤销 | 401 + 40100/40113/40114 |
| 归属 | 不是自己的画布 | 404 + 40410 |
| 版本 | 客户端版本落后 | 409 + 40920 |
| 图结构 | 悬空连线 / 重复 id | 400 |
| 数据库 | 唯一索引冲突 / 连接超时 | 500 |
| 事务提交 | 死锁 | 500（可重试） |

**这张表就是接口的"失败矩阵"**，写进 `api.md` 让前端能穷举处理。

## 五、为什么要有 traceId

单机日志里，一次请求的 8 条日志是交错在其他请求之间的。没有 traceId 时，排查只能靠时间戳猜。

有了 traceId：
- 日志里 `grep 92c6af3c` 就是一次完整请求；
- 响应体里回传，用户报错时截图就能定位；
- 跨服务时透传（阶段 8 接网关后，同一个 id 贯穿多个服务）。

**实现代价极小**（一个 Filter + MDC），收益极大，属于"必须有"的基础设施。

### 一个已知局限

异步线程里 MDC 会丢。阶段 6 做异步生成任务时，`@Async` 线程池需要配 `TaskDecorator` 把 MDC 复制过去，否则异步任务的日志没有 traceId。这一条写在阶段 0 的 `tech/04` 里，到阶段 6 要兑现。

## 六、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| SQL 日志 | Slf4jImpl | StdOutImpl | 要进日志文件、要带 traceId |
| 校验时机 | Bean Validation + Service 二次校验 | 只在 Controller | 结构校验（Bean）和业务校验（图结构）分层 |
| 事务边界 | Service 方法 | Controller | 见 03 篇 |
| 返回值 | 只回 version | 回全量 | 见 03 篇 |

## 七、面试考察点

### 基础题

**Q1：一个请求进来，Spring MVC 的处理顺序？**

`Filter` → `DispatcherServlet` → `HandlerMapping`（找 Controller） → `HandlerAdapter` → 参数解析 + `@Valid` → 方法体 → 返回值处理（`HttpMessageConverter`） → 响应。异常走 `HandlerExceptionResolver`（`@RestControllerAdvice`）。

**Q2：`@Valid` 什么时候执行？**

参数解析阶段（`RequestResponseBodyMethodProcessor` 里），**在进入方法体之前**。所以方法体里不需要再判空。

### 进阶题

**Q3：这条链路上哪里加了锁？**

只有数据库层：DELETE 和 UPDATE 会给行加排他锁。应用层没有显式锁。`@Transactional` 保证这些锁在同一个事务里持有到提交。

**Q4：如果第 5 步批量插入失败，前两步的 DELETE 会怎样？**

回滚。因为整个方法在一个事务里，异常往上抛到代理，代理执行 `rollback`，把 DELETE 一起撤销。实测并发场景验证过：冲突那次事务里删了又插的数据全部撤销，库里只剩成功那次。

**Q5：86ms 里最慢的是哪一步？**

批量插入 30 个节点（22ms）。因为每个节点有 JSON 字段，且要写 30 行索引。如果要优化：① 减少索引数量；② JSON 列改 TEXT（写入更快但失去校验）；③ 分片并行插——但 30 个节点不值得，**优化要有量级意识**。

### 陷阱题

**Q6：为什么日志里 `delete` 显示 `Updates: 0`？**

第一次保存时这个项目下还没有节点，所以删除 0 行。这是正常现象，不是错误。**看日志时不要把 `Updates: 0` 一律当成失败**——`updateById` 返回 0 才是问题（版本冲突），`delete` 返回 0 通常只是"没东西可删"。

**Q7：traceId 是请求头传进来的还是服务端生成的？**

两者都有。`TraceIdFilter` 优先读请求头 `X-Trace-Id`（用于跨服务透传），没有就生成一个 32 位十六进制。响应头也会回写，方便前端日志对齐。

## 八、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 日志里没有 SQL | 用了 StdOutImpl | 换 Slf4jImpl |
| 日志没有 traceId | 异步线程 MDC 丢失 | `TaskDecorator` 复制 MDC |
| `Updates: 0` 一律当失败 | 误判 | 区分 delete 和 update 的语义 |
| 在 Controller 里做业务判断 | 逻辑散落、难复用 | 收口到 Service |
| 事务里做远程调用 | 连接被占住、超时 | 远程调用放事务外 |
