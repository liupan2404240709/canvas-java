# 01 · 三张表的关系与字段设计

## 一、一句话定位

画布数据的存储模型：**项目是聚合根，节点和连线是附属数据**。三张表决定后面所有代码的形状，改表的代价远高于改代码，所以这一篇要能说服面试官"为什么不是一张表存 JSON"。

## 二、完整结构

```
t_canvas_project（聚合根）
├── id, user_id, title
├── background_mode, show_image_info
├── viewport_x, viewport_y, viewport_k
├── node_count, connection_count     ← 冗余计数
├── version                          ← 乐观锁
├── created_at, updated_at, deleted
│
├── t_canvas_node（1 : N）
│   ├── id, project_id
│   ├── node_key                     ← 前端节点 id，项目内唯一
│   ├── type, title
│   ├── pos_x, pos_y, width, height
│   └── metadata (JSON)
│
└── t_canvas_connection（1 : N）
    ├── id, project_id
    ├── edge_key                     ← 前端连线 id
    └── from_node_key, to_node_key
```

对应前端 `web/src/types/canvas.ts`：

| 前端结构 | 数据库落点 |
| --- | --- |
| `CanvasProject.title` | `t_canvas_project.title` |
| `CanvasProject.viewport {x,y,k}` | 三个 DOUBLE 列（不建 JSON，因为要按它排序/统计时不想解 JSON） |
| `CanvasProject.nodes[]` | `t_canvas_node` 多行 |
| `CanvasProject.connections[]` | `t_canvas_connection` 多行 |
| `CanvasNodeData.position {x,y}` | `pos_x` / `pos_y` 两列 |
| `CanvasNodeData.metadata` | `metadata JSON` 整块 |
| `CanvasProject.chatSessions[]` | **本阶段不落库**，阶段 7 单独建表 |

## 三、逐字段拆解

### 3.1 为什么 `node_key` 不直接当主键

前端节点 id 是 nanoid 之类的字符串（`n_1a2b3c`）。完全可以拿它当主键，但这里没这么做：

| 方案 | 好处 | 代价 |
| --- | --- | --- |
| `node_key` 当主键 | 少一列，连线直接外键 | 主键变成"外部可控字符串"，长度、字符集、大小写规则都被前端牵着走；换 id 生成策略要动主键 |
| 独立雪花主键 + `node_key` 业务键 | 主键内部可控，索引短且有序 | 多一列 + 一个唯一索引 |

代码里选的是后者。`(project_id, node_key)` 建唯一索引，等于把"项目内 id 唯一"这条约束交给数据库兜底——Service 里已经校验过一次，但并发或代码漏改时数据库还能拦住。

**顺序很重要**：`(project_id, node_key)` 而不是 `(node_key, project_id)`。因为查询永远是"先按项目过滤"，最左前缀能直接用上；反过来写，`WHERE project_id = ?` 就用不到这个索引。

### 3.2 为什么 `metadata` 用 JSON 列而不是拆字段

`metadata` 里有 30 多个可选字段：`prompt`、`model`、`images[]`、`fontSize`、`seconds`、`videoTaskId`……而且**随节点类型变化**，插件节点还会有自定义字段。

| 方案 | 问题 |
| --- | --- |
| 拆成 30 个列 | 加一个节点类型就要改表；90% 的列对某类节点永远是 NULL |
| 存 `TEXT` 字符串 | 能用，但数据库不知道这是 JSON，没法校验、没法用 `JSON_EXTRACT` 查 |
| 存 `JSON` 列 | 插入时校验合法性，可用 `->>` 查询，体积比 TEXT 小 |

实测时验证过：

```sql
SELECT JSON_EXTRACT(metadata,'$.prompt'), JSON_EXTRACT(metadata,'$.nested.k')
FROM t_canvas_node;
-- "日落"   1.5
```

**边界在哪**：`metadata` 里不该放需要"按它过滤/排序/统计"的字段。比如以后要做"按模型筛选生成记录"，就应该把 `model` 提成独立列并建索引，而不是每次 `JSON_EXTRACT` 扫全表。

### 3.3 为什么主表要冗余 `node_count` / `connection_count`

列表页每张卡片要显示"N 个节点 · M 条连线"（见 `canvas-project-card.tsx`）。如果不冗余：

```sql
-- 20 条画布 = 20 次子查询，或者一个 GROUP BY，都要额外扫节点表
SELECT p.*, (SELECT COUNT(*) FROM t_canvas_node n WHERE n.project_id = p.id) FROM ...
```

冗余之后列表页只读主表，一次索引扫描搞定。代价是**必须保证同步更新**——所以 `saveSnapshot`、`copy`、`importProject` 里都显式设置了这两个值。这是典型的"用写复杂度换读性能"，读远多于写的场景才值得。

### 3.4 `version` 为什么从 0 开始、每次 +1

`int` 足够：一天保存 1000 次也要 5800 年才溢出。不从时间戳或 UUID 是因为乐观锁只需要"能比较是否变化"，递增整数还能顺带看出改了多少次。

### 3.5 `deleted` 为什么是 TINYINT 而不是 BIT

MyBatis-Plus 的 `@TableLogic` 默认用 `0/1`，`BIT(1)` 映射到 Java `Boolean` 时，不同驱动行为不一致（有的返回 `byte[]`）。用 `TINYINT` + `Integer` 最稳。

### 3.6 时间列为什么给数据库默认值

`created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP`。

节点表刻意**没有**在实体里映射这两个字段（见 `CanvasNode`），这样批量插入时不用为每行填充时间，数据库自己兜底。少两次反射，也少两个参数。

## 四、索引设计

| 索引 | 服务于哪条 SQL | 为什么这么建 |
| --- | --- | --- |
| `idx_project_user_updated (user_id, deleted, updated_at)` | 列表页 `WHERE user_id=? AND deleted=0 ORDER BY updated_at DESC` | 三列顺序 = 过滤 + 排序，能避免 filesort |
| `uk_node_project_key (project_id, node_key)` | 唯一约束 + 按项目查节点 | 最左前缀同时满足"查全量节点"和"校验唯一" |
| `idx_node_project (project_id)` | 上面那个唯一索引其实已覆盖 | **冗余**，可以删；保留是为了表意清晰（`uk_` 前缀容易被误认为只服务约束） |
| `uk_edge_project_key (project_id, edge_key)` | 同上 | 同上 |

**注意 `deleted` 放在索引中间**：它只有 0/1 两个值，选择性极差，单独建索引没意义；但放在 `user_id` 后面能让"查未删除"直接走索引，而不用回表过滤。

## 五、设计决策对比

| 决策 | 选了 | 替代方案 | 为什么 |
| --- | --- | --- | --- |
| 节点存储 | 独立表 | 项目表一个 JSON 字段 | 见 3.2；JSON 方案没法做节点级操作，也练不到事务和批量写 |
| 节点主键 | 雪花 + 业务键 | 业务键直接当主键 | 主键不该被外部输入控制 |
| 连线存端点 | `from_node_key` / `to_node_key` | 存贝塞尔控制点 | 控制点由前端按坐标实时算，存下来节点一动就不一致 |
| 计数 | 主表冗余 | 每次 `COUNT(*)` | 读多写少，值得 |
| 软删除 | `deleted` 标记 | 物理删除 | 创作内容误删成本高，回收站是标配 |

## 六、面试考察点

### 基础题

**Q1：为什么画布不直接存一个大 JSON？**

要点：能存，很多小产品就这么做。但代价是：① 无法按节点查询/更新，改一个节点要读全量再写全量；② 并发控制粒度变成整份文档，冲突率高；③ 数据库无法校验内部结构；④ 简历上体现不出表设计能力。反过来，如果节点数量极大、结构极不稳定，JSON 反而合适——所以要说"取决于访问模式"。

**Q2：`(project_id, node_key)` 和 `(node_key, project_id)` 有什么区别？**

最左前缀。查询条件里一定有 `project_id`，所以前者能用上索引，后者要全索引扫描。这是复合索引最常考的点。

### 进阶题

**Q3：`node_count` 冗余会不一致，怎么保证？**

三个层面：① 所有写路径（保存/复制/导入）都在同一个事务里更新；② 可以在 `t_canvas_node` 上加触发器强制同步（不推荐，难维护）；③ 兜底做一个定时任务对账（阶段 8 可加）。面试时可以说"我选了①，因为写路径只有三条且都在 Service 里收口"。

**Q4：为什么 `pos_x` / `pos_y` 是 DOUBLE 而不是 DECIMAL？**

坐标是渲染用的浮点数，不需要精确十进制运算，DOUBLE 足够且更快。DECIMAL 适合金额。

**Q5：如果要做"按节点类型统计"怎么办？**

`type` 是独立列且有值，可以直接 `GROUP BY type`。这也是 `metadata` 里不放 `type` 的原因——**需要聚合的字段必须提成列**。

### 陷阱题

**Q6：`deleted` 放在索引里会不会让索引失效？**

不会，但要放对位置。`(user_id, deleted, updated_at)` 里 `deleted` 是等值条件，后面还能接排序；如果把 `deleted` 放最后，`ORDER BY updated_at` 就用不上索引顺序。

**Q7：`JSON` 列能不能建索引？**

MySQL 8 可以建函数索引或生成列索引，例如 `ALTER TABLE ... ADD COLUMN prompt VARCHAR(255) GENERATED ALWAYS AS (metadata->>'$.prompt') VIRTUAL, ADD INDEX (prompt)`。但索引会随 metadata 变大而变宽，只在真的需要按它查时才做。

## 七、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 唯一索引写成 `(node_key, project_id)` | 按项目查节点变慢 | 违反最左前缀 |
| `DATETIME` 当毫秒用 | 同一秒内两条记录排序随机 | `DATETIME` 默认精度 0，要毫秒用 `DATETIME(3)` |
| `TEXT` 存 JSON 后想 `->>` | 语法报错或结果奇怪 | `TEXT` 不是 JSON 类型，要先 `CAST(... AS JSON)` |
| 忘加 `project_id` 条件删节点 | 删掉所有画布的节点 | 每个节点操作都必须带项目维度 |
| 用 `SELECT *` | 加列后结果映射错位 | 显式列名（`CanvasProjectMapper.xml` 里用 `<sql id="columns">` 收口） |
