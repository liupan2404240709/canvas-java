# 04 · 乐观锁与并发保存

## 一、一句话定位

两个人同时开着同一张画布，后保存的那个应该**被拒绝并提示刷新**，而不是静默覆盖别人的修改。这一篇讲 `version` 字段从读到写、两道校验怎么配合，以及实测的并发结果。

## 二、完整代码

```java
// 第一道：显式比较
CanvasProject project = requireProject(userId, projectId);
if (!Objects.equals(project.getVersion(), request.version())) {
    throw new BizException(ResultCode.PROJECT_VERSION_CONFLICT);
}

// ... 删除旧节点、插入新节点 ...

// 第二道：由 SQL 的 WHERE 条件兜底
int rows = projectMapper.updateById(project);
if (rows == 0) {
    throw new BizException(ResultCode.PROJECT_VERSION_CONFLICT);
}
```

拦截器配置在阶段 0 就写好了（`MybatisPlusConfig`）：

```java
interceptor.addInnerInterceptor(new OptimisticLockerInnerInterceptor());
```

## 三、逐段拆解

### 3.1 为什么要两道校验

第一道是**快速失败**：客户端拿的是 5 分钟前的 version，本地就能判断出"你肯定落后了"，没必要走后面的删除和插入。

第二道是**并发兜底**。第一道校验到 `updateById` 之间有一个时间窗口：

```
线程A: 读 version=3 ────────────────────────┬─ UPDATE WHERE version=3 ✓
线程B:      读 version=3 ──┬─ 校验通过 ─────┴─ UPDATE WHERE version=3 ✗ (已是4)
                            ↑
                    两个都能通过第一道
```

只有数据库的 `WHERE version = ?` 能真正裁决。**应用层判断永远有竞态，最终一致性必须靠存储层**。

### 3.2 第二道校验的 SQL 长什么样

实测日志（`/tmp/s2-run.log`）：

```
==>  Preparing: UPDATE t_canvas_project SET user_id=?, title=?, background_mode=?, ...,
    version=?, created_at=?, updated_at=?
    WHERE id=? AND version=? AND deleted=0
```

三点：

- `SET version=?` 里的值是**拦截器改写后的新版本**（旧值+1）；
- `WHERE version=?` 是**旧版本**；
- 追加的 `deleted=0` 来自 `@TableLogic`。

### 3.3 为什么 `rows == 0` 直接抛异常，而不是重试

自动重试听起来更友好，但在这里是错的：**重试意味着把客户端的旧数据强行写进最新版本**，等于绕过了冲突检测，把 B 的修改覆盖掉。

正确处理是抛 409，让前端：① 提示"画布已在其他窗口修改"；② 重新拉 `/projects/{id}`；③ 让用户决定要不要覆盖。

### 3.4 为什么 `copy` 出来的项目 version 是 0

`newProject()` 里显式 `setVersion(0)`。版本号表达的是"这份内容被改过几次"，副本是全新内容，从 0 开始合理。

## 四、实测：真实并发

用两个线程在同一时刻用**同一个 version** 保存：

```python
results = []
def racer(idx):
    body = {"version": ver, "nodes": [dict(nodes[0], title=f"并发{idx}")], "connections": []}
    st, r = call("PUT", f"/projects/{pid}/snapshot", body, token)
    results.append((idx, st, r.get("code")))

threads = [threading.Thread(target=racer, args=(i,)) for i in (1, 2)]
```

结果：

```
并发结果: [(1, 409, 40920), (2, 200, 0)]
成功数: 1 冲突数: 1
```

一次成功、一次 40920，符合预期。再查详情确认**成功那次的数据是完整的**，没有出现"节点被删了但没写回"的中间态——这是事务 + 乐观锁共同作用的结果。

### 如果想验证"没有乐观锁会怎样"

把 `@Version` 注解去掉再跑同样的测试，两次都会返回 200，最后库里是**后提交者的数据**，先提交的修改无声消失——这就是"丢更新"（lost update）。

## 五、乐观锁 vs 悲观锁 vs 分布式锁

| | 乐观锁（本项目） | 悲观锁 `SELECT ... FOR UPDATE` | Redis 分布式锁 |
| --- | --- | --- | --- |
| 实现 | version 字段 | 数据库行锁 | `SETNX` + 过期时间 |
| 冲突时 | 后到者失败，重试 | 后到者阻塞等待 | 后到者等待或失败 |
| 适用 | 冲突少、读多写少 | 冲突多、必须串行 | 跨服务、跨库 |
| 代价 | 需要重试逻辑 | 连接被占住，可能死锁 | 多一个依赖，要考虑锁续期 |

画布保存是"用户手停之后才触发"的低频操作，冲突概率低——乐观锁是最合适的。如果真的出现大量冲突，说明产品设计有问题（比如每移动一个节点就保存一次）。

## 六、`version` 的保护范围：只保护"内容"

`PATCH /projects/{id}` 改名时**不递增 version**：

```java
// 注意这里不动 version：改标题不影响画布内容
projectMapper.update(null, wrapper);
```

实测：

```
重命名  HTTP 200  {"title": "改过名的画布", "updatedAt": "..."}
version 是否未变: True (2 -> 2)
```

**理由**：如果重命名也算版本变化，那用户 A 在列表页改个名字，用户 B 正在编辑的画布就会保存失败——这不合理，因为两者根本没碰同一份数据。

**推论**：`version` 是"内容版本"，不是"行版本"。这个区分要想清楚，否则协作场景下会刷出大量无意义冲突。

## 七、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 并发控制 | 乐观锁 + 两道校验 | 悲观锁 | 见第五节 |
| 冲突处理 | 拒绝 + 提示刷新 | 自动重试 | 重试等于覆盖别人的修改 |
| 版本粒度 | 整个画布 | 每个节点一个版本 | 节点级版本要维护 N 个计数器，且前端合并逻辑极其复杂 |
| 改名是否递增 | 不递增 | 递增 | 见第六节 |

## 八、面试考察点

### 基础题

**Q1：乐观锁和悲观锁的区别？**

一句话：乐观锁假设冲突少，先干活最后检查；悲观锁假设冲突多，先锁住再干活。展开时补上"各自适用场景"和"实现方式"。

**Q2：`@Version` 注解怎么工作的？**

MP 的 `OptimisticLockerInnerInterceptor` 在 update 前改写 SQL，SET 里 `version = version + 1`，WHERE 里追加 `version = 旧值`。返回 0 行表示版本已被别人改过。

### 进阶题

**Q3：为什么应用层比较了 version，还要靠 SQL？**

因为应用层比较和实际写入之间有窗口，两个请求可能都通过比较。数据库的行锁 + 条件更新是原子的，只有它能裁决。标准说法：**检查与写入必须在同一个原子操作里**。

**Q4：如果业务要求"合并两个人的修改"怎么办？**

那就不是锁的问题了，需要 CRDT / OT 这类协同算法（Figma、Google Docs 的做法）。对画布来说，可以按节点做合并：以 `nodeKey` 为粒度比较两边的 diff，冲突的节点再让用户选。这远超阶段 2 的范围，但面试时能说出这个方向会加分。

**Q5：`version` 用 `int` 会不会溢出？**

一次保存 +1，一天 1000 次也要 5800 年。真担心可以用 `long`，或者定期归一化。

### 陷阱题

**Q6：`updateById` 传一个 `new` 出来的实体（只设 id 和 version）会怎样？**

其它字段会被设成 null 吗？不会——MP 的 update 只更新非 null 字段。但 `version` 会正常参与条件。所以"只更新部分字段 + 乐观锁"是可行的，只是本项目选择读全量再改，因为需要返回完整的 VO。

**Q7：逻辑删除和乐观锁会打架吗？**

会叠加：`WHERE id=? AND version=? AND deleted=0`。如果记录被逻辑删除了，`updateById` 也会返回 0，看起来像"版本冲突"，实际是"记录没了"。所以 `requireProject` 必须在最前面先查一次，把"不存在"和"版本冲突"分开。

## 九、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 实体 version 为 null | 乐观锁静默失效 | 必须从库里读或手动 set |
| 冲突后自动重试 | 别人的修改被覆盖 | 抛 409 让前端刷新 |
| 忘了判断 `rows == 0` | 冲突被当成成功 | 必须判断返回值 |
| PATCH 也递增 version | 协作时大量假冲突 | 只让内容变更递增 |
| 用 `update(entity, wrapper)` 且 wrapper 带 version | 条件重复 | 二选一即可 |
