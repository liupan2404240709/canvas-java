# 07 · 分页与关键字搜索

## 一、一句话定位

列表页要"按更新时间倒序、支持标题搜索、分页不重复不遗漏"。看起来是最简单的接口，坑却最多。

## 二、完整代码

```java
@Override
public PageResult<ProjectSummaryVO> list(Long userId, String keyword, long page, long size) {
    long safePage = Math.max(page, 1);
    long safeSize = size <= 0 ? DEFAULT_PAGE_SIZE : Math.min(size, MAX_PAGE_SIZE);

    LambdaQueryWrapper<CanvasProject> wrapper = new LambdaQueryWrapper<CanvasProject>()
            .eq(CanvasProject::getUserId, userId)
            .like(StringUtils.hasText(keyword), CanvasProject::getTitle, keyword == null ? null : keyword.trim())
            .orderByDesc(CanvasProject::getUpdatedAt)
            .orderByDesc(CanvasProject::getId);

    Page<CanvasProject> result = projectMapper.selectPage(new Page<>(safePage, safeSize), wrapper);
    List<ProjectSummaryVO> items = result.getRecords().stream().map(ProjectSummaryVO::from).toList();
    return new PageResult<>(safePage, safeSize, result.getTotal(), items);
}
```

## 三、逐段拆解

### 3.1 参数兜底：`Math.max` / `Math.min`

```java
long safePage = Math.max(page, 1);          // page=0 或负数 → 1
long safeSize = size <= 0 ? 20 : Math.min(size, 100);   // size=500 → 100
```

实测：

```
size=500 被压到: 100
```

**为什么要压上限**：`size=100000` 会让 MySQL 一次吐出整表，既慢又可能 OOM。上限是接口契约的一部分，要写进 `api.md`。

**为什么不报错而是静默压**：分页参数是"可容错的展示参数"，报 400 会让前端一个手误就白页。压到边界更符合使用习惯。（如果是写操作参数，就该报错。）

### 3.2 条件构造：`.like(condition, column, value)`

`like` 的第一个参数是 boolean 开关：`StringUtils.hasText(keyword)` 为 false 时，这个条件整段不拼进 SQL。

这样**一个 wrapper 覆盖"有搜索"和"无搜索"两种情况**，不用写两个方法。

生成的 SQL：

```sql
-- 有 keyword
WHERE user_id = ? AND deleted = 0 AND title LIKE '%改过名%'
-- 无 keyword
WHERE user_id = ? AND deleted = 0
```

`deleted = 0` 是 `@TableLogic` 自动加的。

### 3.3 为什么排序要两个字段

```java
.orderByDesc(CanvasProject::getUpdatedAt)
.orderByDesc(CanvasProject::getId)
```

`updated_at` 是 `DATETIME`，**精度只有秒**。实测中连续两次保存的 `updatedAt` 都是 `17:19:42`——同一秒内更新的多条记录，只按时间排序结果是**不确定**的（MySQL 可能返回任意顺序）。

后果：翻页时同一行可能在第 1 页和第 2 页都出现，或者两页都漏掉。

加 `id DESC` 作为第二排序键，排序就变成全序，结果稳定。**这是分页接口的铁律：ORDER BY 必须有唯一键兜底。**

### 3.4 `PageResult` 的字段和前端对齐

```java
public record PageResult<T>(long page, long pageSize, long total, List<T> list) {
```

字段名 `list` 而不是 `records` / `items` / `rows`——因为前端 `web/src/services/api` 里已有的分页结构用的是 `list`。**接口字段名要对齐前端既有类型，而不是让前端来适配后端。**

## 四、`like '%x%'` 的索引问题

```sql
WHERE user_id = ? AND title LIKE '%改过名%'
```

`title` 上的索引**用不上**（前导 `%`）。但整个查询还是能走 `idx_project_user_updated`——因为 `user_id` 是等值条件，先用它过滤到"这个用户的几十张画布"，再逐行 `LIKE`。

**关键认知**：`LIKE '%x%'` 不是"必然全表扫描"，取决于**前面有没有等值条件先缩小范围**。这里一个用户最多几十张画布，逐行匹配毫无压力。

如果要做全站搜索（跨用户），那就该上全文索引或 ES 了。

### 转义问题

标题里如果有 `%` 或 `_`，`LIKE` 会把它当通配符。比如搜 `100%` 会匹配到 `100分`。

本项目没处理，因为：① 影响只是多匹配几条；② 处理要写 `ESCAPE` 子句，且在 `LambdaQueryWrapper.like` 里不方便。属于"已知小瑕疵"，写进文档而不是假装没有。

如果要修：

```java
String escaped = keyword.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
wrapper.apply("title LIKE CONCAT('%', {0}, '%') ESCAPE '\\\\'", escaped);
```

## 六、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 分页插件 | MP `PaginationInnerInterceptor` | 手写 `LIMIT` | 自动 count、自动方言，且阶段 0 已配 |
| 越界参数 | 静默压到边界 | 抛 400 | 展示参数容错优先 |
| 排序 | `updated_at DESC, id DESC` | 只按时间 | 秒级精度会重复/漏数据 |
| 搜索 | `LIKE '%kw%'` | 全文索引 | 个人空间数据量小，够用 |
| 列表内容 | 摘要（无节点） | 完整对象 | 20 条 × 几百节点 = 几 MB |

## 七、面试考察点

### 基础题

**Q1：MP 的分页是怎么实现的？**

`PaginationInnerInterceptor` 拦截 SQL，先改写成 `SELECT COUNT(*)` 查总数，再拼 `LIMIT offset, size`。方言由 `DbType` 决定（MySQL / Oracle / PostgreSQL 语法不同）。

**Q2：`Page` 的 `searchCount` 是干什么的？**

控制要不要查总数。列表页需要总数做页码，但如果只是"下拉加载更多"，就设 `new Page<>(page, size, false)` 省掉一次 count 查询。

### 进阶题

**Q3：深分页为什么慢？怎么优化？**

`LIMIT 100000, 20` 要先扫 100000 行再丢弃。优化：
1. **游标分页**（seek method）：`WHERE id < 上一页最后一个 id ORDER BY id DESC LIMIT 20`；
2. 延迟关联：先用覆盖索引查 id，再回表；
3. 限制最大页数。

本项目用页码分页，因为画布列表总量在几十到几百，深分页不会发生。**能说清"什么场景不需要优化"同样是能力。**

**Q4：`ORDER BY updated_at` 有索引吗？**

`idx_project_user_updated (user_id, deleted, updated_at)` 覆盖了 `WHERE user_id=? AND deleted=0 ORDER BY updated_at DESC`，可以直接用索引顺序，不用 filesort。加上 `id DESC` 之后排序变成两列，索引只能保证第一列有序，所以会做一次小范围排序——但数据量已经是"单个用户的画布"，代价可忽略。

**Q5：`total` 查询会不会很慢？**

`COUNT(*)` 在 InnoDB 要扫索引。单个用户几十条记录，毫秒级。如果是全站统计，就该用缓存或近似值。

### 陷阱题

**Q6：为什么 `size` 上限是 100 而不是 1000？**

接口契约要能解释：前端一页最多显示 100 条（列表页实际是 20），超过这个数没有使用场景，只会让慢查询有可乘之机。

**Q7：`keyword` 传空字符串会怎样？**

`StringUtils.hasText("")` 为 false，条件不拼——等价于不带 keyword。如果写成 `keyword != null`，空字符串会变成 `LIKE '%%'`，匹配所有行（虽然结果一样，但多了一次无谓的匹配，且 SQL 变长）。

## 八、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 只按时间排序 | 翻页重复/漏数据 | 加唯一键兜底 |
| `size` 不设上限 | 一次拉全表 | `Math.min` |
| `page=0` | `LIMIT -20` 语法错 | `Math.max(page,1)` |
| 空字符串当"有值" | 多拼一个 `LIKE '%%'` | `hasText` |
| 列表返回完整对象 | 响应几 MB | 摘要 VO |
