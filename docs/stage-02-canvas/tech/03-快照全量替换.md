# 03 · 快照全量替换

## 一、一句话定位

`saveSnapshot` 是阶段 2 最核心的方法：**一个事务里删光旧的节点和连线，再整批写入新的**。整个画布的持久化只有一个入口、一条路径。

## 二、完整代码

```java
@Override
@Transactional(rollbackFor = Exception.class)
public SaveSnapshotVO saveSnapshot(Long userId, Long projectId, SaveSnapshotRequest request) {
    CanvasProject project = requireProject(userId, projectId);

    // 第一道版本校验
    if (!Objects.equals(project.getVersion(), request.version())) {
        throw new BizException(ResultCode.PROJECT_VERSION_CONFLICT);
    }

    List<CanvasNodeDTO> nodes = request.nodes() == null ? List.of() : request.nodes();
    List<CanvasConnectionDTO> connections = request.connections() == null ? List.of() : request.connections();
    validateGraph(nodes, connections);

    // 整份替换
    nodeMapper.delete(new LambdaQueryWrapper<CanvasNode>().eq(CanvasNode::getProjectId, projectId));
    edgeMapper.delete(new LambdaQueryWrapper<CanvasEdge>().eq(CanvasEdge::getProjectId, projectId));
    insertNodes(projectId, nodes.stream().map(node -> toNodeEntity(projectId, node)).toList());
    insertEdges(projectId, connections.stream().map(connection -> toEdgeEntity(projectId, connection)).toList());

    project.setNodeCount(nodes.size());
    project.setConnectionCount(connections.size());
    if (request.viewport() != null) {
        project.setViewportX(request.viewport().x());
        project.setViewportY(request.viewport().y());
        project.setViewportK(request.viewport().k());
    }

    // 第二道版本校验
    int rows = projectMapper.updateById(project);
    if (rows == 0) {
        throw new BizException(ResultCode.PROJECT_VERSION_CONFLICT);
    }
    return new SaveSnapshotVO(project.getId(), project.getVersion(),
            project.getNodeCount(), project.getConnectionCount(), project.getUpdatedAt());
}
```

## 三、为什么是"全量替换"而不是"差量比对"

另一种常见做法是：把请求里的节点和库里的节点做 diff，算出新增/更新/删除三组，分别执行 insert / update / delete。

| | 全量替换 | 差量比对 |
| --- | --- | --- |
| 代码量 | 一条路径，约 20 行 | 三组逻辑 + 集合运算 |
| 正确性 | 用户删掉的节点一定会消失 | 差集算错就留下"幽灵节点" |
| 性能 | 30 个节点重插，约 5ms | 只有改动的行被写，但要多查一次全量做比对 |
| 主键稳定性 | 全换新 id | 保留原 id |

**选全量替换的关键理由**：画布的节点量级是"几十到几百"，不是"几万"。这个量级下重写的成本可以忽略，而"少一条可能出错的路径"收益巨大。

代价是节点主键每次都变。但前端只认自己生成的 `nodeKey`，主键对它不可见——**把不稳定的实现细节藏在后端**，这是这个设计成立的前提。

### 什么时候该反过来选差量

- 节点数量到万级（重插成本真的高）
- 节点上有外部引用（比如分享链接指向某个节点的评论），主键不能变
- 需要保留节点的创建时间做"最近编辑"统计

## 四、事务边界为什么这么划

`@Transactional(rollbackFor = Exception.class)` 加在整个方法上。考虑四个失败点：

```
① requireProject 失败（404）        → 没写任何数据，无需回滚
② 版本校验失败（409）               → 同上
③ 图结构校验失败（400）             → 同上
④ delete 成功、insert 失败（如唯一索引冲突）→ 必须回滚，否则节点被删光了却没写回去
⑤ insert 成功、updateById 版本冲突（409）→ 必须回滚，否则节点是新数据但版本没变
```

④ 和 ⑤ 就是事务存在的理由。特别是 ⑤：**如果不在同一个事务里，并发的第二个请求会把节点写成自己的数据、然后版本更新失败，库里就留下了一份"没有版本归属"的脏数据**。

实测验证过这条：两个线程同时用同一个 version 保存，结果是 `[(1, 200, 0), (2, 409, 40920)]` —— 一个成功一个冲突，且成功那次的节点数据完整（见 04 篇）。

### `rollbackFor = Exception.class` 有必要吗

有必要。Spring 默认只对 `RuntimeException` 和 `Error` 回滚，受检异常不回滚。虽然本项目业务异常都是 `RuntimeException`，但显式声明能防住以后有人引入受检异常时踩坑。

## 五、`saveSnapshot` 的完整时序

```
客户端                      Controller            Service                      MySQL
  │                            │                    │                            │
  ├─ PUT /projects/1/snapshot →│                    │                            │
  │                            ├─ currentUserId()   │                            │
  │                            ├─ saveSnapshot() ──→│                            │
  │                            │                    ├─ SELECT * FROM t_canvas_project WHERE id=1 ──→│
  │                            │                    │←─ version=3 ───────────────┤
  │                            │                    ├─ 3 == 3 ? 继续              │
  │                            │                    ├─ 校验 nodeKey/edge 引用      │
  │                            │                    ├─ DELETE FROM t_canvas_node WHERE project_id=1 ─→│
  │                            │                    ├─ DELETE FROM t_canvas_connection WHERE ... ─→│
  │                            │                    ├─ INSERT INTO t_canvas_node VALUES (..),(..) ─→│
  │                            │                    ├─ INSERT INTO t_canvas_connection VALUES .. ─→│
  │                            │                    ├─ UPDATE t_canvas_project SET ... , version=version+1
  │                            │                    │    WHERE id=1 AND version=3 AND deleted=0 ─→│
  │                            │                    │←─ affected rows = 1 ───────┤
  │                            │←─ SaveSnapshotVO ──┤                            │
  │←─ { version: 4 } ──────────┤                    │                            │
```

两次 SELECT 之间没有加锁，所以理论上存在"读到 version=3，别人也读到 3，都通过第一道校验"的窗口——这正是第二道校验存在的意义。

## 六、为什么先删后插，而不是先插后删

如果先插再删，会有唯一索引冲突：新旧节点 `node_key` 相同，`(project_id, node_key)` 唯一索引直接报错。所以必须**先删后插**（同一事务内，删除对后续 insert 立即可见）。

如果担心"删完插入失败导致数据丢了"，完全不用担心——事务保证要么全成、要么全回到删除前的状态。

## 七、设计决策

| 决策 | 选了 | 替代 | 原因 |
| --- | --- | --- | --- |
| 保存语义 | 整份替换 | 差量 upsert | 见第三节 |
| 事务范围 | 整个方法 | 只包 insert | 版本冲突必须能回滚 insert |
| 节点删除 | 物理删除 | 逻辑删除 | 附属数据跟随快照，留历史没有业务意义 |
| 返回内容 | 只回 version 和计数 | 回整份快照 | 几 MB 数据保存后没用途 |

## 八、面试考察点

### 基础题

**Q1：`@Transactional` 失效的场景有哪些？**

四条必答：
1. **同类内部调用**——`this.method()` 不走代理，注解无效；
2. **方法不是 public**——Spring 的代理只拦 public（CGLIB 能拦 protected 但不建议）；
3. **异常被吞了**——`try/catch` 没往外抛，事务管理器不知道要回滚；
4. **异常类型不匹配**——默认只回滚 `RuntimeException`；
5. 补充：**多线程**——事务绑定在 ThreadLocal 上，子线程里的操作不在同一事务。

**Q2：为什么在 Service 上加 `@Transactional` 而不是 Controller？**

事务边界应该等于"一个完整的业务操作"。Controller 可能有参数校验、响应组装，不该被事务包住（事务开得越久，占用连接越久）。

### 进阶题

**Q3：全量替换会不会有性能问题？**

要给出量级：30 个节点、29 条连线，两条 DELETE + 两条多值 INSERT，本地实测保存接口整体在 10ms 量级。如果节点上万，就要换成差量；但那种数据量前端也渲染不动，属于"设计上不该出现的场景"。

**Q4：两个请求同时保存，具体会发生什么？**

按时间线说：
1. A、B 都读到 version=3，都通过第一道校验；
2. A 先执行 DELETE，给这些行加了排他锁；
3. B 的 DELETE 被阻塞（等锁）；
4. A 完成 insert 和 `UPDATE ... WHERE version=3`，提交；
5. B 恢复执行，删除的是 A 刚插入的节点（当前读，能看到已提交数据）；
6. B 的 `UPDATE ... WHERE version=3` 匹配不到（已是 4），影响行数 0，抛异常；
7. B 的事务回滚，它删掉又插入的数据全部撤销，库里只剩 A 的。

结论：**B 的修改完全丢失，但库里不会脏**。前端收到 409 后重新拉快照即可。

**Q5：为什么不在保存时加 `SELECT ... FOR UPDATE`？**

那是悲观锁：会阻塞其他读，连接占用时间变长，且"两个窗口同时开着"是正常场景，直接卡住体验很差。乐观锁的代价只是让后提交的人重试一次。

### 陷阱题

**Q6：`delete(Wrapper)` 会不会被 MP 的防全表删除插件拦下来？**

不会，因为条件里有 `project_id = ?`。`BlockAttackInnerInterceptor` 只在**没有 WHERE 条件**时抛异常。这也是配置该插件后必须检查每个 delete 的原因。

**Q7：如果客户端传了 `nodes: null`，会怎样？**

代码里 `request.nodes() == null ? List.of() : request.nodes()` 把 null 当成空列表——**这意味着传 null 等于"清空画布"**。这是个需要明确的语义：如果前端只想改视口，应该用 `PATCH /projects/{id}` 而不是保存快照。接口文档里写清了这一点。

## 九、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 先插后删 | 唯一索引冲突 | 新旧 `node_key` 相同 |
| 忘了包事务 | 中途失败后画布变空 | 删除已生效 |
| 在循环里 `insert` | 30 次网络往返 | 应该用批量插入（06 篇） |
| 校验放在删除之后 | 校验失败但已删数据 | 校验必须在任何写操作之前 |
| `nodes` 传 null 以为"不改" | 画布被清空 | null == 空列表，语义要写进文档 |
