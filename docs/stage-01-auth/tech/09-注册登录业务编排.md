# 09 · 注册登录业务编排

## 一句话定位

`AuthServiceImpl` 是阶段 1 的核心：它把 BCrypt、JWT、Redis 白名单、失败计数这些零件按正确顺序串起来，是面试时讲"我做过什么"最容易展开的地方。

## 方法清单

| 方法 | 做了什么 | 涉及的技术点 |
| --- | --- | --- |
| `register` | 唯一性校验 → BCrypt → 插入 → 签发令牌 | 并发唯一性（唯一索引兜底）、唯一键异常翻译 |
| `login` | 锁定检查 → 等时校验 → 状态检查 → 清计数 → 更新登录信息 → 签发 | 时序攻击、失败计数、批量更新 |
| `refresh` | 解析 → 类型校验 → 白名单校验 → 用户状态 → 轮换 | token 轮换、重放检测 |
| `logout` | 拉黑 access → 撤销 refresh | 幂等性、归属校验 |
| `issueTokens` | 签发一对令牌并写白名单 | 单一职责的私有复用点 |

## 注册流程

```java
@Override
public TokenVO register(RegisterRequest request) {
    String username = request.username().trim();
    String email = normalizeEmail(request.email());

    if (findByUsername(username) != null) throw new BizException(ResultCode.USERNAME_TAKEN);
    if (email != null && findByEmail(email) != null) throw new BizException(ResultCode.EMAIL_TAKEN);

    User user = new User();
    user.setUsername(username);
    user.setEmail(email);
    user.setPasswordHash(passwordEncoder.encode(request.password()));
    user.setNickname(StringUtils.hasText(request.nickname()) ? request.nickname().trim() : username);
    user.setStatus(User.STATUS_ENABLED);

    try {
        userMapper.insert(user);
    } catch (DuplicateKeyException e) {
        String message = e.getMessage() == null ? "" : e.getMessage();
        throw new BizException(message.contains("uk_user_email") ? ResultCode.EMAIL_TAKEN : ResultCode.USERNAME_TAKEN);
    }

    return issueTokens(user);
}
```

### ① 为什么"先查一次"还要 catch 异常

这是一段典型的**双保险**写法，也是面试高频追问点。

只做前置检查的问题：`SELECT` 和 `INSERT` 之间永远存在时间窗口。两个请求同时注册 `demo`，都查到"不存在"，然后都去插入——如果只靠应用层判断，就会插进两条同名记录（或者第二条报数据库异常但用户看到 500）。

**真正的唯一性只能由数据库保证**：唯一索引 `uk_user_username` 是最终防线。应用层的提前检查只是为了给出友好提示（"用户名已被占用"而不是"服务异常"）。

`DuplicateKeyException` 是 Spring 对 `SQLIntegrityConstraintViolationException` 的翻译，属于 `DataIntegrityViolationException` 的子类。

### ② 靠异常信息里的索引名区分是哪个字段冲突

```java
message.contains("uk_user_email")
```

Spring 的 `DuplicateKeyException` 不会告诉你"哪个约束冲突"，只能从 `e.getMessage()` 里解析。MySQL 的报错长这样：

```
Duplicate entry 'a@x.com' for key 't_user.uk_user_email'
```

所以能用 `contains("uk_user_email")` 判断。**这是脆弱的**——数据库换成 PostgreSQL 或索引改名就失效。更稳的写法是前置检查 + 兜底统一返回"用户名或邮箱已被占用"。当前实现选择精确提示，代价是耦合了 MySQL 的报错格式，属于已知取舍。

### ③ 邮箱归一化

```java
return email.trim().toLowerCase(Locale.ROOT);
```

不归一化的问题：`A@x.com` 和 `a@x.com` 是两个不同的字符串，但大多数邮件服务器认为是同一个邮箱。

但表上的唯一索引用的是 `utf8mb4_0900_ai_ci`（大小写不敏感），所以 `A@x.com` 和 `a@x.com` 在索引层面**已经会冲突**了。归一化让应用层的判断和索引层的判断保持一致——否则会出现"前置检查说没占用，插入时报冲突"的诡异现象。

`Locale.ROOT` 而不是默认 locale：土耳其语的 `toLowerCase()` 会把 `I` 变成 `ı`（无点 i），用 ROOT 避免这种 locale 相关的坑。

### ④ 注册成功直接返回令牌

比"注册成功后让前端再调一次登录"少一次往返，体验更好。代价是注册接口也要签发令牌，逻辑和登录有重叠——所以抽了 `issueTokens`。

## 登录流程

```java
public TokenVO login(LoginRequest request, String clientIp) {
    String account = request.account().trim();

    long lockedSeconds = loginAttemptGuard.lockedSeconds(account);
    if (lockedSeconds > 0) {
        throw new BizException(ResultCode.ACCOUNT_LOCKED,
                "登录失败次数过多，请 " + Math.max(1, lockedSeconds / 60) + " 分钟后再试");
    }

    User user = findByAccount(account);
    String hash = user == null ? dummyHash : user.getPasswordHash();
    boolean matched = passwordEncoder.matches(request.password(), hash);

    if (user == null || !matched) {
        int remaining = loginAttemptGuard.recordFailure(account);
        if (remaining <= 0) {
            throw new BizException(ResultCode.ACCOUNT_LOCKED,
                    "登录失败次数过多，请 " + loginAttemptGuard.lockDuration().toMinutes() + " 分钟后再试");
        }
        throw new BizException(ResultCode.BAD_CREDENTIALS, "用户名或密码错误，还可尝试 " + remaining + " 次");
    }

    if (!user.active()) throw new BizException(ResultCode.ACCOUNT_DISABLED);

    loginAttemptGuard.clear(account);
    touchLastLogin(user.getId(), clientIp);
    return issueTokens(user);
}
```

### ⑤ 顺序设计：廉价检查在前，昂贵计算在后

```
锁定检查（1 次 Redis GET）
  → 查用户（1 次 MySQL 查询，走唯一索引）
    → BCrypt 校验（约 60ms CPU）
      → 状态检查
        → 清计数 + 更新登录信息（1 次 UPDATE）
          → 签发 2 个 JWT + 1 次 Redis SET
```

把 BCrypt 放最后（在能拿到 hash 之后），把 Redis 计数检查放最前。如果顺序反了——先 BCrypt 再判断锁定——那么被锁定的账号每次请求仍会烧 60ms CPU，攻击者用 100 并发就能把 CPU 打满。

### ⑥ `user == null || !matched` 合并判断

注意这里不能拆成两个 if：

```java
if (user == null) throw ...;        // 错：这条分支跳过了 BCrypt
if (!matched) throw ...;
```

因为 `hash` 已经用 `dummyHash` 兜底了，两个分支都应该走"记录失败 + 报错"。合并成一个判断保证行为完全一致。

### ⑦ 失败时的两种文案

```java
if (remaining <= 0) → "登录失败次数过多，请 15 分钟后再试"   // 429
else                → "用户名或密码错误，还可尝试 N 次"        // 401
```

第一次触及上限的那一次，返回的是 429 而不是 401——因为此时账号已经被锁，语义变了。前端可以据此显示不同的提示。

`Math.max(1, lockedSeconds / 60)`：向上取整的简化写法，避免"还剩 30 秒"时显示"请 0 分钟后再试"。

### ⑧ 先查密码再查状态

```java
if (user == null || !matched) { ... }   // 密码不对，先拒
if (!user.active()) { ... }             // 密码对了，才告诉你账号被禁用
```

如果反过来（先判断禁用），攻击者可以用"账号已被禁用"这个提示来**确认账号存在**。现在必须知道正确密码才能看到"禁用"提示，账号枚举的价值就没了。

### ⑨ `touchLastLogin` 用 `LambdaUpdateWrapper` 而不是 `updateById`

```java
userMapper.update(null, new LambdaUpdateWrapper<User>()
        .eq(User::getId, userId)
        .set(User::getLastLoginAt, LocalDateTime.now())
        .set(User::getLastLoginIp, clientIp));
```

- `updateById(user)` 会把整个对象的所有非 null 字段都更新一遍（包括 `passwordHash`、`username`），既浪费又可能在并发下覆盖别人的修改（丢失更新）。
- `UpdateWrapper` 只 set 需要的两列，SQL 是 `UPDATE t_user SET last_login_at = ?, last_login_ip = ? WHERE id = ? AND deleted = 0`。

**注意 `update` 的第一个参数传 null**：这是 MyBatis-Plus 的约定，表示"不基于实体对象，只用 wrapper 里的 set"。

### ⑩ 登录成功才清计数

```java
loginAttemptGuard.clear(account);
```

放在密码校验之后、签发之前。如果放在最前面，那么"锁定状态下"的请求也会把计数清掉，锁定形同虚设。

## 刷新流程

```java
public TokenVO refresh(String refreshToken) {
    Claims claims;
    try {
        claims = jwtService.parse(refreshToken);
    } catch (JwtException | IllegalArgumentException e) {
        throw new BizException(ResultCode.TOKEN_INVALID);
    }

    if (!JwtService.TYPE_REFRESH.equals(jwtService.typeOf(claims))) {
        throw new BizException(ResultCode.TOKEN_INVALID);
    }

    String jti = claims.getId();
    Long owner = tokenStore.findRefreshTokenOwner(jti);
    if (owner == null) {
        log.warn("refresh token 不在白名单中，疑似重放 jti={} userId={}", jti, claims.getSubject());
        throw new BizException(ResultCode.TOKEN_REVOKED);
    }

    User user = userMapper.selectById(owner);
    if (user == null || !user.active()) {
        tokenStore.revokeRefreshToken(jti);
        throw new BizException(ResultCode.ACCOUNT_DISABLED);
    }

    tokenStore.revokeRefreshToken(jti);
    return issueTokens(user);
}
```

### ⑪ 为什么必须校验 `type`

access 和 refresh 是同一把密钥签的，验签都能通过。如果不判断 `type`：

- 拿 access token 调刷新接口 → 30 分钟的有效期被无限续期，access token 短有效期的设计彻底失效。

### ⑫ 白名单查不到时为什么返回"已失效"而不是"无效"

语义区分对前端有用：
- `TOKEN_INVALID`（40112）→ 这不是一个合法令牌，直接跳登录页；
- `TOKEN_REVOKED`（40114）→ 曾经合法但已被撤销，可能是重复使用了旧 token。

同时打一条 warn 日志：如果短时间内大量出现，说明有人在重放 token。

### ⑬ 用户被禁用时顺手撤销

```java
tokenStore.revokeRefreshToken(jti);
```

否则这个 refresh token 会一直留在 Redis 里到 14 天后过期，虽然每次刷新都会再判断一次状态，但早点清理更干净。

## 登出流程

```java
public void logout(LoginUser current, String refreshToken) {
    tokenStore.blacklistAccessToken(current.tokenId(), current.tokenExpiresAt());

    if (StringUtils.hasText(refreshToken)) {
        try {
            Claims claims = jwtService.parse(refreshToken);
            Long owner = tokenStore.findRefreshTokenOwner(claims.getId());
            if (owner != null && owner.equals(current.id())) {
                tokenStore.revokeRefreshToken(claims.getId());
            }
        } catch (JwtException | IllegalArgumentException e) {
            log.debug("登出时忽略无效的 refreshToken: {}", e.getMessage());
        }
    }
}
```

### ⑭ 两个细节

1. **归属校验**：`owner.equals(current.id())`。没有这一句，攻击者拿到别人的 refresh token 就可以反复调登出接口把别人踢下线（虽然拿不到 token 本身，但能造成骚扰）。
2. **必须幂等**：refresh token 过期、格式错，都不该让登出失败。access token 拉黑已经生效，用户已经"登出成功"了。所以 catch 后只打 debug 日志。

## 设计决策对比

| 决策 | 选的 | 替代 | 代价 |
| --- | --- | --- | --- |
| 唯一性保证 | 前置查询 + 唯一索引兜底 | 只靠前置查询 | 多一次查询，但并发安全 |
| 唯一冲突提示 | 解析索引名 | 统一"已被占用" | 提示更准，但耦合数据库报错格式 |
| 登录失败响应 | 区分 401 / 429 | 统一 401 | 语义更准，前端分支稍多 |
| 注册返回 | 直接给令牌 | 只返回用户信息 | 少一次往返，接口职责稍重叠 |
| 事务 | 未加 `@Transactional` | 加事务 | 见下方说明 |

### 关于"为什么没有 `@Transactional`"

注册和登录各自只做一次写操作（insert 或 update），不存在"多表写入需要原子性"的场景，所以不需要事务。

**但要注意**：`register` 里"insert + 写 Redis 白名单"是两个数据源的操作。如果 insert 成功、Redis 写失败，会得到一个"注册成功但没 token"的状态——用户重新登录即可恢复，不构成数据不一致。这种"跨数据源无法强一致"的场景，正确做法是用最终一致性（补偿任务）而不是分布式事务，阶段 1 不需要。

阶段 2 保存画布时会用到 `@Transactional`（多表写入），到时候再讲。

## 面试考察点

**基础**

- 注册接口为什么不能只判断"用户名是否存在"就插入？—— 并发下会重复注册。
- 登录失败为什么要计数？计数为什么放 Redis？
- 登录时为什么先校验密码再判断账号状态？—— 否则可以枚举账号。

**进阶**

- `DuplicateKeyException` 是怎么来的？—— Spring 的 `SQLExceptionTranslator` 把数据库错误码翻译成 `DataAccessException` 体系。
- 为什么 `updateById` 在并发场景下可能丢失更新？—— 它更新所有非 null 字段，两个请求各自基于旧数据修改不同字段时会互相覆盖。更严谨的做法是只更新变化的字段，或加版本号（`@Version` 乐观锁）。
- 刷新接口为什么必须校验 token 类型？—— access/refresh 同密钥，不校验会导致 access 无限续期。
- refresh token 被重放时应该怎么做？—— 撤销该用户全部 refresh token 并强制重新登录（当前只记录日志，属于可扩展点）。
- 登录接口的响应时间应该一致吗？—— 是，否则会被时序攻击枚举账号。

**陷阱**

- "在 `@Transactional` 方法里发消息/写 Redis"—— 事务未提交时外部系统已经看到了数据，回滚后不一致。
- "`@Transactional` 加在 private 方法上"—— Spring AOP 代理不生效。
- "把 `loginAttemptGuard.clear()` 写在方法第一行"—— 锁定失效。

## 常见坑

1. `passwordEncoder.matches(raw, null)` 会抛 `IllegalArgumentException`，所以 `dummyHash` 是必须的，不能传 null。
2. `LambdaUpdateWrapper` 如果不带 `eq` 条件，会被 `BlockAttackInnerInterceptor` 拦下来抛异常——这是阶段 0 配的防护在起作用。
3. `clientIp` 取的是 `request.getRemoteAddr()`，经过 Nginx 反向代理后永远是 `127.0.0.1`，真实 IP 要从 `X-Forwarded-For` 取（阶段 8 部署时处理）。
