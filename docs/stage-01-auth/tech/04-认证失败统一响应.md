# 04 · 认证失败统一响应

## 一句话定位

`RestAuthenticationEntryPoint`（401）和 `RestAccessDeniedHandler`（403）是 Security 的两个异常出口，作用是把 Security 内部抛出的 `AuthenticationException` / `AccessDeniedException` **翻译成和业务接口一致的 JSON**。

## 完整代码

```java
@Component
public class RestAuthenticationEntryPoint implements AuthenticationEntryPoint {

    private final ObjectMapper objectMapper;
    // 构造注入省略

    @Override
    public void commence(HttpServletRequest request, HttpServletResponse response, AuthenticationException authException)
            throws IOException {
        Object reason = request.getAttribute(JwtAuthenticationFilter.ATTR_AUTH_ERROR);
        ResultCode resultCode = reason instanceof ResultCode code ? code : ResultCode.UNAUTHORIZED;

        response.setStatus(resultCode.getHttpStatus());
        response.setContentType(MediaType.APPLICATION_JSON_VALUE);
        response.setCharacterEncoding(StandardCharsets.UTF_8.name());
        objectMapper.writeValue(response.getOutputStream(), Result.fail(resultCode));
    }
}
```

`RestAccessDeniedHandler` 结构完全相同，只是固定用 `ResultCode.FORBIDDEN`。

## 逐段拆解

### ① 为什么需要这两个接口

Spring Security 的异常处理链是这样的：

```
异常发生
  ├─ AuthenticationException  → ExceptionTranslationFilter 捕获
  │                              └→ AuthenticationEntryPoint.commence()      （401）
  └─ AccessDeniedException    → ExceptionTranslationFilter 捕获
                                 └→ AccessDeniedHandler.handle()            （403）
```

关键点：**这些异常发生在 `DispatcherServlet` 之前**，所以 `@RestControllerAdvice` 里的 `@ExceptionHandler` **抓不到**它们。不自己实现这两个接口，就会落到 Security 的默认行为：

| 默认行为 | 前端看到什么 |
| --- | --- |
| `Http403ForbiddenEntryPoint` | 空 body 的 403，没有 code 字段 |
| 表单登录的 `LoginUrlAuthenticationEntryPoint` | 302 跳转到 HTML 登录页 |

前端拦截器拿不到 `code`，就没法区分"需要重新登录"和"没有权限"，只能靠 HTTP 状态码硬判断——一旦以后加了网关把所有错误包成 200，就全乱了。

### ② 为什么认证失败要读出 `ATTR_AUTH_ERROR`

`AuthenticationEntryPoint` 的入参只有一个 `AuthenticationException`，它没有"token 过期"和"token 无效"的区分能力——对 Security 来说，两者都是"没有有效的认证信息"。

而我们需要给前端不同的处理：
- `40113 登录已过期` → 触发静默刷新
- `40112 凭证无效` → 直接跳登录页
- `40100 未登录` → 跳登录页

所以让 `JwtAuthenticationFilter` 把具体原因挂在 request 属性上（`ATTR_AUTH_ERROR`），这里读出来用。属性名用 `类全名 + ".error"` 的写法是为了避免和其他框架的属性名撞车。

```java
ResultCode resultCode = reason instanceof ResultCode code ? code : ResultCode.UNAUTHORIZED;
```

模式匹配 instanceof + 默认兜底：请求压根没带 token 时属性是 null，落到 `UNAUTHORIZED`。

### ③ 为什么要手动设 `response` 的三件套

```java
response.setStatus(resultCode.getHttpStatus());
response.setContentType(MediaType.APPLICATION_JSON_VALUE);
response.setCharacterEncoding(StandardCharsets.UTF_8.name());
```

- `setStatus`：`HttpServletResponse` 默认 200，不设就是一个"成功"的 401 响应体，前端和网关都会误判。
- `setContentType` + `setCharacterEncoding`：**必须分开设**。如果只写 `setContentType("application/json;charset=UTF-8")`，在某些容器下 `getWriter()` 已经按默认编码初始化过就会失效。分开设是最稳的写法。

**不设 charset 会怎样**：`Result.message` 里全是中文，Windows 默认 GBK 环境下浏览器解析出乱码。

### ④ 用 `getOutputStream()` 而不是 `getWriter()`

`objectMapper.writeValue(OutputStream, obj)` 内部会按 UTF-8 写字节，比 `getWriter()` 少一层字符流包装，也避免"writer 已被调用过"的 `IllegalStateException`。

注意：`getWriter()` 和 `getOutputStream()` **不能同时使用**，用了其中一个另一个就抛异常。

### ⑤ 为什么 `RestAccessDeniedHandler` 现在用不上还要写

阶段 1 所有受保护接口都只要求"已登录"，不存在"已登录但权限不足"的情况，所以这个 Handler 现在触发不到。

但一旦阶段 2 加了"只能操作自己的画布"这类规则（用 `@PreAuthorize` 或手写判断抛 `AccessDeniedException`），没有它就会退化成 Security 默认的空 403 页面。**提前写好是零成本的**，比到时候排查"为什么 403 没有 message"便宜。

### ⑥ traceId 是怎么进到响应体里的

`Result.fail()` 内部调用 `TraceId.current()` 从 MDC 取。而 `TraceIdFilter` 的 order 是 `Ordered.HIGHEST_PRECEDENCE`（`Integer.MIN_VALUE`），Security 过滤链的 order 是 `-100`，所以 **traceId 一定先于 Security 执行**，MDC 里已经有值。

这也是为什么过滤器顺序不能乱调：如果 `TraceIdFilter` 排到了 Security 后面，401 响应里的 traceId 会是空字符串。

## 设计决策对比

| 决策 | 选的 | 替代 | 代价 |
| --- | --- | --- | --- |
| 错误详情传递 | request 属性 | 自定义 `AuthenticationException` 子类 | 属性更简单，但类型不安全（要 instanceof 判断）；自定义异常更类型安全，但要额外写 `AuthenticationEntryPoint` 的映射 |
| 响应体 | 复用 `Result` | 单独的 ErrorResponse | 复用保证前后端只解析一种结构 |
| 状态码 | 真实 401/403 | 全部 200 + 业务码 | 真实状态码让网关、监控、浏览器原生行为都正常 |

## 面试考察点

**基础**

- `AuthenticationEntryPoint` 和 `AccessDeniedHandler` 分别在什么时候触发？—— 未认证 / 已认证但无权限。
- 为什么 `@RestControllerAdvice` 抓不到 Security 抛的异常？—— 发生在 DispatcherServlet 之前。
- 401 和 403 的语义区别？—— 401 是"你是谁我不知道"，403 是"我知道你是谁，但你不能做这个"。

**进阶**

- 为什么不直接用 Security 默认的 401？—— 无 body、无法区分过期/无效，前端没法自动刷新。
- 在 EntryPoint 里能拿到 `traceId` 吗？—— 能，前提是 traceId 过滤器排在 Security 之前。
- `ExceptionTranslationFilter` 具体做了什么？—— 捕获链中抛出的两类异常，按"是否匿名"分派到 EntryPoint 或 AccessDeniedHandler。
- 如果 `AuthenticationEntryPoint` 里再抛异常会怎样？—— 直接冒泡到容器，返回 Tomcat 默认 500 页面。

**陷阱**

- "我的接口 401 但没有响应体"—— 没配 `authenticationEntryPoint`。
- "401 响应中文乱码"—— 没设 `characterEncoding`。
- "异常处理器里加了 `@ExceptionHandler(AccessDeniedException.class)`，但没生效"—— 权限异常在 MVC 之前就抛了，走不到 Advice。

## 常见坑

1. 在 Handler 里调用 `response.getWriter()` 之后又调 `getOutputStream()` → `IllegalStateException`。
2. 忘记 `response.setStatus()` → 前端拿到 200 + `code:40100`，axios 拦截器不会走 error 分支。
3. 在 Handler 里注入 `ObjectMapper` 时用了 `new ObjectMapper()` → 丢掉了 `JacksonConfig` 里注册的 `LocalDateTime` 序列化器，响应里的时间格式会和其他接口不一致。
