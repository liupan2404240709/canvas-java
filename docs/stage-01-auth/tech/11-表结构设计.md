# 11 · 表结构设计

## 一句话定位

`t_user` 只有 12 个字段，但每个字段的类型、长度、默认值、索引都有理由。这一篇逐列解释，并处理"逻辑删除 + 唯一索引"这个经典冲突。

## 完整 DDL

```sql
CREATE TABLE IF NOT EXISTS t_user
(
    id            BIGINT       NOT NULL COMMENT '主键，MyBatis-Plus 雪花 ID 生成',
    username      VARCHAR(32)  NOT NULL COMMENT '登录名，全局唯一',
    email         VARCHAR(128) DEFAULT NULL COMMENT '邮箱，可空；唯一索引允许多个 NULL',
    password_hash VARCHAR(100) NOT NULL COMMENT 'BCrypt 密文，固定 60 位，留余量给算法升级',
    nickname      VARCHAR(32)  DEFAULT NULL COMMENT '展示昵称',
    avatar_url    VARCHAR(512) DEFAULT NULL COMMENT '头像地址',
    status        TINYINT      NOT NULL DEFAULT 1 COMMENT '1=正常 0=禁用',
    last_login_at DATETIME     DEFAULT NULL COMMENT '最近一次登录成功时间',
    last_login_ip VARCHAR(45)  DEFAULT NULL COMMENT '最近一次登录 IP，兼容 IPv6 长度',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    deleted       TINYINT      NOT NULL DEFAULT 0 COMMENT '逻辑删除 0=未删 1=已删',
    PRIMARY KEY (id),
    UNIQUE KEY uk_user_username (username),
    UNIQUE KEY uk_user_email (email)
) ENGINE = InnoDB
  DEFAULT CHARSET = utf8mb4
  COLLATE = utf8mb4_0900_ai_ci COMMENT ='用户表';
```

## 逐列设计说明

| 列 | 类型 | 为什么 |
| --- | --- | --- |
| `id` | `BIGINT` | 雪花 ID 是 64 位。**用有符号 BIGINT 而不是 UNSIGNED**：JDBC 读 UNSIGNED BIGINT 到 `Long` 时，超过 `Long.MAX_VALUE` 会报错，虽然雪花 ID 不会超，但没必要留隐患 |
| `username` | `VARCHAR(32)` | 32 字符对用户名足够（`@Pattern` 限制 4-20 位，留了余量给以后放宽）。`VARCHAR` 按实际长度存储，不会浪费 |
| `email` | `VARCHAR(128)` | 主流邮箱地址上限 254，但业务上 128 够用；如果以后要放宽，`ALTER` 即可 |
| `password_hash` | `VARCHAR(100)` | BCrypt 固定 60 字符，留 40 字符余量给以后换成 `{argon2}` 这类带前缀的格式。**不要用定长 CHAR**，算法升级时会截断 |
| `nickname` | `VARCHAR(32)` | 和 DTO 的 `@Size(max=32)` 对齐。**列长度必须 >= DTO 限制**，否则会出现"校验通过、入库报错" |
| `avatar_url` | `VARCHAR(512)` | URL 可能很长（带签名参数的 CDN 地址），512 是常见折中 |
| `status` | `TINYINT` | 只有 0/1 两个值，`TINYINT` 占 1 字节。**不用 `BIT`**：JDBC 映射成 `Boolean`，MyBatis-Plus 处理起来反而麻烦；**不用 `ENUM`**：加一个状态就要 `ALTER` |
| `last_login_at` | `DATETIME` | 见下方"时间类型选择" |
| `last_login_ip` | `VARCHAR(45)` | IPv6 最长 45 字符（`ffff:ffff:ffff:ffff:ffff:ffff:255.255.255.255`），用 `VARCHAR(15)` 会存不下 IPv6 |
| `created_at` | `DATETIME` | 建表加 `DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `DATETIME` | 加 `ON UPDATE CURRENT_TIMESTAMP`，兜住直接改库的场景 |
| `deleted` | `TINYINT` | 逻辑删除标记 |

### 时间类型：`DATETIME` vs `TIMESTAMP`

| | `DATETIME` | `TIMESTAMP` |
| --- | --- | --- |
| 范围 | 1000-9999 年 | 1970-2038 年 |
| 时区 | **不受时区影响**，存什么读什么 | 存入时转 UTC，读取时转会话时区 |
| 占用 | 5 字节（MySQL 5.6+） | 4 字节 |

本项目的 JDBC URL 已设 `serverTimezone=Asia/Shanghai`，应用层用的也是 `LocalDateTime`（无时区概念）。选 `DATETIME` 意味着"存进去的字符串原样存原样读"，行为最可预期。

2038 问题在 `TIMESTAMP` 上真实存在，业务表用 `DATETIME` 是更稳的选择。

### 字符集与排序规则

```sql
DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_0900_ai_ci
```

- **`utf8mb4` 而不是 `utf8`**：MySQL 的 `utf8` 实际是 `utf8mb3`，只支持 3 字节字符，**存不了 emoji**。用户昵称里带 emoji 是极常见的需求，用 `utf8` 会直接报错。
- **`utf8mb4_0900_ai_ci`**：MySQL 8 的默认排序规则，`ai` = accent insensitive（é 等同 e），`ci` = case insensitive（大小写不敏感）。

大小写不敏感有个直接后果：**`Demo` 和 `demo` 在唯一索引上会冲突**。这既是特性（防止大小写变体注册）也带来约束（`LoginAttemptGuard` 的 key 必须统一小写，见 07 篇）。

### 唯一索引：为什么邮箱允许 NULL

`UNIQUE KEY uk_user_email (email)` 加上 `DEFAULT NULL`：

- MySQL 的规则是 **NULL 不参与唯一性比较**，所以可以有任意多个 `email IS NULL` 的行；
- 但一旦填了值，就必须全局唯一。

这正是"邮箱可选"场景需要的语义。如果写成 `NOT NULL DEFAULT ''`，那第二个不填邮箱的用户就会因为 `'' = ''` 冲突而注册失败。

## 逻辑删除与唯一索引的冲突（重点）

这是 MyBatis-Plus + 逻辑删除组合下最经典的问题。

**场景**：用户 `demo` 注销（`deleted = 1`），半年后想用同一个用户名重新注册。

**会发生什么**：

```sql
-- 插入新记录 username = 'demo', deleted = 0
INSERT INTO t_user (username, deleted) VALUES ('demo', 0);
-- ERROR 1062: Duplicate entry 'demo' for key 'uk_user_username'
```

因为唯一索引只看 `username` 一列，不管 `deleted`。

**四种解决方案**：

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 唯一索引带上 deleted | `UNIQUE (username, deleted)` | 改动最小 | 只能删一次，删第二次还是冲突 |
| 删除时改名 | `username = 'demo#deleted#123456'` | 能无限次复用 | 数据被污染，用户名不可读 |
| 换成删除时间戳 | `deleted_at DATETIME NULL` + `UNIQUE (username, deleted_at)` | 时间戳天然唯一，能无限删 | 索引多一列，查询要判 `IS NULL` |
| 不允许复用用户名 | 注销即永久占用 | 实现最简单 | 产品上不友好 |

**本项目的选择：暂不处理，明确记录**。阶段 1 没有注销功能，而且真实产品里"注销后用户名是否可复用"往往是产品决策（很多平台选择保留 30 天再释放）。

**为什么不选方案一**：`UNIQUE (username, deleted)` 在"删除两次"时依然冲突——第一次删除记录 `deleted=1`，第二次删除另一条也是 `deleted=1`，两行 `('demo', 1)` 冲突。这个方案只解决了"删一次"的情况，误以为解决了问题。

## `CREATE TABLE IF NOT EXISTS` 与 `spring.sql.init`

```yaml
spring:
  sql:
    init:
      mode: always
      encoding: UTF-8
      schema-locations: classpath:db/schema.sql
```

### 为什么用 `spring.sql.init` 而不是 Flyway

| | `spring.sql.init` | Flyway |
| --- | --- | --- |
| 能力 | 启动时执行 SQL 脚本 | 版本化迁移，记录已执行版本 |
| 幂等 | 靠 `IF NOT EXISTS` 手写保证 | 内置，按版本号跳过 |
| 改表 | 做不到（老表加列需要手写 `ALTER`） | 天然支持（每个版本一个脚本） |
| 适用 | 学习项目、单表初始化 | 生产环境、多人协作 |

**为什么现在不用 Flyway**：阶段 1 只有一张表，引入 Flyway 会让"建表"这件事多一层概念（`V1__init.sql` 命名规范、`flyway_schema_history` 表、校验和机制）。等阶段 8 部署时再引入，那时正好有"线上不能随便改表"的真实场景来支撑这个决策。

### `mode: always` 的含义

- `embedded`（默认）：只在 H2/HSQLDB 这类内嵌库执行；
- `always`：任何数据库都执行；
- `never`：不执行。

因为用的是 MySQL（非内嵌），必须显式设 `always`，否则脚本压根不会执行——**这个默认值让很多人以为"配了 schema-locations 就会执行"，其实没有**。

### `encoding: UTF-8` 不能省

`schema.sql` 里的注释和 `COMMENT` 都是中文。默认编码依赖 JVM 的 `file.encoding`，Windows 上可能是 GBK，导致建表注释乱码甚至语法错误。

### 生产环境不应该开 `mode: always`

应用启动去改表结构是危险操作：
- 多实例同时启动会并发执行 DDL；
- DDL 没有回滚（MySQL 的 DDL 是隐式提交的）；
- 出问题无法追溯"谁在什么时候改了表"。

所以这个配置只放在 `application-dev.yml` 里。

## 索引检查

当前只有两个唯一索引（`uk_user_username`、`uk_user_email`）和主键。

**够不够用**：登记的查询只有 `WHERE username = ? OR email = ?`。这条 SQL 在 MySQL 里**可能走索引合并（index merge）**，但更常见的是全表扫描——因为 `OR` 涉及两个不同索引，优化器会评估成本。

数据量小的时候（几千条）无所谓。数据量大时的优化方向：
1. 拆成两条查询（先按 username 查，查不到再按 email 查），各自走索引；
2. 或者用 `UNION ALL` 改写。

阶段 1 选简单的 `OR` + `LIMIT 1`，在文档里记下这个优化点。**面试时能主动说出"我这里用了 OR，量大时应该拆成两次查询"比假装没这回事更好。**

## 面试考察点

**基础**

- `utf8` 和 `utf8mb4` 的区别？—— 前者最多 3 字节，存不了 emoji 和部分生僻字。
- `DATETIME` 和 `TIMESTAMP` 的区别？—— 时区处理、范围、存储大小。
- `VARCHAR(32)` 里的 32 是字符还是字节？—— 字符（MySQL 4.0 之后）。
- 唯一索引允许多个 NULL 吗？—— 允许，NULL 不参与唯一性比较。

**进阶**

- 逻辑删除怎么和唯一索引共存？—— 见上面四种方案。
- 为什么主键不建议用 UUID？—— 随机性导致 B+ 树页分裂、索引体积大；雪花 ID 趋势递增，插入更友好。
- `ON UPDATE CURRENT_TIMESTAMP` 在什么情况下不生效？—— 如果 update 语句里显式给该列赋了值（比如赋成原值），MySQL 不会自动更新。
- 为什么 `VARCHAR(100)` 存 60 字符的 BCrypt 密文不用 `CHAR(60)`？—— 定长在算法升级（如加 `{bcrypt}` 前缀）时会截断。

**陷阱**

- "用 `INT` 存手机号"—— 手机号有前导 0 的可能、长度可能超过 10 位，且不会参与运算，必须用字符串。
- "所有字符串都建 `VARCHAR(255)`"—— 索引长度限制（InnoDB 单列索引最大 3072 字节，`utf8mb4` 下约 768 字符）和内存占用都要考虑。
- "用 `TIMESTAMP` 存创建时间"—— 2038 年溢出。

## 常见坑

1. `spring.sql.init.mode` 不设 `always`，脚本不执行，然后报"表不存在"。
2. `schema.sql` 编码不是 UTF-8（Windows 下用记事本保存可能变成 GBK），中文注释导致 SQL 语法错误。
3. `CREATE TABLE IF NOT EXISTS` 不会更新已存在表的结构——改了 DDL 后重启应用，**老表不会变**，必须手动 `DROP` 或写 `ALTER`。
4. 建表时 `DEFAULT CHARSET` 只影响新表，已有表要单独 `ALTER TABLE ... CONVERT TO CHARACTER SET utf8mb4`。
