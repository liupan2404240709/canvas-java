# 07 · 登录失败锁定

## 一句话定位

`LoginAttemptGuard` 用 Redis 计数器实现"同一账号连续失败 5 次锁 15 分钟"，防的是**密码爆破**；配合 05 篇的等时校验，防的是**账号枚举**。两者是不同的攻击面。

## 完整代码

```java
@Component
public class LoginAttemptGuard {

    private static final String PREFIX = "auth:login:fail:";

    private final StringRedisTemplate redis;
    private final LoginProtectionProperties properties;

    public long lockedSeconds(String account) {
        String value = redis.opsForValue().get(key(account));
        if (value == null) {
            return 0L;
        }
        int failures = Integer.parseInt(value);
        if (failures < properties.getMaxAttempts()) {
            return 0L;
        }
        Long ttl = redis.getExpire(key(account));
        return ttl == null || ttl < 0 ? 0L : ttl;
    }

    public int recordFailure(String account) {
        String key = key(account);
        Long failures = redis.opsForValue().increment(key);
        if (failures != null && failures == 1L) {
            redis.expire(key, properties.getLockDuration());
        }
        int used = failures == null ? 1 : failures.intValue();
        return Math.max(0, properties.getMaxAttempts() - used);
    }

    public void clear(String account) {
        redis.delete(key(account));
    }

    private String key(String account) {
        return PREFIX + account.toLowerCase();
    }
}
```

## 逐段拆解

### ① 稀疏的"计数器 + 过期时间"模型

这里没有用"锁定时间戳"这种字段，而是让 **Redis key 的 TTL 同时承担两个职责**：

```
auth:login:fail:demo  =  "3"     TTL 还有 9 分钟
```

- value 是失败次数；
- TTL 是**计数窗口**，也是**锁定时长**。

好处：不需要额外的"解锁时间"存储，TTL 一到，计数自动归零，用户不需要任何人工干预。

**代价**：锁定到期时间和"最后一次失败时间 + 15 分钟"绑在一起（因为只在第一次失败时设置 TTL）。这意味着如果用户在 14 分钟内连续输错 5 次，那么剩下 1 分钟就解锁——比"从锁定时刻起 15 分钟"更宽松。这是因为 `expire` 只在 `failures == 1` 时设一次。

**为什么只在第一次设 TTL**：如果每次失败都 `expire`，那窗口会不断往后推——攻击者每 14 分钟试一次，这个 key 永远不会过期，被锁的用户永远解不开。这是个很容易写错的点。

### ② `failures == 1L` 判断的陷阱

```java
Long failures = redis.opsForValue().increment(key);
if (failures != null && failures == 1L) { ... }
```

`failures` 是 `Long` 包装类型，`failures == 1L` 会自动拆箱比较，**看起来没问题，但必须判 null**。如果 Redis 连接异常返回 null，`failures == 1L` 会抛 NPE。

代码里 `failures != null && failures == 1L` 的顺序不能反（短路求值）。

### ③ `lockedSeconds` 里为什么要再查一次 values

```java
String value = redis.opsForValue().get(key(account));
int failures = Integer.parseInt(value);
if (failures < maxAttempts) return 0;
```

不能只靠 `hasKey`：key 存在不代表已锁定（输了 1 次也存在）。所以要先把计数读出来比对。

**优化空间**：这样是两次网络往返（`get` + `getExpire`）。可以用 Lua 脚本一次拿到计数和 TTL，或者干脆用 Redis 的 `TTL` 配合 `GET` 的 pipeline。当前量级（登录接口）完全没必要优化，写清楚更重要。

### ④ `getExpire` 返回值可能有三种

| 返回值 | 含义 |
| --- | --- |
| `> 0` | 剩余秒数 |
| `-1` | key 存在但没有过期时间（**异常状态**，说明有人写 key 时忘了设 TTL） |
| `-2` | key 不存在 |

代码里 `ttl == null || ttl < 0 ? 0L : ttl` 把 `-1` 和 `-2` 都当成"未锁定"。对 `-1` 这种情况其实是个隐患：如果真的出现无 TTL 的 key，用户会**永久锁死**。所以这里选择"放行"而不是"锁死"——宁可放过一次爆破，也不能让用户永久登不上。

### ⑤ 为什么 key 要 `toLowerCase()`

```java
return PREFIX + account.toLowerCase();
```

如果数据库的用户名字段用的是 `utf8mb4_0900_ai_ci`（大小写不敏感排序规则），那么 `Demo` 和 `demo` 会命中**同一个用户**。如果 key 区分大小写，攻击者就可以用 `Demo`、`DEMO`、`dEmo` 各试 5 次——相当于把 5 次限制放宽到 5×N 次。

统一小写后，无论怎么变换大小写，计数都落在同一个 key 上。

**注意这是跟数据库排序规则强耦合的**：如果以后把用户名的 collation 改成 `_bin`（区分大小写），那这里就不能小写了。这个细节值得在代码注释里写清楚。

### ⑥ 计数为什么不能只放内存

用 `ConcurrentHashMap` 也能实现，但：

1. **重启即清零**：攻击者只要能触发应用重启（或者赶上发版），失败计数就白费了；
2. **多实例不共享**：3 个实例负载均衡，每个实例各算 5 次，实际允许 15 次。

Redis 天然解决这两个问题。这也是"为什么这个项目必须用 Redis"的一个真实理由（而不是为了用而用）。

### ⑦ 锁定的维度选择

当前是**按账号**锁。其他维度对比：

| 维度 | 优点 | 缺点 |
| --- | --- | --- |
| 账号（当前） | 精准，不影响他人 | 可被用来恶意锁定他人账号（DoS） |
| IP | 能挡住"同一来源撞库多账号" | NAT 后的公司/校园网会集体被锁 |
| 账号 + IP | 兼顾 | 攻击者换 IP 就绕过；实现复杂度翻倍 |
| 账号 + 全局 IP 计数 | 生产常见做法 | 需要两套计数器和不同的阈值策略 |

阶段 1 选最简单的账号维度，并在文档里明确它的 DoS 风险——**知道取舍比假装没有取舍更专业**。

### ⑧ 成功登录后必须 `clear`

```java
loginAttemptGuard.clear(account);
```

不清的话，用户上午输了 4 次、密码改对了登进去，下午再输错 1 次就被锁——体验极差且难以理解。

## 设计决策对比

| 决策 | 选的 | 替代 | 代价 |
| --- | --- | --- | --- |
| 存储 | Redis | 内存 Map | 换来重启不丢、多实例共享 |
| 窗口模型 | 固定窗口（首次失败起算） | 滑动窗口 / 令牌桶 | 固定窗口简单，代价是边界处可能有 2 倍突发 |
| 阈值来源 | 配置类 | 硬编码常量 | 可调，代价是多一个配置项 |
| 参数 | 5 次 / 15 分钟 | 10 次 / 30 分钟 | 5 次偏严格，真实产品常见 5~10 次 |

## 面试考察点

**基础**

- 为什么登录接口要做失败次数限制？—— 防密码爆破。
- 计数放内存有什么问题？—— 重启丢失、多实例不共享。
- 锁定到期怎么解锁？—— 靠 Redis TTL 自动过期。

**进阶**

- 固定窗口和滑动窗口的区别？固定窗口的边界问题是什么？—— 边界处（窗口末尾 + 下个窗口开头）可能出现 2 倍于阈值的请求。
- 为什么只在第一次失败时设 TTL？—— 每次都续期会导致窗口无限后移，被锁用户永远解不开。
- 锁账号会不会被用来 DoS？怎么缓解？—— 会。缓解手段：按账号+IP 组合计数、增加验证码、锁定期间仍允许通过邮箱重置密码解锁。
- 和网关层限流的区别？—— 网关限流按接口/来源 QPS；这里是按业务账号的失败次数，解决的是不同问题。

**陷阱**

- "只在失败时 +1，成功后清空"—— 对，但别忘了"用户不存在"也要计数，否则能通过计数差异枚举账号。
- "用 `expire` 每次都刷新"—— 会导致永不过期。
- "锁定后直接返回 403"—— 429 更准确（Too Many Requests），前端也能区分"重试"和"没权限"。

## 常见坑

1. `Integer.parseInt` 遇到脏数据（比如人工改成 `"abc"`）会抛 `NumberFormatException`，应该 catch 后当 0 处理。当前实现没做，属于可接受的风险（这个 key 只有代码会写）。
2. Redis 不可用时，`increment` 抛异常 → 登录接口 500。要不要降级成"放开"？安全优先的话应该**失败关闭**（宁可登不上，也不能让攻击者绕过限制）；用户体验优先则反之。当前未做降级，Redis 挂了整个登录就不可用——这在架构上是可接受的，因为 Redis 已经是认证链路的强依赖。
3. 阈值改了之后，**已在 Redis 里的旧计数不会变**，需要等 TTL 过期或用 SCAN 清理。
