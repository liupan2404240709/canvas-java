# 12 · 越权防护与资料接口

## 一句话定位

`UserController` 演示了一个原则：**凡是"我的资源"的接口，URL 里都不该出现 id**。用户 id 只能从 token 里取，这样才能从结构上杜绝越权。

## 完整代码

```java
@RestController
@RequestMapping(ApiPath.USERS)
public class UserController {

    @GetMapping("/me")
    public Result<UserVO> me() {
        return Result.ok(userService.me(SecurityUtils.currentUserId()));
    }

    @PutMapping("/me")
    public Result<UserVO> updateProfile(@Valid @RequestBody UpdateProfileRequest request) {
        return Result.ok(userService.updateProfile(SecurityUtils.currentUserId(), request));
    }
}
```

```java
@Override
public UserVO updateProfile(Long userId, UpdateProfileRequest request) {
    requireUser(userId);

    LambdaUpdateWrapper<User> wrapper = new LambdaUpdateWrapper<User>().eq(User::getId, userId);
    boolean changed = false;
    if (request.nickname() != null) {
        wrapper.set(User::getNickname, request.nickname().trim());
        changed = true;
    }
    if (request.avatarUrl() != null) {
        wrapper.set(User::getAvatarUrl, StringUtils.hasText(request.avatarUrl()) ? request.avatarUrl().trim() : null);
        changed = true;
    }
    if (!changed) {
        return me(userId);
    }
    userMapper.update(null, wrapper);
    return me(userId);
}
```

## 逐段拆解

### ① 为什么 URL 里不写 `PUT /users/{id}`

两种写法的对比：

```java
// 危险写法
@PutMapping("/{id}")
public Result<UserVO> update(@PathVariable Long id, @RequestBody UpdateProfileRequest req) {
    return Result.ok(userService.updateProfile(id, req));   // 忘了校验 → 越权
}
```

| | `/users/{id}` | `/users/me` |
| --- | --- | --- |
| 越权风险 | 每个接口都要写一次"id 是不是当前用户" | **结构上不可能越权** |
| 漏写一次的后果 | 任何人可以改任何人的资料 | 不存在 |
| 前端调用 | 要传 id | 不传 |
| 管理员改别人资料 | 同一个接口能做 | 需要单独的 `/admin/users/{id}` |

安全设计的原则是**用结构消除可能性**，而不是靠开发者的自觉。写 `/me` 之后，越权从"需要检查"变成"无法表达"。

### ② `SecurityUtils.currentUserId()` 中间接了一层

```java
public static Long currentUserId() {
    return currentUser().id();
}
```

不在 Controller 里写：

```java
LoginUser user = (LoginUser) SecurityContextHolder.getContext()
        .getAuthentication().getPrincipal();     // 每个 Controller 重复一遍
```

集中到 `SecurityUtils` 的好处：
- 强制判空（未认证时抛 401，而不是 NPE 500）；
- 以后换认证方式（比如网关透传用户 id 到 Header）只改一处。

### ③ `requireUser` 为什么抛 `TOKEN_REVOKED`

```java
private User requireUser(Long userId) {
    User user = userMapper.selectById(userId);
    if (user == null) {
        throw new BizException(ResultCode.TOKEN_REVOKED);
    }
    return user;
}
```

场景：token 还没过期（最多 30 分钟），但用户已经被删了。

这时候返回 404（"用户不存在"）语义上是错的——对前端来说，这不是"某个资源找不到"，而是"你的登录态已经失效了"。返回 `40114` 前端会走登出流程，体验正确。

### ④ `LambdaUpdateWrapper` 只更新传了的字段

```java
boolean changed = false;
if (request.nickname() != null) { wrapper.set(...); changed = true; }
if (request.avatarUrl() != null) { wrapper.set(...); changed = true; }
if (!changed) return me(userId);
```

这解决了"部分更新"（PATCH 语义）的核心问题：

| 方案 | 问题 |
| --- | --- |
| `updateById(entity)` | 把所有非 null 字段都更新一遍，null 字段跳过 → **无法把字段清空** |
| `UpdateWrapper` + 逐个判断 | 只更新明确传了的字段，null 表示"不改" |
| PATCH + `Optional<String>` | 语义最准确，但 record + Jackson 处理 `Optional` 很别扭 |

配合 DTO 里的 `@Pattern(regexp = "^$|...")`：空串合法，所以 **`""` 表示清空，`null` 表示不改**。这是两种不同语义，代码里通过 `StringUtils.hasText` 区分：

```java
wrapper.set(User::getAvatarUrl, StringUtils.hasText(request.avatarUrl()) ? request.avatarUrl().trim() : null);
```

### ⑤ `if (!changed) return me(userId)` 的意义

两个字段都没传时，不去执行一条什么都没更新的 SQL。省一次数据库往返，也避免 `UPDATE ... SET` 空语句（MyBatis-Plus 会生成 `UPDATE t_user WHERE id = ?` 这种没有 SET 的非法 SQL 而报错）。

### ⑥ 为什么 `updateProfile` 不用 `@Transactional`

只有一个写操作（`userMapper.update`），后面再 `me(userId)` 读一次数据库。读取不需要和写入在同一事务里——即使读到的是别人刚改的值，也不影响正确性（这是"读自己的数据"的常见容忍）。

阶段 2 保存画布时会涉及"删旧节点 + 插新节点 + 更新项目版本"，那种场景必须加事务。

### ⑦ 更新后重新查库返回，而不是改内存对象

```java
userMapper.update(null, wrapper);
return me(userId);
```

如果自己 `user.setNickname(...)` 然后 `UserVO.from(user)`，返回的是内存里的值——但数据库里的 `updated_at` 已经变了，返回的却是旧值。重新查库保证**返回值和数据库一致**，代价是一次多余的查询（可接受）。

## 越权防护的三层结构

| 层次 | 手段 | 本项目 |
| --- | --- | --- |
| 传输层 | HTTPS，防中间人 | 阶段 8（Nginx） |
| 认证层 | 校验 token，确认"你是谁" | 阶段 1（JwtAuthenticationFilter） |
| 授权层 | 确认"你能不能做这件事" | `/me` 结构消除 + 阶段 2 的归属校验 |

**"认证"不等于"授权"**：token 有效只能证明"你是张三"，不能证明"张三有权删李四的画布"。阶段 2 的画布接口会出现 `DELETE /canvases/{id}` 这种必须传 id 的路径，那时就必须在 Service 里校验 `canvas.userId == currentUserId`——校验失败要返回 **404 而不是 403**，避免泄露"这个 id 确实存在"。

## 设计决策对比

| 决策 | 选的 | 替代 | 代价 |
| --- | --- | --- | --- |
| 资源定位 | `/me` | `/users/{id}` + 校验 | 管理员场景需要额外接口 |
| 更新语义 | 只改非 null 字段 | 全量覆盖（PUT 严格语义） | 前端要区分"不改"和"清空" |
| 用户不存在 | 40114 | 404 | 语义更准，但需要前端理解 |
| 返回值 | 重新查库 | 内存对象 | 多一次查询，保证一致性 |

## 面试考察点

**基础**

- 认证和授权的区别？
- 水平越权和垂直越权的区别？—— 水平：同级用户之间互相访问（改别人的数据）；垂直：低权限用户访问高权限功能（普通用户调管理接口）。
- 为什么 `PUT /users/{id}` 容易出越权？—— 需要每个接口手动校验归属，漏一个就是漏洞。

**进阶**

- 越权校验失败应该返回 403 还是 404？—— 查得到但无权限 → 403；查不到或不该让对方知道存在 → 404。对"别人的资源"，返回 404 更安全。
- 除了 URL，还有哪些地方会出现越权？—— 请求体里的 id（`{"userId": 2}`）、查询参数、Header。所以**永远不要相信客户端传来的身份标识**。
- 怎么在架构上减少越权？—— 资源路径用 `/me`、Service 层统一从 `SecurityContext` 取用户、用 MyBatis-Plus 的租户插件自动加 `user_id` 条件。
- 什么是"多租户插件"？—— MyBatis-Plus 的 `TenantLineInnerInterceptor`，自动给所有 SQL 加 `tenant_id = ?`，从机制上隔离数据。

**陷阱**

- "只在 Controller 层校验归属"—— Service 被其他入口（定时任务、MQ 消费者）复用时校验就丢了，应该在 Service 层做。
- "用前端传的 userId 作为身份"—— 最典型的水平越权漏洞。
- "把 `passwordHash` 放进 `UserVO` 但设成 null"—— 字段存在就有被序列化的风险，正确的做法是 VO 里根本没有这个字段。

## 常见坑

1. `SecurityUtils.currentUser()` 在异步线程里抛 401（ThreadLocal 不传递），阶段 6 处理。
2. `LambdaUpdateWrapper` 没带 `eq` 条件会被 `BlockAttackInnerInterceptor` 拦住抛异常——这是好事，说明防护生效了。
3. `update` 的第一个参数必须是 `null`（wrapper 模式），传实体对象会和 wrapper 的 set 冲突。
