# 09　搜索、标签过滤与稳定分页

> 代码位置：`PromptServiceImpl#list`、`resources/mapper/PromptMapper.xml#selectTagFacet`

## 1. 一次列表请求要满足的四个条件

前端传 `keyword`、`tag[]`、`category`、`page`，组合关系是：

```
(user_id = 我)                       ← 永远是第一个条件
AND (source_id IN 启用中的源)         ← 源筛选 + 停用隔离
AND (title LIKE %kw% OR prompt LIKE %kw% OR description LIKE %kw%)
AND (JSON_CONTAINS(tags_json, '"a"') OR JSON_CONTAINS(tags_json, '"b"'))
ORDER BY source_id, sort_index, id
LIMIT offset, size
```

每一段都有坑。

## 2. 关键字：`LIKE` 的三个问题

```java
wrapper.and(q -> q.like(Prompt::getTitle, kw)
        .or().like(Prompt::getPrompt, kw)
        .or().like(Prompt::getDescription, kw));
```

生成的 SQL：

```sql
AND (title LIKE '%kw%' OR prompt LIKE '%kw%' OR description LIKE '%kw%')
```

### 2.1 为什么必须用 `and(...)` 包起来

不用嵌套的话：

```sql
WHERE user_id = ? AND title LIKE ? OR prompt LIKE ? OR description LIKE ?   -- ❌
```

`AND` 的优先级高于 `OR`，实际语义变成 `(user_id = ? AND title LIKE ?) OR ...`——**只要 prompt 里匹配，就会返回别人的数据**。这是一个真实的越权 bug，而且测试时如果只有一个用户，根本发现不了。

MyBatis-Plus 的 `.and(Consumer)` 会生成带括号的子条件，是正确写法。

### 2.2 `%kw%` 用不上索引

左侧通配符导致 B+ 树无法定位起点，只能扫"该用户该源范围内"的所有行。

当前规模（单用户几千条）可接受。如果数据量上来：

| 方案 | 适用 |
| --- | --- |
| MySQL 全文索引（`FULLTEXT` + `MATCH ... AGAINST`） | 需要中文分词（ngram parser） |
| Elasticsearch | 数据量大、需要相关度排序、高亮 |
| 单独维护"搜索字段"列 + 前缀索引 | 只支持前缀匹配 |

**现在不做**，理由：`LIKE` 在几千行上的耗时是毫秒级，引入 ES 等于给学习项目加一个必须运维的组件。写进 `docs/database.md` 的"改进方向"。

### 2.3 `%` 和 `_` 没有转义

用户输入 `100%` 会变成"匹配任意字符"，属于"结果不符合预期"而不是安全问题（参数是预编译的，注入不了）。

要修就是转义 + `ESCAPE`：

```java
String escaped = kw.replace("\\", "\\\\").replace("%", "\\%").replace("_", "\\_");
```

当前没做——理由：用户搜 `%` 的概率极低，而转义会让 SQL 变复杂。**这是一个明确的取舍，不是遗漏**。

## 3. 标签：JSON 数组 + 或语义

```java
List<String> effectiveTags = tags.stream().filter(StringUtils::hasText).map(String::trim).distinct().toList();
if (!effectiveTags.isEmpty()) {
    wrapper.and(q -> {
        for (int i = 0; i < effectiveTags.size(); i++) {
            if (i > 0) q.or();
            q.apply("JSON_CONTAINS(tags_json, JSON_QUOTE({0}))", effectiveTags.get(i));
        }
    });
}
```

生成：

```sql
AND (JSON_CONTAINS(tags_json, JSON_QUOTE(?)) OR JSON_CONTAINS(tags_json, JSON_QUOTE(?)))
```

### 3.1 为什么是"或"

前端：

```ts
if (options.tags.length && !options.tags.some(tag => item.tags.includes(tag))) return false;
```

`some` = 命中任意一个。如果后端做成"且"，用户勾第二个标签会得到空结果，看起来像 bug。

### 3.2 `JSON_QUOTE({0})` 是什么

`JSON_CONTAINS(target, candidate)` 的 candidate 必须是**合法 JSON 值**。标签 `人像` 直接传进去会被当成非法 JSON 表达式。

- `JSON_QUOTE('人像')` → `"人像"`（带引号的 JSON 字符串）
- 所以候选值是 `"人像"`，能正确匹配数组里的元素

### 3.3 为什么用 `{0}` 而不是字符串拼接

```java
.apply("JSON_CONTAINS(tags_json, JSON_QUOTE({0}))", tag)   // ✅
.apply("JSON_CONTAINS(tags_json, JSON_QUOTE('" + tag + "'))")  // ❌ 注入
```

MyBatis-Plus 的 `{0}` 会转成 JDBC 的 `?` 占位符，值走预编译。单引号拼接会让 `tag = "x') OR 1=1 --"` 变成注入点。

**任何用户输入进 SQL，都必须走占位符**，包括看起来"只是标签"的字段。

### 3.4 `JSON_CONTAINS` 与 NULL

`tags_json` 为 NULL 时，`JSON_CONTAINS(NULL, ...)` 返回 NULL（不是 false），在 `WHERE ... OR ...` 里等于"不成立"。

所以同步时要保证写入 `[]` 而不是 NULL（见 `PromptJson.write` 的注释）——否则"没有标签的提示词"在带标签筛选时会被排除（这是对的），但在 `NOT` 组合条件下行为会反直觉。

## 4. 分栏：`category` 是源名

```java
List<PromptSource> sources = promptSourceService.enabled(userId);   // 只取启用中的
List<String> categories = sources.stream().map(PromptSource::getName).toList();

List<PromptSource> scoped = sources;
if (isActiveCategory(category)) {
    scoped = sources.stream().filter(s -> category.equals(s.getName())).toList();
}
if (scoped.isEmpty()) {
    return new PromptListVO(List.of(), List.of(), categories, 0, safePage, safeSize);
}
```

三个细节：

1. **只看启用中的源**：停用的源数据还在，但不参与查询、不出现在分栏里。这是"停用"和"删除"的区别。
2. **按名字匹配而不是 id**：前端的 `category` 就是源名（见 [design.md D24](../design.md)）。
3. **分栏不存在时返回空列表而不是 404**：这是一个"筛选条件"，筛不到东西是正常结果，不应该报错。

## 5. 稳定分页：三列排序

```java
wrapper.orderByAsc(Prompt::getSourceId)
        .orderByAsc(Prompt::getSortIndex)
        .orderByAsc(Prompt::getId);
```

### 5.1 为什么只按 `sort_index` 不够

不同源的下标都是 0、1、2…，混在一起是乱序：

```
source 1001: sort 0,1,2
source 1002: sort 0,1,2
只按 sort 排 → 1001-0, 1002-0, 1001-1, 1002-1 ...（交错）
```

加上 `source_id` 就先按源分组，和前端"每个源一个分栏"的观感一致。

### 5.2 为什么要加 `id`

MySQL **不保证**"排序值相同的行"返回顺序稳定。如果两条记录的 `(source_id, sort_index)` 都相同（理论上不该发生，但数据被手工改过就可能），翻页时同一行可能出现两次、另一行永远不出现。

`id` 唯一，加上它顺序就是确定的。**分页排序的最后一列必须能唯一确定一行**，这是通用规则。

### 5.3 为什么不是 `id DESC`

新入库的提示词排后面，符合"源内保持上游顺序"的目标。用 `id DESC` 会变成"最新的在最前"，同步一次顺序全变。

## 6. 分页参数压制

```java
long safePage = Math.max(1, page);
long safeSize = pageSize <= 0 ? DEFAULT_PAGE_SIZE : Math.min(pageSize, MAX_PAGE_SIZE);   // 100
```

- `page=0` / 负数 → 压成 1（否则 `offset = (0-1)*20 = -20`，SQL 报错）；
- `pageSize=1000` → 压成 100（防止一次拉全表）。

**为什么不返回 400**：分页参数越界属于"调用方粗心"，静默压制比报错更友好，而且前端通常会用返回值里的 `page/pageSize` 校正自己的状态。

## 7. 标签云：故意忽略标签筛选

```java
promptMapper.selectTagFacet(userId, sourceIds, keyword, limit)
```

参数里**没有 tag**。生成：

```sql
SELECT DISTINCT jt.tag
FROM t_prompt p
JOIN JSON_TABLE (p.tags_json, '$[*]' COLUMNS (tag VARCHAR(64) PATH '$')) jt
WHERE p.user_id = ? AND p.source_id IN (...)
  AND (title LIKE ... OR prompt LIKE ... OR description LIKE ...)
ORDER BY jt.tag
LIMIT 100
```

为什么忽略 tag：如果带上，用户勾了「人像」之后，左侧标签列表就只剩「人像」了——**没法继续多选**。

> 这个细节在阶段 3（素材库）也是同样的处理，front-end 的 `fetchPrompts` 会算两遍：
> `withoutTagFilter` 用来出标签云，`filtered` 用来出列表。

所以 `total` 和 `tags` 来自**不同的筛选条件**，这不是 bug。

## 面试考察点

**Q1：`WHERE a AND b OR c` 有什么问题？**
`AND` 优先级高于 `OR`，等价于 `(a AND b) OR c`。多条件搜索必须显式加括号，否则会漏掉第一个条件（在带 `user_id` 的场景里就是越权）。

**Q2：`LIKE '%kw%'` 为什么用不上索引？怎么优化？**
左侧通配符无法确定 B+ 树的扫描起点，只能全扫。优化：全文索引（需中文分词）、ES、或改成前缀匹配 `kw%`（能走索引但语义变窄）。

**Q3：`JSON_CONTAINS` 的第二个参数为什么要 `JSON_QUOTE`？**
候选值必须是合法 JSON。`JSON_QUOTE('人像')` 得到 `"人像"`，才能与数组元素比较。直接传原文会被当成非法 JSON。

**Q4：分页为什么要三列排序？**
`source_id` 分组、`sort_index` 保序、`id` 兜底唯一。MySQL 对"排序值相同的行"顺序不确定，最后不加唯一列会导致翻页重复/遗漏。

**Q5：为什么标签云不应用已选标签？**
否则勾一个标签后其他标签消失，无法多选。所以响应里的 `total`（应用了标签）和 `tags`（未应用标签）来自不同筛选条件。

**Q6：`page=0` 应该报错还是纠正？**
纠正。这是"调用方粗心"而非"恶意输入"，静默压制 + 在响应里回传实际生效的 `page/pageSize`，前端可以据此校正。参数格式错误（比如 `page=abc`）才应该 400。
