# 04　幂等同步：内容摘要与条件请求

> 代码位置：`service/impl/PromptServiceImpl#syncOne`

## 1. 问题：每 30 分钟重写一遍几千行，值不值

提示词源默认 30 分钟同步一次。如果每次都"删光 + 重插"：

| 代价 | 具体表现 |
| --- | --- |
| 主键全变 | `AUTO_INCREMENT` 意义上的 id 暴涨；若有外部引用会全断 |
| `created_at` 被重置 | 丢失"首次入库时间" |
| 分页锚点漂移 | 用户正在翻第 3 页，同步完内容跳了 |
| 事务体积大 | 几千行 DELETE + INSERT 的 undo/redo，长事务容易撞锁等待 |
| 无谓 IO | 内容根本没变，却写了一遍磁盘 |

而上游的特性是：**内容变化很慢**（人工维护的仓库，一周更新几次）。

所以核心思路是：**先判断"变没变"，没变就什么都不写。**

## 2. 两道闸门

```
                    ┌─────────────────────────┐
   fetch(url,        │  304 Not Modified ?     │──是──▶ 只更新 last_fetched_at / last_success_at
   etag, lastMod) ──▶│                         │
                    └───────────┬─────────────┘
                                │ 否（200）
                                ▼
                    ┌─────────────────────────┐
                    │ sha256(body) == 库里的? │──是──▶ 只更新校验值和时间戳
                    └───────────┬─────────────┘
                                │ 否
                                ▼
                       解析 → upsert → 差量删除 → 更新摘要
```

### 闸门 1：HTTP 条件请求

```java
PromptFetcher.FetchResult fetched = promptFetcher.fetch(
        source.getUrl(),
        force ? null : source.getEtag(),
        force ? null : source.getLastModified());
```

`PromptFetcher` 把它们放进请求头：

```java
if (StringUtils.hasText(etag)) headers.set(HttpHeaders.IF_NONE_MATCH, etag);
if (StringUtils.hasText(lastModified)) headers.set(HttpHeaders.IF_MODIFIED_SINCE, lastModified);
```

命中时上游返回 **304，且没有响应体**——连 JSON 都不用下载。这是最省的一层。

前提是上游支持。GitHub raw 支持（返回 `ETag`），很多自己搭的静态 JSON 服务不支持（永远 200）。

### 闸门 2：内容摘要

```java
String contentHash = sha256(fetched.body());
if (!force && contentHash.equals(source.getContentSha256())) {
    markSuccess(source.getId(), previousCount, contentHash, fetched.etag(), fetched.lastModified(), now);
    return success(source, previousCount, now, true);
}
```

算的是**响应体的 SHA-256**，存进 `t_prompt_source.content_sha256`（`CHAR(64)`）。

为什么不用"条数变化"判断：条数一样不代表内容一样（改了一条、删了一条）。

为什么不用 `body.length()`：长度很容易碰撞（改一个字长度不变）。

为什么 SHA-256 而不是 MD5：MD5 已经能人为构造碰撞。这里不是安全场景，但用 SHA-256 没有额外成本（`MessageDigest` 都是 JDK 自带），没必要用一个"有已知弱点"的算法。

### 为什么两道都需要

| 场景 | 闸门 1 | 闸门 2 |
| --- | --- | --- |
| 上游支持 ETag，内容没变 | ✅ 命中（省下载） | 用不到 |
| 上游不支持 ETag | ❌ 永远 200 | ✅ 命中（省写库） |
| 上游换了 ETag 但内容没变 | ❌ | ✅ 命中 |
| 内容真变了 | ❌ | ❌ |

一个是"省网络"，一个是"省磁盘"，互补。

## 3. `force` 开关

```java
promptFetcher.fetch(url, force ? null : etag, force ? null : lastModified);
...
if (!force && contentHash.equals(source.getContentSha256())) { ... }
```

`force=true` 时两道闸门都被绕过：不带条件请求头、不比对摘要。

为什么需要：用户点"同步"的意图可能是"我不信你，重跑一遍"（比如怀疑数据被手工改过）。如果被"内容没变"挡住，用户会觉得功能坏了。

代价：`force` 会真的重写一遍（触发 upsert + 差量删除）。所以默认 `false`，控制台的"同步全部"按钮用的是 `force=true`（一次性的手动操作，能接受）。

## 4. 状态更新的三个分支

`t_prompt_source` 上有三个时间字段，语义必须分清，否则前端会显示错误信息：

| 字段 | 什么时候写 | 用途 |
| --- | --- | --- |
| `last_fetched_at` | **每次尝试**（成功或失败） | 定时任务的"到期判断"依据 |
| `last_success_at` | 只有成功 | 前端显示"上次同步于 X" |
| `last_error` | 失败时写原因，成功时**清空** | 前端显示失败原因 |

对应三个方法：

```java
markSuccess(sourceId, count, hash, etag, lastModified, now);   // 成功（含 skipped）
markFailure(source, now, error);                                // 失败：不动 last_success_at
```

### 一个必须显式处理的坑

```java
.set(PromptSource::getLastError, null)
```

MyBatis-Plus 的 `updateById(entity)` 和 `update(entity, wrapper)` **默认忽略 null 字段**（这是它"安全更新"的设计：不会因为实体没填某个字段就把它清空）。

放在这里就变成一个 bug：同步成功后 `last_error` 不会被清空，前端永远显示"上次失败：Connection timed out"，哪怕后来成功了 10 次。

解决：用 `LambdaUpdateWrapper` 显式 `.set(col, null)`。这也是阶段 2 里 `updatedAt` 要用 `setFieldValByName` 强制覆盖的同一类问题——**"默认忽略 null"这条规则，在"要清空字段"时就是反的**。

## 5. 失败分支也要落库

```java
} catch (PromptSyncException e) {
    return fail(source, now, e.getMessage());
}
```

`fail` 里：

```java
markFailure(source, now, message);   // 只更新 last_fetched_at + last_error
return new PromptRefreshResultVO(..., count = 旧值, lastSuccessAt = 旧值, success = false, ...);
```

关键点：
- **不覆盖 `prompt_count`**（前端显示"上次成功同步了 500 条"，不是"0 条"）；
- **不动 `content_sha256`**（下次成功的判断基准还在）；
- **不删任何提示词**（失败 ≠ 源清空）。

这三条合起来保证"一次失败不会让用户的数据看起来消失"。

## 6. 为什么摘要算的是原始 body，不是"归一化后的 JSON"

`sha256(fetched.body())` 而不是 `sha256(objectMapper.writeValueAsString(parsed))`。

原因：
- 原始 body 的哈希更"便宜"（不用先解析 5000 条）；
- 上游哪怕只改了字段顺序/空白，也会被识别为"变化"——这其实是**误判**（内容语义没变），但代价只是多写一次库；
- 反过来如果用归一化结果，解析逻辑一改（比如新增一个字段），所有源的摘要全部变化，会触发一次全量重写。

**选择"宁可多写一次，也不要因为代码改动而误判成没变"**。前者是可观测的多余写入，后者是隐蔽的数据不更新。

## 7. 端到端效果

e2e 里对应的两个断言：

```
第一次同步 → success=true,  skipped=false, count=8
第二次同步 → success=true,  skipped=true,  count=8     ← 没有写库
force=true → success=true,  skipped=false             ← 强制重写
```

日志里也能看到"定时同步完成: source=..., skipped=true"。

## 面试考察点

**Q1：为什么需要内容摘要，不是有 ETag 就够了吗？**
上游不一定支持条件请求（自建静态服务、对象存储的某些配置）。ETag 是"省下载"，摘要是"省写库"，两者防的是不同成本。

**Q2：摘要为什么用 SHA-256 而不是文件长度或修改时间？**
长度会碰撞（改一个字长度不变）；修改时间不可靠（上游可以复制文件不改时间，也可能每次部署都刷新时间但内容没变）。

**Q3：`skipped=true` 时还算"同步成功"吗？**
算。`success=true, skipped=true`。语义是"这次同步正常完成，但没有需要写入的变化"。前端据此提示"内容未变化"，而不是"失败"。

**Q4：如果两次请求同时通过了摘要检查，会怎样？**
两道闸门都不是原子的，理论上可能两个请求都认为"变了"并都去写。但写之前要过 Redis 锁（`prompt:refresh:{id}`），所以实际只会有一个执行。而且即使执行两次，`upsert + 差量删除` 是幂等的，结果一致——**判重不原子，但结果幂等**，这是设计时的兜底思路。

**Q5：同步失败后 `prompt_count` 为什么不清零？**
`prompt_count` 表示"上次成功同步的条数"。清零会让用户以为数据丢了（实际旧数据还在，只是这次没拉到）。三个字段各管一件事，不要用一个字段表达两种状态。
