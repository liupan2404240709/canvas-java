# 12　完整链路：从一次列表请求到定时同步

> 把前 11 篇串成一条时间线。读完这篇，应该能在脑子里"放电影"。

## 场景 1：用户第一次打开提示词页

```
GET /v1/prompts?keyword=&page=1&pageSize=20
  Authorization: Bearer <token>
```

```
JwtAuthenticationFilter        解析 token → 塞 LoginUser 到 SecurityContext
  ↓
PromptController.list()        SecurityUtils.currentUserId()  →  userId
  ↓
PromptServiceImpl.list()
  ├─ promptSourceService.enabled(userId)
  │    ├─ ensureBuiltIns(userId)        查已有 source_key → 缺的补上（7 个内置源）
  │    │    └─ 并发时撞 uk_prompt_source_user_key → 吞掉 DuplicateKeyException
  │    └─ SELECT ... WHERE user_id=? AND enabled=1 ORDER BY id
  ├─ categories = 源名列表                    → 前端左栏分栏
  ├─ sourceIds = [1001..1007]                → 查询范围
  ├─ scoped = 按 category 过滤（首屏是全部）
  ├─ wrapper:
  │    user_id = ? AND source_id IN (...)     ← 用 idx_prompt_user_source_order
  │    [keyword → (title LIKE OR prompt LIKE OR description LIKE)]
  │    [tag → (JSON_CONTAINS OR JSON_CONTAINS)]
  │    ORDER BY source_id, sort_index, id
  ├─ promptMapper.selectPage(...)            → Page（MP 自动多查一次 count）
  ├─ promptTagCache.getOrLoad(...)
  │    ├─ key = prompt:tags:{userId}:{ver}:{sourceIds}:{keyword}
  │    ├─ 命中 → 返回
  │    └─ 未命中 → JSON_TABLE 聚合 → 写缓存（空结果也写，防穿透）
  └─ toVO(prompt, source)                     → category / githubUrl 从这里补
```

**关键点**：`total` 来自"应用了全部筛选"的 count，`tags` 来自"忽略标签筛选"的聚合。两者不一致是**设计意图**（否则勾选一个标签后其他标签会消失）。

**首屏响应**：`items` 为空（还没同步），`categories` 有 7 个名字，`tags` 为空，`total=0`。前端显示"0 条"，左侧能看到 7 个分栏——这正是 `ensureBuiltIns` 的价值。

## 场景 2：用户新增一个源并同步

```
POST /v1/prompt-sources
{ "name": "本地样例库", "url": "http://127.0.0.1:8081/api/demo/prompts-sample.json" }
```

```
PromptSourceServiceImpl.create()
  ├─ requireHttpUrl(url)        PromptUrls.parseHttp → 协议/host 校验，非法 → 400/40040
  ├─ trimName(name)             ≤100，空 → 400
  ├─ requireNameAvailable()     同用户同名 → 409/40940
  ├─ sourceKey = "src_" + UUID 前 12 位
  └─ insert                      built_in=0, enabled=1, interval=30
```

```
POST /v1/prompt-sources/src_xxx/refresh
```

```
PromptServiceImpl.refresh()
  ├─ promptSourceService.getOwned(userId, "src_xxx")    越权/不存在 → 404/40440
  ├─ redisLock.tryLock("prompt:refresh:1008", 3min)     抢不到 → 429/42920
  │
  └─ syncOne(source, force=false)
       │
       ├─ promptFetcher.fetch(url, etag=null, lastMod=null)
       │    ├─ PromptUrls.parseHttp      → URI
       │    ├─ hostAllowed(uri, allowPrivate)  → 私网检查（dev 放开）
       │    ├─ RestClient GET（建连 5s / 读 20s / UA / Accept）
       │    └─ exchange:
       │         304 → notModified
       │         2xx → readLimited(8MB) → FetchResult(body, etag, lastModified)
       │         其它 → PromptSyncException("上游返回 HTTP 404")
       │
       ├─ sha256(body) 与 source.content_sha256 比较  → 相同则只更新时间戳，返回 skipped
       │
       ├─ promptJsonParser.parse(body, sourceKey, sourceUrl)
       │    ├─ 顶层非数组 → PromptSyncException("不是 JSON 数组")
       │    ├─ 每条：title/prompt 必填、id 缺失则补 {sourceKey}-0001、
       │    │        tags/referenceImageUrls 转数组、相对 URL 用 URI.resolve 补全、
       │    │        超长字段截断、时间四段降级解析
       │    └─ LinkedHashSet 按 key 去重，保留源内顺序
       │
       ├─ parsed.isEmpty() && builtIn == 1 → PromptSyncException("已保留本地数据")
       │
       └─ transaction {                      ← 事务只包这一步，网络请求在外面
            upsertPrompts(source, parsed)    → 每 200 行一条 INSERT ... AS new ON DUPLICATE KEY UPDATE
            deleteNotInKeys(sourceId, keys)  → 上游删掉的条目物理删除
            markSuccess(...)                 → count / sha256 / etag / 时间戳 / last_error=NULL
          }
          
          promptTagCache.invalidate(userId)  → INCR prompt:tags:ver:{userId}
          return PromptRefreshResultVO(success=true, skipped=false, count=8)
```

**注意锁的释放**：`finally { redisLock.unlock(key, token) }`，Lua 脚本比对 token 后删除。

## 场景 3：用户再点一次同步（内容没变）

```
promptFetcher.fetch(url, etag="W/\"abc\"", lastModified="Mon, 01 Jul 2025 ...")
  ├─ 请求头带 If-None-Match / If-Modified-Since
  ├─ 上游 → 304（无响应体）
  └─ FetchResult(notModified=true)
```

→ `markSuccess(count 不变, hash 不变, etag 更新, 时间戳更新)` → `skipped=true`。

如果上游不支持条件请求（永远 200）：

→ `sha256(body)` 与库里相同 → 同样只更新时间戳 → `skipped=true`。

**两条路径的出口一样，日志都能看出"没写库"**。这就是"第二次刷新走缓存"的验收点。

## 场景 4：定时任务

```
每 5 分钟：PromptRefreshScheduler.scanDueSources()
  ↓
PromptServiceImpl.refreshDue()
  ├─ PromptSourceMapper.selectDueSources(20)
  │    WHERE deleted=0 AND enabled=1 AND interval>0
  │      AND (last_fetched_at IS NULL OR last_fetched_at <= NOW() - INTERVAL interval MINUTE)
  │    ORDER BY last_fetched_at IS NOT NULL, last_fetched_at
  │    LIMIT 20
  │
  └─ foreach source:
       refreshQuietly(source, force=false)
         ├─ tryLock 失败 → 记一条 "该源正在同步中" 的结果，继续下一个
         ├─ syncOne(...)                    与手动同步完全同一条路径
         └─ catch RuntimeException → log.error，继续下一个
```

多实例部署时，两个实例都可能扫到同一批，但只有一个能拿到锁；另一个直接跳过且**不更新 `last_fetched_at`**，所以下一轮它仍然到期，但拿到锁的实例已经更新过了——不会重复劳动。

## 场景 5：用户停用源 / 删除源

**停用** `PATCH {"enabled": false}`：

```
UPDATE t_prompt_source SET enabled=0 WHERE id=? AND user_id=?
promptTagCache.invalidate(userId)
```

之后：`enabled()` 不再返回它 → `categories` 少了它 → `source_id IN (...)` 不含它 → 它的提示词查不到（但数据还在）。定时任务也不会再刷它（`enabled=1` 条件）。

**删除** `DELETE /v1/prompt-sources/src_xxx`：

```
transaction {
  DELETE FROM t_prompt WHERE source_id = ?     ← 物理删（提示词没有 deleted）
  UPDATE t_prompt_source SET deleted = 1        ← 逻辑删
}
promptTagCache.invalidate(userId)
```

## 如果现在要排查一个问题，按这个顺序看

1. **`GET /v1/prompt-sources`** → 源在不在？`count` 多少？`lastError` 写了什么？
2. **日志** → 搜 `source=` 看有没有 `定时同步完成/失败`，`logback` 里带 traceId。
3. **Redis** → `KEYS prompt:refresh:*` 看有没有卡住的锁（正常应该为空）；`GET prompt:tags:ver:{userId}` 看版本号有没有涨。
4. **数据库** → `SELECT COUNT(*), MAX(created_at) FROM t_prompt WHERE source_id=?` 看数据到底写进去没有。
5. **网络** → 从服务器上 `curl` 那个 URL（注意 UA），确认是"网络不通"还是"代码问题"。

这个顺序是"从外到内"：先看用户能看到的现象（源状态），再看日志/中间件/数据，最后才是网络。**排查要按成本从低到高**，而不是一上来就看代码。

## 面试考察点

**Q1：描述一次同步的完整流程。**
取源 → 抢锁 → 条件请求 → 摘要比对 → 解析归一化 → 事务内 upsert + 差量删 + 更新状态 → 缓存失效 → 释放锁。重点讲清"网络在事务外""内容没变就零写入"。

**Q2：如果同步到一半服务重启了会怎样？**
事务回滚，本地保持旧快照；`last_fetched_at` 没更新成功，下一轮扫描仍会重试。因为同步幂等，重试无害。

**Q3：为什么列表和标签云要分两次查询？**
列表需要分页（LIMIT），标签云需要"忽略标签筛选的全量聚合"。一个 SQL 同时做两件事会导致：要么标签云只能基于当前页（不完整），要么列表不能分页。

**Q4：`ensureBuiltIns` 放在 `list()` 里，会不会每次都写库？**
不会。先查 `source_key` 集合，只有缺失时才 insert。7 个都存在时就是一次 SELECT + 一次无写入。

**Q5：这套设计里，哪个环节最脆弱？**
外网可达性（内置源依赖 GitHub raw）和 SSRF 防护的完整性（DNS rebinding、重定向）。前者是环境问题、有 `lastError` 兜底；后者是安全边界，已记录在文档里并给了修复方向。
