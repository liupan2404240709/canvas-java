# 08　标签缓存与版本号失效

> 代码位置：`infra/prompt/PromptTagCache.java`、`PromptServiceImpl#list`

## 1. 为什么只缓存标签，不缓存列表

提示词页一次请求要做两件事：

```sql
-- ① 列表（有索引）
SELECT * FROM t_prompt
WHERE user_id = ? AND source_id IN (...) AND tags_json ...
ORDER BY source_id, sort_index, id
LIMIT 20;

-- ② 标签云（无索引，要炸 JSON）
SELECT DISTINCT jt.tag
FROM t_prompt p
JOIN JSON_TABLE (p.tags_json, '$[*]' COLUMNS (tag VARCHAR(64) PATH '$')) jt
WHERE p.user_id = ? AND p.source_id IN (...) AND (title LIKE ... )
ORDER BY jt.tag
LIMIT 100;
```

| | ① 列表 | ② 标签云 |
| --- | --- | --- |
| 是否走索引 | 是（`idx_prompt_user_source_order`） | 否（`JSON_TABLE` 必然全扫范围内的行） |
| 成本与什么相关 | 页大小（20） | 筛选后的总行数（可能几千） |
| 参数变化频率 | 用户每翻一页就变 | 同一批筛选下重复率极高 |
| 是否值得缓存 | 否（缓存命中率低、失效复杂） | **是** |

所以只缓存 ②。**缓存要看"谁的边际成本最高"，不是"谁被请求得最多"。**

## 2. key 的设计

```java
return CACHE_KEY + userId + ":" + version + ":" + sources + ":" + keyword;
// prompt:tags:12:3:[1001, 1002, 1003]:霓虹
```

四个组成部分对应查询的四个维度：

| 段 | 来源 | 不加会怎样 |
| --- | --- | --- |
| `userId` | 登录态 | 用户 A 看到 B 的标签 |
| `version` | `prompt:tags:ver:{userId}` | 同步后仍然命中旧缓存 |
| `sources` | 启用中的源 id 列表 | 停用某个源后，标签云还包含它的标签 |
| `keyword` | 搜索词 | 搜"霓虹"时看到全部标签（其实应该只看到相关的） |

### 为什么不做哈希

```java
// 没有这么做
String key = "prompt:tags:" + userId + ":" + sha256(keyword + sources);
```

理由：这里没有超长参数（关键词一般 < 20 字，源 id 列表 < 10 个），而**可读性带来的排查收益更大**：

```
> KEYS prompt:tags:12:*
1) "prompt:tags:12:3:[1001]:霓虹"
```

一眼能看出是用户 12、第 3 版缓存、只筛源 1001、关键词"霓虹"。哈希之后全是十六进制，排查时要反推。

（Redis key 是二进制安全的，中文、空格、冒号都能直接用。）

## 3. 版本号失效：为什么不是一个 `DEL`

同步成功后需要让该用户的所有标签缓存失效。

### 方案 A：pattern 删除

```java
Set<String> keys = redisTemplate.keys("prompt:tags:12:*");
redisTemplate.delete(keys);
```

问题：
- `KEYS` 是 **O(N) 且阻塞 Redis 单线程**，key 多了直接卡住整个实例（生产事故常见原因）；
- `SCAN` 虽然不阻塞，但要遍历整个 keyspace，在大库上也很贵；
- 删除是 N 次，key 多了要分批。

### 方案 B：版本号（采用）

```java
public void invalidate(Long userId) {
    stringRedisTemplate.opsForValue().increment("prompt:tags:ver:" + userId);
}
```

一次 `INCR`，O(1)。

旧 key 不会被删除，但因为 key 里带版本号，**再也不会有人拼出它们**，等 TTL（5 分钟）自然过期。

```
同步前： key = prompt:tags:12:2:[1001]:霓虹   （旧数据）
同步后： ver 从 2 → 3
下次读： key = prompt:tags:12:3:[1001]:霓虹   （未命中 → 查库 → 写入）
旧 key： 自然过期，无需任何操作
```

**用"改命名空间"代替"删除旧数据"**，这是缓存失效里非常常用的技巧（也叫 cache versioning / generational cache）。

## 4. 缓存穿透：空结果也要缓存

```java
redisTemplate.opsForValue().set(key, tags, properties.getTagCacheTtl());
```

`tags` 可能是空列表，照样写进去。

如果不缓存空结果：用户输入一个不存在的关键字（或者连续输入过程中产生的中间态，比如"霓"→"霓虹"），每次都要打一遍 `JSON_TABLE` 聚合。这类"查不到但一直查"的请求就是缓存穿透的最朴素形态。

### 为什么敢缓存空结果

因为 key 里包含了**完整的查询参数**。一个空结果只对"这组参数"成立，不会污染别的查询。

如果 key 只按 `userId` 设计（"缓存这个用户的全部标签"），那空结果就会导致"整个标签云显示为空"——那就是 bug 而不是优化。**key 的粒度必须等于结果的粒度。**

## 5. 降级：Redis 挂了不能影响功能

```java
try {
    Object cached = redisTemplate.opsForValue().get(key);
    if (cached instanceof List<?> values) return ...;
} catch (RuntimeException e) {
    log.warn("读取标签缓存失败，降级查库: {}", e.getMessage());
}
```

读写都包了 try/catch。Redis 连不上时：
- `get` 抛异常 → 忽略，走查库；
- `set` 抛异常 → 忽略，返回查库结果。

**为什么这么设计**：缓存的收益是"省一次聚合"，不是"没有它功能就不可用"。让缓存故障升级成 500 是最典型的过度设计。

### 但锁不一样

`RedisLock.tryLock` 抛异常时**不能降级成"没锁也执行"**——那等于把并发保护直接关掉。所以锁的异常应该往上抛（当前实现是让 `RedisConnectionFailureException` 冒泡成 500，同步失败）。

**"可降级"和"不可降级"要分开判断**：
- 缓存：丢了只是慢，可降级；
- 锁：丢了会并发写坏数据，不可降级；
- token 黑名单：丢了等于登出失效，不可降级。

## 6. TTL 与"版本号"的分工

| 机制 | 作用 |
| --- | --- |
| 版本号 | **立即**让旧数据失效（同步完成那一刻） |
| TTL 5 分钟 | 兜底回收内存；覆盖"版本号没加上"的情况（比如 Redis 抖动导致 INCR 失败） |

两者不是重复：
- 只靠 TTL：同步后 5 分钟内用户看到旧标签（体验差）；
- 只靠版本号：旧 key 永远占内存（除非手动清理）。

**"主动失效 + 被动过期"是缓存的标准组合**。

## 7. 缓存击穿会不会发生

`getOrLoad` 是"读不到就查库再写"，没有互斥。所以一个热点 key 刚失效时，多个请求会同时查库（缓存击穿）。

为什么这里不处理：
- 标签云的并发量很低（一个用户不会同时开 10 个页面查同一个关键词）；
- 查库的代价是"几千行的 JSON_TABLE"，几十毫秒，不是"打穿数据库"级别；
- 加互斥锁（或 `SETNX` 只让一个线程回源）会让代码复杂度上升一个档，收益在这个场景下不成立。

**如果这是一个秒杀商品详情页，就必须处理**。判断标准是"回源的成本 × 并发量"。

## 面试考察点

**Q1：为什么只缓存标签，不缓存整个列表？**
缓存要看成本。列表走索引、成本与页大小相关；标签云要 `JSON_TABLE` 炸数组，成本与筛选后的总行数相关。后者才是真正的瓶颈。

**Q2：失效为什么用版本号而不是删 key？**
删 key 需要 `KEYS`/`SCAN` 找匹配，`KEYS` 会阻塞 Redis，`SCAN` 在大库上也贵。版本号是一次 `INCR`，旧 key 靠 TTL 自然回收。

**Q3：为什么空结果也要缓存？**
防缓存穿透。用户反复查一个不存在的关键字时，每次都回源打 `JSON_TABLE`。前提是 key 的粒度等于结果粒度，空结果不会污染别的查询。

**Q4：Redis 挂了，标签功能还能用吗？**
能，降级查库。但同步接口会失败（锁不能降级）。这两类缓存/中间件的降级策略要分开判断——判断标准是"丢了之后是慢还是错"。

**Q5：TTL 设 5 分钟的依据？**
版本号负责即时失效，TTL 只负责回收内存和兜底。所以 TTL 可以设得比"数据变化频率"长很多。这里取 5 分钟，既能及时释放内存，又不会因为频繁过期导致反复回源。

**Q6：`JSON_TABLE` 是什么？为什么不能走索引？**
MySQL 8 的表函数，把 JSON 数组展开成行（`["a","b"]` → 两行）。它是运行时展开，没有对应的物理索引，所以只能扫范围内的行再展开。这也是"标签要不要拆关联表"的取舍点。
