# 10　内置源播种与归属隔离

> 代码位置：`infra/prompt/BuiltInPromptSources.java`、`PromptSourceServiceImpl#ensureBuiltIns` / `#getOwned`

## 1. 内置源是什么

前端 `prompt-source-presets.ts` 里写死了 7 个公开仓库：

```ts
export const DEFAULT_PROMPT_SOURCES: PromptSource[] = [
    registrySource("banana-prompt-quicker", "Banana Prompt Quicker", "https://glidea.github.io/..."),
    registrySource("davidwu-gpt-image2-prompts", "DavidWu GPT Image 2", "https://github.com/..."),
    ...
];
```

后端 `BuiltInPromptSources` 与之一一对应（**id / name / URL 必须逐字一致**，否则前端本地状态对不上）。

## 2. 为什么写死在代码里，不放数据库

| 方案 | 问题 |
| --- | --- |
| 放 `t_prompt_source` 初始数据（SQL 脚本） | 需要"老用户升级时补数据"的 migration；改内置源要写 UPDATE 脚本 |
| 放配置文件 | 可以，但配置文件的定位是"部署差异"，内置源是"产品默认值"，跟着代码走更合适 |
| **写死在 Java 常量（采用）** | 跟着版本走；改内置源 = 改代码 = 有 code review |

关键区别：**这些源不是"运营数据"，是"产品自带的默认值"**。它们和代码里的默认文案、默认主题色同性质。

## 3. 播种：为什么是"每用户 7 行"

### 3.1 如果做成全局共享

```
t_prompt_source (user_id NULL = 全局)
   ↓
所有用户看到同一行 → enabled 也是同一列 → A 停用，B 也看不到了
```

要支持"每人能独立启停"，就得再加一张 `t_user_prompt_source`（订阅表）：3 张表、更多 join、更复杂的删除语义。

### 3.2 每用户各存一份

```
user 12: banana-prompt-quicker, davidwu..., ...   (7 行)
user 13: banana-prompt-quicker, davidwu..., ...   (7 行)
```

- 启用状态天然属于用户（就是自己那行）；
- 同步状态天然属于用户（A 的网络超时不影响 B）；
- 删除语义简单（`built_in=1` 禁止删，只能停用）；
- 不需要第三张表。

**代价**：多用户会重复拉同一份 JSON。在"几十个用户"的量级下完全可接受；真要做成产品，正确方向是"全局池 + 订阅表 + 后台统一同步"，那是另一个设计（`docs/database.md` 的演进预留里记了）。

### 3.3 为什么是"懒播种"而不是"注册时播种"

```java
private void ensureBuiltIns(Long userId) {
    List<PromptSource> existing = promptSourceMapper.selectList(...);
    Set<String> keys = ...;
    for (BuiltInPromptSources.BuiltIn builtIn : BuiltInPromptSources.ALL) {
        if (keys.contains(builtIn.key())) continue;
        promptSourceMapper.insert(source);
    }
}
```

调用点：`list()` 和 `enabled()`。

如果放在注册流程里：
- 注册事务里多 7 次 INSERT，注册变慢；
- 历史用户（阶段 1~3 注册的）没有这 7 行，要么写 migration、要么永远看不到内置源；
- 内置源列表变更时（加第 8 个），老用户不会被补上。

懒播种天然幂等：**谁先访问，谁负责补齐**。老用户升级后第一次进页面就自动有了。

## 4. 并发播种：唯一索引兜底

页面同时发两个请求（`GET /prompt-sources` 和 `GET /prompts`）都会触发 `ensureBuiltIns`：

```
线程 A: SELECT 现有 → 空 → 准备插 7 条
线程 B: SELECT 现有 → 空 → 准备插 7 条
```

两个都插 → 第二个撞 `uk_prompt_source_user_key (user_id, source_key)` → `DuplicateKeyException`。

处理：

```java
try {
    promptSourceMapper.insert(source);
} catch (DuplicateKeyException e) {
    log.debug("内置源已被并发创建，跳过: {}", builtIn.key());
}
```

**先查后插不是原子的**，唯一索引才是最终裁决。这和阶段 3 秒传的第三层判断是同一个思路：
- 应用层查（快，覆盖 99% 的情况）；
- 数据库唯一索引（慢但准确，兜住并发）。

吞掉异常而不是 `INSERT IGNORE`：`INSERT IGNORE` 会把**所有**错误都吞掉（包括列超长、类型错误），排查时非常痛苦。只捕获 `DuplicateKeyException` 语义更精确。

## 5. 内置源的保护：能停用，不能改也不能删

```java
// update
boolean structuralChange = request.name() != null || request.url() != null || request.homepage() != null;
if (source.getBuiltIn() == 1 && structuralChange) {
    throw new BizException(ResultCode.PROMPT_SOURCE_READ_ONLY);
}

// delete
if (source.getBuiltIn() == 1) {
    throw new BizException(ResultCode.PROMPT_SOURCE_READ_ONLY);
}
```

为什么这么严：

- 内置源是"所有用户共享的产品内容"的入口。如果能改地址，一个用户就能把库指向别处（虽然是自己的行，但概念上破坏了"内置"的语义）；
- 能删的话，用户误删后没法恢复（懒播种只在 `list` 时补，删了下次会重新出现——这会让用户困惑"为什么删了又回来了"）。

所以：**停用是唯一允许的操作**。停用后数据保留，随时能恢复。

## 6. 归属隔离：越权返回 404 而不是 403

```java
public PromptSource getOwned(Long userId, String sourceKey) {
    PromptSource source = promptSourceMapper.selectOne(new LambdaQueryWrapper<PromptSource>()
            .eq(PromptSource::getUserId, userId)
            .eq(PromptSource::getSourceKey, sourceKey));
    if (source == null) {
        throw new BizException(ResultCode.PROMPT_SOURCE_NOT_FOUND);
    }
    return source;
}
```

两个要点：

1. **`user_id` 进 WHERE，不是查出来再比对**。这样"别人的源"和"不存在的源"在 SQL 层面就是同一个结果，不可能因为后续代码漏判断而泄露。
2. **统一返回 404 `/ 40440`**，不用 403。403 等于告诉攻击者"这个 id 是存在的，只是不属于你"，可以用来枚举。这个约定从阶段 2 就定下了。

`getOwned` 同时被 CRUD 和同步服务复用——**归属校验只有一处实现**，不会出现"某个接口忘了检查"。

## 7. 删除时连带清理

```java
@Transactional(rollbackFor = Exception.class)
public void delete(Long userId, String sourceKey) {
    PromptSource source = getOwned(userId, sourceKey);
    if (source.getBuiltIn() == 1) throw ...;
    promptMapper.delete(new LambdaQueryWrapper<Prompt>().eq(Prompt::getSourceId, source.getId()));
    promptSourceMapper.deleteById(source.getId());   // 逻辑删除
    promptTagCache.invalidate(userId);
}
```

三个动作必须同一事务：
- 提示词**物理删除**（它们没有 `deleted` 列，见 [01](./01-表结构设计.md)）；
- 源**逻辑删除**（保留"曾经有过这个源"的痕迹，也便于以后做恢复）；
- 标签缓存失效（否则标签云还会显示已删源的标签，最多 5 分钟）。

顺序：先删子、再删父。反过来的话，如果第二步失败，会留下"父没了但子还在"的孤儿数据——虽然外键不存在，数据库不会拦，但逻辑上脏了。

## 面试考察点

**Q1：内置数据为什么写死代码而不放库？**
它是"产品默认值"，跟着代码版本走，需要 code review。放库就要写 migration、要考虑老用户补数据、改默认值要写 UPDATE 脚本。

**Q2：为什么懒播种而不是注册时播种？**
注册事务会变长；历史用户不会自动获得；内置源列表变更时老用户不会被补上。懒播种幂等且对老用户友好。

**Q3：并发首次访问会不会插入重复数据？**
不会，靠 `uk_prompt_source_user_key (user_id, source_key)` 兜底，捕获 `DuplicateKeyException` 即可。先查后插不是原子的，唯一索引才是最终裁决。

**Q4：越权为什么返回 404 而不是 403？**
403 泄露"资源存在"这个信息，可以被枚举。404 让"不存在"和"不属于你"无法区分。

**Q5：`getOwned` 里为什么把 `user_id` 放进 WHERE 而不是查出来再比？**
SQL 层面就把别人的数据排除掉，后续代码无论怎么改都不会把不属于自己的对象带出来。这是"纵深防御"的思路——不依赖调用方记得检查。

**Q6：内置源为什么允许停用但不允许删除？**
停用可逆、数据保留；删除不可逆，而且懒播种会让它"删了又回来"，用户体验很怪。功能上也没有"必须删除内置源"的真实需求。
