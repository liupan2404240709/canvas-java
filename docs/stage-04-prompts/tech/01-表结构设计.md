# 01　表结构设计：源与提示词的父子关系

> 代码位置：`resources/db/schema.sql`（阶段 4 段）、`entity/PromptSource.java`、`entity/Prompt.java`
> 权威表结构文档：[`docs/database.md`](../../database.md) 第六节之后

## 1. 这块在链路里的位置

```
用户新增源 → t_prompt_source 一行
手动/定时同步 → 请求源 url → 解析 → t_prompt 若干行（挂在源下面）
列表查询 → t_prompt 按 source_id 过滤 → 出参补上源的 name
删除源 → t_prompt 物理删 + t_prompt_source 逻辑删
```

理解了"谁是聚合根、谁是附属数据"，后面所有写入路径都变得很自然。

## 2. 两张表的分工

| | `t_prompt_source` | `t_prompt` |
| --- | --- | --- |
| 是什么 | 一个 JSON 地址 + 它的同步状态 | 从那个地址解析出来的条目 |
| 归属 | `user_id` | `user_id`（冗余）+ `source_id` |
| 生命周期 | 用户创建 → 停用 → 删除 | 跟随同步：增、改、删都由同步决定 |
| 逻辑删除 | 有（`deleted`） | **无**（物理删） |
| 对外标识 | `source_key`（字符串） | `prompt_key`（源内 id） |
| 唯一约束 | `(user_id, source_key)` | `(source_id, prompt_key)` |
| 接口 | 5 个（CRUD + 同步） | **0 个**（只能通过同步写入） |

**"附属数据没有独立接口"** 是这个项目反复出现的一条原则：阶段 2 的 `t_canvas_node` 只能通过快照接口写，阶段 4 的 `t_prompt` 只能通过同步写入。

### 为什么提示词不该有独立的增删改

用户能对一条提示词做什么？改标题？改正文？那同步一次就全被覆盖了——因为源是权威。

真正需要"改一条提示词"的需求，本质是**把我喜欢的存成我自己的东西**，那属于素材库（`t_asset`，kind=text），不是提示词库。职责分清楚，模型就不会打架。

## 3. 关键字段的取舍

### 3.1 `source_key` 而不是数据库主键对外

```java
private String sourceKey;   // banana-prompt-quicker / src_1a2b3c4d5e6f
```

前端 `PromptSource.id` 是字符串，内置源还是 registry 里的固定 id。如果对外用雪花主键：

- 前端内置配置（`prompt-source-presets.ts`）里的 id 全部失效；
- 换库/换环境重新播种后主键变化，前端本地状态对不上。

所以主键只做物理标识。和阶段 2 的 `node_key`、阶段 3 的 `storage_key` 是同一套思路：**业务键稳定，主键可以变**。

### 3.2 同步状态放在源上，不建任务表

`prompt_count` / `content_sha256` / `etag` / `last_modified` / `last_fetched_at` / `last_success_at` / `last_error` —— 7 个字段。

考虑过建 `t_prompt_sync_task`（每次同步一行，记录耗时、成功/失败、条数变化），否决理由：

- 业务上只需要"最后一次结果"（前端就展示这一条）；
- 任务表只增不减，一年后几百万行，还得写归档任务；
- 真要审计，日志文件更合适（`logback` 已经在按天切了）。

**判断标准**：需要"历史趋势"（成功率曲线、耗时分布）才建任务表；只需要"当前状态"就放主表。

### 3.3 `t_prompt.user_id` 是冗余，但值得

严格说可以从 `source_id` 推出来。但列表查询的每一条都是：

```sql
SELECT ... FROM t_prompt
WHERE user_id = ? AND source_id IN (?, ?, ...) AND ...
ORDER BY source_id, sort_index, id
LIMIT ...
```

有 `user_id` 就能直接用 `idx_prompt_user_source_order (user_id, source_id, sort_index)`；没有它就得 join 源表或者写成子查询，而且索引的第一列变成 `source_id`（IN 列表），排序会退化。

**代价**：写入时必须从源带出来（当前唯一写入路径是同步，天然满足，不接受客户端传）。

### 3.4 `sort_index` 保留上游的策展顺序

源的 JSON 数组顺序是有意义的——仓库维护者把好用的放前面。存下标的收益：

- 用户看到的顺序和上游一致（不至于"我明明记得它在第 3 个"）；
- 分页有稳定的排序依据（配合 `source_id` 和 `id`）。

不存的话只能按 `created_at DESC`，每次同步（新行）顺序都会变。

### 3.5 JSON 字段仍然存 `String`

`reference_image_urls` / `tags_json` 在 Java 里是 `String`，不是 `JsonNode` 或 `List`。

理由和阶段 2 的节点 `metadata` 完全一样：
- MyBatis 对 `List` 的映射需要 TypeHandler，多一层配置；
- 后端不需要理解数组里是什么，原样存取最省事；
- 需要写 `JSON_CONTAINS` 时，SQL 里直接操作列即可。

代价：Java 里读出来要自己转（`PromptJson.read`）。这点成本换来"零 TypeHandler 配置"是划算的。

## 4. 索引设计与对应的 SQL

| 索引 | 列 | 支撑的查询 |
| --- | --- | --- |
| `uk_prompt_source_user_key` | `(user_id, source_key)` | 播种判重、按业务键查源、`getOwned` |
| `idx_prompt_source_due` | `(enabled, deleted, last_fetched_at)` | 定时任务扫描"到期的源" |
| `uk_prompt_source_key` | `(source_id, prompt_key)` | upsert 判重、按源加载 |
| `idx_prompt_user_source_order` | `(user_id, source_id, sort_index)` | 列表查询 + 排序 |

两个细节：

1. **`idx_prompt_source_due` 的列序**：`enabled`、`deleted` 是等值条件，`last_fetched_at` 是范围条件，等值必须在前，否则范围列之后的条件用不上索引。
2. **`uk_prompt_source_key` 顺便当查询索引**：`WHERE source_id = ?` 命中它的左前缀，所以不需要再建一个 `(source_id)` 的单列索引（阶段 2 的 `idx_node_project` 就是这种冗余索引，这里没再犯）。

## 5. 一次同步对两张表的写入

```sql
-- 一个事务内
INSERT INTO t_prompt (...) VALUES (...) AS new
ON DUPLICATE KEY UPDATE title = new.title, ...;       -- 分批，每批 200 行

DELETE FROM t_prompt
WHERE source_id = ? AND prompt_key NOT IN (?, ?, ...); -- 差量删除

UPDATE t_prompt_source
SET prompt_count = ?, content_sha256 = ?, etag = ?, last_modified = ?,
    last_fetched_at = ?, last_success_at = ?, last_error = NULL
WHERE id = ?;
```

注意 `last_error = NULL` 是**显式写**的：MyBatis-Plus 默认忽略实体里的 null 字段，不显式 `set` 的话，一次成功之后 `last_error` 永远清不掉，前端会一直显示上次的失败原因。

## 面试考察点

**Q1：为什么源和提示词不合成一张表？**
A：源有独立的生命周期和状态（地址、启用、同步结果），提示词只是它的内容。合成一张表就表达不了"源存在但还没同步"（`count=0`），也会让 `etag`、`last_error` 在几千行里重复。父子表 + 附属数据无独立接口，是这里最自然的模型。

**Q2：为什么提示词表不加 `deleted`？**
A：它没有"单条删除"的业务语义。用户的操作只有"同步"，源里没了的条目由差量删除处理。加了 `deleted` 会导致：每次同步都要判断"这行是删了还是源里没了"；差量删除变成逻辑删除后表无限膨胀。跟着父级物理删除更干净。

**Q3：对外用业务键而不是主键，好处和代价？**
好处：业务键稳定（内置源 id 就是 registry id），换环境重新播种不影响前端；主键可以随便重建（阶段 2 每次保存都重建节点主键）。
代价：每次按业务键查都要走唯一索引（而不是主键直达），并且业务键必须自己保证唯一（`uk (user_id, source_key)`），生成规则要防冲突。

**Q4：`sort_index` 有什么用？不加会怎样？**
它会保留上游数组的策展顺序。不加就只能按 `created_at` 排，而 `created_at` 在同步时是不变的（upsert 不覆盖），所以顺序会变成"入库顺序"，和上游不一致；另外分页会缺少一个稳定的排序键。

**Q5：为什么索引里 `deleted` 放中间？**
`(enabled, deleted, last_fetched_at)`：前两个是等值条件，最后一个是范围条件。B+ 树索引只有在"等值列都在范围列之前"时，范围列才能用于范围扫描；如果把 `last_fetched_at` 放中间，后面的 `deleted` 就退化成回表后过滤。
