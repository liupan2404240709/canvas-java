# 07　定时调度设计

> 代码位置：`scheduler/PromptRefreshScheduler.java`、`PromptSourceMapper#selectDueSources`、`CanvasApplication`（`@EnableScheduling`）

## 1. 需求：每个源按自己的间隔刷新

前端有一个设置项：`intervalMinutes`，可选 `[0, 30, 60, 360, 1440]`（0 = 关闭自动刷新）。

后端把它落成 `t_prompt_source.refresh_interval_minutes`——**每行一个值**，不是一个全局配置。

这就决定了调度不能是"每 30 分钟把所有源刷一遍"。

## 2. 两种实现思路

### 2.1 每个源注册一个 `ScheduledFuture`

```java
taskScheduler.scheduleWithFixedDelay(() -> sync(source), interval);
```

| 问题 | 说明 |
| --- | --- |
| 间隔是数据不是配置 | 用户改间隔 → 必须取消旧任务、注册新任务，要维护 `Map<sourceId, ScheduledFuture>` |
| 源删除要注销 | 忘了就是内存泄漏 + 一直报 404 |
| 重启后要重建 | 启动时要遍历所有源注册一遍，几千个源就是几千个任务 |
| 精度 | 每个任务独立计时，源多了调度线程会争抢 |

### 2.2 扫描 + 到期判断（采用）

```java
@Scheduled(cron = "${app.prompt.scan-cron:0 */5 * * * *}")
public void scanDueSources() {
    promptService.refreshDue();
}
```

```sql
SELECT * FROM t_prompt_source
WHERE deleted = 0
  AND enabled = 1
  AND refresh_interval_minutes > 0
  AND (last_fetched_at IS NULL
       OR last_fetched_at <= DATE_SUB(NOW(), INTERVAL refresh_interval_minutes MINUTE))
ORDER BY last_fetched_at IS NOT NULL, last_fetched_at
LIMIT 20
```

一个定时器，扫"谁该刷了"。间隔变化只是改一行数据，下一次扫描自然生效。

## 3. 为什么是"扫描间隔 + 到期条件"两层

| 层 | 值 | 作用 |
| --- | --- | --- |
| `app.prompt.scan-cron` | `0 */5 * * * *`（每 5 分钟） | 多久检查一次"有没有到期的源" |
| `refresh_interval_minutes` | 每源不同（默认 30） | 这个源多久需要刷一次 |

两层分离的好处：扫描频率是**系统负载参数**（可以为了省资源调成 10 分钟），刷新间隔是**业务参数**（用户可改）。混成一个值，调系统参数就会改变业务行为。

代价：实际刷新时间有最多 5 分钟误差。对提示词库完全无影响。

## 4. SQL 里的四个条件

```sql
WHERE deleted = 0                      -- 逻辑删除的源不刷
  AND enabled = 1                      -- 用户停用的不刷
  AND refresh_interval_minutes > 0     -- 0 = 只手动，不参与调度
  AND (last_fetched_at IS NULL
       OR last_fetched_at <= DATE_SUB(NOW(), INTERVAL refresh_interval_minutes MINUTE))
```

第 4 个条件是整个设计的关键：

- `last_fetched_at IS NULL`：新建的源从没刷过，应该尽快刷一次。**如果只写 `<=` 比较，NULL 参与比较结果是 NULL（不成立）**，新源永远不会被选中——这是最容易被忽略的 SQL 陷阱。
- `<=` 而不是 `<`：正好到点（差值恰好等于间隔）时也应该刷。阶段 3 的孤儿清理就踩过"用严格小于导致同秒数据被漏掉"的坑。
- `DATE_SUB(NOW(), INTERVAL ... MINUTE)`：把"间隔"作用在数据库当前时间上，避免 Java 和 MySQL 的时钟/时区不一致。

## 5. 排序与限流

```sql
ORDER BY last_fetched_at IS NOT NULL, last_fetched_at
LIMIT 20
```

- `last_fetched_at IS NOT NULL` 排序：`0`（从未刷过）排前面，`1`（刷过的）排后面。**新源优先**。
- `last_fetched_at` 升序：最久没刷的优先。
- `LIMIT ${scheduleBatch}`（默认 20）：单次最多处理 20 个源。

为什么要限流：
- 服务刚启动时如果库里有几百个到期源，一口气全拉 = 瞬间打满连接池和上游；
- 20 个/5 分钟 = 每小时 240 个源的吞吐，对"几百个源"的量级完全够用；
- 超出的下一轮继续处理（因为它们的 `last_fetched_at` 还是旧的，仍然到期）。

## 6. 单源失败不影响整批

```java
for (PromptSource source : due) {
    PromptRefreshResultVO result = refreshQuietly(source, false);
    if (result.success()) log.info("定时同步完成: ...");
    else log.warn("定时同步失败: source={} error={}", ...);
}
```

`refreshQuietly` 内部：
- 拿不到锁 → 返回 `success=false, lastError="该源正在同步中"`，继续下一个；
- 同步异常 → `try/catch` 转成结果对象，继续下一个。

**批量任务里，单条失败必须被隔离**。否则第 3 个源超时抛异常，第 4~20 个源这轮就不跑了。

最外层还有一道：

```java
try {
    promptService.refreshDue();
} catch (RuntimeException e) {
    log.error("提示词定时同步整体失败", e);
}
```

Spring 的 `TaskScheduler` 本身会捕获异常并打日志，不会让调度线程死掉。但自己再兜一层，日志里能明确区分"单个源失败"和"整批失败"（比如数据库连不上）。

## 7. `@EnableScheduling` 放在哪

放在 `CanvasApplication` 上：

```java
@SpringBootApplication(exclude = UserDetailsServiceAutoConfiguration.class)
@MapperScan("com.infinitecanvas.canvas.mapper")
@EnableScheduling
public class CanvasApplication { ... }
```

理由：它是**应用级开关**，放在启动类上让人一眼看出"这个服务有后台任务"。放在某个 `@Configuration` 里，排查"为什么定时任务没跑"时容易漏看。

## 8. 多实例部署会重复执行吗

会扫到同一批源，但**不会重复劳动**：

```
实例 A：扫到 source 1..20 → 抢 lock:prompt:refresh:1 → 拿到 → 同步
实例 B：扫到 source 1..20 → 抢 lock:prompt:refresh:1 → 失败 → 跳过，不写 last_fetched_at
```

A 同步成功后会更新 `last_fetched_at`，下一轮 B 扫的时候这些源就不到期了。

所以**不需要选主**（不需要 Quartz 集群模式、不需要 ShedLock）。代价是"每个实例都做一次 SELECT"，这个开销可以忽略。

这也说明了一个判断标准：**任务本身能靠锁去重，就不要引入选主机制**。

## 9. 为什么方法上不加 `@Transactional`

`refreshDue` 会调用 `syncOne`，里面包含 HTTP 请求。

如果整个方法在事务里：
- 事务时长 = 20 个源 × 平均几秒 = 几分钟；
- 一个数据库连接被占几分钟，连接池（默认 10）很快就空；
- MySQL 的 `innodb_lock_wait_timeout`、`wait_timeout` 都可能被触发。

正确做法：事务边界只包"写库那三步"（用 `TransactionTemplate` 显式控制），见 [05](./05-批量upsert与差量删除.md)。

## 10. 时间精度与"最近一次"的语义

`last_fetched_at` 是 `DATETIME`（秒级）。两种边界：

- 手动同步和定时同步同时发生 → 锁保证只有一个执行；
- 同步耗时跨越了"到期点" → 下一轮扫描时 `last_fetched_at` 已经被这次同步更新，不会重复。

如果同步失败，`last_fetched_at` 也会更新（`markFailure`）。这意味着**失败的源也会等一个完整间隔再重试**，不会疯狂重试打爆上游。这是一个有意的取舍：失败重试的及时性 < 保护上游。

## 面试考察点

**Q1：为什么不用 `@Scheduled(fixedDelay)` 给每个源定时？**
刷新间隔是用户可改的数据，不是启动时确定的配置。每源一个任务需要动态注册/注销、管理句柄、重启重建；扫描 + 到期判断只需要一条 SQL。

**Q2：`last_fetched_at IS NULL` 这一句为什么不能省？**
SQL 里 `NULL <= x` 的结果是 NULL（不是 true），新源会被永久排除在调度之外。必须显式 `IS NULL OR ...`。

**Q3：为什么用 `DATE_SUB(NOW(), ...)` 而不是在 Java 里算好时间传进去？**
避免 JVM 与 MySQL 的时钟/时区不一致。让数据库自己算，只依赖一个时间源。而且条件只依赖单行字段，SQL 表达最直接。

**Q4：多实例部署怎么防止重复执行？**
靠 Redis 锁去重，不靠选主。被跳过的实例不更新 `last_fetched_at`，下一轮仍然到期，但拿到锁的那个实例已经更新过了，所以不会重复。

**Q5：定时任务里的异常要处理吗？Spring 不是会捕获吗？**
会捕获，调度线程不会死。但要区分"单个源失败"（继续下一个）和"整批失败"（数据库连不上）。前者用 try/catch 包单个源，后者在最外层再兜一层并打 error 日志。

**Q6：`LIMIT 20` 会不会导致某些源永远轮不到？**
不会，因为排序是"最久未刷的优先"，且被处理的源会更新 `last_fetched_at` 排到队尾。这是典型的轮转调度，不会饿死。
