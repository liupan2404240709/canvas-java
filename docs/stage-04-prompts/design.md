# 阶段 4 设计文档：提示词库

记录这一阶段真正需要"选一条路"的地方。每条写清楚：**选了什么、否决了什么、为什么、代价是什么**。

## 一、数据模型

### D1　源和提示词分两张表，而不是一张

| | 方案 A：一张表（源信息冗余在每行提示词上） | **方案 B：父子两张表（采用）** |
| --- | --- | --- |
| 同步状态 | 每个提示词行都要带 `last_error`、`etag`，几千行重复 | 源上只有一份 |
| "源存在但还没同步" | 表达不了（没有提示词就没有行） | 源行在，`count=0` |
| 改源地址 | `UPDATE ... WHERE source_id` 全表刷 | 改一行 |
| 查询 | 单表，少一次关联 | 需要 join 或冗余源名 |

**选 B**。这个阶段最核心的概念就是"源"：它有自己的生命周期（新增、停用、同步、删除）、自己的状态（上次成功时间、失败原因）。把它塞进提示词的某一列，等于放弃了这个概念。

**代价**：列表要拿源名（`category`）和源主页（`githubUrl` 兜底）。解决办法见 D5。

### D2　内置源按用户各存一份，不做"全局池 + 订阅表"

| | 方案 A：全局共享（`user_id=0` 或 NULL）+ `t_user_prompt_source` 订阅表 | **方案 B：每用户各 7 行（采用）** |
| --- | --- | --- |
| 表数量 | 3 张 | 2 张 |
| 上游请求量 | 7 次/全局 | 7 次/用户 |
| 启用状态 | 天然按用户 | 天然按用户（就是自己的行） |
| 同步状态 | 只能是全局的（谁的失败算谁的？） | 按用户 |
| 删除语义 | 内置源不能删，订阅表要"软取消" | 简单：`built_in=1` 禁止删 |

**选 B**。理由不是"表少"，而是**同步状态天然属于用户**：A 的机器访问 GitHub 超时了，不应该让 B 看到"上次失败"；A 点同步也不该占用 B 的锁。

**代价**：多个用户会重复拉同一份 JSON。在"学习项目 + 单机 + 几十个用户"的量级下完全可以接受；真要优化，正确做法是**后台维护一份全局缓存 + 用户表只记订阅关系**，那是另一个设计（见 `docs/database.md` 的演进预留）。

### D3　对外用 `source_key`，不用数据库主键

前端 `PromptSource.id` 是字符串：内置源是 `banana-prompt-quicker` 这种 registry id，自定义源是 `nanoid`。如果对外暴露雪花主键：

- 内置源的 id 就变成了一串数字，前端 `prompt-source-presets.ts` 里的默认配置全部失效；
- 每次重新播种（换库、换环境）主键都会变，前端的本地状态对不上。

所以：**数据库主键 `id` 只做物理标识，对外一律 `source_key`**。这和阶段 2 的 `node_key` 是同一个思路。

### D4　`t_prompt` 没有 `deleted`

提示词没有"单条删除"的业务语义。用户能做的只有"同步源"，源里没了的条目由差量删除处理。

如果给它加 `deleted`：
- 每次同步都要判断"这行是删了还是源里没了"，两个状态混在一起；
- 差量删除变成逻辑删除，表会无限膨胀（每次上游改一次 id 就留一堆垃圾）。

所以它是**附属数据**，跟着源走。源被删时它的提示词**物理删除**。

### D5　`t_prompt` 冗余 `user_id`

严格说它可以从 `source_id` 推出来，属于冗余。但列表查询的每一条都要：

```sql
WHERE user_id = ? AND source_id IN (...) AND ...
```

有 `user_id` 就能直接用 `idx_prompt_user_source_order`；没有就得 `JOIN t_prompt_source` 或者用子查询，而且索引要建在 `source_id` 上，范围查询会退化。

**代价**：写入时必须从源带出，不能接受客户端传（当前唯一的写入路径是同步，天然满足）。

## 二、同步策略（本阶段最关键的四条）

### D6　幂等靠"内容摘要 + 条件请求"，不是靠"先删后插"

三种可选做法：

| 做法 | 每次同步的代价 | 问题 |
| --- | --- | --- |
| 删全部 + 批量插入 | 几千行 DELETE + INSERT | 主键全变、`created_at` 重置、长事务、分页锚点漂移 |
| 逐条比对再增删改 | N 次 SELECT + N 次写 | 网络往返爆炸 |
| **摘要比对 + upsert（采用）** | 内容没变：0 次写；变了：1 次批量 upsert + 1 次差量删 | 需要一次 SHA-256 |

具体两道闸门：

1. **HTTP 条件请求**：带上上次的 `ETag` / `Last-Modified`，命中 304 就直接结束（连 JSON 都不用下载）；
2. **内容摘要**：拿到 200 后算响应体的 SHA-256，与库里存的比较，相同就只更新时间戳。

第 2 道闸门不是为了替代第 1 道，而是**兜住不支持条件请求的上游**（GitHub raw 支持，但很多自建 JSON 服务不支持）。

`force=true` 同时绕过两道闸门——用户明确要求"重跑一遍"时不该被"内容没变"挡住。

### D7　upsert + 差量删除，而不是整份替换

`INSERT ... ON DUPLICATE KEY UPDATE` 依赖 `uk_prompt_source_key (source_id, prompt_key)`。

为什么值得多写这几十行：

| 维度 | 整份替换 | **upsert + 差量删（采用）** |
| --- | --- | --- |
| 主键 | 每次都变 | 稳定 |
| `created_at` | 被重置 | 保留"首次入库时间" |
| 分页稳定性 | 翻页时内容会跳 | 稳定 |
| 事务体积 | 删 N + 插 N | 只更新变化的行（MySQL 仍会写 undo，但少一次删） |

差量删除用 `prompt_key NOT IN (...)`：上游删掉的条目本地也要消失，否则用户会看到"源里已经不存在的提示词"。

顺序是**先 upsert 再删除**：万一事务回滚，本地至少还是完整的旧快照（而不是"旧的删了、新的没进去"）。

### D8　`ON DUPLICATE KEY UPDATE ... AS new` 而不是 `VALUES(col)`

MySQL 8.0.20 起 `VALUES(col)` 被标记 deprecated。当前用的是 8.0.19+ 的行别名写法：

```sql
INSERT INTO t_prompt (...) VALUES (...) AS new
ON DUPLICATE KEY UPDATE title = new.title, ...
```

两者功能一样，但新写法不会在日志里刷 deprecation warning，而且语义更清楚（`new` 就是"这次要插入的那行"）。

### D9　同步失败返回 HTTP 200 + `success=false`

这是**有意的反直觉设计**，值得单独解释：

- "接口调用失败"（401、404、参数错）→ 应该抛 HTTP 错误码；
- "任务执行失败"（上游 404、返回非数组、返回 0 条）→ 接口本身是成功的，失败的是这次同步。

如果失败也返回 502，前端拿到的是统一错误结构，`lastError` 会被全局处理器换成"服务暂时不可用"，用户根本不知道是哪个源、因为什么失败。

所以：**失败原因写进 `t_prompt_source.last_error`，同时原样放进响应体的 `lastError`**，HTTP 状态保持 200。

### D10　内置源返回 0 条 = 失败，不覆盖本地

如果某个内置源某天返回了空数组（上游临时故障、仓库被删），按"整份同步"的语义就该把本地清空——这是灾难。

所以规则是：**内置源解析出 0 条 → 抛 `PromptSyncException`，保留旧数据并记录 `last_error`**。

自定义源不适用这条：用户自己填的源，返回空数组是完全合理的（他刚建了个空文件）。

## 三、并发与调度

### D11　Redis 锁，不排队

用户在页面上连点两次「同步」、或者定时任务正好撞上手动同步，都会并发进入。

处理方式：`SET prompt:refresh:{sourceId} <token> NX PX 180000`。

- 拿不到锁 → 直接抛 `429 / 42920`（"该源正在同步中"），**不阻塞等待**；
- 理由：同步是 10~30 秒的重操作，"排队 30 秒然后成功"对用户来说和"失败重试"体验差不多，但前者会占住 Tomcat 线程。

否决的方案：

| 方案 | 否决理由 |
| --- | --- |
| `synchronized` / `ReentrantLock` | 只对单实例有效，多实例部署等于没锁 |
| 数据库 `SELECT ... FOR UPDATE` | 事务里等网络请求，长事务 + 连接占用 |
| 消息队列串行化 | 为了一个同步任务引入 MQ，运维成本远大于收益 |

### D12　定时任务用"扫描 + 到期判断"，不给每个源注册定时器

`@Scheduled(cron = "${app.prompt.scan-cron}")` 每 5 分钟跑一次，SQL 里判断"谁该刷了"：

```sql
WHERE enabled = 1 AND refresh_interval_minutes > 0
  AND (last_fetched_at IS NULL
       OR last_fetched_at <= DATE_SUB(NOW(), INTERVAL refresh_interval_minutes MINUTE))
LIMIT 20
```

为什么不给每个源一个 `ScheduledFuture`：

- 刷新间隔是**数据**不是配置：用户随时能改，改完要重建任务；
- 要自己管理任务句柄的注册/注销（源删除时忘了注销就是内存泄漏）；
- 扫描天然限流（`LIMIT 20`），重启后不会瞬间把 100 个源全拉一遍。

**代价**：调度精度是"扫描间隔"（5 分钟），不是精确到秒。对提示词库这种场景完全没有影响。

### D13　多实例下靠锁去重，而不是靠"只有主节点跑"

两个实例各扫到同一批到期源 → 都去抢 `prompt:refresh:{id}` → 只有一个拿到。

被跳过的那个实例**不记录失败**（`last_fetched_at` 由拿到锁的实例更新），所以下一轮扫描时它们已经不到期了。这个设计让"没有选主"也不会有重复劳动。

### D14　同步是串行的

`refreshAll` 用 `for` 循环一个个来，不用 `CompletableFuture` 并发。

理由：
- 7 个源并发拉取会瞬时限速上游（GitHub raw 对无 UA/高频请求不友好）；
- 串行的总耗时是可预期的（7 × 平均 2 秒），并发省下的时间对"手动点一下"这个场景意义不大；
- 出错时日志顺序清晰，排查不用对时间线。

**已知代价**：全部同步一次可能要十几秒，HTTP 请求会一直挂着。控制台里按钮会显示"同步中…"，并且有 60 秒超时的兜底。真要做成后台任务，应该返回 `202 + 任务 id`，那是下一层设计。

## 四、查询与缓存

### D15　标签用 JSON 列 + `JSON_CONTAINS`，不建关联表

和阶段 3 的素材标签同一个理由：标签是弱结构数据，从源里来、整体替换，没有独立生命周期。

多选标签的语义是**或**（命中任意一个）——这和前端 `tags.some(tag => item.tags.includes(tag))` 完全一致。有意的细节：如果做成"且"，用户勾第二个标签会得到空结果，看起来像 bug。

### D16　排序用 `source_id, sort_index, id` 三列

只按 `sort_index` 会出问题：不同源的下标都是 0、1、2…，混在一起是乱序。

三列的组合语义：

| 列 | 作用 |
| --- | --- |
| `source_id` | 先按源分组，和前端"每个源一个分栏"的观感一致 |
| `sort_index` | 源内保持上游数组顺序（策展顺序），用户看到的和仓库里一致 |
| `id` | 兜底：排序值全相同时保证顺序确定，否则翻页会重复/漏 |

### D17　标签云缓存用"版本号"，不删 key

缓存 key：`prompt:tags:{userId}:{version}:{sourceIds}:{keyword}`

同步成功后：`INCR prompt:tags:ver:{userId}` → 所有旧 key 立刻失效（没人再拼出旧 key），靠 TTL 自然回收。

对比"删 key"：

| 方式 | 代价 |
| --- | --- |
| `DEL prompt:tags:{userId}:*` | 需要先 `KEYS`/`SCAN` 找 key；`KEYS` 阻塞 Redis，`SCAN` 在大库上也会打满 CPU |
| **版本号（采用）** | 一个 `INCR`，O(1) |

### D18　空结果也缓存

`tags=[]` 同样写进缓存（TTL 一样）。否则一个搜不到的关键字被反复提交时，每次都要打一遍 `JSON_TABLE` 聚合——这就是缓存穿透的最朴素形态。

之所以敢缓存空结果：缓存 key 里带了完整的查询参数（用户 + 版本 + 源范围 + 关键字），一个空结果不会"污染"别的查询。

### D19　Redis 不可用时降级，不影响主流程

`PromptTagCache` 的读写都包了 `try/catch`，异常只 `warn` 一行日志，然后直接查库。

理由：缓存的收益是"省一次聚合"，不是"没有它功能就不可用"。让缓存故障变成 500 是最典型的过度设计。

（**锁**不一样：锁拿不到是**业务冲突**，必须显式报错——这两个东西的降级策略不能一致。）

## 五、安全与健壮性

### D20　出站请求的地址校验（SSRF）

用户能填任意 URL，服务器会去请求它 → 这是教科书级的 SSRF 入口。

当前做了三层：

1. **协议白名单**：只允许 `http` / `https`。不拦的话 `file:///etc/passwd` 会进到 HTTP 客户端；
2. **私网地址检查**（`allow-private-host=false` 时）：DNS 解析后逐个 IP 判断回环/内网/链路本地/组播。只做字符串前缀匹配是挡不住的（`0x7f.0.0.1`、十进制 IP、指向 127.0.0.1 的域名）；
3. **响应体上限**：流式读取累计 8MB 立刻中断。

**开发环境默认 `allow-private-host=true`**，因为 e2e 需要请求本机的样例 JSON。这个开关的名字和注释都写得很直白，就是为了让人在上线前一定会看到它。

**已知局限**（写在这里而不是藏着）：挡不住 DNS rebinding（解析时公网、连接时内网）。彻底解决要在连接层固定解析出的 IP，属于网关/代理的活。

### D21　超时必须显式设，不能依赖默认值

`SimpleClientHttpRequestFactory` 不设超时 = 无限等待。一个不响应的域名会占住 Tomcat 线程，几个源就能把线程池耗光。

所以 `promptRestClient` 是**独立 bean**：建连 5s、读 20s，和业务接口的超时策略完全分开。

### D22　解析容错：单条坏数据不拖垮整批

上游是人工维护的 JSON，字段缺失、类型错乱是常态。规则：

| 情况 | 处理 |
| --- | --- |
| 顶层不是数组 | 整体失败（这是格式不兼容，没法救） |
| 缺 title 或 prompt | 丢弃这一条 |
| 缺 id | 补 `{sourceKey}-0001` |
| `tags` 是字符串/数字/null | 转成空数组 |
| 超长字段 | 按列宽截断（否则严格模式下整批 INSERT 失败） |
| 时间格式不认识 | 存 NULL，前端显示空 |
| 单源超过 5000 条 | 截断（防止撑爆 `max_allowed_packet`） |

原则：**批量同步要"能救就救"，单条校验才应该"严格报错"**。

### D23　只支持"JSON 数组"，不做 HTML 抓取 / 多格式适配

前端 `runPromptSource` 只认 JSON 数组，后端保持一致。

考虑过支持 RSS / HTML 抓取，否决理由：
- 每个站点结构不同，等于维护一堆爬虫规则；
- 反爬、Cookie、JS 渲染会让"同步"变成一个无底洞；
- 当前 7 个内置源都是 JSON，没有真实需求。

## 六、和前端契约的取舍

### D24　`category` = 源名称（而不是源 id）

前端：

```ts
category: source.name          // 写入时
categories: enabledSources().map(s => s.name)   // 筛选器
```

所以后端 `category` 必须返回**源名**，筛选参数也必须按名字匹配。虽然用 id 更"正确"，但那样前端要改代码——本阶段的约束是"前端一行不动"。

**代价**：源名必须唯一（同一用户下）。所以新增/改名时会校验 `(user_id, name)` 唯一，冲突返回 `409 / 40940`。

### D25　时间字段存 `DATETIME`，输出 `ISO_LOCAL_DATE_TIME`

源里的 `createdAt` / `updatedAt` 是自由格式字符串（可能是 `2025-03-11T09:20:00Z`、`2025-03-11`、甚至空）。

- 入库前解析成 `LocalDateTime`，解析失败存 NULL；
- 出参统一 `2025-03-11T09:20:00`（带 `T`、不带时区）。

为什么不直接把原始字符串存下来：前端用 `new Date(value)` 解析，带 `T` 的 ISO 在各浏览器都稳定，而 `"2025-03-11 09:20:00"`（空格分隔）在部分环境里会得到 `Invalid Date`。

### D26　"加入素材库"不在本阶段实现

前端在提示词卡片上有「加入素材」按钮，它调用的是素材接口（`addAsset` + `metadata.source = "prompt-library"`）。

这属于**前端组合两个接口**，后端不需要新增接口：`POST /v1/assets` 传 `kind=text` + `content=prompt` + `metadata`。阶段 3 已经支持。所以本阶段不提供 `POST /v1/prompts/{id}/to-asset`，避免多一条"只做转发"的接口。

## 七、决策速查表

| # | 决策 | 一句话理由 |
| --- | --- | --- |
| D1 | 源/提示词分表 | 源有自己的生命周期和状态 |
| D2 | 内置源按用户播种 | 同步状态天然属于用户 |
| D3 | 对外用 `source_key` | 前端 id 是字符串且必须稳定 |
| D4 | `t_prompt` 无 `deleted` | 附属数据，没有单条删除语义 |
| D5 | `t_prompt` 冗余 `user_id` | 列表查询免 join，索引能直接用 |
| D6 | 摘要 + 条件请求 | 内容没变就零写入 |
| D7 | upsert + 差量删 | 主键稳定、分页稳定 |
| D8 | `AS new` 语法 | `VALUES()` 已 deprecated |
| D9 | 同步失败返回 200 | 是任务结果，不是接口失败 |
| D10 | 内置源 0 条视为失败 | 宁可不更新，也不清空用户数据 |
| D11 | Redis 锁不排队 | 同步是重操作，干等不如快失败 |
| D12 | 扫描 + 到期判断 | 间隔是数据，重启不炸 |
| D13 | 锁去重而非选主 | 少一套选主机制 |
| D14 | 串行同步 | 限速上游、日志清晰 |
| D15 | 标签 JSON + 或语义 | 标签是弱结构、多选是"或" |
| D16 | 三列排序 | 保证分页不重不漏 |
| D17 | 版本号失效 | 一个 INCR 代替 pattern 扫描 |
| D18 | 空结果缓存 | 防穿透 |
| D19 | 缓存降级 | 缓存挂了不该影响功能 |
| D20 | 协议+私网校验 | 用户填 URL = SSRF 入口 |
