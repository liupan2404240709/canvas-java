# 10 厂商预设与"会变的事实"

> 对应代码：`infra/channel/ChannelPresets.java`（87 行）、`ChannelServiceImpl#presets`

## 一、预设解决什么问题

新建渠道要填四样东西：显示名、Base URL、协议、模型名。其中**三样是"查文档才知道"的**：

- 百炼的地址是 `.../compatible-mode/v1` 还是 `.../api/v1`？
- 方舟的 `/api/v3` 要不要再加 `/v1`？
- 硅基流动的模型 id 是 `Qwen-Image` 还是 `Qwen/Qwen-Image`？

用户为了配一个渠道去翻半小时文档，这件事本身就是产品缺陷。
预设把这三样填好，用户只需要粘一把自己的 Key。

**但不预置 Key，也不预置"默认渠道"**：
Key 是用户自己的资产，凭空插一条空 Key 的渠道只会让列表里多一行永远调不通的配置。

## 二、六家预设，以及各自的坑

```java
new Preset("bailian", "阿里云百炼（通义）",
        "https://dashscope.aliyuncs.com/compatible-mode/v1", "openai", ...)
new Preset("ark", "火山方舟（豆包）",
        "https://ark.cn-beijing.volces.com/api/v3", "openai", ...)
new Preset("zhipu", "智谱 AI（GLM）",
        "https://open.bigmodel.cn/api/paas/v4", "openai", ...)
new Preset("siliconflow", "硅基流动 SiliconFlow",
        "https://api.siliconflow.cn/v1", "openai", ...)
new Preset("deepseek", "DeepSeek（深度求索）",
        "https://api.deepseek.com", "openai", ...)     // 注意：不带 /v1
new Preset("ollama", "本地 Ollama（自建）",
        "http://127.0.0.1:11434/v1", "openai", ...)
```

| 厂商 | 地址特征 | 注意点 |
| --- | --- | --- |
| 百炼 | 末段 `v1`，前面有 `/compatible-mode` | 只能用 `compatible-mode` 这个前缀，不能用原生 dashscope 路径 |
| 方舟 | 末段 `v3`，前面有 `/api` | 文本模型 ID 带日期后缀 |
| 智谱 | 末段 `v4`，前面有 `/api/paas` | |
| 硅基流动 | 末段 `v1` | 模型 ID 形如 `组织/模型名` |
| DeepSeek | **不带版本段** | 拼接逻辑会自动补 `/v1/models` |
| Ollama | 本地地址 | 需要 `allow-private-host: true` |

这六种形态正好覆盖了 [tech/03](./03-BaseURL归一化.md) 里归一化规则的所有分支——
写预设的过程同时也是在验证那条规则。

## 三、`note` 字段：装"必须提醒但不该写进逻辑"的事

```java
"地址末尾是 /api/v3 不需要再加版本段。文本模型 ID 带日期后缀（如 doubao-seed-2-1-pro-260628），
 请从控制台复制完整 ID。"
```

有些事实**不适合硬编码**：

- 方舟的文本模型 ID 带日期后缀，且会随版本更新变化。如果预设里写死一个，
  三个月后它就是错的；
- 硅基流动的模型列表有几百个，预设只能放几个代表作。

这些信息用一句 `note` 挂出来，前端显示成一行灰字。**提示而不代劳**——
用户知道该去控制台复制，而不是以为"预设里的就是全部"。

## 四、核心问题：这类"事实"一定会过时

### 4.1 已经发生过的事

DeepSeek 的 `deepseek-chat` 在 2026-07 退役了。如果一年前的代码里写死了
`new PresetModel("deepseek-chat", "text")`，用户选中预设、保存、调用，会直接 404。

**模型名、端点路径、甚至厂商的命名风格，都是会变的事实。** 任何写死它们的设计
都在给自己攒技术债。

### 4.2 三条应对

| 做法 | 说明 |
| --- | --- |
| 只放"能力明确、名字稳定"的模型 | 如 `qwen-image-3.0`、`Qwen/Qwen-Image`，不放大版本号可能变的 |
| 会变的写进 `note`，不写进代码 | 方舟的带日期后缀 ID 就是这样处理的 |
| **预设只是脚手架，探测才是长期答案** | 建好渠道后点一次「探测」，用上游真实列表覆盖 |

第三条是关键。预设的价值是"让用户 30 秒跑通第一次"，
而不是"永远正确的模型清单"。真正的清单只能从上游拿。

### 4.3 所以预设里故意不全

比如 Ollama 预设的 `models` 是**空列表**，note 写"先在本机 ollama pull，
再点「拉取上游模型」把已有模型加进来"。

因为本地装了哪些模型完全取决于用户，猜不了也不该猜。

## 五、为什么放代码里，不进数据库

| | 方案 A：`t_channel_preset` 表 | **方案 B：final 类常量（采用）** |
| --- | --- | --- |
| 修改预设 | 后台改数据 | 改一行代码 + 发版 |
| 版本一致 | 不同环境的库内容可能不同 | 代码即配置，环境一致 |
| 多租户定制 | 支持 | 不支持 |
| 迁移成本 | 建表 + 初始化脚本 + 版本管理 | 0 |

**选 B**。理由：

1. 预设**不含任何用户数据**，也没有"每个用户不同"的需求；
2. 它是**静态配置**，改一次要发版完全可以接受（一年可能改两次）；
3. 放数据库就要处理"老用户库里是旧预设怎么办"，那是一整套迁移逻辑，
   而它在代码里就是"重启即生效"。

**判断标准：有没有人需要在不发版的情况下改它？** 没有，就别建表。

## 六、预设与"用户已建渠道"是两回事

预设接口 `GET /v1/channels/presets` 返回的是**模板**，不是渠道。
用户选中预设后：

1. 前端把 `baseUrl` / `apiFormat` / `models` 填进表单；
2. 用户粘上自己的 Key；
3. 点保存 → `POST /v1/channels` → 落库一条**独立的**渠道。

所以预设改了、删了，都不影响已建的渠道。渠道是渠道自身数据的快照，
不是对预设的引用（没有 `preset_key` 外键）。

这是刻意的：如果渠道引用预设，那"改预设"就变成了"改所有人的渠道"，
是一个能把线上配置改坏的开关。

## 七、招聘视角：这段代码体现什么

这段代码本身很简单（一个 `List.of`），但它体现的判断值得说：

1. **识别"会变的事实"**：模型名、端点路径、甚至"哪家厂商更主流"都会变。
   把它放代码里就要接受它会过时，并用 `note` 和"探测"两条通道兜住；
2. **知道边界**：预设负责"零配置跑通第一次"，不负责"永远正确"；
3. **不为了统一而过度设计**：静态配置不建表。这跟"能自动判断的事不问用户"是同一类判断。

## 八、面试考察点

**Q1：预设为什么放代码里而不是数据库？**
A：它是静态配置，不含用户数据，也没有多租户定制需求。放数据库要建表、写初始化脚本、
处理"老用户库里还是旧预设"的迁移，而放代码就是重启生效。判断标准是"有没有人需要
不发版就改它"。

**Q2：模型名会过时，你的设计怎么应对？**
A：三层。①只放名字稳定的模型；②会变的信息（带日期后缀的 ID）写进 `note` 让用户去控制台复制；
③预设只是脚手架——建好渠道后点「探测」用上游真实列表覆盖，那才是长期正确的做法。

**Q3：为什么 Ollama 预设没有预置模型？**
A：本地装了哪些模型完全取决于用户，猜不了也不该猜。note 里引导用户先 `ollama pull`，
再点「探测」把已有模型加进来。

**Q4：预设改了会影响已建的渠道吗？**
A：不会。渠道保存的是自己的快照（baseUrl、模型列表都是复制过来的），
不是对预设的引用。如果引用，改预设就等于改所有人的线上配置。

**Q5：为什么不预置 OpenAI / Claude？**
A：这个项目是国产化改写，预设只放国产厂商与本地自建。接口本身是 OpenAI 兼容的，
用户照样可以手动填 OpenAI 的地址——预设是脚手架，不是白名单。
