# 12 完整链路：一次"新建并验证渠道"的全过程

> 把前 11 篇串起来，看清楚一个请求从进入 Tomcat 到落库、再到回给前端，中间经过哪些层、
> 每层做了什么判断。

---

## 一、先看用户视角的三步

```
① 选预设 → 表单自动填充（纯前端，不请求后端）
② 点「探测」 → POST /v1/channels/probe   （打到上游 API，不落库）
③ 点「保存」 → POST /v1/channels         （加密落库）
④ 之后随时 → POST /v1/channels/{key}/test（再探测一次，结果落库）
```

② 和 ③ 是两条独立链路，都会走"出站探测"或"加密存储"的核心逻辑。
下面分别走一遍。

---

## 二、链路 A：探测（`POST /v1/channels/probe`）

```
ChannelController.probe(request)
  │
  ├─ SecurityUtils.currentUserId()          ← 从 JWT 取 userId，不信任请求体
  │
  ├─ ChannelServiceImpl.probe()
  │    ├─ requireBaseUrl(request.baseUrl())
  │    │     └─ ChannelApiUrls.normalize()  → 校验协议/host，去锚点与末尾斜杠
  │    │        null → BizException(40050)
  │    │
  │    ├─ normalizeFormat(request.apiFormat(), "openai")
  │    │     非 openai/gemini → BizException(400)
  │    │
  │    ├─ 取 Key 二选一：
  │    │    request.apiKey 有值  → 用它
  │    │    channelKey 有值     → requireChannel() 校验归属 → secretCipher.decrypt(cipher)
  │    │    都没有               → BizException(40051)
  │    │
  │    └─ ChannelProbe.probe(baseUrl, apiKey, apiFormat)
  │         ├─ ChannelApiUrls.modelsUrl()   → 拼接 /models 或 /v1/models
  │         ├─ OutboundHosts.allowed()      → allow-private-host=false 时拒绝内网
  │         ├─ RestClient.get().exchange()  ← channelRestClient（5s / 15s）
  │         │    ├─ 401/403 → translate → "鉴权失败…"
  │         │    ├─ 404     → "地址不对…"
  │         │    ├─ 5xx     → "上游服务异常…"
  │         │    └─ 2xx     → readLimited(1MB) → parseModels()
  │         │           ├─ 不是 JSON → "地址返回的不是 JSON…"
  │         │           ├─ 认 data / models / 数组三种外壳
  │         │           ├─ Gemini 剥 "models/" 前缀
  │         │           └─ 去重 + 截断到 500 个
  │         │
  │         └─ Outcome(ok, message, models, latencyMs, httpStatus)
  │
  └─ toProbeVO(outcome, channelId)
       ├─ 查已有模型名 → exists 标记
       └─ ModelCapability.guess(name) → 填初始分类
```

**注意这条链路全程没有数据库写操作**（只有 `requireChannel` 的一次读）。
所以"探测"可以随便点，不会留下任何痕迹。

### 2.1 为什么错误不抛异常

`ChannelProbe` 内部把所有失败都转成 `Outcome(ok=false, message=...)`，
**一个异常都不往外抛**（除了 `BizException` 那种"参数本身不合法"的）。

这样才能做到"探测失败返回 200 + `ok=false`"（D13）。

## 三、链路 B：保存（`POST /v1/channels`）

```
ChannelController.create(request)
  │
  └─ ChannelServiceImpl.create()   @Transactional
       │
       ├─ requireBaseUrl()            → 归一化，非法 40050
       ├─ requireApiKey()             → 空 40051
       ├─ normalizeFormat()           → openai / gemini
       │
       ├─ 组装 Channel
       │    ├─ channelKey = "ch_" + 12 位 hex        ← 业务键，后端生成
       │    ├─ name       = 请求值，空则取 URI host
       │    ├─ apiKeyCipher = secretCipher.encrypt(plain)   ← AES-256-GCM，每次新 IV
       │    ├─ apiKeyHint   = secretCipher.mask(plain)      ← sk-a****wxyz
       │    └─ enabled = 1, sortIndex = 0
       │
       ├─ channelMapper.insert(channel)     ← createdAt/updatedAt 由 MetaObjectHandler 填
       │
       ├─ insertModels(userId, channelId, request.models())
       │    └─ dedupe()  去空名、去重名、保留顺序
       │         └─ 每个模型：capability 没传就 guess()，sortIndex = 下标
       │
       └─ toVO(channel, models)             ← 只含 apiKeyHint，永不含明文
```

### 3.1 事务边界

`@Transactional(rollbackFor = Exception.class)` 包住整个方法。
下面任何一个环节抛异常，渠道和模型一起回滚：

- 模型 `capability` 非法 → 40052（**渠道不会残留**）
- 并发情况下撞唯一键 → `DuplicateKeyException` → 回滚

**这一点值得单独测**：e2e 里有"传非法 capability → 40052"的用例，
但真正验证的是"渠道没被创建"——如果事务没生效，会留下一条空渠道。

### 3.2 加密发生在什么时候

```
明文 Key ──encrypt()──► v1:base64(iv‖ciphertext‖tag) ──► 落库
         └─mask()────► sk-a****wxyz ──────────────────► 落库
```

**明文只在内存里存活一次方法调用**。之后：

- 不在实体上（实体只存 cipher）；
- 不在日志里（代码里没有 `log.info(key)`）；
- 不在响应里（VO 只有 hint）。

## 四、链路 C：测试已存渠道（`POST /v1/channels/{key}/test`）

和链路 A 的差别只有两处：

```
1. Key 来源固定：secretCipher.decrypt(channel.getApiKeyCipher())
2. 探测结束后写库：

   channelMapper.update(null, new LambdaUpdateWrapper<Channel>()
        .eq(Channel::getId, channel.getId())
        .set(Channel::getLastTestAt, now)
        .set(Channel::getLastTestOk, ok ? 1 : 0)
        .set(Channel::getLastTestError, ok ? null : truncate(message))   ← 必须显式 null
        .set(Channel::getUpdatedAt, now));
```

第三行 `.set(..., null)` 是整个方法的关键。写成 `patch.setLastTestError(null)` + `updateById`
的话，`SET last_test_error = NULL` **不会生成**，上一次的失败原因永久留在库里。

后果：用户修好 Key、测试成功，列表上仍然红色显示"鉴权失败"。

### 4.1 为什么没有把这个写操作放进事务

它是**单表单行更新**，且发生在**网络请求之后**。把长耗时的出站请求包进事务，
会让数据库连接被占用十几秒——高并发下直接耗尽连接池。

正确做法就是：先做慢操作（探测），再用一条短更新落结果。

## 五、四条跨模块的"隐形契约"

这一阶段有几处依赖，看不见但很关键：

| 契约 | 谁依赖谁 | 违反的后果 |
| --- | --- | --- |
| `channelKey::modelName` 格式 | 前端 ↔ 后端 ↔ 阶段 6 | 前端存进节点数据的字符串解析不出来 |
| `capability` 四个值逐字一致 | 后端枚举 ↔ 前端类型 | 前端选择器全部失效，且不报错 |
| `apiKey` 只回 hint | 后端 → 前端 | 前端"编辑渠道"无法预填 Key（这是设计，不是缺陷） |
| `lastTestOk` 可为 null | 后端 → 前端 | 用 `if (x)` 判断会把"失败"当"没测过" |

**接口契约不只是字段名和类型，还包括"哪些值可能出现、哪些情况字段会缺失"。**
后者往往才是 bug 的来源。

## 六、这一阶段的四条主线（面试总纲）

如果要在一分钟里讲清阶段 5 做了什么，就讲这四条：

### 6.1 密钥安全：加密 + 脱敏 + 三条不落地纪律

AES-256-GCM（不是 CBC，因为要能发现篡改），每次随机 12 字节 IV（GCM 复用 IV 是灾难），
密文带 `v1:` 前缀（为密钥轮转留通道）。列表接口只回 `apiKeyHint`，
**一行密文都不用解**——这样换密钥时列表不会跟着挂。

### 6.2 出站探测：一个动作回答三个问题

OpenAI 兼容端点没有 ping，`GET /models` 就是最轻的存活证明。
所以"测试连通"和"拉模型"合成一个接口，返回 `ok + models + latency + httpStatus`。

安全上只做一件事：**不回显上游响应体**。因为渠道地址允许指向内网（本地 Ollama），
回显就等于开了个内网读取代理。错误只翻译状态码——401 是 Key 错、404 是地址错，
这两个结论足够用户排查了。

### 6.3 保存语义：三种"空"必须区分

`apiKey` 的 null 和 `""` 都是"保持原值"；`models` 的 null 是"不改"、`[]` 是"清空"。
混淆的后果是"改个名字把 Key 弄丢"和"模型永远删不完"。

模型按名字做**差量**而不是全删全插，因为主键必须稳定（阶段 6 要引用）。
更新走 `LambdaUpdateWrapper.set(..., null)` 而不是 `updateById`，因为后者跳过 null 字段。

### 6.4 地址归一：一条正则覆盖所有厂商

只看末段是不是 `v\d+[a-z]*`：是就补 `/models`，不是就补 `/v1/models`。
这样百炼的 `.../compatible-mode/v1` 不会变成 `/v1/v1/models`，
DeepSeek 的 `https://api.deepseek.com` 也不会漏掉 `/v1`。
不给每家厂商写分支——那覆盖不了自建网关（vLLM、One-API），新厂商还要改代码。

## 七、常见追问与答法

**"你这个 Key 加密，密钥放配置文件里，不还是能被拿到？"**
是。这是应用层加密，比明文好、比 KMS 弱。拿到服务器 + 配置文件就能解。
生产环境应该走 KMS：密钥独立托管、每次解密被审计、可随时吊销。
这里选应用层加密是因为成本几乎为零且明显优于明文，属于"性价比最高的一档"。

**"探测接口允许访问内网，这不是 SSRF 吗？"**
是有限的 SSRF。能验证"某内网端口有没有 OpenAI 兼容的 /models"，
但拿不到响应内容、不跟随重定向、错误只给状态码。要彻底防死只能做域名白名单，
那样本地 Ollama 就没了——这是明示的取舍，配置文件里写了"对外暴露时改成 false"。

**"为什么不用 PATCH 做局部更新？"**
用了 PUT 但语义是局部更新。因为 JSON Merge Patch（RFC 7386）规定 `null` 表示
"删除该字段"，而我们的语义是"不改"，用 PATCH 反而会让人按 RFC 猜错。
真正的单字段操作（启停）单独开了 `PATCH /enabled`。

**"模型为什么不做成 JSON 列？"**
阶段 6 要按 `capability` 查"我有哪些生图模型"，JSON 列做不了带条件的聚合。
而且模型能单独启停、单独挂脚本，有独立生命周期。

**"如果上游模型名重复了怎么办？"**
`dedupe()` 用 `LinkedHashMap.putIfAbsent` 保留第一个。不做的话批量 insert
会撞 `uk_channel_model_name`，抛 `DuplicateKeyException` 变成 500。
用户从探测结果全选、再手动加一个已存在的，这种事一定会发生。
