# 09 归属隔离与业务键

> 对应代码：`ChannelServiceImpl#requireChannel`、`controller/ChannelController.java`

## 一、归属字段只信 token

```java
// controller
public Result<List<ChannelVO>> list() {
    return Result.ok(channelService.list(SecurityUtils.currentUserId()));
}
```

所有方法的第一个参数都是 `userId`，**只来自 `SecurityUtils.currentUserId()`**（解析 JWT）。

DTO 里**没有** `userId` 字段。这是刻意的：一旦 DTO 里出现 `userId`，
迟早会有人写成 `request.userId()`，而前端可以随便改这个值——
那就是一个"改个 id 就能操作别人数据"的洞。

这条约定在阶段 2（画布）就定下了，这里只是继续遵守。

---

## 二、`user_id` 放进 WHERE，而不是查出来再比对

```java
Channel channel = channelMapper.selectOne(new LambdaQueryWrapper<Channel>()
        .eq(Channel::getUserId, userId)
        .eq(Channel::getChannelKey, channelKey));
if (channel == null) {
    throw new BizException(ResultCode.CHANNEL_NOT_FOUND);   // 40450
}
```

对比"查出来再判断"：

```java
// 反面写法
Channel channel = selectByKey(channelKey);
if (channel == null) throw NOT_FOUND;
if (!channel.getUserId().equals(userId)) throw FORBIDDEN;   // 403
```

两种写法的**功能**都对，但安全语义不同：

| | 查出来再比对 | **放进 WHERE（采用）** |
| --- | --- | --- |
| 越权返回 | 403 | **404** |
| 泄露的信息 | "这个 key 存在，只是不是你的" | 什么都没有 |
| 代码路径 | 两条 | 一条 |
| 索引 | 需要按 key 单独查（`uk_channel_user_key` 用不上最左列） | 唯一索引 `(user_id, channel_key)` 完全命中 |

**404 不泄露存在性**，这是安全设计的常规做法：攻击者无法通过枚举
`ch_xxx` 来判断哪些是真实存在的渠道。

顺带的好处是索引：`uk_channel_user_key` 是 `(user_id, channel_key)`，
两个条件都给了，等值命中唯一索引，最多一行。

## 三、业务键的生成与格式

```java
channel.setChannelKey("ch_" + UUID.randomUUID().toString().replace("-", "").substring(0, 12));
```

`ch_` + 12 位 hex = 48 位随机性。

### 3.1 为什么不用数据库主键

1. **JS 精度**：雪花 ID 是 19 位十进制，超过 `Number.MAX_SAFE_INTEGER`（2^53），
   `JSON.parse` 之后会丢精度（末几位变 0）。虽然我们的序列化用字符串能规避，
   但只要有一个地方没注意（比如前端 `Number(id)`），就会串号。
2. **可迁移**：换库、数据迁移时主键会变，但业务键可以保持不变，
   历史数据里的引用不会失效。
3. **可以做"预分配"**：将来如果要支持离线创建（客户端先生成 key，联网后再同步），
   业务键可以客户端生成，主键不行。

### 3.2 为什么是 12 位 hex 而不是完整 UUID

48 位随机性对"单用户几十个渠道"的场景远远足够（生日碰撞概率约 10^-10）。
完整 UUID 是 32 位字符，URL 里太长、日志里太占地方。

### 3.3 为什么不用自增序号（`ch_1`, `ch_2`）

自增序号会泄露规模（"这家只有 3 个用户"），而且多实例部署时无法本地生成。
随机 hex 两个问题都没有。

## 四、唯一索引是最后一道防线

```sql
UNIQUE KEY uk_channel_user_key (user_id, channel_key)
```

即使业务键生成有 bug（比如随机源被固定），数据库也不会让同一用户出现两个相同 key。

`(user_id, channel_key)` 而不是全局唯一 `channel_key`：因为不同用户可以拥有相同的
业务键（理论上），而查询永远是"我的 + 这个 key"。加 `user_id` 既保证语义，
又让唯一索引本身就能服务查询（最左前缀）。

## 五、删除的语义：逻辑删渠道 + 物理删模型

```java
@Transactional(rollbackFor = Exception.class)
public void delete(Long userId, String channelKey) {
    Channel channel = requireChannel(userId, channelKey);
    channelModelMapper.delete(new LambdaQueryWrapper<ChannelModel>()
            .eq(ChannelModel::getChannelId, channel.getId()));
    channelMapper.deleteById(channel.getId());     // @TableLogic → UPDATE deleted=1
}
```

两个动作必须在**同一个事务**里，否则会出现"渠道还在、模型没了"：
前端渲染渠道卡片时显示 0 个模型，但点进去又能看到（如果缓存没刷新）。

### 5.1 为什么渠道要逻辑删除

三个理由：

1. 排查问题需要：用户报"我的渠道没了"，如果物理删了就无从查起（至少能看到曾经有过）；
2. 阶段 6 的生成任务可能引用了 `channel_id`，物理删会产生悬空引用；
3. 将来做回收站是低成本的（行还在，加个恢复接口就行）。

### 5.2 为什么模型要物理删除

见 [tech/06](./06-模型差量保存.md) 第六节：没有独立生命周期，
且逻辑删除会让 `uk_channel_model_name` 挡住同名重建。

**注意这里的不对称是刻意的**，不是漏了。

## 六、越权测试要覆盖全部动词

e2e 脚本里对每个需要鉴权的接口都测了别人的 token：

| 请求 | 期望 |
| --- | --- |
| `GET /channels/{key}` （别人的） | 404 / 40450 |
| `PUT /channels/{key}` | 404 |
| `DELETE /channels/{key}` | 404 |
| `POST /channels/{key}/test` | 404 |
| `GET /models`（别人账号） | 空列表 |
| `GET /channels`（别人账号） | 空列表 |

**为什么每个动词都要测**：越权漏洞最常见的形态是"读接口做了校验，写接口忘了"。
因为读接口通常先写、测试也先测；写接口是后补的，容易漏掉那行 `eq(userId)`。

**为什么 `POST /test` 也要测**：它看起来只是"测试"，但它会**发起一次出站请求**
（用别人的 Key 打别人的端点），并且会把结果写回 `last_test_*`。
不校验归属的话，就是一个"用别人的凭证做任意请求 + 篡改别人数据"的组合漏洞。

## 七、面试考察点

**Q1：越权访问为什么返回 404 而不是 403？**
A：403 等于告诉攻击者"这个资源存在，只是不属于你"，是一个免费的信息泄露。
把 `user_id` 放进 WHERE，查不到就是 404，什么都不泄露。

**Q2：`user_id` 为什么不放在 DTO 里？**
A：一旦 DTO 有 `userId`，就会有人用它，而前端可以随便改这个值。
归属只能来自 token（`SecurityUtils.currentUserId()`）。

**Q3：业务键为什么不用数据库主键？**
A：①雪花 ID 是 19 位，超出 JS 安全整数范围，容易丢精度；②迁移时主键会变，
历史引用失效；③将来若要支持离线创建，业务键可以客户端生成。

**Q4：为什么渠道逻辑删除、模型物理删除？**
A：判断标准是"有没有独立生命周期 + 有没有恢复诉求"。渠道有（排查、将来的回收站、
阶段 6 的引用），模型没有（渠道没了就是悬空数据，逻辑删除还会挡住同名重建）。

**Q5：删除渠道为什么必须放在一个事务里？**
A：否则会出现"渠道还在、模型没了"的中间状态，前端渲染出 0 个模型的渠道卡片，
而且这种状态无法自愈。

**Q6：越权测试为什么要覆盖写接口？**
A：越权漏洞的典型形态是"读校验了、写忘了"。而且 `POST /test` 这种"看起来只是测试"
的接口风险更高——它会用别人的 Key 发出站请求并篡改别人的数据。
