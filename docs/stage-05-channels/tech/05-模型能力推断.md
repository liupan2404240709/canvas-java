# 05 模型能力推断

> 对应代码：`infra/channel/ModelCapability.java`（75 行）

## 一、问题：上游只给名字

`GET /models` 的返回长这样：

```json
{"data": [{"id": "qwen-image-3.0"}, {"id": "qwen-max"}, {"id": "wan2.5-t2v"}]}
```

**没有任何字段告诉你是生图、生视频还是对话。**

但系统的下一步（阶段 6）要按能力筛模型：前端"生图"页签只该看到生图模型。
所以必须有一个分类，而这个分类只能从**名字**推。

## 二、四个枚举值必须与前端逐字一致

```java
public enum ModelCapability {
    IMAGE("image"), VIDEO("video"), TEXT("text"), AUDIO("audio");
```

前端的 `ModelCapability` 类型就是这四个字符串。如果后端返回 `picture`，
前端的选择器会全部失效且**不会报错**（JSON 里多一个字符串值，TypeScript 运行时不管）。

所以 `parse()` 严格校验，非法值返回 null，由调用方抛 40052：

```java
public static ModelCapability parse(String raw) {
    for (ModelCapability capability : values()) {
        if (capability.code.equals(value)) return capability;
    }
    return null;
}
```

**未知值不静默兜底成 text**——那样用户把 `image` 拼错成 `imag`，会得到一堆"对话模型"
却不知道为什么。

---

## 三、关键字表的顺序是这个类的核心

```java
if (VIDEO_KEYS.stream().anyMatch(name::contains)) return VIDEO;
if (AUDIO_KEYS.stream().anyMatch(name::contains)) return AUDIO;
if (IMAGE_KEYS.stream().anyMatch(name::contains)) return IMAGE;
return TEXT;   // 兜底
```

**顺序是 video → audio → image → text**，不能乱。

### 3.1 为什么 video 必须第一个

`seedance`（豆包的视频模型）名字里没有 `image`，但有些视频模型叫
`hunyuan-video-image-to-video`——同时含 `video` 和 `image`。
先判 video 才正确。

### 3.2 为什么 audio 在 image 之前

`qwen-audio-3.0-tts` 含 `audio`；而某些语音模型的封面字段叫 `voice-image`。
更实际的例子：`cosyvoice` 含 `voice`（音频关键字），如果先判 image 且名字里恰好有
`image`（比如 `CosyVoice-image-clone`），就会误判。

### 3.3 兜底是 text 而不是 image

```java
return TEXT;
```

理由：**误判成 text 的代价远小于误判成 image**。

如果 `qwen-max` 被判成 image，用户点"生图"时看到一堆对话模型，会去用，然后报错；
如果反过来，某个生图模型被判成 text，它只是没出现在生图列表里，用户手动改一下就行。

"少一个选项"比"给一个错误选项"体验好。

### 3.4 关键字比前端多补了国产模型

```java
private static final List<String> IMAGE_KEYS = List.of(
    "image", "seedream", "dall-e", "dalle", "imagen", "flux", "sdxl",
    "stable-diffusion", "midjourney", "kolors", "cogview", "wanx", "wan2", "hunyuan-image");
```

前端的 `guessCapability` 里有 `wan` 这个关键字，用来识别视频模型。
但那会把 `wanx-v1`（通义万相 **生图**）误判成视频。

所以这里改用更精确的 `wanx` / `wan2`：`wanx-v1` 命中 image，`wan2.5-t2v` 命中 video
（因为含 `t2v`，且 video 先判）。**同一个业务规则，在不同数据分布下需要不同的关键字**。

## 四、推断只发生在"客户端没传"的时候

```java
private String capabilityOf(String raw, String modelName) {
    if (!StringUtils.hasText(raw)) {
        return ModelCapability.guess(modelName).code();
    }
    ModelCapability capability = ModelCapability.parse(raw);
    if (capability == null) {
        throw new BizException(ResultCode.CHANNEL_CAPABILITY_INVALID);
    }
    return capability.code();
}
```

三个分支，对应三种意图：

| 客户端传了什么 | 含义 | 处理 |
| --- | --- | --- |
| 没传 / 空串 | "你帮我判断" | `guess(modelName)` |
| 合法值 | "我明确指定" | 用它，**不覆盖** |
| 非法值 | 拼错了 / 传了脏数据 | 40052，**不猜测** |

**关键点：用户指定的一定优先于推断。** 因为推断只是 best-effort，
用户在界面上改过之后，保存时传的就是他改的值，不能被"再猜一次"覆盖回去。

## 五、推断发生在两个地方

1. **`probe` 返回候选列表时**：`ModelCandidateVO.capability` 是猜的，
   前端可以直接展示"这个看起来是生图模型"，用户确认即可；
2. **`create` / `update` 落库时**：客户端没传就用同一套规则猜。

两处用**同一个方法**，保证"探测看到的分类"和"保存后的分类"一致。
如果两处各写一套，会出现"探测显示 image，存完变成 text"这种灵异现象。

---

## 六、为什么不在数据库里做"能力字典表"

`capability` 是四值枚举，且**永不扩展**（除非引入 3D 生成之类的新模态）。
建一张 `t_capability` 表，换来的是每次查询多一次 join，收益为零。

用 `VARCHAR(16)` 存字符串而不是 `TINYINT`：可读性优先。
索引里的 `'image'` 比 `1` 好排查得多，16 字节的代价可以忽略。

## 七、面试考察点

**Q1：上游 `/models` 不返回能力分类，你怎么判断？**
A：按模型名做关键字匹配，`guess()` 是 best-effort。推断结果只是"初始值"，
用户可以在界面上改，改完以用户为准。

**Q2：为什么判定顺序是 video → audio → image？**
A：因为一个名字可能同时命中多个关键字。`hunyuan-video-image-to-video` 含 video 和 image，
必须 video 优先；`qwen-audio-3.0-tts` 含 audio 和 tts（都属音频），要在 image 之前判。

**Q3：兜底为什么是 text？**
A：误判成 text 的代价是"少一个选项"，误判成 image 的代价是"给用户一个会报错的选项"。
前者用户能自己改，后者会让他踩坑。

**Q4：用户明确传了 capability，还猜吗？**
A：不猜。`capabilityOf` 里"传了合法值就用它"，只有没传时才推断。
推断是给人省事的默认值，不是覆盖用户意图的机制。

**Q5：非法值为什么报错而不是兜底？**
A：兜底会掩盖前端 bug（拼错 `imag` 得到一堆 text 模型，还没人知道）。报 40052 能立刻发现。
