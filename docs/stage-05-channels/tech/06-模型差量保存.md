# 06 模型列表的差量保存

> 对应代码：`ChannelServiceImpl#replaceModels` / `#dedupe` / `#insertModels`

## 一、要解决的矛盾

"保存渠道配置"这个动作，在界面上是**一次性提交整份表单**（渠道信息 + 所有模型）。
落到数据库时有两条路：

| | 方案 A：全删全插 | **方案 B：按名字 diff（采用）** |
| --- | --- | --- |
| 代码量 | 10 行 | 50 行 |
| 主键 | **每次保存都换** | 稳定 |
| `created_at` | 每次保存被刷新 | 保留首次 |
| 行锁范围 | 该渠道下全部模型行 | 只有变动的行 |
| 库的写入量 | N 删 + N 插 | 只写差异 |

多 40 行代码换四条好处，值。

---

## 二、决定性理由是"主键必须稳定"

阶段 6 的 AI 生成任务要记住"用户上次用的哪个模型"。两种记法：

- 记名字 `Qwen/Qwen-Image`：大小写会变、带 `/`、将来可能改名；
- 记 `t_channel_model.id`：永不变。

如果保存时全删全插，所有历史 id 全部失效，用户打开一张旧画布会发现
"上次用的模型不存在了"——而实际上它还在，只是换了个 id。

这和阶段 2 的画布快照"整份替换"是**不同的判断**：

| | 画布节点 | 渠道模型 |
| --- | --- | --- |
| 数据来源 | 前端本地生成、每次都整份回传 | 用户维护的配置 |
| 主键意义 | `node_key` 由前端生成，本来就不稳定 | 数据库 id 被外部引用 |
| 结论 | 全删全插 | 差量 |

**同一种"整体保存"的动作，因为主键语义不同，实现方式应该不同。**

## 三、实现：三个集合的比对

```java
List<ChannelModel> existing = selectList(byChannelId);
Map<String, ChannelModel> existingByName = ...;

Set<String> keep = new HashSet<>();
int index = 0;
for (ChannelModelDTO dto : dedupe(incoming)) {
    String name = dto.name().trim();
    ChannelModel current = existingByName.get(name);
    if (current == null) {
        insert(newModel(... sortIndex(index++)));
    } else {
        update(byId(current.getId()), capability, script, enabled, sortIndex(index++));
    }
    keep.add(name);
}
// 剩下的就是被用户删掉的
deleteBatchIds(existing.stream().filter(m -> !keep.contains(m.getName())).map(getId).toList());
```

三种情况，一条循环全覆盖：

| 情况 | 判断 | 动作 |
| --- | --- | --- |
| 客户端新增的 | `existingByName` 里没有 | INSERT |
| 两边都有的 | 命中 | UPDATE（以客户端为准） |
| 客户端删掉的 | 循环结束后 `keep` 里没有 | DELETE |

### 3.1 为什么用名字做匹配键

`name` 是渠道内的业务键（`uk_channel_model_name`），也是用户能看到的唯一标识。
客户端拿不到 `id`（`ChannelModelVO` 故意不输出数据库主键），所以只能按名字匹配。

这带来一个副作用：**改名 = 删一条 + 加一条**。在这个业务上是正确的
（改名后对上游来说就是另一个模型，能力分类、脚本都可能不同）。

### 3.2 `sortIndex` 由循环下标决定

```java
index++   // 0, 1, 2, ...
```

客户端传的数组顺序就是展示顺序，后端用下标覆盖 `sort_index`，
**不接受客户端传具体序号**。避免前端算出 `10, 20, 30, 20` 这种有歧义的序列。

## 四、去重：必须先做，否则撞唯一键

```java
private List<ChannelModelDTO> dedupe(List<ChannelModelDTO> incoming) {
    Map<String, ChannelModelDTO> unique = new LinkedHashMap<>();
    for (ChannelModelDTO dto : incoming) {
        if (dto == null || !StringUtils.hasText(dto.name())) continue;
        unique.putIfAbsent(dto.name().trim(), dto);
    }
    return new ArrayList<>(unique.values());
}
```

三件事一起做：

| 问题 | 处理 | 不做会怎样 |
| --- | --- | --- |
| 空名 / 全空格 | `hasText` 跳过 | 库里出现一条 `name=''` 的模型，前端显示空白卡片 |
| 同名重复 | `putIfAbsent` 保留第一个 | 批量 insert 撞 `uk_channel_model_name`，抛 `DuplicateKeyException` → 500 |
| 顺序 | `LinkedHashMap` | 用 `HashMap` 会让模型顺序每次保存都随机变化 |

**"重复名"是必然会发生的**：用户从探测结果里全选，再手动加一个已经存在的，
前端不一定拦得住。后端必须自己兜。

## 五、更新为什么走 `LambdaUpdateWrapper`

```java
channelModelMapper.update(null, new LambdaUpdateWrapper<ChannelModel>()
        .eq(ChannelModel::getId, current.getId())
        .set(ChannelModel::getCapability, capability)
        .set(ChannelModel::getScript, script)          // 可能是 null
        .set(ChannelModel::getEnabled, enabled)
        .set(ChannelModel::getSortIndex, index++)
        .set(ChannelModel::getUpdatedAt, LocalDateTime.now()));
```

**`updateById(entity)` 会跳过 null 字段**（MyBatis-Plus 默认 `FieldStrategy.NOT_NULL`）。
所以 `model.setScript(null)` 根本不会生成 `SET script = NULL`。

结果是：用户清空了某个模型的脚本，保存后刷新，脚本还在。**删不掉。**

`.set(Column, null)` 明确生成 `SET script = NULL`，这才是我们想要的语义。

同一个坑在阶段 4 的 `prompt_source.last_error` 上踩过一次
（同步成功时要把上次的失败原因清空，用 `updateById` 清不掉），
这是第二次，所以代码里写了两处注释。

### 5.1 为什么这里不用 `@TableField(updateStrategy = FieldStrategy.ALWAYS)`

那会让**所有** null 字段都写进 SQL（包括 `created_at = NULL`），
后果是每次更新都把创建时间清空。风险远大于收益。

"哪些字段允许被写成 null"是**业务语义**，应该在具体语句里表达，而不是给实体打全局开关。

## 六、删除用物理删除

```java
channelModelMapper.deleteBatchIds(removeIds);
```

`t_channel_model` 没有 `deleted` 列，这是**故意的**：

- 模型没有独立生命周期，渠道没了它就是悬空数据；
- 逻辑删除会让 `uk_channel_model_name` 挡住"以后重新添加同名模型"
  （唯一键不认 `deleted`，这是 MySQL 的唯一索引行为）；
- 这些"已删除"的行永远不会被读到，纯占空间。

对比阶段 3 的 `t_asset`：素材有逻辑删除，因为**用户可能想恢复**
（删除后才发现删错了，回收站能救回来）。模型没有这种诉求——
你想重新加某个模型，从探测列表里勾一下就有了。

---

## 七、事务边界

```java
@Transactional(rollbackFor = Exception.class)
public ChannelVO update(...) { ... replaceModels(...); ... }
```

整份保存是一个事务。如果"改渠道名"成功但"删模型"失败，
会出现"名字变了但模型还在"的中间状态，用户看到的界面和数据对不上。

注意方法末尾的 `return get(userId, channelKey)` 在**同一个事务里**重新查库：
能读到本事务未提交的修改（READ COMMITTED / REPEATABLE READ 下都是自己的写），
所以返回的一定是保存后的状态。

## 八、面试考察点

**Q1：整体保存模型时，全删全插有什么问题？**
A：主键和 `created_at` 每次都变。外部如果引用了模型 id（阶段 6 的生成任务要记"上次用的模型"），
全部失效。而且全删全插会锁住该渠道下所有模型行，写入量也更大。

**Q2：为什么用名字而不是 id 做匹配？**
A：客户端拿不到数据库主键（VO 故意不输出）。名字是渠道内的业务键（唯一索引），
也是用户在界面上唯一认识的标识。

**Q3：用户清空脚本后保存，为什么脚本没删掉？**
A：`updateById` 默认跳过 null 字段，`setScript(null)` 不会生成 `SET script = NULL`。
必须用 `LambdaUpdateWrapper.set(Column, null)` 显式写 NULL。

**Q4：为什么不给实体统一配 `updateStrategy = ALWAYS`？**
A：那会让所有 null 字段都进 SQL，包括 `created_at`，每次更新都把创建时间清空。
"哪个字段允许写 null"是业务语义，应该在语句里表达。

**Q5：模型为什么物理删除，素材却逻辑删除？**
A：判断标准是"用户有没有恢复的诉求"。素材删错了会想找回（画布里的图片引用会裂），
模型删了重新加一下就有。而且逻辑删除会挡住同名重建（唯一键不认 deleted）。

**Q6：如果两个请求同时保存同一个渠道的模型列表会怎样？**
A：目前没有并发控制，后写的覆盖先写的（last write wins）。因为这是**单用户自己的配置**，
并发场景只有"同一个人开两个标签页"，冲突概率极低且后果可控。
真正需要并发控制的是画布内容（阶段 2 用了 `@Version` 乐观锁），因为那是多人协作的核心资产。
