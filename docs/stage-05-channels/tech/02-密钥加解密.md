# 02 API Key 的加密存储

> 对应代码：`infra/crypto/SecretCipher.java`（146 行）

## 一、要解决的问题

用户的 API Key 是**别人的资产**：拿到就能消耗额度、可能还能读账单。
一旦泄露，损失不在我们系统内部。

三种典型泄露路径，加密只能挡住前两种，第三种要靠"不打印"：

| 泄露路径 | 加密能挡吗 |
| --- | --- |
| 数据库被拖库 / 备份文件流出 | ✅ 拿到的是密文 |
| 运维直接 `SELECT *` 看表 | ✅ 同上 |
| 应用日志把请求体打出来 | ❌ 只能靠代码约束（日志脱敏） |

所以这一节讲的是"落库加密"，同时代码里另有三条纪律：**明文不进日志、不进异常信息、不进响应体**。

## 二、为什么是 AES-GCM 而不是 AES-CBC

| | CBC | **GCM（采用）** |
| --- | --- | --- |
| 机密性 | ✅ | ✅ |
| **完整性** | ❌ 密文被改解出来是乱码，程序察觉不到 | ✅ 自带 128 位认证标签，改一个字节就抛异常 |
| 能否并行 | 否（链式） | 是 |
| 是否需要额外 MAC | 需要（Encrypt-then-MAC） | 不需要 |

CBC 的问题不是"理论上不安全"，而是**它不告诉你数据被动过**。攻击者如果能写数据库
（SQL 注入、内网被渗透），就可以把 A 用户的密文换成 B 用户的，或者翻转某个字节，
系统会拿着一个"看起来正常"的解密结果去调别人的接口。

GCM 是 AEAD（带关联数据的认证加密）：解密时先验标签，不通过直接抛
`AEADBadTagException`。这是"要么完整还原、要么明确失败"，没有中间状态。

**这是选型的核心：对密钥这种高价值数据，能发现篡改比什么都重要。**

## 三、IV 必须每次随机，且随密文一起存

GCM 有一个著名陷阱：**同一密钥下 IV 绝不可复用**。

两条密文（用同一个 IV）异或，密钥流就被消掉了，只剩明文的异或——
如果两条明文有已知结构（API Key 都有 `sk-` 前缀），基本等于泄露。

所以：

```java
byte[] iv = new byte[12];
random.nextBytes(iv);       // SecureRandom，每次新 IV
```

12 字节 = 96 位，是 GCM 的**原生**长度，性能最好（不需要再经过 GHASH 压缩）。
不是 16 字节——16 字节会先被压成 12 字节，白做一次运算。

IV 不需要保密，但必须和密文一起存，否则无法解密。格式：

```
v1:base64( iv[12] || ciphertext || tag[16] )
```

**直接后果：同一把 Key 加密两次，密文不同。** 这不是 bug，e2e 里有断言专门验证这一点。

## 四、密钥从"人写的字符串"派生

```java
public SecretCipher(@Value("${app.crypto.secret}") String secret) {
    if (secret == null || secret.length() < 16) {
        throw new IllegalStateException("app.crypto.secret 长度必须 >= 16");
    }
    this.keySpec = new SecretKeySpec(sha256(secret), "AES");
}
```

### 4.1 为什么不要求 base64 / hex

要求使用者去 `openssl rand -base64 32` 再把结果贴进配置，是一道**无意义的门槛**：
多一步手工操作，就多一批"复制漏了一个字符"的事故。

用 SHA-256 派生：任意长度字符串 → 固定 32 字节（AES-256 的密钥长度）。
SHA-256 的输出是均匀分布的，所以只要输入本身熵够，密钥质量就有保证。

### 4.2 代价：启动时必须校验长度

SHA-256 会把任意输入变成 32 字节，**包括 `"123"`**。如果把 `"123"` 拿去当密钥，
熵只有个位数，暴力破解是分钟级的事。

所以构造器里直接判断 `< 16` 就抛 `IllegalStateException`——**应用起不来**。

这是有意的：宁可在启动时炸掉，也不要静默地用一把弱密钥加密一堆用户的 Key，
然后在半年后才发现。这属于"fail fast"，配置错误就该在最早的时刻暴露。

## 五、`v1:` 前缀是为密钥轮转留的

```java
private static final String PREFIX = "v1:";
```

它看着像装饰，其实是**迁移通道**。两个真实场景：

1. **换算法**（GCM → 后量子算法）：新密文写 `v2:`，老密文还是 `v1:`；
2. **换密钥**（怀疑泄露、员工离职）：新密文用新密钥 + `v2:` 前缀。

有前缀，就可以写一个后台任务：

```
扫描 api_key_cipher LIKE 'v1:%' 的行 → 用旧密钥解 → 用新密钥加 → 写回 'v2:...'
```

过程中新旧并存，服务不中断。没有前缀，就只能全表停服重来（而且要事先知道
"哪一行是什么时候加密的"——那得再加一列）。

### 5.1 现在换密钥会怎样

`decrypt` 里 GCM 验签失败 → 抛 `BizException(SECRET_DECRYPT_FAILED)` → **50010**。

前端收到 50010 的提示是"API Key 解密失败，可能是服务端加密密钥已更换，请重新填写"。
也就是说：**当前实现是"换密钥 = 用户重填"**，还没实现自动轮转。

这是有意的取舍：轮转逻辑要写后台任务 + 双密钥配置 + 进度跟踪，
对一个还没有真实用户的项目是过度设计。留好前缀，将来加得上。

## 六、`mask()`：为什么短 Key 整个打码

```java
private static final int MASK_SAFE_LEN = 8;

public String mask(String plain) {
    if (plain.length() <= MASK_SAFE_LEN) {
        return "****";
    }
    return plain.substring(0, 4) + "****" + plain.substring(len - 4);
}
```

"前 4 后 4"在 Key 足够长时是安全的（暴露 8/40 个字符，剩余熵仍然极高）。
但 **8 个字符的 Key 露出 8 个字符**，等于完全没有脱敏。

所以阈值是 8：`<= 8` 一律打码成 `****`。虽然真实 API Key 都远长于 8，
但"用户把 `test` 填进了 Key 输入框"这种事一定会发生。

## 七、三条"不落地"纪律

加密只解决存储，不解决"密钥在运行时满天飞"。代码里的三条约束：

| 位置 | 做法 |
| --- | --- |
| 日志 | `ChannelServiceImpl` 从不 `log` 明文；`SecretCipher` 失败时只记异常类名 |
| 异常信息 | `decrypt` 的失败信息是固定文案，不带任何密文/明文片段 |
| 响应体 | `ChannelVO` 只有 `apiKeyHint`，实体 `Channel` 不参与序列化 |

最后一条容易被忽略：如果哪天有人图省事直接返回 `Channel` 实体，
`apiKeyCipher` 就跟着出去了。所以 VO 和 Entity 严格分开，
**"哪些字段能出接口"由 VO 决定，不由实体决定**。

## 八、面试考察点

**Q1：为什么用 GCM 不用 CBC？**
A：CBC 只保证机密性，不保证完整性。密文被改一个字节，解密出来是乱码，程序察觉不到；
攻击者能把 A 用户的密文替换成 B 用户的。GCM 是 AEAD，带 128 位认证标签，篡改必然在解密时抛异常。
对 API Key 这种"解错就是拿错误凭证去打别人服务器"的场景，能发现篡改是第一需求。

**Q2：IV 为什么要随机？复用了会怎样？**
A：GCM 下同密钥 + 同 IV 是灾难性的：两条密文异或就消掉密钥流，剩下的只有两条明文的异或。
API Key 都有固定前缀，泄露后基本等于明文。所以每次 `SecureRandom` 生成 12 字节新 IV，
并且 IV 不需要保密、跟密文拼在一起存。

**Q3：为什么 IV 是 12 字节不是 16？**
A：12 字节（96 位）是 GCM 的原生长度，可以直接作为计数器初值。16 字节会先经过一次
GHASH 压缩成 12 字节，白做一次运算，没有安全性收益。

**Q4：密文前缀 `v1:` 有什么用？**
A：密钥轮转的通道。换算法或换密钥后，新密文写 `v2:`，后台任务可以按前缀分批重加密，
新旧并存、服务不中断。没有前缀就只能停服全表重来。

**Q5：为什么把配置字符串 SHA-256 之后当密钥，不直接用它？**
A：AES-256 要求恰好 32 字节，而人写的字符串长度任意。SHA-256 既补齐长度又均匀化输出。
代价是弱输入也会被"变成"32 字节，所以必须额外校验原始长度，短于 16 直接拒绝启动。

**Q6：这套方案和 KMS 比差在哪？**
A：差在"密钥和应用同机"。拿到服务器 + 配置文件就能解出所有 Key。
KMS 把密钥放到独立服务，应用只能"请求解密"且被审计、可随时吊销。
生产环境应该走 KMS；这里用应用层加密是因为它的成本几乎为零、明显优于明文，
是"性价比最高的一档"，而不是"最优解"。
