# 01 表结构设计：两张表为什么这样拆

> 对应代码：`src/main/resources/db/schema.sql`（阶段 5 段）、`entity/Channel.java`、`entity/ChannelModel.java`
> 全库视角另见 [`docs/database.md`](../../database.md) 第八节。

## 一、这一阶段只有两张表

```
t_channel                t_channel_model
┌──────────────────┐     ┌──────────────────────┐
│ id          雪花  │◄────│ channel_id  (逻辑引用)│
│ user_id     归属  │     │ user_id     冗余      │
│ channel_key 业务键│     │ name        上游模型名 │
│ name              │     │ capability  image/... │
│ base_url          │     │ script      可选脚本   │
│ api_key_cipher    │     │ enabled / sort_index  │
│ api_key_hint      │     └──────────────────────┘
│ api_format        │
│ enabled/sort_index│     关联：1 : N
│ last_test_* 三列  │     删除：渠道逻辑删 → 模型物理删
│ deleted           │
└──────────────────┘
```

**没有 `t_channel_preset`**：预设是静态配置，放代码里（`ChannelPresets`），理由见
[design.md D26](../design.md)。

**没有 `t_channel_test_log`**：连通性测试只保留"最近一次"结果，三列平铺在渠道表上。
要不要留历史是另一个问题（真要做，应该是独立的监控表 + 定期聚合，而不是在这里加日志表）。

## 二、`t_channel` 逐字段

| 字段 | 类型 | 为什么是这个类型 |
| --- | --- | --- |
| `id` | `BIGINT` | 雪花 ID，`IdType.ASSIGN_ID`。**不对外暴露** |
| `user_id` | `BIGINT` | 归属，永远取自 token，不看请求体 |
| `channel_key` | `VARCHAR(64)` | 业务键 `ch_` + 12 位 hex。对外就是 `channelId` |
| `name` | `VARCHAR(100)` | 显示名，允许重复（用户可能真的建两个"百炼"，一个测试一个生产） |
| `base_url` | `VARCHAR(512)` | 归一化后写入：去末尾 `/`、去锚点 |
| `api_key_cipher` | `VARCHAR(512)` | **NOT NULL**，`v1:` + base64(iv‖ciphertext‖tag) |
| `api_key_hint` | `VARCHAR(32)` | `sk-a****wxyz`，纯展示，不可还原 |
| `api_format` | `VARCHAR(16)` | `openai` / `gemini`，默认 `openai` |
| `enabled` | `TINYINT` | 0/1。停用后模型不进 `/v1/models` |
| `sort_index` | `INT` | 用户排序，跨渠道 |
| `last_test_at` | `DATETIME` | 最近一次测试时间，NULL = 从未测 |
| `last_test_ok` | `TINYINT` | **1/0/NULL** 三态，NULL 表示"从未测过" |
| `last_test_error` | `VARCHAR(500)` | 已翻译的人话，**不含 Key、不含上游响应体** |
| `created_at` / `updated_at` | `DATETIME` | 容器默认值 + `MetaObjectHandler` 双保险 |
| `deleted` | `TINYINT` | 逻辑删除，`@TableLogic` |

### 2.1 为什么 `last_test_ok` 用 `TINYINT` 而不是 `BOOLEAN`

`BOOLEAN` 在 MySQL 里就是 `TINYINT(1)`，两者物理一样；差别在 Java 侧：
`boolean` 只有 true/false，**表达不了"没测过"**。

"没测过"和"测了但失败"在 UI 上是两种完全不同的状态：
前者应该显示灰色的"未验证"，后者应该显示红色的失败原因。
如果强行用 `boolean`，新建的渠道一上来就显示"失败"，用户会以为坏了。

所以 Java 用 `Integer`（可 null），出参 `ChannelVO.lastTestOk` 用 `Boolean`（可 null），
Jackson 配了 `non_null`，null 时字段**整个不出现**，前端 `if (x === true)` 天然正确。

### 2.2 为什么 `api_key_cipher` 不给默认值

给了默认值（比如 `''`）意味着"允许没有 Key 的渠道存在"。这种渠道：
拉不到模型、生成不了图、列表里永远显示一条配置错误。

用户真正的诉求是"我先填好地址，Key 待会儿再弄"——这由**草稿探测**
（`POST /v1/channels/probe`，不落库）满足，不需要在库里留半成品。

### 2.3 `api_key_hint` 为什么是单独一列而不是每次现算

如果只存密文，列表接口要显示 `sk-a****wxyz` 就得**逐行解密**。后果：

1. 列表变成"依赖密钥可用"的操作。换了 `app.crypto.secret` 之后整页 50010，
   连"看一眼我有哪些渠道"都做不到；
2. 解密要拿密钥，密钥一旦被注入到某个不该有的调用链上，泄露面变大；
3. 100 个渠道 = 100 次 AES 解密 + 100 次可能的异常处理。

多存 32 字节，换来列表接口**一行密文都不用碰**。这是典型的"空间换稳定性"。

## 三、`t_channel_model` 逐字段

| 字段 | 说明 |
| --- | --- |
| `id` | 雪花。**必须稳定**——阶段 6 的生成任务会按 id 记住"上次用的模型" |
| `user_id` | 冗余自渠道，为了"跨渠道按能力查"能走单表（见 D5） |
| `channel_id` | 所属渠道，逻辑引用，**没有物理外键** |
| `name` | 上游模型名，如 `Qwen/Qwen-Image`。渠道内唯一 |
| `capability` | `image` / `video` / `text` / `audio` |
| `script` | `MEDIUMTEXT`，可选自定义请求脚本 |
| `enabled` | 单模型启停（同一渠道里可能有 50 个模型，只想要其中 3 个） |
| `sort_index` | 渠道内顺序 |
| `created_at` / `updated_at` | 同上 |

**注意没有 `deleted`**：模型没有"回收站"语义。渠道删了，模型就是悬空数据；
逻辑删除只会让 `uk_channel_model_name` 挡住"以后重新添加同名模型"。

### 3.1 唯一键为什么是 `(channel_id, name)`

同一个模型名在**不同渠道**里完全可能存在：`Qwen/Qwen-Image` 在硅基流动上有，
在百炼上也有（不同的 id 格式）。所以唯一性范围是渠道内。

**不能**是 `(user_id, name)`：那样用户就不能同时配两个都提供 `gpt-image-1` 的渠道了。

### 3.2 `script` 为什么是 `MEDIUMTEXT` 而不是 `VARCHAR`

前端允许用户粘一段自定义请求脚本（几百到几千字符）。`VARCHAR(4000)` 上限不够，
`TEXT`（64KB）对单条脚本足够，`MEDIUMTEXT`（16MB）留了余量。

这类字段在 InnoDB 里是**行外存储**（溢出页），不占聚簇索引主行，对常规查询影响很小——
这也是"大字段放同一张表"在这类场景可以接受的原因。

## 四、索引设计

| 表 | 索引 | 列 | 服务的 SQL |
| --- | --- | --- | --- |
| `t_channel` | PRIMARY | `id` | 按主键取 |
| | `uk_channel_user_key` | `(user_id, channel_key)` | 按业务键查（**唯一性保证**） |
| | `idx_channel_user_sort` | `(user_id, deleted, sort_index)` | 列表查询 + 排序 |
| `t_channel_model` | PRIMARY | `id` | 按主键取 |
| | `uk_channel_model_name` | `(channel_id, name)` | 唯一性 + 保存时按名字比对 |
| | `idx_channel_model_user_cap` | `(user_id, capability)` | `/v1/models?capability=image` |

### 4.1 为什么列表索引要带 `deleted`

```sql
SELECT * FROM t_channel
WHERE user_id = ? AND deleted = 0
ORDER BY sort_index, id
```

`deleted` 是 `@TableLogic` 自动加的条件，**每条查询都有**。把它放进索引中间
（`user_id` 后、`sort_index` 前），等值条件全部命中前缀，`sort_index` 才能继续用来排序。

如果索引是 `(user_id, sort_index)`，`deleted` 就要回表逐行过滤，`ORDER BY` 也用不上，
MySQL 会走 filesort。

### 4.2 为什么没有 `(base_url)` 索引

没做"同一地址只能建一个渠道"的约束。理由：用户可能真的需要两个渠道指向同一地址、
用两把不同的 Key（一把测试额度、一把生产额度）。做唯一约束会挡住这种正当用法。

去重提示放在前端（能提示、不强制），而不是数据库。

---

## 五、为什么没有物理外键

和全库的约定一致（见 `docs/database.md` 3.9）：

1. **逻辑删除与物理外键冲突**：`t_channel` 是逻辑删除，行还在，外键约束永远满足不了
   "删渠道就删模型"的语义，反而会挡住物理删除模型；
2. 外键会在插入时对父表加共享锁，高并发下容易死锁；
3. 分库分表后外键必然要拆。

代价是"可能产生悬空模型"。靠两点控制：

- 所有写路径都在**同一个事务**里（`@Transactional`）；
- 模型只通过渠道接口写入，没有"单独插入模型"的入口。

## 六、面试考察点

**Q1：为什么模型不放在渠道表的一个 JSON 列里？**
A：三个原因。①阶段 6 要按 `capability` 查"我有哪些生图模型"，这是带条件的聚合，
JSON 列上做不了（函数索引只能挡"包含某值"）；②模型能单独启停、单独挂脚本，有独立生命周期；
③JSON 列更新要整行读写，一个模型改一个字也要重写整个数组。

**Q2：`last_test_ok` 为什么不用 `boolean`？**
A：表达不了"从未测试"。`boolean` 只有真假两态，新建渠道会被误显示成"失败"。
用 `Integer` 的 1/0/NULL 三态，出参转 `Boolean` 并配 `non_null`，null 时字段不出现。

**Q3：`api_key_hint` 是不是冗余？**
A：是冗余，但是**刻意的**。列表页是最高频接口，如果靠解密现算，它就会依赖"密钥可用"；
换密钥后整页报错。多存 32 字节换列表零解密，非常划算。

**Q4：为什么两张表的 `deleted` 不一致？**
A：判断标准是"有没有独立生命周期"。渠道有（用户想清掉、将来可能做回收站），模型没有
（渠道没了它就是悬空数据）。给模型加逻辑删除只会让唯一键挡住同名重建。
这和阶段 4"源逻辑删、提示词物理删"是同一条规则的两次应用。

**Q5：`t_channel_model` 冗余 `user_id` 违反范式吗？**
A：违反第三范式（`user_id` 传递依赖于 `channel_id`）。但"查我的所有生图模型"是跨渠道查询，
没有它就要 join 或先查一批 channel_id 再 IN。一致性由"模型只在渠道保存时写入、
`user_id` 从 token 取"来保证，风险可控。

**Q6：唯一键为什么不是 `(user_id, name)`？**
A：同一模型名可能出现在不同渠道（聚合平台尤其常见）。唯一性范围应该是"渠道内"，
否则用户不能同时配两个都提供同名模型的渠道。
