# 07 局部更新的三种"空"

> 对应代码：`ChannelServiceImpl#update`、`dto/UpdateChannelRequest.java`

## 一、一个 PUT 接口，三种"什么都没传"

`PUT /v1/channels/{channelKey}` 的请求体所有字段都可选。但"不传"在不同的字段上
含义完全不同，这是本阶段**最容易传错**的地方：

| 字段 | 不传 / null | 传空串 `""` | 传空数组 `[]` |
| --- | --- | --- | --- |
| `name` | 不改 | 回落成 Base URL 的主机名 | — |
| `baseUrl` | 不改 | 40050（不合法） | — |
| `apiKey` | **保持原 Key** | **保持原 Key** | — |
| `models` | **不动模型列表** | — | **清空所有模型** |

两处最危险：

1. `apiKey: ""` 如果被理解成"清空"，用户改个名字就会把 Key 弄丢，
   而且**没有任何提示**（保存成功，但下次调用全部 401）；
2. `models: []` 如果被理解成"不改"，用户就永远删不掉最后一个模型
   （前端提交空列表，后端当作没传）。

所以这两条必须同时出现在：DTO 的 Javadoc、接口文档、以及控制台的提示文案里。

## 二、null 直接绑成"不修改"

Jackson 反序列化时，JSON 里没有的字段在 record 里就是 `null`。
所以判断条件就是最简单的：

```java
if (request.name() != null)            { patch.setName(...); changed = true; }
if (request.baseUrl() != null)         { patch.setBaseUrl(...); changed = true; }
if (StringUtils.hasText(request.apiKey())) { ... }
if (request.models() != null)          { replaceModels(...); }
```

注意 `apiKey` 用的是 `hasText` 而不是 `!= null`：
**空串和 null 是同一个意思**（保持原值）。这是刻意的宽容——
前端表单清空后提交的是 `""`，不是 `null`，两者都当"没填"处理。

而 `models` 用 `!= null`：空数组是**有意义的输入**（清空），不能被当成"没填"。

---

## 三、`updateById` 的 null 陷阱

```java
Channel patch = new Channel();
patch.setId(channel.getId());       // 只设置有变的字段
...
channelMapper.updateById(patch);
```

`updateById` 的默认字段策略是 `NOT_NULL`：**值为 null 的字段不生成 SET 子句**。
这正好符合"没传就不改"的语义，所以这里用它是正确的。

陷阱在**反方向**：当你想把某个字段**改成 null** 时，`updateById` 做不到。

本阶段有两处需要写 null：

| 场景 | 写法 |
| --- | --- |
| 测试成功后清空 `last_test_error` | `LambdaUpdateWrapper.set(Column, null)` |
| 换 Key / 换地址后清空 `last_test_ok` | 同上 |
| 用户清空模型的 `script` | 同上 |

```java
// test() 里
LambdaUpdateWrapper<Channel> wrapper = new LambdaUpdateWrapper<Channel>()
        .eq(Channel::getId, channel.getId())
        .set(Channel::getLastTestAt, now)
        .set(Channel::getLastTestOk, outcome.ok() ? 1 : 0)
        // 成功时必须显式写 NULL，否则上一次的失败原因永远留着
        .set(Channel::getLastTestError, outcome.ok() ? null : truncate(outcome.message()))
        .set(Channel::getUpdatedAt, now);
```

**如果不这么写会怎样**：用户第一次测试失败（Key 错），修好 Key 再测成功，
列表上仍然显示红色的"鉴权失败：API Key 不正确"——因为清不掉。
这个 bug 极难自查，因为数据库里 `last_test_ok` 确实是 1，只有 `last_test_error` 是旧值。

## 四、wrapper 更新不会触发自动填充

```java
.set(Channel::getUpdatedAt, LocalDateTime.now())
```

`AuditMetaObjectHandler` 只在**实体经过 MyBatis-Plus 的 update 流程**时才生效
（`updateById(entity)` / `insert(entity)`）。用 `update(null, wrapper)` 时
MetaObject 里没有实体，填充器根本不参与。

所以每一处 wrapper 更新都手动补了 `updatedAt`。三处：`test()`、`setEnabled()`、
`replaceModels()` 里的模型更新。

**这是设计上的取舍**：如果给每个 wrapper 都手写时间，容易漏；
但改成"所有更新都走实体"又做不到（null 场景）。所以选择"在 wrapper 场景显式写"，
并在代码里用注释标出来。

## 五、端点变化要清空测试状态

```java
boolean endpointChanged = false;
if (request.baseUrl() != null) {
    endpointChanged |= !baseUrl.equals(channel.getBaseUrl());
}
if (StringUtils.hasText(request.apiKey())) {
    endpointChanged = true;       // 换 Key 一定算
}
if (request.apiFormat() != null) {
    endpointChanged |= !apiFormat.equals(channel.getApiFormat());
}
if (endpointChanged) {
    clearTestState(channel.getId());
}
```

理由：`last_test_ok = true` 的意思是"**当前这套配置**在某时刻验证通过"。
换了地址或 Key 之后，这个结论自动失效——旧配置通过不代表新配置通过。

不清的话，用户换了一把错误的 Key，列表上仍然显示绿色的"通"，
直到他手动再点一次测试才发现。这是一个**主动误导**。

`clearTestState` 只清 `last_test_ok` 和 `last_test_error`，**保留 `last_test_at`**：
"上次测试发生在什么时候"这个事实仍然成立，只是结论不成立了。

## 六、为什么不用 PATCH 语义

HTTP 语义上，局部更新应该是 `PATCH`，全量替换是 `PUT`。

这里用了 `PUT` 但语义是局部更新，原因：

1. 前端表单提交的是**整份可见配置**（名字、地址、格式、模型列表），
   从客户端视角看就是"保存这一屏"；
2. `PATCH` 在实践中有个歧义：JSON Merge Patch（RFC 7386）规定 `null` 表示"删除该字段"，
   而我们的语义是"不改"。用 `PATCH` 反而会让人误解。
3. 真正的"单字段快捷操作"（启停）单独开了 `PATCH /enabled`。

**HTTP 方法的选择在这里是表达"意图"，而不是严格遵循 RFC。** 但必须在文档里写清楚，
否则前端会按 RFC 猜语义，猜错就是数据丢失。

## 七、面试考察点

**Q1：局部更新接口里，`null` 和空串、空数组分别是什么意思？**
A：`apiKey` 的 null 和 `""` 都是"保持原 Key"；`models` 的 null 是"不动列表"、
`[]` 是"清空"。这几个必须区分清楚，混淆的后果是"改个名字把 Key 弄丢"或"模型永远删不完"。

**Q2：`updateById` 能清空字段吗？**
A：不能。它默认跳过 null 字段（`FieldStrategy.NOT_NULL`），`setXxx(null)` 不会生成
`SET xxx = NULL`。要清空必须用 `LambdaUpdateWrapper.set(Column, null)`。

**Q3：为什么不给实体配 `updateStrategy = ALWAYS` 一劳永逸？**
A：那会让所有 null 字段都进 SQL，包括 `created_at`，每次更新都把创建时间清空。
"哪个字段允许写 null"是业务语义，得在语句里表达。

**Q4：为什么换 Key 要清空测试状态？**
A：`last_test_ok` 的含义是"这套配置验证通过"。换了 Key 或地址，旧结论自动失效。
不清的话用户会看到绿色的"通"，而实际配置是错的——主动误导。

**Q5：wrapper 更新为什么时间字段没自动填？**
A：`MetaObjectHandler` 只在实体经过 update 流程时生效；`update(null, wrapper)` 没有实体，
填充器不参与。所以三处 wrapper 更新都手动写了 `updatedAt`。
