# 08 跨渠道模型视图

> 对应代码：`ChannelServiceImpl#models`、`controller/ModelController.java`

## 一、为什么单独开一个 `/v1/models`

前端的模型下拉框要的是"**我所有能用的生图模型**"，不是一个"先选渠道再选模型"的两级选择。

如果挂在 `/channels/{key}/models` 下，前端要写：

```js
const channels = await api("/channels");            // 1 次
const all = channels.flatMap(c => c.models);         // 拍平
const usable = all.filter(m => m.enabled);           // 过滤停用模型
const final = usable.filter(m => /* 所在渠道也启用 */); // 还要过滤停用渠道
```

三次判断全在客户端，每个客户端都要重写一遍。而在后端，这只是一个
`WHERE user_id=? AND enabled=1 AND capability=?`。

**判断标准：能用一个参数表达的筛选，不要在客户端做。**

## 二、`id` 的格式是硬契约

```java
new ModelOptionVO(
    channel.getChannelKey() + "::" + model.getName(),   // id
    channel.getChannelKey(),                            // channelId
    channel.getName(),                                  // channelName
    model.getName(),                                    // name
    model.getCapability());
```

`id = channelKey::modelName`，**和原前端的约定逐字一致**。

为什么这个格式不能改：

- 前端把它整个存进画布节点数据（`node.data.model`），导出/导入都带着；
- 后端**不在这一层解析校验**——它只是个不透明标识，真正的解析发生在调用生成接口时。

这带来一个隐含要求：`channelKey` 和 `modelName` 里都不能含 `::`。
`channelKey` 是我们自己生成的（`ch_` + hex），天然安全；模型名来自上游，
理论上可能含冒号，但实际所有厂商的模型 id 都是 `[a-zA-Z0-9._/-]`。
真要严谨，应该在 `insertModels` 里拒绝含 `::` 的模型名——留给阶段 6 的调用方去校验。

## 三、必须过滤"停用的渠道"

这是本方法里**最容易漏的一步**：

```java
List<Channel> enabledChannels = channelMapper.selectList(... enabled = 1 ...);
Map<Long, Channel> channelById = ...;
...
return models.stream()
        .filter(model -> channelById.containsKey(model.getChannelId()))   // ← 关键
        .sorted(...)
        .map(...)
        .toList();
```

为什么容易漏：`t_channel_model` 冗余了 `user_id`，所以只查模型表就能拿到"我的所有模型"，
看起来不需要碰渠道表。但模型表**没有**渠道的启用状态。

漏掉的后果很具体：用户停用了整个渠道（比如额度用完了），
下拉框里却还能选到它的模型，一用就 401。

### 3.1 为什么用内存过滤而不是 SQL join

```sql
-- 也可以这么写
SELECT m.* FROM t_channel_model m
JOIN t_channel c ON c.id = m.channel_id AND c.deleted = 0 AND c.enabled = 1
WHERE m.user_id = ? AND m.enabled = 1
```

两种做法都能正确工作。选内存过滤的理由：

1. 渠道数量是个位数到几十个，全查出来的成本可以忽略；
2. 拿到 `Channel` 对象后要取 `channelKey` 和 `name` 拼 `ModelOptionVO`，
   join 还得再查一次或者写 `resultMap`；
3. 少一条手写 SQL 要维护（`ChannelModelMapper` 现在是零 XML）。

**如果渠道数量会到几百个**，就该改成 join + 数据库分页。现在不需要。

## 四、排序：渠道顺序优先，其次渠道内顺序

```java
.sorted(Comparator
        .comparingInt(m -> channelOrder.getOrDefault(m.getChannelId(), Integer.MAX_VALUE))
        .thenComparingInt(m -> m.getSortIndex() == null ? 0 : m.getSortIndex()))
```

`sort_index` 在两张表上的含义不同：

- `t_channel.sort_index`：**渠道之间**的顺序（用户拖拽调整）
- `t_channel_model.sort_index`：**渠道内部**的顺序

所以不能只按模型表的 `sort_index` 排——那样不同渠道的模型会交错在一起
（渠道 A 的第 0 个，渠道 B 的第 0 个，渠道 A 的第 1 个…），前端按渠道分组显示时会乱。

先按"渠道在列表中的位置"，再按"渠道内位置"，得到的才是用户在界面上看到的顺序。

### 4.1 为什么不用 SQL 的 `ORDER BY c.sort_index, m.sort_index`

可以，但那要求 join；既然已经选了内存过滤，排序也跟着在内存做，保持一致性。
几十到几百条数据的排序开销可以忽略（微秒级）。

## 五、能力的过滤参数要严格校验

```java
ModelCapability parsed = null;
if (StringUtils.hasText(capability)) {
    parsed = ModelCapability.parse(capability);
    if (parsed == null) {
        throw new BizException(ResultCode.CHANNEL_CAPABILITY_INVALID);   // 40052
    }
}
String capCode = parsed == null ? null : parsed.code();
```

然后：

```java
.eq(capCode != null, ChannelModel::getCapability, capCode)
```

`eq(condition, column, value)` 是 MyBatis-Plus 的**条件式拼接**：
第一个参数为 false 时这一段完全不生成。用它可以避免写两个方法或者拼 SQL 字符串。

**非法值报 40052 而不是静默返回空列表**：`?capability=picture` 返回 `[]`，
前端会以为"用户没有生图模型"，而实际是参数拼错了。报错能立刻发现。

## 六、空渠道的短路

```java
if (enabledChannels.isEmpty()) {
    return List.of();
}
```

一个刚注册的用户什么渠道都没有。没有这个短路，后面的代码会执行
`.in(ChannelModel::getChannelId, emptyList)` —— MyBatis-Plus 对空集合的处理
是拼成 `IN ()`，部分版本会抛 SQL 语法错误。

**空集合是"批量查询"最常见的边界**，每个 `IN` 之前都该想一下。

## 七、面试考察点

**Q1：为什么要单独开 `/v1/models` 而不是挂在渠道下？**
A：前端要的是"所有可用的生图模型"，是跨渠道的视图。挂在渠道下会让每个客户端都写
"拉全部渠道 → 拍平 → 过滤停用模型 → 过滤停用渠道"这段逻辑，而后端一个参数就能表达。

**Q2：停用渠道后，它的模型为什么还能查到？**
A：因为 `t_channel_model` 只冗余了 `user_id`，不带渠道状态。必须在应用层用
"启用渠道 id 集合"过滤一次。这是冗余字段省掉 join 之后必须付的代价。

**Q3：`sort_index` 在两张表上有什么区别？**
A：渠道表上是渠道之间的顺序，模型表上是渠道内部的顺序。跨渠道展示时必须
"先按渠道位置、再按渠道内位置"排，否则不同渠道的模型会交错。

**Q4：`?capability=picture` 为什么报错而不是返回空？**
A：返回空会让前端以为"用户没有这类模型"，实际是参数拼错。40052 能立刻暴露问题。

**Q5：如果用户有 500 个渠道，这个实现还能用吗？**
A：不能。现在是全量查 + 内存过滤/排序，500 个渠道会有明显开销。那时应该改成
join 查询 + 数据库分页/流式返回。目前的规模（个位数到几十）不需要。
