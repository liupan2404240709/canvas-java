# 阶段 5 设计文档：渠道与模型配置

记录这一阶段真正需要"选一条路"的地方。每条写清楚：**选了什么、否决了什么、为什么、代价是什么**。

---

## 一、数据模型

### D1　渠道与模型分两张表，模型不做 JSON 列

| | 方案 A：`t_channel.models` 存 JSON 数组 | **方案 B：`t_channel_model` 独立表（采用）** |
| --- | --- | --- |
| 按能力查 | 做不了（函数索引只能挡"包含某值"） | `WHERE user_id=? AND capability=?` 直接命中索引 |
| 单模型启停 | 要读出整个 JSON、改一项、写回 | 一行 UPDATE |
| 单模型挂脚本 | JSON 里塞长字符串，整行读写放大 | 独立列 |
| 表数量 | 1 张 | 2 张 |
| 整体保存 | 天然整体 | 需要做差量 |

**选 B**。决定性因素是阶段 6：生成接口要先回答"这个用户有哪些 `image` 能力的模型可选"，
这是一次**带条件的聚合查询**，JSON 列上给不出。何况模型能单独停用、单独挂脚本，
本来就有独立生命周期——有生命周期的东西不该塞进一列。

**代价**：保存时要处理"新增 / 更新 / 删除"三种情况（见 D18）。

### D2　Key 存密文 + 单独一列脱敏提示

| | 方案 A：只存密文，列表时解密再打码 | 方案 B：只存密文，列表显示 "已配置" | **方案 C：密文 + hint 两列（采用）** |
| --- | --- | --- | --- |
| 列表性能 | 每行一次 AES 解密 | 不解密 | 不解密 |
| 用户能否认出是哪把 Key | 能 | **不能** | 能 |
| 解密失败影响面 | 列表整体报错 | 无 | 无 |

**选 C**。列表是全页最高频的接口，让它依赖"密钥可用"是很脆的耦合：一旦换了
`app.crypto.secret`，整页渠道都会 50010，"看一眼列表"这种只读操作也被拖下水。
hint 的代价是 32 字节，换来的是列表接口**一行密文都不用碰**。

### D3　`api_key_cipher` 不允许 NULL、不给默认值

建渠道时 Key 必填。允许"空 Key 渠道"只会让列表里多一行永远调不通的配置，
而用户真正想做的"我先建好、Key 待会儿填"用**草稿探测**（`POST /channels/probe`）就能满足，
不需要先把半成品落库。

### D4　`channel_key` 由后端生成，不用数据库主键

前端的模型值格式是 `channelId::modelName`，这个 `channelId` 会被**存进画布节点数据**、
写进导出文件。用雪花主键有两个问题：

1. 主键是 19 位数字，前端 JS 的 `Number` 精度只有 53 位，容易在 JSON 往返中被截断；
2. 换数据库、数据迁移时主键会变，历史数据里的引用全部失效。

所以生成 `ch_" + 12 位 hex`，和阶段的 `source_key`、`node_key` 是同一套思路：
**对外标识和存储标识分离**。

### D5　`t_channel_model` 冗余 `user_id`

模型已经属于渠道，渠道上有 `user_id`，按范式不该冗余。但"查我所有生图模型"是
**跨渠道**的查询，没有 `user_id` 就只能 `JOIN t_channel` 或先查一批 channel_id 再 `IN`。
冗余一列换来单表查询。

一致性靠"模型只在渠道保存时写入"保证：`user_id` 从 `SecurityUtils` 取，不可能写错。

### D6　`t_channel` 有 `deleted`，`t_channel_model` 没有

渠道有"删除"语义（用户想清掉），也可能将来做回收站，所以逻辑删除。
模型没有独立生命周期——渠道没了，模型就是悬空数据，逻辑删除只会让
`uk_channel_model_name` 挡住"以后重建同名模型"。所以渠道删除时**物理删模型**。

这和阶段 4 的"源逻辑删除、提示词物理删除"是同一个判断标准：
**有没有独立生命周期，决定要不要 `deleted`**。

## 二、密钥安全

### D7　AES-256-GCM，不是 CBC

CBC 只保证机密性：密文被改一个字节，解出来是乱码，**程序无法察觉**。
攻击者可以把"某个字段"翻成另一个值而系统照单全收。
GCM 是 AEAD，自带 128 位认证标签，篡改在解密时抛 `AEADBadTagException`。

对 API Key 这种"解错就是用错误的凭证去打别人服务器"的场景，**能发现篡改**比什么都重要。

### D8　每次加密都换 IV，且 IV 随密文一起存

GCM 对同一密钥复用 IV 是**灾难性**的：两条密文异或就能消掉密钥流，明文关系直接泄露。
所以 IV 必须 `SecureRandom` 生成（12 字节 = 96 位，GCM 原生长度），
并且拼在密文前面一起 base64。

因此**同一把 Key 连续加密两次，密文不同**——这是正确行为，e2e 里有断言。

### D9　密钥从配置字符串 SHA-256 派生，不要求用户生成 base64

`app.crypto.secret` 是人写的一串字符，用 SHA-256 派生成固定 32 字节 AES key。
好处是不逼使用者去 `openssl rand -base64 32`，代价是这串字符本身的熵必须够——
**所以启动时校验长度，`< 16` 直接抛 `IllegalStateException` 拒绝启动**。

宁可启动即失败，也不要用一把弱密钥加密一堆用户的 Key。

### D10　密文带 `v1:` 前缀

不是装饰。将来换算法（GCM → 别的）或换密钥时，靠前缀区分新旧密文，
才能做"旧密文用旧密钥解、后台任务逐步重加密成 v2"的平滑轮转。
没有前缀就只能全表停服重来。

### D11　解密失败统一返回 50010，而不是 500

三种情况（密钥换了、密文被改、格式不对）对用户的处理方式完全一样：**重新填一次 Key**。
所以给一个专门的业务码，前端可以精确提示"请重新填写 API Key"。
如果混进 500，用户只会看到"服务暂时不可用"，然后去重启服务——完全找错方向。

## 三、出站探测

### D12　"测试连通"和"拉取模型"是同一个动作

OpenAI 兼容端点没有 `ping`。最轻的存活证明就是 `GET /models`。
分成两个接口的后果是：用户点"测试连接"通过、再点"拉取模型"失败，非常困惑。

所以 `probe` 一次返回 `ok + models + latencyMs + httpStatus`，一个按钮解决两件事。

### D13　探测失败返回 200 + `ok=false`

"连不上"是业务答案，不是请求错误。返回 500 会让前端每个调用点都写 try/catch，
而且会污染监控的错误率（用户填错 Key 不该算服务端故障）。

### D14　错误信息只翻译状态码，**绝不回显上游响应体**

这是本阶段最重要的安全决策。渠道地址**允许指向内网**（本地 Ollama 是核心场景），
一旦回显响应体，这个接口就变成一个"能读内网 HTTP 响应"的代理。

三种典型状态码的翻译写在 `ChannelProbe#translate`：

| 状态码 | 给人的话 |
| --- | --- |
| 401 / 403 | 鉴权失败：Key 不正确，或该 Key 没有 /models 权限 |
| 404 | 地址不对：这个地址下没有 /models，检查 Base URL 是否多写或漏写 /v1 |
| 429 | 请求过于频繁 |
| 5xx | 上游服务异常，通常与本地配置无关 |

用户看到 "401" 和看到上游的 `{"error":"invalid api key"}`，对排查的帮助差别很小；
但后者一旦被滥用，代价大得多。

### D15　解析失败要报错，不能当"没有模型"

把控制台首页（返回 200 + 一坨 HTML）填进 Base URL 是最常见的配置错误。
如果只是"解析出 0 个模型"就返回成功，用户会以为自己配对了、只是账号没模型。
所以 JSON 解析失败时返回**明确的失败**："地址返回的不是 JSON，请确认填的是接口地址而不是控制台网页地址"。

### D16　Base URL 归一化：只认"最后一段是不是版本号"

各家文档给的根地址五花八门：

| 厂商 | 根地址 | 拉模型打 |
| --- | --- | --- |
| 阿里百炼 | `.../compatible-mode/v1` | `.../models` |
| 火山方舟 | `.../api/v3` | `.../models` |
| 智谱 | `.../api/paas/v4` | `.../models` |
| 硅基流动 | `.../v1` | `.../models` |
| DeepSeek | `https://api.deepseek.com` | `/v1/models` |
| 本地 Ollama | `http://127.0.0.1:11434/v1` | `.../models` |

规则：末段匹配 `v\d+[a-z]*`（`v1` / `v3` / `v4` / `v1beta`）就只补 `/models`，
否则补 `/v1/models`。一条正则覆盖所有厂商，不需要写 switch，也不会拼出 `/v1/v1/models`。

**否决的方案**：让用户在表单里选"我的地址是否含版本号"。把可推导的事实交给用户选，
就是给自己制造配置错误。

### D17　超时比提示词同步更短（5s / 15s vs 5s / 20s）

提示词同步是后台任务，慢一点没人感知；渠道探测是**用户盯着屏幕等**的交互式请求。
让用户在页面上等 20 秒还不知道成不成，体验比"3 秒告诉我连不上"差得多。

所以两个独立的 `RestClient` bean，各有各的超时，不共用默认值
（Spring 的默认值是**没有超时**，一个丢包的域名可以永久占住线程）。

## 四、保存语义

### D18　模型按名字做差量，不全删全插

| | 方案 A：`DELETE` 全部 + 批量 `INSERT` | **方案 B：按名字 diff（采用）** |
| --- | --- | --- |
| 实现复杂度 | 极简 | 需要比对三个集合 |
| 主键稳定性 | 每次保存都换 | 稳定 |
| `created_at` | 每次刷新 | 保留首次 |
| 行锁 | 整个渠道的模型行全锁 | 只锁变动的行 |

**选 B**。决定性理由是**主键要稳定**：阶段 6 的生成任务要记住"用户上次用的哪个模型"，
引用 id 比引用名字可靠（名字里可能有 `/`、大小写会变）。全删全插会让所有引用悬空。

阶段 2 的画布快照用了"全删全插"，那是因为节点本来就是前端生成的临时数据结构、
每次保存都是整份覆盖；这里的模型是**用户维护的配置**，两者语义不同。

### D19　`null` / 空串 / 空数组在 `PUT` 里含义各不相同

| 传什么 | 含义 |
| --- | --- |
| `apiKey` 不传 或 `""` | **保持原 Key 不变** |
| `apiKey` 传新值 | 换 Key，并清空上一次的测试结果 |
| `models` 不传 | **不动模型列表** |
| `models` 传 `[]` | **清空所有模型** |

这两条必须写进接口文档，否则一定会出事：
把 `apiKey: ""` 理解成"清空"，用户改个名字就把 Key 弄丢了；
把 `models: []` 理解成"不改"，用户就永远删不掉最后一个模型。

**换 Key 或换地址时清空 `last_test_ok`**：上一次"测试通过"是针对旧端点/旧 Key 的，
留着会让用户以为新配置已经验证过。

### D20　模型更新走 `LambdaUpdateWrapper`，不走 `updateById`

MyBatis-Plus 的 `updateById` 默认**忽略 null 字段**（`FieldStrategy.NOT_NULL`），
所以 `model.setScript(null)` 根本不会生成 `SET script = NULL`，
用户想把脚本删掉时会发现"删不掉"。

`.set(Column, null)` 则明确生成 `SET script = NULL`。同一个坑在阶段 4 的
`last_error` 上踩过一次，这里是第二次，所以在代码里写了两处注释。

### D21　删除渠道：逻辑删渠道 + 物理删模型，同一个事务

渠道有回收站语义（至少保留数据以便排查），模型没有。两者必须同事务，
否则会出现"渠道还在、模型没了"的中间状态，前端渲染时渠道卡片显示 0 个模型却还能选中。

## 五、接口形态

### D22　单独开 `/v1/models`，不挂在 `/channels` 下

前端的下拉框要的是"我所有能用的生图模型"，不是"先选渠道再选模型"。
挂在 `/channels/{key}/models` 下，前端必须先拉全部渠道、自己拍平、自己过滤停用渠道——
三次判断，而在后端只是一个 `capability` 参数。

这个接口的返回值**可以直接当成"当前真正可用的模型清单"**：停用的渠道、停用的模型都不在内。

### D23　路径用 `channelKey`，不用主键

和 `sourceKey`、`node_key` 一致。附带好处是 `ChannelVO.id` 和模型值的 `channelId` 是同一个字符串，
前端不需要维持"主键 ↔ 业务键"的映射表。

### D24　`PATCH /enabled` 单独一个接口

前端一个开关不该触发"把整份配置（含所有模型）传一遍"。虽然 `PUT` 也能表达，
但传整份就有"覆盖掉别人并发修改"的风险，而且请求体大、日志噪音大。

### D25　越权统一 404，不用 403

`user_id` 直接放进 `WHERE`，查不到就是 404。
返回 403 等于告诉攻击者"这个 key 存在，只是不属于你"，是一个免费的信息泄露。

### D26　预设放代码里，不进数据库

预设是**静态配置**，不含任何用户数据：不会有人改"百炼的地址是什么"，
也不需要运营后台去维护。放 `ChannelPresets` 这个 final 类里，改一行就生效，
不需要写迁移脚本、不需要考虑"老用户库里的旧预设怎么办"。

代价是改预设要发版。对一个学习项目，这个代价远小于"建一张 `t_channel_preset` 表 +
一套同步逻辑"的成本。
