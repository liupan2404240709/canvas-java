# 01 · 表结构设计：为什么拆成 t_file 和 t_asset

## 一、一句话定位

**`t_file` 管"字节"，`t_asset` 管"业务"**。一张表负责磁盘上的内容，另一张负责用户看到的卡片——两者生命周期不一样，混在一起必然互相妥协。

## 二、两张表

```sql
CREATE TABLE t_file
(
    id            BIGINT       NOT NULL,
    user_id       BIGINT       NOT NULL,
    sha256        CHAR(64)     NOT NULL,   -- 内容标识
    storage_key   VARCHAR(160) NOT NULL,   -- 磁盘相对路径
    original_name VARCHAR(255),
    mime_type     VARCHAR(128) NOT NULL,
    extension     VARCHAR(16),
    bytes         BIGINT       NOT NULL,
    width         INT,
    height        INT,
    biz_type      VARCHAR(32)  NOT NULL DEFAULT 'asset',
    created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_file_user_sha (user_id, sha256),
    KEY idx_file_sha (sha256)
);

CREATE TABLE t_asset
(
    id            BIGINT        NOT NULL,
    user_id       BIGINT        NOT NULL,
    kind          VARCHAR(16)   NOT NULL,   -- text / image / video / audio
    title         VARCHAR(200)  NOT NULL,
    cover_url     VARCHAR(1024),
    source        VARCHAR(100),
    note          VARCHAR(500),
    content       MEDIUMTEXT,               -- 只有 text 有值
    file_id       BIGINT,                   -- 只有媒体素材有值
    storage_key   VARCHAR(160),
    width         INT,
    height        INT,
    bytes         BIGINT,
    mime_type     VARCHAR(128),
    duration_ms   INT,
    tags_json     JSON,
    metadata_json JSON,
    created_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at    DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    deleted       TINYINT       NOT NULL DEFAULT 0,
    PRIMARY KEY (id),
    KEY idx_asset_user_created (user_id, deleted, created_at),
    KEY idx_asset_user_kind (user_id, deleted, kind),
    KEY idx_asset_file (file_id)
);
```

## 三、为什么不合成一张表

假设合成一张 `t_asset`，把 `sha256 / storage_key / bytes / mime_type` 全塞进去：

| 问题 | 具体表现 |
| --- | --- |
| 秒传没法做 | 秒传要求"这个用户传过这份内容"就复用，但这张表的语义是"素材"。用户可能上传了文件却**没建素材**（比如上传完发现传错了就关页面），下次再传同一张图，就没法判断"其实已经有了" |
| 删除语义纠缠 | 删素材 ≠ 删文件。合成一张表后，"删掉这条记录"到底删不删磁盘？没有地方表达"还有别人在用这份字节" |
| 上传接口被迫造业务数据 | `POST /files/upload` 必须顺手插一条"素材"，但此刻标题、标签都还不知道 |
| 宽高/字节无处安放 | 画布节点也要传图，它不需要素材，但同样需要宽高 |

拆开之后职责很干净：**`t_file` = 一次上传的产物；`t_asset` = 一次业务建模**。上传接口只写 `t_file`，建素材时再引用它。

## 四、关系是 0..1 : N，不是 1:1

- 文本素材：`file_id = NULL`，没有任何文件；
- 图片素材：`file_id` 指向一条 `t_file`；
- **同一个 `t_file` 可以被多条素材引用**（比如"原图"和"参考图"两条素材用同一个文件），所以素材删了不能直接删文件。

## 五、几个字段的取舍

### 为什么不存 `url`

`url = /api/media/{storageKey}` 是**服务端拼出来的**。一旦把 url 落库：

- 换域名 → 全表 `UPDATE`；
- 挂 CDN → 全表 `UPDATE`；
- 迁对象存储（带签名、有有效期）→ url 根本不是静态值，必须每次现算。

**能推导出来的东西不要存**，这条比"少算一次"重要得多。

### 为什么要冗余 `bytes / mime_type / storage_key` 到 `t_asset`

列表页要显示"320×240 · 1.2KB · image/png"。如果只存 `file_id`，每页 20 条就要 join 一次 `t_file`。
冗余三列换掉一个 join，在这个场景下是划算的——**前提是这几列永不独立变化**（文件内容不可变，所以在建素材时复制一次就永久正确）。

### `filename` 不存扩展名

`extension` 单独一列，`storage_key` 里**不带扩展名**。原因见 [04 内容寻址](./04-SHA256秒传与内容寻址.md)：扩展名进路径会让同一份内容落两份盘。

### `t_file` 没有 `deleted`

文件是技术资源，没有"回收站"语义。素材删除是可恢复的（逻辑删除），文件删除不可恢复——**两种语义不要硬统一**，否则会写出"恢复素材时发现文件早被删了"这种 bug。

## 六、索引

| 索引 | 为什么 |
| --- | --- |
| `uk_file_user_sha (user_id, sha256)` | 秒传查询的等值条件；同时**用唯一约束兜住并发上传** |
| `idx_file_sha (sha256)` | 引用计数要 `COUNT(*) WHERE sha256 = ?`，跨用户查，用不上上面那个组合索引的前缀 |
| `idx_asset_user_created` | 列表默认排序 `user_id = ? AND deleted = 0 ORDER BY created_at DESC`，三列刚好覆盖过滤 + 排序 |
| `idx_asset_user_kind` | 按类型筛选 |
| `idx_asset_file` | `NOT EXISTS (SELECT 1 FROM t_asset WHERE file_id = ?)` 的反连接探测 |

注意 `idx_asset_user_created` 里 `deleted` 放在中间：因为逻辑删除的查询条件一定会带 `deleted = 0`，把它放在 `user_id` 后面才能让索引连续命中；如果放最后，`ORDER BY created_at` 就用不上索引了。

## 七、面试考察点

**Q1：图片为什么不直接存数据库 BLOB？**

四个层面：
1. **备份与迁移**：几百 GB 的 BLOB 让 `mysqldump` / 主从同步变得极慢；
2. **内存**：InnoDB 读 BLOB 会占用 buffer pool，把真正热点的行挤出去；
3. **传输**：走数据库意味着必须过应用服务器，无法用 CDN / Nginx 直接吐文件；
4. **成本**：对象存储每 GB 单价远低于块存储。

什么时候可以存？**小图标（<100KB）且强一致性要求高**（比如必须和业务数据同事务提交）的场景。

**Q2：为什么唯一索引是 `(user_id, sha256)` 而不是 `sha256`？**

如果 `sha256` 全局唯一，就变成"全库共享一条记录"：A 删了自己的文件，B 的文件也没了；而且 B 上传时"命中"的是 A 的记录，`user_id` 该写谁？
把记录做成"每个用户各一条引用"，磁盘字节共享，业务语义才干净。

**Q3：`CHAR(64)` 和 `VARCHAR(64)` 存 sha256 有什么区别？**

sha256 的十六进制表示**恒定 64 字符**，用 `CHAR(64)` 定长，InnoDB 不需要额外存长度字节，行格式更紧凑；而且定长列在做比较时不需要先读长度。`VARCHAR` 适合长度可变的场景，这里不是。

**Q4：`tags_json` 用 JSON 列还是文本列？**

JSON 列能做 `JSON_CONTAINS` / `JSON_TABLE` / 生成列 + 索引；文本列只能 `LIKE '%tag%'`，既慢又会误匹配（`"夜景"` 会匹配到 `"夜景人像"`）。既然 MySQL 8 已经原生支持 JSON，没有理由退化成文本。

## 八、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| `TEXT` 列存不下长文 | 插入报 `Data too long` | `TEXT` 只有 64KB，提示词用 `MEDIUMTEXT`（16MB） |
| 组合索引顺序写反 | 排序用不上索引 | 等值条件列在前，排序列在后 |
| 给 `t_file` 加 `deleted` | 引用计数越算越乱 | 文件没有回收站语义 |
| `cover_url` 长度不够 | base64 dataURL 被截断 | 前端可能直接传 dataURL，`VARCHAR(1024)` 留足余量 |
