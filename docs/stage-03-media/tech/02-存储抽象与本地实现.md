# 02 · 存储抽象与本地实现

## 一、一句话定位

`FileStorage` 只回答一个问题：**字节放哪儿、怎么拿出来**。它不关心用户、秒传、素材——正是这种"无知"让它能换成 MinIO。

## 二、接口

```java
public interface FileStorage {
    String keyOf(String sha256);
    Path createTemp() throws IOException;
    void commit(Path tempFile, String storageKey) throws IOException;
    boolean exists(String storageKey);
    Resource load(String storageKey);
    void delete(String storageKey);
    String publicUrl(String storageKey);
}
```

七个方法，没有一个方法名里出现 `user` / `asset` / `dedup`。**判断抽象是否合格的标准：换实现时，调用方需不需要改代码。** 这里换 MinIO，只改 `LocalFileStorage` → `MinioFileStorage`，`FileServiceImpl` 一行不动。

## 三、本地实现的关键三段

### 1. 内容寻址的 key

```java
@Override
public String keyOf(String sha256) {
    return sha256.substring(0, 2) + "/" + sha256;
}
```

结果：`a3/a3f9c1e2b7...`。

为什么是"前两位"而不是"完整哈希铺平"：

| 方案 | 单目录文件数 | 说明 |
| --- | --- | --- |
| 不分片 `a3f9...` | 全部 | 10 万个文件挤在一个目录，`ls`、备份、同步都会明显变慢（ext4 的 dir_index 也救不了冷目录扫描） |
| 前两位分片 | /256 | 十万文件 ≈ 每目录 400 个，均衡且层级浅 |
| 前两位/前四位两级 | /65536 | 每个目录个位数文件，但目录树巨大，遍历时 inode 开销高 |

两级分片是"千万级文件"的选择，本项目用一级足够。**这是个可以给出量级判断的面试点。**

### 2. 临时文件必须和正式目录同一个文件系统

```java
@Override
public Path createTemp() throws IOException {
    return Files.createTempFile(root.resolve(TEMP_DIR), "upload-", ".part");
}

@Override
public void commit(Path tempFile, String storageKey) throws IOException {
    Path target = resolve(storageKey);
    Files.createDirectories(target.getParent());
    if (Files.exists(target)) {
        Files.deleteIfExists(tempFile);
        return;
    }
    try {
        Files.move(tempFile, target, StandardCopyOption.ATOMIC_MOVE);
    } catch (FileAlreadyExistsException e) {
        Files.deleteIfExists(tempFile);
    }
}
```

如果临时文件建在 `java.io.tmpdir`（Windows 上是 `C:\Users\...\AppData\Local\Temp`），而存储根目录在 `D:\`，那 `Files.move` 会因为跨文件系统抛 `AtomicMoveNotSupportedException`，JVM 退化成"复制 + 删除"——大文件慢一倍，而且复制中途崩溃会留下半截文件。

**放在 `{root}/.tmp/` 就是让它和正式目录同盘。** 这是"原子重命名"能成立的前提。

`ATOMIC_MOVE` 的意义：文件要么在 `.tmp` 里，要么在正式位置，**不存在"写了一半的正式文件"这种中间态**。读者永远看不到半成品。

### 3. 路径越界校验

```java
private Path resolve(String storageKey) {
    if (!StringUtils.hasText(storageKey)) {
        throw new IllegalArgumentException("storageKey 不能为空");
    }
    Path target = root.resolve(storageKey).normalize();
    if (!target.startsWith(root)) {
        throw new IllegalArgumentException("非法存储路径：" + storageKey);
    }
    return target;
}
```

`normalize()` 会消掉 `..`，然后 `startsWith(root)` 判断是否还在根目录里。

现在 `storageKey` 只来自 sha256，理论上不会有 `../`。但它是**从数据库读出来再拼路径**的——数据库里的值可能来自手工 UPDATE、数据迁移脚本、或者某个未来新增的接口。攻击面是"数据"而不是"参数"，同样要防。

```java
root.resolve("../etc/passwd").normalize()          // → root 的父目录/etc/passwd
root.resolve("../../etc/passwd").normalize()       // → 更上层
```
没有这行 `startsWith`，就是一个任意文件读取。

## 四、`publicUrl` 为什么在接口里

```java
@Override
public String publicUrl(String storageKey) {
    return contextPath + properties.getPublicPrefix() + "/" + storageKey;
}
```

因为"怎么访问"本身就是存储实现的差异：

| 实现 | 返回什么 |
| --- | --- |
| 本地 | `/api/media/a3/a3f9...`（静态映射） |
| MinIO（公开桶） | `https://cdn.example.com/bucket/a3/a3f9...` |
| OSS（私有桶） | `https://bucket.oss.../a3/a3f9...?Expires=...&Signature=...`（每次都不一样） |

如果把这个逻辑放在 Service 里，迁对象存储时就得在 Service 里加 `if (是OSS) {...}`。放进接口，Service 永远只调 `fileStorage.publicUrl(key)`。

## 五、`@Value("${server.servlet.context-path:}")` 这个注入

```java
public LocalFileStorage(StorageProperties properties,
                        @Value("${server.servlet.context-path:}") String contextPath) {
```

有人会问：为什么不直接写 `/api`？因为**它已经在 `application.yml` 里配置了**，写死就是两处真相。用 `:` 给个默认空串，这样把 context-path 去掉时不会因为占位符解析失败而启动不了。

## 六、静态资源映射与它的一致性

```java
@Override
public void addResourceHandlers(ResourceHandlerRegistry registry) {
    String location = storageProperties.rootPath().toUri().toString();
    if (!location.endsWith("/")) {
        location = location + "/";
    }
    registry.addResourceHandler(storageProperties.getPublicPrefix() + "/**")
            .addResourceLocations(location)
            .setCachePeriod(86400);
}
```

两个容易错的点：

1. **`location` 必须以 `/` 结尾**。以 `file:/data/uploads`（没有斜杠）注册，Spring 会把它当成"父目录"，实际去找 `/data/uploads` 的**兄弟**路径。
2. **`addResourceHandler` 的路径是 servlet path**，所以写 `/media/**`，不是 `/api/media/**`。Security 的 `PUBLIC_PATHS` 同理。

## 七、面试考察点

**Q1：为什么存储要抽象成接口？直接写工具类不行吗？**

工具类（`FileUtils.save()`）的问题是**调用方要提供参数**（目录、命名规则），换存储时调用方得改。接口把"参数"藏在实现里，调用方只说"存这个 key"，实现自己决定放哪。
一句话：**工具类封装行为，接口封装变化。**

**Q2：`Files.move` 的 `ATOMIC_MOVE` 在什么情况下会失败？**

- 跨文件系统（最常见）；
- 目标文件系统不支持原子重命名（少数网络文件系统、FAT32 的部分操作）；
- Windows 上目标文件已存在（`REPLACE_EXISTING` + `ATOMIC_MOVE` 组合在某些 provider 上会抛异常）。

所以代码里"目标已存在就直接丢弃临时文件"，而不是 `REPLACE_EXISTING` 硬覆盖——内容寻址下目标已存在意味着字节完全相同，覆盖毫无意义。

**Q3：为什么 `delete` 里的 IOException 只记日志不抛？**

因为删除磁盘文件失败**不应该让"删素材"这个业务动作失败**。业务上的目标是"这条记录不再可见"，磁盘空间是次要目标，失败了留给 cleanup 或运维处理。
**分清"业务必须成功"和"尽力而为"**，是写服务端代码的基本判断。

**Q4：`exists()` 有什么用？直接被 `load()` 的 404 取代不行吗？**

`FileSystemResource` 在文件不存在时，`contentLength()` 返回 0 而不抛异常，最后会输出一个 0 字节的 200 响应——比 500 更难排查。所以 `content()` 里先 `exists()` 检查，明确返回"文件内容已丢失"的 404。

## 八、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 临时文件建在系统 temp | 大文件上传明显变慢 | 跨文件系统，原子 move 退化成复制 |
| `addResourceLocations` 忘了结尾 `/` | 静态资源 404 但磁盘上明明有 | Spring 当成父目录 |
| handler 路径写成 `/api/media/**` | 401 或 404 | 那是 context-path，不参与 servlet 匹配 |
| 没有 `normalize()` | 目录里出现奇怪的相对路径文件 | 拼路径时没消掉 `..` |
| 用 UUID 命名 | 秒传永远不命中，磁盘涨得飞快 | 同一份内容每次都是新路径 |
