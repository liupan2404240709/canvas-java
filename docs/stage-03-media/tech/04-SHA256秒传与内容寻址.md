# 04 · SHA-256 秒传与内容寻址

## 一、一句话定位

上传接口先算 `sha256`，然后**查库**、命中就直接返回已有记录——用户传 100MB 视频，服务端一个字节都不用写。

## 二、核心代码

```java
String sha256 = HexFormat.of().formatHex(digest.digest());

// ① 查这个用户有没有传过同一份内容
FileRecord existing = findBySha(userId, sha256);
if (existing != null) {
    return FileVO.of(existing, fileStorage.publicUrl(existing.getStorageKey()), true);   // deduped = true
}

// ② 没命中，落到内容寻址的位置
String storageKey = fileStorage.keyOf(sha256);        // ab/abcdef...
int[] size = MediaTypes.isImage(mime) ? ImageMetadata.readSize(temp) : null;
fileStorage.commit(temp, storageKey);
temp = null;

// ③ 写记录。并发时唯一索引会把后插的那条挡下来
try {
    fileRecordMapper.insert(record);
} catch (DuplicateKeyException e) {
    FileRecord winner = findBySha(userId, sha256);
    if (winner == null) {
        throw e;
    }
    return FileVO.of(winner, fileStorage.publicUrl(winner.getStorageKey()), true);
}
```

## 三、"秒传"到底省了什么

| 环节 | 没命中 | 命中秒传 |
| --- | --- | --- |
| 客户端上传字节 | ✅ 全传 | ✅ **仍然全传**（浏览器不知道服务端有没有） |
| 服务端写临时文件 | ✅ | ✅ 仍然写（要算 sha256 必须读到全部字节） |
| 服务端 move 到正式位置 | ✅ | ❌ 跳过 |
| 服务端 INSERT | ✅ | ❌ 跳过 |
| 磁盘占用 | +N | 0 |

**必须说清楚的一点**：这个"秒传"只省服务端的**存储和数据库写入**，不省带宽。

真正省带宽的秒传要多一次交互：

```
① 客户端先算 sha256（Web Crypto API：crypto.subtle.digest）
② POST /files/exists {sha256} → 服务端答"有/没有"
③ 有 → 直接用；没有 → 才开始传
```

本项目**没有做**这一步，因为：
- 浏览器算 100MB 文件的 sha256 要几百毫秒到几秒，还要占内存；
- 多一次往返，小文件反而更慢；
- 学习项目的重点在"服务端去重与引用计数"，不在省流量。

这是个值得在面试里主动说出来的取舍——**能讲清"我这个方案省了什么、没省什么"，比说"我实现了秒传"有说服力**。

## 四、为什么用内容做路径

```
{root}/9f/9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

| 能力 | 说明 |
| --- | --- |
| 天然去重 | 同一份内容 → 同一个路径 → 无论谁传、传几次，磁盘只有一份 |
| 幂等 | `commit` 发现目标已存在就直接丢弃临时文件，重复调用安全 |
| 完整性 | 存储路径就是期望的哈希，读出来可以校验（本项目没做读校验，但能力在） |
| 缓存友好 | `Cache-Control: max-age=86400` 可以放心给，因为**同一 URL 的字节永不改变** |

UUID 命名做不到上面任何一条：同一张图传两次就是两份字节，缓存也没法长存（URL 变了）。

## 五、三层命中，一层兜底

```
① 应用层查库          findBySha(userId, sha256)
② 磁盘层            commit() 里 Files.exists(target) → 丢弃临时文件
③ 数据库唯一索引      uk_file_user_sha → DuplicateKeyException
```

为什么三处都要有：

- ① 挡住绝大多数重复（正常路径）；
- ② 挡住"别的用户已经传过同一份内容"（跨用户共享磁盘）；
- ③ 挡住"两个请求同时通过①"的竞态。**唯一索引是最后一道，也是唯一不会骗人的一道**——应用层的检查都有 TOCTOU 窗口。

```java
// ① 和 ③ 之间的窗口
T1: select ... where user_id=1 and sha256=X  → null
T2: select ... where user_id=1 and sha256=X  → null
T1: insert → 成功
T2: insert → DuplicateKeyException  ← 靠这个兜住
```

捕获 `DuplicateKeyException` 之后，**不能简单重试 insert**（会一直冲突），要回查一次拿 winner。这个模式在"幂等插入"里非常常见。

## 六、`deduped` 这个字段有没有必要

有必要，它是**给调用方和测试用的可观测信号**：
- 前端可以据此提示"该文件已存在，已为你复用"；
- e2e 脚本靠它断言秒传生效；
- 排查"用户说传了两遍占了两倍空间"时，一眼能看出是真没命中还是统计错了。

严格来说它不属于"文件资源"的属性（同一个文件这次命中、下次不命中），所以只在 `GET /files/{id}` 里恒为 `false`。这在 REST 纯度上有瑕疵，但**可观测性的收益更大**——文档里写清楚即可。

## 七、引用计数：内容寻址的代价

路径共享之后，"删文件"不再是 `Files.delete` 那么简单：

```java
private boolean removeIfOrphaned(FileRecord file) {
    Long remaining = fileRecordMapper.selectCount(new LambdaQueryWrapper<FileRecord>()
            .eq(FileRecord::getSha256, file.getSha256()));
    if (remaining != null && remaining > 0) {
        return false;                    // 别人还在用，磁盘留着
    }
    fileStorage.delete(file.getStorageKey());
    return true;
}
```

少了这一步的典型 bug：A 和 B 都上传了同一张图（磁盘一份），A 删掉自己的文件 → 磁盘文件消失 → **B 的图片变成裂图，而且 B 什么都没做**。

这类 bug 的特点是"复现条件苛刻、现象莫名其妙"，只能靠设计阶段想到。详见 [11 引用计数](./11-引用计数与孤儿清理.md)。

## 八、面试考察点

**Q1：秒传的原理？**

客户端/服务端先算文件的内容摘要（本项目是服务端流式算 SHA-256），用摘要查库；命中就复用已有记录和磁盘文件，跳过落盘和写库。本质是**用内容当主键**，把"是否重复"变成一次等值查询。

追问"能省带宽吗"→ 不能，除非先问后传（见第三节）。

**Q2：为什么是 SHA-256 不是 MD5？**

- MD5 已被证明可以构造碰撞（同哈希不同内容），秒传场景下碰撞意味着"用户 A 的文件被用户 B 的文件顶掉"，是安全问题不是概率问题；
- SHA-256 碰撞在实践中不存在；
- 性能差距在现代 CPU（有 SHA 扩展指令）上已经很小。

**Q3：如果两个用户同时上传同一份内容会怎样？**

三条防线依次生效，最终结果一定是"一条记录、一份磁盘文件"。具体时间线：

```
T1: 查库 → null
T2: 查库 → null
T1: commit → 磁盘落文件
T2: commit → 目标已存在 → 丢弃自己的临时文件
T1: insert → 成功
T2: insert → DuplicateKeyException → 回查 → 返回 T1 的记录（deduped=true）
```

**Q4：文件内容变了但 sha256 没变，可能吗？**

理论上是碰撞，实践上不可能。但**反向**情况很常见：文件内容"看起来一样"，sha256 却不同——因为 PNG 重新编码过、JPEG 改了 EXIF、视频换了封装。这时秒传不会命中，是正确行为。

## 九、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 只查库不查磁盘 | `commit` 覆盖了别人的文件 | 磁盘层也要有 exists 判断 |
| 捕获 `DuplicateKeyException` 后直接重试 | 死循环 | 应该回查 winner |
| 把 sha256 存成 `VARCHAR(64)` 且带空格 | 永远不命中 | 编码/trim 问题，用 `CHAR(64)` 定长 |
| 秒传命中后还去读宽高 | 白读一次 | 直接返回已有记录的宽高 |
| 删文件不查引用计数 | 别人图片裂图 | 见第七节 |
