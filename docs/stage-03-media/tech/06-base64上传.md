# 06 · base64 上传：解析 dataURL

## 一、一句话定位

前端画布里"粘贴截图""canvas.toDataURL()""AI 返回 b64_json"都天然产出 dataURL，所以后端必须能直接吃它——**但 base64 不是给小文件用的万能通道**。

## 二、核心代码

```java
String raw = request.dataUrl().trim();
String declaredMime = "";
String payload = raw;
if (raw.startsWith("data:")) {
    int comma = raw.indexOf(',');
    if (comma < 0) {
        throw new BizException(ResultCode.BAD_REQUEST, "dataURL 格式错误：缺少逗号分隔");
    }
    String header = raw.substring(5, comma);          // image/png;base64
    int semicolon = header.indexOf(';');
    declaredMime = semicolon > 0 ? header.substring(0, semicolon) : header;
    payload = raw.substring(comma + 1);
}

// 先按长度粗算体积，别为一个超大串真的去分配内存
if ((long) payload.length() / 4 * 3 > limit) {
    throw new BizException(ResultCode.FILE_TOO_LARGE, limitMessage(limit, category));
}

// MimeDecoder 会忽略换行/空格等非 base64 字符，比 replaceAll 少一次大数组拷贝
byte[] bytes = Base64.getMimeDecoder().decode(payload);
```

## 三、dataURL 的格式

```
data:[<mediatype>][;base64],<data>
```

| 形式 | 说明 |
| --- | --- |
| `data:image/png;base64,iVBOR...` | 最常见 |
| `data:image/svg+xml;utf8,<svg...>` | **非 base64**，是 URL 编码的文本 |
| `data:,hello` | 省了 MIME，默认 `text/plain;charset=US-ASCII` |
| `iVBOR...`（无前缀） | 裸 base64，本项目兼容 |

解析时只需要两个位置：第一个 `,`（分隔头和体）和头里的 `;`（分隔 MIME 和 `base64` 标记）。

**不要用正则去匹配整个 dataURL**——base64 里可能出现任意字符，`.*` 会贪婪匹配导致截断。用 `indexOf` 是唯一稳的写法。

## 四、为什么先按长度粗算再解码

base64 的膨胀率是 **4/3**（每 3 字节 → 4 个字符）。

```java
if ((long) payload.length() / 4 * 3 > limit) { ... }
```

如果直接 `decode`：

1. 一个 200MB 的 dataURL 字符串已经在内存里了（Jackson 反序列化时就分配了）；
2. `decode` 会再分配 150MB 的 `byte[]`；
3. 全部结束了才发现"超过 20MB 上限"。

而按长度粗算只读一个 `length()` 字段，**0 分配**就能拒绝。

注意这里用 `/4*3` 而不是 `*3/4`：整数运算，先除后乘避免溢出（`length` 是 int，`length * 3` 在 21 亿以上会溢出；转成 long 之后其实两种都对，但先除更保险）。

## 五、为什么用 `MimeDecoder` 而不是 `Decoder`

```java
Base64.getMimeDecoder().decode(payload)     // 忽略所有非 base64 字符
Base64.getDecoder().decode(payload)         // 遇到换行直接抛 IllegalArgumentException
```

dataURL 在跨行传输时可能带换行：

```
data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAABAAAAAQCAYAAAAf8/
9hAAAAKklEQVR42mNk+M9Qz0AEYBxVSF+FAP5FDvcfRYWgLHIrXUFQBWKNEL0A
...
```

用严格要求字母表的 `Decoder` 会抛 `IllegalArgumentException`，用户看到的是"base64 解码失败"——但数据其实是对的。

另一个写法是先 `payload.replaceAll("\\s", "")` 再去解码，这会对一个几十 MB 的字符串**再复制一份**。`MimeDecoder` 是流式忽略，不额外分配。

## 六、请求体膨胀的真实代价

| 原始 | base64 后 | 加上 JSON 转义与 HTTP 头 |
| --- | --- | --- |
| 1MB | 1.33MB | ≈1.34MB |
| 10MB | 13.3MB | ≈13.4MB |
| 100MB | 133MB | **超过默认 max-request-size，直接 413** |

所以文档里要明确写：**base64 只用于小文件（图片），视频必须走 multipart**。

这也是为什么两个入口最后都汇到同一个 `store()`：

```
POST /files/upload  ──┐
                      ├─→ store(userId, InputStream, name, mime, bizType)
POST /files/base64  ──┘
```

base64 入口只做"解码成 `ByteArrayInputStream`"，之后的校验、秒传、落盘、写库完全复用。**新增一个入口不应该新增一条业务路径**，否则两边的规则迟早会漂。

## 七、一个容易忽略的语义

base64 上传和 multipart 上传同一份内容，必须命中同一个秒传：

```
① POST /files/upload  (red.png, 1234 字节)        → fileId = 100，deduped = false
② POST /files/base64  (同样的 1234 字节)          → fileId = 100，deduped = true
```

因为秒传的判据是 `sha256(字节)`，与"从哪个入口进来的"无关。这一条在 e2e 脚本里是显式断言的第 8 项。

如果哪天有人为了"区分来源"在 sha256 之外加了盐（比如拼上 filename），秒传就废了——**摘要必须只对内容计算**。

## 八、面试考察点

**Q1：base64 会让数据变大多少？为什么？**

4/3 ≈ 133%。因为 base64 用 64 个可打印字符（6 bit）表示 8 bit 字节，每 3 字节编码成 4 字符，加上可能的 `=` 填充。

追问"为什么不用 base85/base91"→ 编码效率更高（25%/23% 膨胀），但字符集包含 JSON/URL 需要转义的字符，用在 JSON 里反而要再转义一次，得不偿失。

**Q2：为什么不用 `new String(bytes).getBytes()` 这类方式处理？**

那是"把字节当文本"的经典错误：任何不能解码成合法字符序列的字节都会被替换成 `U+FFFD`，**数据被永久破坏且不报错**。二进制必须走 `byte[]`。

**Q3：如何防止 base64 上传把内存打爆？**

1. 先按 `length/4*3` 估算，超限立刻拒绝（0 分配）；
2. 同时配 `max-request-size`，容器层先挡一道；
3. 大文件强制走 multipart（流式，内存常数）。

## 九、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 用 `Decoder` 解带换行的串 | 解码失败但数据是对的 | 应该用 `MimeDecoder` |
| `replaceAll("\\s","")` | 大文件时内存翻倍 | 多一次全串拷贝 |
| 用正则解析 dataURL | 偶发截断 | base64 字符集与 `.*` 贪婪冲突 |
| 不检查 `,` 是否存在 | `StringIndexOutOfBoundsException` | `indexOf` 返回 -1 |
| 把 base64 也当二进制存文件名 | 文件名是 `data:image/png;...` | 没传 `filename` 时要给默认名 |
| 忽略 `;utf8` 形式的 dataURL | 解码失败 | 那不是 base64，要单独判断 |
