# 11 · 引用计数与孤儿文件清理

## 一、一句话定位

内容寻址带来"磁盘只有一份字节"，代价是**删除变成了引用计数问题**。这个模块负责两件事：删的时候别删到别人在用的，以及把"上传了但没建成素材"的垃圾收掉。

## 二、核心代码

### 1. 删文件（被素材引用就拒绝）

```java
@Override
@Transactional(rollbackFor = Exception.class)
public void delete(Long userId, Long fileId) {
    FileRecord file = requireFile(userId, fileId);

    Long references = assetMapper.selectCount(new LambdaQueryWrapper<Asset>()
            .eq(Asset::getFileId, fileId));
    if (references != null && references > 0) {
        throw new BizException(ResultCode.FILE_IN_USE,
                "文件已被 " + references + " 个素材引用，请先删除对应素材");
    }

    fileRecordMapper.deleteById(fileId);
    removeIfOrphaned(file);
}
```

### 2. 引用计数判定

```java
private boolean removeIfOrphaned(FileRecord file) {
    Long remaining = fileRecordMapper.selectCount(new LambdaQueryWrapper<FileRecord>()
            .eq(FileRecord::getSha256, file.getSha256()));
    if (remaining != null && remaining > 0) {
        return false;                        // 别人还在引用同一份字节
    }
    fileStorage.delete(file.getStorageKey());
    return true;
}
```

注意这里统计的是 **`t_file` 的记录数**，不是 `t_asset`。因为磁盘文件被 `t_file` 引用，`t_asset` 只是间接引用。

### 3. 孤儿查询

```xml
<select id="selectOrphans" resultType="com.infinitecanvas.canvas.entity.FileRecord">
    SELECT f.id, f.user_id, f.sha256, f.storage_key, ...
    FROM t_file f
    WHERE f.user_id = #{userId}
      AND f.created_at &lt; #{before}
      AND NOT EXISTS (SELECT 1 FROM t_asset a WHERE a.file_id = f.id)
    ORDER BY f.id
    LIMIT #{limit}
</select>
```

## 三、为什么"删素材"不能直接删文件

```
用户 A 上传 cat.png（sha = X）           t_file: (id=1, sha=X)
用户 B 上传同一张图（秒传共享磁盘）        t_file: (id=2, sha=X)
                                        磁盘: {root}/ab/X   ← 只有一份

用户 A 删文件 → 如果直接 Files.delete(X)
            → 用户 B 的素材变成裂图，而 B 什么都没做
```

这类 bug 的特点：**复现条件苛刻**（要两个用户传同一张图）、**现象莫名其妙**（B 说"我的图自己没了"）、**日志里什么都没有**（没有任何报错）。

修法就是 `removeIfOrphaned` 里的那次 `COUNT`。

## 四、为什么删素材不删文件

```java
@Override
public void delete(Long userId, Long assetId) {
    requireAsset(userId, assetId);
    // 逻辑删除，磁盘文件不在这里删
    assetMapper.deleteById(assetId);
}
```

素材是逻辑删除（可恢复），文件删除不可恢复。如果删素材就删文件，那"恢复素材"会得到一个**指向不存在文件的记录**——比不恢复更糟。

所以两个删除的语义刻意不一致：

| 对象 | 删除方式 | 磁盘文件 |
| --- | --- | --- |
| `t_asset` | 逻辑删除 | 不动 |
| `t_file` | 物理删除 | 引用计数为 0 时删 |

## 五、孤儿清理：`NOT EXISTS` 那行注释

```java
List<FileRecord> selectOrphans(userId, before, limit);
// 子查询：NOT EXISTS (SELECT 1 FROM t_asset a WHERE a.file_id = f.id)
```

**注意子查询里没有 `a.deleted = 0`。**

这是本模块最容易写错的一行。两难：

| 写法 | 结果 |
| --- | --- |
| `WHERE a.file_id = f.id`（本项目） | 已删除素材也算"引用过" → 删素材不会导致文件被清 → **可恢复**，但删除素材不释放空间 |
| `WHERE a.file_id = f.id AND a.deleted = 0` | 删素材后文件变孤儿 → 清理会删掉字节 → **恢复素材时裂图** |

选第一种，理由：**宁可少回收，不要丢数据**。

于是清理接口的语义被精确限定为：

> 清理的是"**上传了但从未建成素材**"的文件——也就是"写文件成功、写库失败"或"用户传完就关页面"这两种情况产生的垃圾。

这个语义正好覆盖 design.md 里选定的"先写文件后写库"失败模式，闭环了。

## 六、宽限期为什么是必需的

```java
int safeGrace = graceMinutes <= 0 ? 24 * 60 : graceMinutes;
LocalDateTime before = LocalDateTime.now().minusMinutes(safeGrace);
```

如果没有 `created_at < before`：

```
T0:00  用户上传 3 张图（t_file 已插入，还没建素材）
T0:01  前端弹窗还没填完标题
T0:02  定时清理任务跑了一次 → 这 3 个文件被判定为孤儿 → 删了
T0:05  用户点保存 → 建素材时 requireFile 404
```

**"上传"和"建素材"之间有一个人工间隔**，任何清理都必须给它留时间。默认 24 小时是"肯定够用户操作完"的值。

## 七、`@Scheduled` 自动清理可以加，但要保留宽限期

本项目**故意不做自动清理**（README 取舍表里写着"阶段 8 加"）。原因：

1. 误删不可逆；
2. 现在没有 `t_asset` 回收站，没法二次确认；
3. 画布节点里存的 `storageKey` **后端追踪不到**——如果用户把图片用在画布上、但没建素材，清理会不会误删？
   - 不会，因为前端用画布图片时也会先 `POST /files/upload`（产生 `t_file` 记录），而"没有素材引用"确实成立 → **会误删**。

第 3 点是真的风险。所以清理留在**手动触发**，并且必须由用户在"我知道这些是垃圾"的心理前提下点。文档里也写清了。

如果要真正解决，有两种做法：

| 方案 | 说明 |
| --- | --- |
| 画布节点也建 `t_file` 引用 | 保存快照时扫描节点 metadata 里的 storageKey，写一张 `t_file_ref` 表 |
| 引入引用计数字段 | `t_file.ref_count`，所有引用方增减 |

都属于"数据模型要改"，不是这一阶段的范围。

## 八、单批 500 与 `hasMore`

```java
var orphans = fileRecordMapper.selectOrphans(userId, before, CLEANUP_BATCH);   // 500
...
return new CleanupResultVO(orphans.size(), removedFiles, freedBytes,
        orphans.size() == CLEANUP_BATCH);
```

`hasMore = 扫到的正好是 500 条`。这不是精确判断（可能恰好有 500 条），但足够指导调用方"再调一次"。

为什么不一次全清：
- 10 万个文件在一个请求里删完，HTTP 超时、事务过大、用户看不到进度；
- 分批 + `hasMore` 是"可中断、可观测"的删法。

## 九、并发清理的竞态

两个 cleanup 请求同时跑：

```
T1: SELECT orphans → [id=5]
T2: SELECT orphans → [id=5]      ← 还没被 T1 删
T1: DELETE FROM t_file WHERE id=5 → 1 行
T1: COUNT(sha) → 0 → 删磁盘文件
T2: DELETE FROM t_file WHERE id=5 → 0 行（已删）
T2: COUNT(sha) → 0 → 删磁盘文件 ← 文件已不存在，deleteIfExists 静默
```

结果：不会报错，但 `removedFiles` 计数会偏大（其实是 1）。本项目接受这个不精确，因为：

- `deleteIfExists` 是幂等的；
- 计数只是展示用，不影响正确性；
- 真要精确，需要 Redis 分布式锁（阶段 8）。

**能说清"这里在什么条件下不准、为什么不修"比假装没有竞态强。**

## 十、面试考察点

**Q1：内容寻址的存储怎么删文件？**

不能只看"这条记录还在不在"，要看"还有没有别的记录指向同一份内容"——也就是引用计数（或 `COUNT(*) WHERE sha256 = ?`）。
更工程化的做法是在 `t_file` 上加 `ref_count` 列，删除时 `UPDATE ... SET ref_count = ref_count - 1 WHERE ref_count > 0`，靠行锁保证原子，再用 `ref_count = 0` 的返回值决定是否删磁盘。本项目用 `COUNT` 更简单，数据量小够用。

**Q2：为什么用 `NOT EXISTS` 而不是 `LEFT JOIN ... IS NULL`？**

语义上等价，执行计划通常也等价（都是反连接）。`NOT EXISTS` 的优势：
- 语义直接："不存在即孤儿"；
- 不会因为 join 出多行而需要 `DISTINCT`；
- 优化器更容易选 `anti-join`。

**Q3：孤儿文件的宽限期为什么不能是 0？**

因为"上传"和"使用"之间有真实的人工间隔。宽限期 0 会把用户正在编辑的文件删掉。
这是"异步流程的时序假设"——凡是"步骤 A 产生中间状态、步骤 B 消费它"的设计，都要问一句"中间状态能存活多久"。

**Q4：如果磁盘文件被手工删了，数据库怎么知道？**

不知道。`content` 接口会 `fileStorage.exists()` 检查并返回 404，但列表里这条记录还在。
要做到自愈需要定期核对（扫库 vs 扫盘），成本不低。本项目只在读取时兜底，并在 design.md 的"遗留问题"里写明。

## 十一、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 删文件不查引用 | 别人图片裂图 | 忘了内容共享 |
| 子查询带 `and deleted = 0` | 恢复素材后裂图 | 已删素材也算引用 |
| 宽限期为 0 | 用户正在用的文件被清 | 上传与建素材之间有间隔 |
| 一次删全表 | 请求超时 | 没有分批 |
| 计数和实际不符 | 报表不准 | 并发删除的竞态 |
| 认为"没有素材引用"= "没人用" | 误删画布引用的文件 | 画布节点没有 `t_file` 关联 |
