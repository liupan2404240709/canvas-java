# 03 · 流式上传与临时文件

## 一、一句话定位

上传接口的核心不是"把字节搬到硬盘"，而是**在一个循环里同时完成三件事**：算摘要、卡上限、写文件——而且内存占用不随文件大小增长。

## 二、核心代码

```java
private long copyToTemp(InputStream in, Path target, MessageDigest digest, long limit, String category)
        throws IOException {
    byte[] buffer = new byte[BUFFER_SIZE];   // 64KB
    long total = 0;
    try (OutputStream out = Files.newOutputStream(target)) {
        int read;
        while ((read = in.read(buffer)) != -1) {
            total += read;
            if (total > limit) {
                throw new BizException(ResultCode.FILE_TOO_LARGE, limitMessage(limit, category));
            }
            digest.update(buffer, 0, read);
            out.write(buffer, 0, read);
        }
    }
    if (total == 0) {
        throw new BizException(ResultCode.FILE_EMPTY);
    }
    return total;
}
```

调用方：

```java
Path temp = fileStorage.createTemp();
MessageDigest digest = MessageDigest.getInstance("SHA-256");
long bytes = copyToTemp(in, temp, digest, limit, category);
String sha256 = HexFormat.of().formatHex(digest.digest());
```

## 三、为什么不能 `file.getBytes()`

`MultipartFile.getBytes()` 会把整个文件读进 `byte[]`：

| 文件 | 堆内存峰值 | 10 并发 |
| --- | --- | --- |
| 2MB 图片 | 2MB | 20MB（还行） |
| 100MB 视频 | 100MB | **1GB**（默认堆 1/4 物理内存，直接 OOM） |

而且 `getBytes()` 还会在 `MultipartFile` 内部再拷一份（Spring 的 `StandardMultipartFile` 底层是 Tomcat 的 `Part`，会先写临时文件再读），实际峰值可能翻倍。

流式处理的内存占用是**常数**（一个 64KB 数组），代价是多写十行循环。这笔交易在任何有"视频"的系统里都必须做。

## 四、为什么"边写边算"而不是"先写完再算"

```java
// 差一点的写法：先落盘，再重新读一遍算摘要
file.transferTo(temp);
String sha256 = sha256Of(temp);   // 又读一遍磁盘
```

多一次完整磁盘读。对 100MB 视频就是多 100MB I/O，在机械盘上直接多几十毫秒到几百毫秒。

`DigestOutputStream` / 手动 `digest.update()` 都是"顺手算"，0 额外 I/O。

## 五、为什么上限要在应用层再卡一次

系统里其实有三道闸：

```
① Nginx / 反向代理          client_max_body_size     （阶段 8 才加）
② Servlet 容器              spring.servlet.multipart.max-file-size = 128MB
③ 应用层                    app.storage.max-image-size = 20MB 等
```

容器那道闸只知道"总共多大"，不认识 MIME。如果只靠它：

- 一个 30MB 的 PNG 会顺利通过（<128MB），然后在业务层才发现超限——白传 30MB；
- 超限时抛的是 `MaxUploadSizeExceededException`，文案是框架的，用户看不懂。

应用层的 `copyToTemp` 在上传**过程中**就中断（读到 20MB 立刻抛），浏览器侧会看到请求被提前断开。**越早失败越省流量。**

这也是为什么要在 `GlobalExceptionHandler` 里给 `MaxUploadSizeExceededException` 一个专门的 handler：容器那道闸被触发时，至少保证返回的是 `400 / 40021` 和一句中文。

```java
@ExceptionHandler(MaxUploadSizeExceededException.class)
public ResponseEntity<Result<Void>> handleMaxUploadSize(MaxUploadSizeExceededException e) {
    log.warn("上传超过容器上限: {}", e.getMessage());
    return build(ResultCode.FILE_TOO_LARGE, "上传文件过大，请压缩后重试");
}
```

## 六、临时文件的生命周期

```
createTemp()                    → {root}/.tmp/upload-8374921.part
copyToTemp()                    → 写入完成
[命中秒传]                       → finally 删掉 .part
[未命中] commit()               → move 到 {root}/ab/abcdef
                               → temp 置 null，finally 不再删
[任何异常]                       → finally 删掉 .part
```

```java
} finally {
    deleteTempQuietly(temp);
}
```

关键点：**`temp` 是局部变量，可以在 commit 成功后置 null**。这是 Java 里表达"所有权已转移"的一种土办法（C++ 的 `std::move` 语义）。

如果不置 null，`finally` 会去删一个已经被 move 走的路径——`deleteIfExists` 不会报错，但如果**恰好**有另一个请求在同一个 sha256 上 commit，就会删掉别人的正式文件。这类 bug 极难复现。

## 七、`MultipartFile` 的两种落盘模式

Spring 解析 multipart 时有一个阈值（Tomcat 默认 `file-size-threshold = 0`）：

| 文件大小 | Tomcat 怎么做 |
| --- | --- |
| 小于阈值 | 直接放内存（`byte[]`） |
| 大于阈值 | 写到 `java.io.tmpdir` 下的临时文件，`MultipartFile` 只是它的句柄 |

所以 `file.getInputStream()` 拿到的可能是内存流，也可能是一个文件流——**代码不需要关心，但要知道它背后发生了什么**。这也解释了为什么"超限时用户已经传完了"：Tomcat 是先收完再让 Spring 判断的（除非超过 `max-request-size`，那时会在读取过程中就中断）。

## 八、面试考察点

**Q1：上传大文件怎么避免 OOM？**

三条：
1. `InputStream` + 固定大小 `byte[]` 循环拷贝，不一次性 `readAllBytes()`；
2. 上传用 `transferTo()` / `Files.copy()`（零拷贝，走内核缓冲区）；
3. 超过阈值让容器落临时文件，不要自己缓存在内存里等校验。

**Q2：`MessageDigest` 是线程安全的吗？**

**不是**。它内部有状态（`engineUpdate` 累加），必须每个请求 `MessageDigest.getInstance("SHA-256")` 新建一个。
不能写成 `@Component` 里的单例字段——多个请求同时 `update`，算出来的摘要会是垃圾，而且**不会报错**，只会让秒传莫名失效、文件内容对不上。

**Q3：为什么用 `HexFormat.of().formatHex()` 而不是自己写循环？**

JDK 17 内置（`java.util.HexFormat`），比自己写 `String.format("%02x")` 快一个量级，且不会写错位。项目规则里"通用能力用成熟实现"说的就是这种。

**Q4：`try-with-resources` 里抛 `BizException` 会怎样？**

`BizException` 是 `RuntimeException`，`try-with-resources` 会先关闭 `OutputStream`（flush 缓冲），再把异常抛出去——所以"写到一半超限"时，已经写进去的字节会被 flush 到磁盘，然后 `finally` 把整个临时文件删掉。**顺序是对的**：先关流再删文件。

## 九、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 复用 `MessageDigest` | 摘要随机错，秒传不稳定 | 非线程安全 |
| `readAllBytes()` | 大文件 OOM | 内存峰值 = 文件大小 |
| 忘了 finally 删临时文件 | `.tmp` 目录越来越大 | 异常路径漏了 |
| commit 后没把 temp 置 null | 偶发删掉别人的正式文件 | 路径已指向正式位置 |
| 缓冲开成 1KB | 100MB 视频要循环 10 万次 | 64KB 是常见折中（能覆盖 SSD 的块大小） |
