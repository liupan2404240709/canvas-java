# 07 · 图片宽高：只读文件头

## 一、一句话定位

要拿到一张图的宽高，**不需要解码整张图**。`ImageReader` 只解析文件头里的几行字节，内存是常数。

## 二、核心代码

```java
public static int[] readSize(Path file) {
    try (ImageInputStream input = ImageIO.createImageInputStream(file.toFile())) {
        if (input == null) {
            return null;
        }
        Iterator<ImageReader> readers = ImageIO.getImageReaders(input);
        if (!readers.hasNext()) {
            return null;
        }
        ImageReader reader = readers.next();
        try {
            reader.setInput(input, true, true);       // 只读元数据，不解码像素
            return new int[]{reader.getWidth(0), reader.getHeight(0)};
        } finally {
            reader.dispose();
        }
    } catch (IOException | IllegalStateException e) {
        log.warn("读取图片宽高失败 file={}", file.getFileName(), e);
        return null;
    }
}
```

## 三、两种写法的内存差距

```java
// 差：整图解码
BufferedImage image = ImageIO.read(file.toFile());
int width = image.getWidth();
```

| 图片 | `ImageIO.read` 内存峰值 | `ImageReader` 内存 |
| --- | --- | --- |
| 1000×1000 PNG | ≈4MB（`TYPE_INT_ARGB` 每像素 4 字节） | 常数（几 KB） |
| 4000×3000 JPEG | ≈48MB | 常数 |
| 8000×8000 PNG | **≈256MB** | 常数 |

上传接口并发 5 个 8000×8000 的图，`ImageIO.read` 就是 1.2GB —— 默认堆（物理内存 1/4）直接 OOM。

而且我们只要两个 `int`。为两个 int 解码 6400 万像素，是典型的**用大炮打蚊子还把自己崩了**。

`reader.setInput(input, true, true)` 的两个 `true` 分别是：
- `seekForwardOnly = true`：允许只顺序读一次（更省内存，但之后不能回退）；
- `ignoreMetadata = true`：不解析 EXIF/XMP 等元数据——注意宽高不在"元数据"里，在图像头（IHDR/SOF）里，所以这个设置不影响 `getWidth()`。

## 四、为什么返回 `int[]` 而不是对象

`int[2]` 不值得为它建一个类：

```java
int[] size = ImageMetadata.readSize(temp);
record.setWidth(size == null ? null : size[0]);
record.setHeight(size == null ? null : size[1]);
```

如果以后要存更多信息（色彩空间、DPI），再换成一个 `record ImageInfo(int width, int height, ...)`。**现在不预留**，因为"预留的扩展点"十有八九是错的。

## 五、失败时为什么返回 `null` 而不是抛异常

三种失败都是"可以继续"的：

| 失败原因 | 结果 |
| --- | --- |
| 文件损坏（头都不完整） | 宽高为空，但文件仍可下载 |
| 格式不被 ImageIO 支持（**WebP**） | 同上 |
| `createImageInputStream` 返回 null | 同上 |

如果抛异常，用户传一张"ImageIO 认不出的合法图片"就完全传不上来了 —— 而那张图本来是可以存、可以下载、可以用的，只是列表里不显示尺寸。

**"缺一个非关键字段"不该等于"整个请求失败"**。

代价是前端要处理 `width` 为 null 的情况。前端本来就该处理（`ImageAsset.width` 在类型里是 required，但服务端出参用了 `non_null`，缺字段等价于 undefined）——这在 api.md 里写明了。

### 已知缺口：WebP

JDK 自带 ImageIO 支持 JPEG / PNG / GIF / BMP / WBMP，**不支持 WebP**（虽然白名单里放了 `image/webp`，因为浏览器能显示它）。

三个补法：

| 方案 | 成本 | 说明 |
| --- | --- | --- |
| 引 TwelveMonkeys `imageio-webp` | 一个依赖 | 最干净 |
| 手解 WebP 头（RIFF + VP8/VP8L/VP8X 分支） | 中 | 三种子格式的宽高位置都不一样，容易写错 |
| 让前端算好传上来 | 低 | 但客户端可伪造，且 base64 入口要另写 |

本项目选"暂时没有"（记在 README 的取舍表里）。**知道缺什么、以及补起来要多少成本，比假装完整更重要。**

## 六、这个宽高从哪来、到哪去

```
上传时（临时文件还在）
    ↓  ImageMetadata.readSize
t_file.width / height
    ↓  建素材时复制
t_asset.width / height
    ↓  出参
AssetVO.data.width / height   →  前端卡片"1920×1080"
FileVO.width / height         →  画布图片节点按原始比例布局
```

只在**上传那一刻**算一次，之后所有地方都读数据库。这就是把 `width/height` 放进 `t_file` 而不是"每次渲染现算"的原因——一张画布上 50 个图片节点，每次打开都解码 50 个头，纯属浪费。

## 七、面试考察点

**Q1：怎么在不 OOM 的前提下获取图片尺寸？**

`ImageIO.createImageInputStream` + `ImageReader.getWidth/getHeight`，只解析文件头。要点是**不要把整个图解码成 BufferedImage**。

**Q2：`ImageIO.read` 返回的 `BufferedImage` 占多少内存？**

`width * height * 每像素字节数`。默认 `TYPE_INT_ARGB` 是 4 字节/像素，所以 4000×3000 ≈ 48MB。
这一点常被忽略：很多人以为"文件 2MB，内存也就 2MB"，实际上压缩格式和解码后的位图相差 20 倍以上。

**Q3：`ImageReader` 用完为什么要 `dispose()`？**

`ImageReader` 内部持有 native 资源（libjpeg 的解码器实例、文件句柄）。不 dispose 会泄漏，在高并发上传下表现为"文件句柄耗尽"或堆外内存持续增长。这也是为什么用 `try/finally`。

**Q4：`seekForwardOnly` 为什么设为 true？**

因为只读一次头，不需要回退。设为 true 允许实现选择更省内存的流式解析（不必把整个文件映射到内存）。**只有当你需要多次 seek 时才设 false。**

## 八、常见坑

| 坑 | 现象 | 原因 |
| --- | --- | --- |
| 用 `ImageIO.read` 拿尺寸 | 大图上传 OOM | 整图解码 |
| 忘了 `reader.dispose()` | 句柄泄漏 | native 资源 |
| 对 WebP 期待有宽高 | 永远 null | JDK 不支持 |
| 读取失败就抛异常 | 合法但"奇怪"的图传不上来 | 非关键字段不该阻断主流程 |
| 在 `content` 接口里现算宽高 | 每次下载都解码 | 应该在上传时算好存库 |
