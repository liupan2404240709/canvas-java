# 02 · 统一响应契约

> 对应源码：`common/api/Result.java`、`common/api/ResultCode.java`、`common/api/PageResult.java`

## 一、一句话定位

这三个类定义了一件事：**所有接口返回给前端的数据，长什么样**。

接口是怎么对的齐的、错误码怎么分段、为什么用 `record` 而不是 Lombok——这些细节决定了后面 9 个阶段的接口风格会不会走样。

## 二、完整代码

### Result.java

```java
public record Result<T>(int code, String message, T data, String traceId) {

    public static <T> Result<T> ok(T data) {
        return new Result<>(ResultCode.SUCCESS.getCode(), ResultCode.SUCCESS.getMessage(), data, TraceId.current());
    }

    public static Result<Void> ok() {
        return ok(null);
    }

    public static <T> Result<T> fail(ResultCode resultCode) {
        return new Result<>(resultCode.getCode(), resultCode.getMessage(), null, TraceId.current());
    }

    public static <T> Result<T> fail(ResultCode resultCode, String message) {
        return new Result<>(resultCode.getCode(), message, null, TraceId.current());
    }
}
```

### ResultCode.java


## 三、逐段拆解

### 3.1 为什么是四个字段

```json
{
  "code": 0,
  "message": "success",
  "data": { "app": "canvas-server", "status": "UP" },
  "traceId": "cec6d4180e3f4878a247765580f4febc"
}
```

| 字段 | 谁用 | 设计意图 |
| --- | --- | --- |
| `code` | 前端 | 唯一判断依据。`0` 成功，非 0 都是失败。前端只写一次 `if (res.code === 0)` |
| `message` | 前端 | 可以直接 `message.error(res.message)` 弹给用户，不用前端再维护一套错误文案 |
| `data` | 前端 | 业务数据放在固定的字段里，成功失败结构一致，前端不用做「有时候有 data 有时候没有」的判断 |
| `traceId` | 用户 + 后端 | **这是把排障成本降到最低的关键**。用户报错时说「接口错了」，前端把 traceId 弹出来截图，后端拿它去日志里 grep，一次命中 |

**为什么失败时 `data` 是 `null` 而不是省略这个字段？**

`application.yml` 里配了 `default-property-inclusion: non_null`，所以实际上 `data: null` **不会出现在 JSON 里**：

```json
{"code": 40400, "message": "接口不存在: /v1/not-exist", "traceId": "75cb..."}
```

这是刻意的：减少无用字段。代价是 TypeScript 里 `data` 要声明成可选（`data?: T`）。

### 3.2 `record` 还是 Lombok

源码用的是 Java 17 的 `record`。对比一下：

| 维度 | `record`（当前） | `@Data` + 普通类 |
| --- | --- | --- |
| 代码量 | 1 行 | 类 + 5 个字段 + 4 个注解 |
| 不可变性 | **天生 final，字段不可改** | 默认可变，谁都能 `setCode(200)` |
| equals / hashCode / toString | 自动，且符合值语义 | Lombok 生成，也是值语义 |
| Jackson 反序列化 | 支持（Jackson 2.12+ 原生支持 record） | 支持 |
| 继承 | **不能继承、不能被继承** | 可以 |
| 适用场景 | DTO / VO / 响应体这类**纯数据载体** | 需要 setter、需要继承、需要可变状态的实体 |

**本项目的取舍**：`Result`、`PageResult`、`HealthVO` 全部用 `record`，因为它们是纯数据载体，响应发出去就不该再改。**MyBatis 实体不用 `record`**——MyBatis 需要通过无参构造 + setter 反射赋值，`record` 只有全参构造，需要额外配置才支持，不划算。

面试如果问「`record` 和 Lombok 怎么选」，就答：**纯数据传输用 `record`，需要可变或需要被 ORM 反射赋值的用 Lombok**。

### 3.3 `Result.<Void>fail(...)` 里的 `<Void>` 是什么

`GlobalExceptionHandler` 里有这么一行：

```java
return ResponseEntity.status(resultCode.getHttpStatus())
        .body(Result.<Void>fail(resultCode, message));
```

这里的 `<Void>` 是**显式指定泛型类型参数**。为什么不能省？

`fail` 的签名是：

```java
public static <T> Result<T> fail(ResultCode resultCode, String message)
```

`T` 不出现在参数里，所以编译器**推断不出来**。写在 `.body(...)` 里时，目标类型是 `Result<Void>`，理论上能推——但 `ResponseEntity.status(...)` 返回 `BodyBuilder`，其 `body(T body)` 是泛型的，中间隔了一层，推断更容易失败。

显式写 `<Void>` 是零成本的确定性写法。**面试可以讲**：泛型方法如果类型参数只出现在返回值里，调用时要显式指定，否则容易退化成 `Object`。

### 3.4 业务码为什么是 40000 这种五位数

```
0        成功
40000    参数错误
40100    未登录
40300    无权限
40400    资源不存在
40900    状态冲突
42900    请求过多
50000    服务端错误
```

规则：**前三位 = HTTP 状态码，后两位 = 业务细分**。

好处：
- 一眼能看出错误大类，不用查表
- 后两位留了 99 个细分空间，比如以后 `40101 = token 过期`、`40102 = token 无效`
- 和 HTTP 状态码对应，网关、监控、日志系统都能直接归类

**对比另一个常见方案**：「全用 HTTP 状态码，不加业务码」。缺点是 401 下面可能有很多种原因（没登录 / token 过期 / token 伪造 / 账号被禁用），前端要靠 message 字符串做分支——这是最脏的做法，因为文案一改逻辑就崩。

### 3.5 为什么 `code` 和 `httpStatus` 要分开

看 `ResultCode` 里一个字段叫 `httpStatus`，它不和 `code` 合并，这是刻意的设计。

```java
SUCCESS(0, "success", 200),
NOT_FOUND(40400, "资源不存在", 404),
```

`build()` 方法里：

```java
return ResponseEntity.status(resultCode.getHttpStatus())   // HTTP 状态码
        .body(Result.<Void>fail(resultCode, message));      // 业务码在 body 里
```

**两者的分工**：

| 谁看 HTTP 状态码 | 谁看业务码 |
| --- | --- |
| 浏览器（决定是否进 `catch`） | 前端业务逻辑（决定弹什么提示） |
| Nginx / 网关（决定是否熔断、限流） | 埋点监控（按业务码统计失败率） |
| 监控告警（4xx/5xx 比例） | |

**反例**：有些项目所有接口都返回 200，错误信息塞在 body 里。后果是：
- axios 的 `catch` 永远不进，前端要手动判断每个响应
- 网关和 APM 看不到错误率，5xx 告警形同虚设
- 浏览器缓存、CDN、重试策略全部失效

**但有个例外要注意**：健康检查接口在 DB 挂掉时仍然返回 200（见 [10 篇](./10-健康检查.md)）。因为「服务活着但依赖故障」属于**可观测信息**，不是请求失败。真正的 503 留给阶段 8 的 Actuator 给负载均衡用。

### 3.6 `PageResult` 的字段名为什么要和前端对齐

```java
public record PageResult<T>(long page, long pageSize, long total, List<T> list)
```

注释里写了：字段名与 `web/src/services/api` 里既有分页结构保持一致。

**为什么这件事值得单独说**：分页结构的字段名在业界至少有 5 种写法：

```
page/size/total/list          ← 当前选择（对齐前端）
pageNum/pageSize/total/records
current/size/total/records    ← MyBatis-Plus 的 IPage 默认
pageNo/limit/total/data
offset/limit/total/rows
```

如果后端用 `IPage` 直接返回，前端每个页面都要写一遍字段映射。**统一成一个结构，阶段 9 对接前端时这部分零改动**。

另外 `total` 用 `long` 不用 `int`：数据量大的时候 `int` 会溢出（21 亿），虽然学习项目不会到，但这是廉价的正确性。

### 3.7 为什么没有做全局 `Long → String` 序列化

这是一个**很多教程会做、但这个项目故意不做**的决定，面试聊起来很有价值。

**问题背景**：雪花 ID（`Long`）是 19 位数字，JavaScript 的 `Number` 最大安全整数是 2^53-1（16 位），超过会丢精度。所以常见的做法是在 Jackson 里全局注册：

```java
// 很多教程的写法
simpleModule.addSerializer(Long.class, ToStringSerializer.instance);
simpleModule.addSerializer(Long.TYPE, ToStringSerializer.instance);
```

**为什么不做**：`Long` 和 `long` 是**同一个类型**。全局改了，`PageResult.total`、`HealthVO.latencyMs`、以及以后所有 `long` 字段都会变成字符串：

```json
{"total": "1250", "latencyMs": "1"}   // 前端算数直接出错
```

**本项目改成**：只在**需要的那几个 ID 字段**上标注。

```java
// 阶段 2 会这么写
@JsonSerialize(using = ToStringSerializer.class)
private Long id;
```

或者更省事的方式——让 VO 里的 ID 字段直接声明为 `String`，在转换时 `String.valueOf(id)`。

**这个决策的价值**：面试时说「我知道全局改 Long 会有坑，所以改成字段级」，比说「我用 ToStringSerializer 解决了精度问题」高一个层次。

## 四、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 响应体字段 | `code/message/data/traceId` | traceId 内置，排障成本最低 | 只放 `code/message/data`，traceId 只放响应头——前端拿不到，用户截图看不到 |
| 业务码编码 | `HTTP状态码 * 100 + 序号` | 可读性 + 可扩展 | 纯递增（如 1001、1002）——分不清大类 |
| HTTP 状态码 | 与业务码分离，都返回 | 网关/监控能识别 | 全返 200——监控失效（见 3.5） |
| DTO 实现 | `record` | 不可变，代码最短 | Lombok `@Data`——可变，容易误改 |
| 泛型失败构造 | 显式 `Result.<Void>fail` | 避免类型推断失败 | 强转——编译期检查丢失 |
| Long 序列化 | **不全局转 String** | 避免 total/latency 变形 | 全局 ToStringSerializer——前端算数出错 |
| 分页字段名 | `page/pageSize/total/list` | 对齐既有前端 | `IPage` 直出——前端要映射 |
| null 字段 | 全局 `non_null` 不输出 | 减小响应体 | 保留 null——前端要判空两次 |

## 五、面试考察点

### 基础题

**Q1：你们的接口响应结构是什么样的，为什么这么设计？**

答题要点：
- 四段式：`code`（业务码，0 成功）、`message`（可直接展示的文案）、`data`（业务数据）、`traceId`（链路标识）
- 成功失败同结构，前端只判断 `code === 0`
- traceId 内置让用户报错时能直接定位

**Q2：业务码和 HTTP 状态码为什么要分开？**

答题要点：
- HTTP 状态码给「基础设施」看：浏览器决定是否进 catch、网关决定熔断限流、监控统计错误率
- 业务码给「业务逻辑」看：同一个 401 下区分「未登录 / token 过期 / 账号禁用」
- 反例是全返 200 + body 里塞错误，会导致网关和 APM 完全失效

**Q3：`record` 和 Lombok `@Data` 有什么区别，你怎么选？**

答题要点：
- `record` 是不可变值类型，自动生成全参构造、getter（命名是 `code()` 不是 `getCode()`）、equals/hashCode/toString，不能继承
- `@Data` 生成可变 JavaBean，有 setter，可继承
- 选择标准：纯 DTO/VO 用 `record`；需要 ORM 反射赋值、需要 setter、需要继承的实体用 Lombok

### 进阶题

**Q4：为什么不用全局 `Long → String` 序列化来解决雪花 ID 精度丢失？**

答题要点：
- `Long` 和 `long` 是同一个类型，全局注册会把 `total`、`latencyMs`、`count` 等所有 long 字段都变成字符串
- 前端 `response.total > 0` 会变成 `"1250" > 0`，字符串和数字比较有隐式转换，看起来能跑但 `total + 1` 会变 `"12501"`
- 正确做法是字段级：`@JsonSerialize(using = ToStringSerializer.class)` 或者 VO 里直接声明 `String`

**Q5：`default-property-inclusion: non_null` 有什么副作用？**

答题要点：
- 好处：响应体小，前端不用区分「字段不存在」和「值为 null」
- 副作用：前端 TypeScript 里所有可能为 null 的字段都要声明成可选 `data?: T`；另外如果某个字段需要显式返回 null（比如 `error: null` 表示成功），会被吞掉
- 本项目里 `HealthVO.Component.error` 成功时就是 null，实际不会出现在 JSON 里——前端判断用 `component.error` 的真假值即可

**Q6：`Result.ok()` 和 `Result.ok(data)` 为什么能共存？**

答题要点：
- 方法重载，参数列表不同
- 无参版本返回 `Result<Void>`，有参版本返回 `<T> Result<T>`
- 无参版内部调 `ok(null)`，`Void` 类型只能接受 null，语义正确

### 陷阱题

**Q7：`ResultCode` 用枚举有什么好处？改用常量类或数据库配置行不行？**

答题要点：
- 枚举：编译期检查、类型安全、可以带多个属性（code/message/httpStatus）、天然单例
- 常量类：无类型约束，`@ExceptionHandler` 没法按类型区分
- 数据库配置：灵活但每次用都要查库，且失去编译期校验，适合「运营可改的文案」而非「错误码」
- 折中方案：枚举定义 code 和默认文案，文案支持 i18n 从 `MessageSource` 取

**Q8：如果前端需要按错误码做多语言，你的结构要怎么改？**

答题要点：
- `ResultCode` 只保留 code 和 httpStatus，message 改成 `MessageSource` 按 code 查
- 请求头带 `Accept-Language`，`LocaleResolver` 解析
- 这样 `message` 保持「可直接展示」，但支持多语言

## 六、常见坑

| 坑 | 现象 | 处理 |
| --- | --- | --- |
| 全局 `Long → String` | 分页 `total` 变成字符串 | 改成字段级 `@JsonSerialize` |
| `record` 的 getter 是 `code()` 不是 `getCode()` | 前端/其他框架反射取不到值 | Jackson 原生支持 record；自定义反射要注意 |
| `record` 当 MyBatis 实体 | 反序列化失败 / 字段全 null | 实体用普通类 + Lombok |
| 失败时省略 `data` 字段 | 前端 `res.data.xxx` 报错 | 前端判 `res.code === 0` 后再取 data |
| 业务码重复 | 前端分支错乱 | 编码规则写死在文档里，新增时按段位分配 |
| `PageResult` 的 `total` 用 `int` | 大数据量溢出 | 用 `long` |
