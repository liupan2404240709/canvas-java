# 01 · 启动类与自动装配

> 对应源码：`src/main/java/com/infinitecanvas/canvas/CanvasApplication.java`

## 一、一句话定位

启动类是 Spring Boot 应用的入口，它只做两件事：**声明配置源**（我是不是一个 Spring Boot 应用、从哪个包开始扫）和**启动容器**（创建 ApplicationContext、跑完刷新流程）。

整个文件只有 12 行，但面试里能问出 20 分钟的内容，因为「一个 `@SpringBootApplication` 背后到底发生了什么」是 Spring Boot 最高频的考点。

## 二、完整代码

```java
package com.infinitecanvas.canvas;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication
public class CanvasApplication {

    public static void main(String[] args) {
        SpringApplication.run(CanvasApplication.class, args);
    }
}
```

## 三、逐段拆解

### 3.1 `@SpringBootApplication` 是一个「组合注解」

这是本文档最核心的一段。点进源码会看到：

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Documented
@Inherited
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan(excludeFilters = {
        @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
public @interface SpringBootApplication {
    // ...
}
```

它等价于同时标注了三个注解。**面试问「三个注解分别干什么」，答案就是这三个**：

| 注解 | 作用 | 底层是什么 | 不写会怎样 |
| --- | --- | --- | --- |
| `@SpringBootConfiguration` | 标记这是一个配置类，允许在里写 `@Bean` | 本质是 `@Configuration` 的派生注解，而 `@Configuration` 内部又是 `@Component` | 启动类不会被视为配置源，`@Bean` 不生效 |
| `@EnableAutoConfiguration` | 开启自动装配，把 starter 里声明的自动配置类按条件加载进来 | `@Import(AutoConfigurationImportSelector.class)` | Tomcat 不会起、数据源不会建、DispatcherServlet 不会注册——等于退回原始 Spring |
| `@ComponentScan` | 从当前类所在包往下扫描 `@Component`/`@Service`/`@Controller`/`@Configuration` | 走 `ClassPathBeanDefinitionScanner` | 自己写的 Controller、Service 全部扫描不到，接口 404 |

#### 为什么 `@SpringBootConfiguration` 不直接用 `@Configuration`？

因为它需要一个**语义明确的唯一标识**。Spring Boot 启动时要判断「这个应用的主配置类在哪」，`@SpringBootConfiguration` 可以被工具类和测试框架专门识别。而且它要求整个应用**只能有一个**（多个会报 `Found multiple @SpringBootConfiguration`），`@Configuration` 没有这个约束。

#### `@ComponentScan` 的两个 `excludeFilters` 是什么意思？

这两个过滤器是**给自动装配让路**的：

- `TypeExcludeFilter`：给测试用的，让 `@TestConfiguration` 之类的类不进入主扫描。
- `AutoConfigurationExcludeFilter`：**关键**。自动配置类本身也带 `@Configuration`，如果不排除，它们会被组件扫描抓一遍、又被自动装配导入一遍，导致 Bean 重复注册。

这也解释了为什么自动配置类要用 `@AutoConfiguration`（`@Configuration(proxyBeanMethods = false)` 的派生）而不是裸 `@Configuration`——为了让这个过滤器能识别。

### 3.2 为什么启动类必须放在包的根

当前启动类在 `com.infinitecanvas.canvas`，所有业务代码都在它下面：

```
com.infinitecanvas.canvas
├── CanvasApplication          ← 在这里
├── common/
├── config/
├── controller/
└── service/
```

`@ComponentScan` 默认扫描的是**启动类所在包及其子包**。如果把启动类挪到 `com.infinitecanvas.canvas.config`，那么 `controller`、`service` 全在扫描范围外，启动不报错、但接口 404——这是新手最难查的坑之一。

**三种解法**（按推荐度排序）：

1. 启动类放根包（当前做法，最省事）
2. 显式指定 `@ComponentScan(basePackages = "com.infinitecanvas.canvas")`
3. 用 `@Import` 手动导入（只适合极少数场景）

### 3.3 `SpringApplication.run()` 做了什么

面试常问「Spring Boot 启动流程」。完整的 12 步可以背，但**能讲清楚 5 个关键阶段**就够了：

```
SpringApplication.run(CanvasApplication.class, args)
│
├─ 1. 构造 SpringApplication
│    推断应用类型（SERVLET / REACTIVE / NONE）
│    → 因为 classpath 里有 spring-webmvc，判定为 SERVLET
│    → 这一步决定了后面创建的是 AnnotationConfigServletWebServerApplicationContext
│
├─ 2. 加载 ApplicationContextInitializer 和 ApplicationListener
│    → 从 META-INF/spring.factories 里读（Spring Boot 3 已迁到 .imports）
│
├─ 3. 准备 Environment
│    → 加载 application.yml、系统属性、环境变量、命令行参数
│    → 这就是配置优先级的来源（见 11 篇）
│
├─ 4. 创建 ApplicationContext，注册主配置类（CanvasApplication）
│
├─ 5. refresh()  ← 真正的核心，Bean 生命周期都在这里
│    ├─ invokeBeanFactoryPostProcessors
│    │    → 解析 @ComponentScan，把 BeanDefinition 塞进容器
│    │    → 解析 @Import，触发 AutoConfigurationImportSelector  ← 自动装配在这
│    ├─ registerBeanPostProcessors
│    ├─ onRefresh → 创建内嵌 Tomcat（ServletWebServerApplicationContext 特有）
│    └─ finishBeanFactoryInitialization → 实例化所有非懒加载单例
│
└─ 6. 发布 ApplicationReadyEvent，打印 "Started CanvasApplication in x seconds"
```

**能讲深的一句**：内嵌 Tomcat 不是启动时最先创建的，而是在 `refresh()` 的 `onRefresh()` 阶段才创建。所以「Tomcat 起不来」的报错通常出现在 Bean 初始化**之后**，日志顺序上能看出来。

### 3.4 自动装配到底是怎么装进来的

这是 `@EnableAutoConfiguration` 的展开，也是 Spring Boot 的核心魔法。链路是：

```
@EnableAutoConfiguration
  └─ @Import(AutoConfigurationImportSelector.class)
        └─ selectImports() 读所有 jar 的
           META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
              （Spring Boot 2.7 之前是 spring.factories 的 EnableAutoConfiguration key）
              └─ 得到 200+ 个自动配置类全限定名
                    └─ 逐个用「条件注解」过滤
                          └─ 通过的才注册成 BeanDefinition
```

**条件注解决定「装不装」**，常见的几个：

| 条件注解 | 含义 | 在本项目里的体现 |
| --- | --- | --- |
| `@ConditionalOnClass` | classpath 有某个类才生效 | 有 `mysql-connector-j` 才装 `DataSourceAutoConfiguration` |
| `@ConditionalOnMissingBean` | 容器里没有这个 Bean 才生效 | 我们自己写了 `RedisTemplate`，默认的就不装了 |
| `@ConditionalOnProperty` | 配置项为某个值才生效 | Swagger 可以用 `springdoc.api-docs.enabled=false` 关掉 |
| `@ConditionalOnWebApplication` | 是 Web 应用才生效 | `WebMvcAutoConfiguration` 只在 SERVLET 类型下装 |

**必须讲明白的一点**：自动装配**不是**「把所有类都塞进容器」，而是「按条件筛选后注册」。默认装了大概 20~30 个配置类，不是 200 个。

**验证方法**（面试官很吃这一套）：

```bash
# 启动时加 --debug，控制台会打印「自动配置报告」
java -jar app.jar --debug

# 报告分三段：Positive matches（装了哪些）、Negative matches（没装及原因）、Exclusions
```

## 四、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 启动类位置 | 根包 `com.infinitecanvas.canvas` | 组件扫描天然覆盖全部业务代码 | 放子包则必须手写 `basePackages`，容易漏 |
| 是否拆多模块 | 单模块 | 学习项目，拆模块会分散注意力 | multi-module 利于依赖隔离，但阶段 1~8 用不上 |
| 是否加 `@MapperScan` | **暂不加** | mapper 包现在为空，加了会刷 `No MyBatis mapper was found` 警告 | 阶段 2 建第一个 Mapper 时加在 `MybatisPlusConfig` 上更内聚 |
| 是否加 `@EnableTransactionManagement` | 不加 | Boot 已自动开启 | 手写反而可能覆盖默认配置 |
| 是否加 `@EnableScheduling` | 不加 | 阶段 4 提示词定时刷新才需要 | 提前加会让 `@Scheduled` 空跑 |

> **这里的「暂不加」是刻意的**：启动日志里那条 `No MyBatis mapper was found in '[com.infinitecanvas.canvas]' package` 警告是预期行为，不是配错了。面试如果被问「启动日志有警告你怎么处理」，可以拿这个当例子讲「区分预期警告和真实故障」。

## 五、面试考察点

### 基础题

**Q1：`@SpringBootApplication` 由哪几个注解组成，各自作用？**

答题要点（必须能一口气说完）：
- `@SpringBootConfiguration`：标识主配置类，是 `@Configuration` 的派生，保证全应用唯一
- `@EnableAutoConfiguration`：开启自动装配，通过 `@Import(AutoConfigurationImportSelector)` 加载所有 starter 的自动配置类，再按条件注解筛选
- `@ComponentScan`：从启动类所在包向下扫描组件，并用两个 `excludeFilters` 排除自动配置类避免重复注册

**Q2：Spring Boot 自动装配的原理？**

答题要点（分四层，能讲到第三层就超过大多数候选人）：
1. `@EnableAutoConfiguration` 导入 `AutoConfigurationImportSelector`
2. 它读取 classpath 下所有 jar 的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`（2.7 之前是 `spring.factories`）
3. 得到候选配置类列表后，用 `@ConditionalOnClass` / `@ConditionalOnMissingBean` / `@ConditionalOnProperty` 等条件注解过滤
4. 通过的配置类注册为 BeanDefinition，参与正常 Bean 生命周期

**Q3：为什么启动类要放在根包？**

答：`@ComponentScan` 默认扫启动类所在包及子包，放子包会漏扫同级或上级的组件，表现为启动成功但接口 404。

### 进阶题

**Q4：自动装配和 `@ComponentScan` 都会注册 Bean，会不会冲突？**

答：不会，因为 `@SpringBootApplication` 的 `@ComponentScan` 带了 `AutoConfigurationExcludeFilter`，把「既是 `@Configuration` 又出现在自动配置清单里」的类排除了。另外自动配置类普遍使用 `@ConditionalOnMissingBean`，即使重复也能保证用户自定义的 Bean 优先。

**Q5：`@ConditionalOnMissingBean` 的生效时机？为什么它能判断「用户有没有自己定义」？**

答：它在**解析 BeanDefinition 阶段**执行（`ConfigurationClassPostProcessor` 处理 `@Import` 时），此时用户自己的 `@Configuration` 已经先被扫描注册了。Spring Boot 保证了「用户配置优先于自动配置」的顺序，所以能正确判断。

这也是为什么自己写一个 `RedisTemplate` Bean（见 07 篇）就能覆盖默认配置——`RedisAutoConfiguration` 上的 `@ConditionalOnMissingBean(name = "redisTemplate")` 不满足了。

**Q6：`SpringApplication.run()` 里 Tomcat 是什么时候启动的？**

答：在 `refresh()` 的 `onRefresh()` 阶段，由 `ServletWebServerApplicationContext` 调用 `createWebServer()` 创建并启动。**不是**在 `main` 方法一开始就起，所以 Bean 初始化失败时 Tomcat 根本没起来，日志里也不会有端口信息。

**Q7：怎么排查「某个自动配置为什么没生效」？**

答：
1. `--debug` 启动，看自动配置报告的 `Negative matches` 段落，会写明「因为缺少哪个类 / 哪个 Bean 已存在」
2. `ApplicationContext.getBeanDefinitionNames()` 直接看容器里有什么
3. IDEA 里用 `Actuator` 的 `/actuator/conditions` 端点（阶段 8 会接）

### 陷阱题

**Q8：我只加 `@Configuration` 不加 `@SpringBootApplication`，能启动吗？**

答：能跑，但会退化。`@Configuration` 只声明了配置源，没有 `@EnableAutoConfiguration` 就没有自动装配——内嵌 Tomcat 不会创建，`DataSource` 不会初始化，等于用 Spring Boot 的依赖写了个原始 Spring 应用。要跑起来得手动 `new AnnotationConfigApplicationContext(...)` 或者额外加 `@EnableAutoConfiguration`。

**Q9：把 `@SpringBootApplication` 换成 `@ComponentScan` + `@Configuration` + `@EnableAutoConfiguration` 三个注解分开写，有区别吗？**

答：功能上等价，但会丢掉 `AutoConfigurationExcludeFilter`，自动配置类可能被组件扫描重复注册（虽然 `@ConditionalOnMissingBean` 通常能兜住，但属于隐患）。另外可读性差，团队规范上不应该这么写。

**Q10：`spring-boot-starter-parent` 和 `spring-boot-dependencies` 有什么区别？**

答：见 [12 依赖与容器](./12-依赖与容器.md)。一句话：`parent` 继承它并额外提供插件配置、资源过滤、`@SpringBootApplication` 相关的 Maven 默认值；`dependencies` 只能 `import` 到 `dependencyManagement` 里，只提供版本仲裁，不提供插件和构建配置。

## 六、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 启动类放子包 | 启动成功但接口 404 | 组件扫描范围不够 | 启动类移到根包 |
| 启动类被 `@ComponentScan` 的 `basePackages` 覆盖 | 同上 | 显式指定包名时覆盖了默认值 | 显式指定时把根包写全 |
| 加了 `@MapperScan` 但 mapper 包是空的 | 启动警告 `No MyBatis mapper was found` | 预期行为 | 阶段 2 再添加 |
| 多个 `@SpringBootConfiguration` | 启动报 `Found multiple @SpringBootConfiguration` | 测试类上误加了该注解 | 测试用 `@SpringBootTest` 即可 |
| 改了包名没改启动类 | 扫描不到 | 路径不一致 | 用 IDEA 的 Move 重构，别手动改 |
