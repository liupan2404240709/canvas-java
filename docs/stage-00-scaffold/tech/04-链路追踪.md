# 04 · 链路追踪（traceId）

> 对应源码：`common/constant/TraceId.java`、`infra/web/TraceIdFilter.java`

## 一、一句话定位

给**每一个 HTTP 请求**分配一个唯一 ID，让「用户说的那次请求」和「日志里的那几百行输出」能对上。

这是整个阶段 0 里性价比最高的一个改动：代码 20 行，排障效率提升一个量级。

## 二、完整代码

### TraceId.java

```java
public final class TraceId {

    public static final String HEADER = "X-Trace-Id";
    public static final String MDC_KEY = "traceId";
    private static final String EMPTY = "-";

    private TraceId() {
    }

    public static String current() {
        String value = MDC.get(MDC_KEY);
        return value == null || value.isBlank() ? EMPTY : value;
    }
}
```

### TraceIdFilter.java

```java
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain chain)
            throws ServletException, IOException {
        String traceId = request.getHeader(TraceId.HEADER);
        if (!StringUtils.hasText(traceId)) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put(TraceId.MDC_KEY, traceId);
        response.setHeader(TraceId.HEADER, traceId);
        try {
            chain.doFilter(request, response);
        } finally {
            MDC.remove(TraceId.MDC_KEY);
        }
    }
}
```

## 三、逐段拆解

### 3.1 为什么需要 traceId

没有 traceId 时，一个请求在日志里是这样的：

```
2026-11-11 22:00:23.101 INFO  [http-nio-8081-exec-1] c.i.c.s.HealthService - 健康检查失败: ...
2026-11-11 22:00:23.105 WARN  [http-nio-8081-exec-2] c.i.c.s.HealthService - 健康检查失败: ...
2026-11-11 22:00:23.107 INFO  [http-nio-8081-exec-1] c.i.c.c.HealthController - ...
2026-11-11 22:00:23.110 ERROR [http-nio-8081-exec-3] c.i.c.e.GlobalExceptionHandler - 未处理异常
```

并发 3 个请求，日志交错在一起，你没法知道哪几行属于同一个请求。线程名 `exec-1` 只能部分区分——同一个线程会复用。

加上 traceId 之后：

```
22:00:23.101 INFO  [http-nio-8081-exec-1] [cec6d4180e3f4878a247765580f4febc] HealthService - ...
22:00:23.105 WARN  [http-nio-8081-exec-2] [75cbf14093a44b1b93709704827489db] HealthService - ...
22:00:23.107 INFO  [http-nio-8081-exec-1] [cec6d4180e3f4878a247765580f4febc] HealthController - ...
```

`grep cec6d418` 一次就能捞出完整链路。

**关键是它还回写到了响应头**：

```java
response.setHeader(TraceId.HEADER, traceId);
```

用户报「刚才点保存报错了」，前端把响应头里的 traceId 弹给用户，用户截图 → 你 grep → 5 秒定位。

### 3.2 优先复用上游传来的 traceId

```java
String traceId = request.getHeader(TraceId.HEADER);
if (!StringUtils.hasText(traceId)) {
    traceId = UUID.randomUUID().toString().replace("-", "");
}
```

**为什么不无脑生成新的**：

如果请求是从 Nginx、网关或另一个服务转发过来的，它已经带了一个 traceId，这里应该**沿用**而不是覆盖。否则一次调用链会在每个服务断成好几段，链路就断了。

**但这里有个安全问题**：直接信任客户端传来的 header 意味着别人可以伪造 traceId 去污染日志，甚至做日志注入（塞 `\n` 伪造日志行）。生产环境的正确做法是：

```java
// 校验格式，只接受 32 位十六进制
if (!traceId.matches("^[0-9a-fA-F]{32}$")) {
    traceId = generate();   // 不合法就重新生成
}
```

本项目阶段 0 没有加这个校验，属于**已知的简化**。面试如果被追问「客户端伪造 traceId 怎么办」，答「应该加格式白名单校验」，比说「没考虑」好得多。

### 3.3 `UUID.randomUUID().replace("-", "")` 的取舍

| 方案 | 长度 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `UUID` 带横线 | 36 | 标准，可读 | 日志里占地方 |
| **`UUID` 去横线**（当前） | 32 | 紧凑，纯十六进制 | 还是 128 位，比需要的长 |
| 雪花 ID | 19 | 有序，能看出时间 | 依赖 WorkerId 分配 |
| 8 位随机串 | 8 | 最短 | 碰撞概率高（32^8 ≈ 1.1 万亿，够用但不严谨） |

32 位十六进制 = 128 bit，理论碰撞概率可以忽略。**日志里的成本是每行多 32 字符**，这个代价可以接受。

如果不追求绝对唯一，业界更常见的是 **TraceId + SpanId** 两段式（OpenTelemetry 规范），那是分布式追踪的范畴，见 3.7。

### 3.4 `MDC` 是什么

`MDC`（Mapped Diagnostic Context）是 SLF4J 提供的一个**线程绑定的键值容器**。

```java
MDC.put("traceId", "abc123");   // 放
MDC.get("traceId");             // 取
MDC.remove("traceId");          // 清
```

**底层是 `ThreadLocal<Map<String, String>>`**：

```java
// org.slf4j.MDC 简化后的实现
private static final ThreadLocal<Map<String, String>> CONTEXT_MAP =
        new ThreadLocal<Map<String, String>>() {
            @Override
            protected Map<String, String> initialValue() {
                return new HashMap<>();
            }
        };
```

**所以 MDC 天然是「线程隔离」的**：A 请求的 traceId 不会串到 B 请求，前提是它们在不同线程。

**logback 怎么把 MDC 拿出来**：`logback-spring.xml` 的 pattern 里写 `%X{traceId:-}`：

```xml
<property name="PATTERN"
          value="%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId:-}] %logger{36} - %msg%n"/>
```

- `%X{key}`：取 MDC 里 key 对应的值
- `%X{traceId:-}`：`:-` 后面是**默认值**，MDC 里没有时输出空字符串
- 这和 `TraceId.current()` 返回 `-` 是两个独立的兜底，一个管日志、一个管响应体

### 3.5 `finally` 里的 `MDC.remove()` 为什么必须写

```java
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove(TraceId.MDC_KEY);
}
```

**两个原因**：

**① 线程复用导致串号（正确性问题）**

Tomcat 的线程池会复用线程。如果不清：

```
请求 A（traceId=aaa）→ 处理完，没清 MDC
请求 B 复用同一个线程 → MDC 里还是 aaa → 日志全部标成 aaa
```

结果就是 B 的日志被记到 A 头上，排障时完全走错方向。

**② 内存泄漏（稳定性问题）**

`ThreadLocal` 的 `Entry` 的 key 是**弱引用**（WeakReference），value 是**强引用**。线程池的线程生命周期很长（几乎不销毁），所以：

```
ThreadLocal → Map → Entry(key=弱引用 traceId, value=强引用 "abc123")
                      ↑ GC 后 key 变 null，但 value 还在
                      ↑ 这个 entry 成了 "key 为 null 的僵尸 entry"
```

虽然 SLF4J 的 `MDC.remove()` 会正确清理，但**如果不清**，`MDC` 内部的 `ThreadLocal` 关联的 Map 会越来越大，最终 OOM。

**这是面试高频题**：`ThreadLocal` 内存泄漏的原因和避免方式。标准答案是「用完必须 `remove()`，且要放在 `finally` 里」。

### 3.6 `OncePerRequestFilter` 与 `@Order`

#### 为什么继承 `OncePerRequestFilter` 而不是直接实现 `Filter`

```java
public abstract class OncePerRequestFilter extends GenericFilterBean {
    public final void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
        // 用 request 属性标记 "已经执行过了"
        String alreadyFilteredAttributeName = getAlreadyFilteredAttributeName();
        if (request.getAttribute(alreadyFilteredAttributeName) != null) {
            chain.doFilter(request, response);   // 跳过，不再执行
            return;
        }
        request.setAttribute(alreadyFilteredAttributeName, Boolean.TRUE);
        try {
            doFilterInternal(request, response, chain);   // 真正的逻辑
        } finally {
            request.removeAttribute(alreadyFilteredAttributeName);
        }
    }
}
```

**解决的场景**：**请求转发（forward）和包含（include）**。

```
请求 /a → Filter 执行 → 转给 /b → Filter 又执行一次
```

如果直接用 `Filter`，`MDC.put` 会执行两次，`finally` 里的 `remove` 也会执行两次——第二次进入时 traceId 已经被删了，`current()` 返回 `-`，日志就断了。

`OncePerRequestFilter` 用 request attribute 做标记，保证**一次请求只执行一次**。

**面试答题要点**：`OncePerRequestFilter` 通过 `request.setAttribute` 标记「已过滤」，避免 forward/include 导致的重复执行。

#### `@Order(Ordered.HIGHEST_PRECEDENCE)` 的作用

`Ordered.HIGHEST_PRECEDENCE = Integer.MIN_VALUE`，即**最高优先级**。

**为什么 traceId 过滤器要最高优先级**：

1. 它必须比其他过滤器**先**执行，这样后续所有日志才带 traceId
2. Spring Security 的过滤器链默认优先级是 `-100`（`SecurityProperties.DEFAULT_FILTER_ORDER`），`Integer.MIN_VALUE` 比它更早

**如果顺序错了会怎样**：Spring Security 在认证失败时打的日志不带 traceId，而认证失败恰恰是最需要排查的场景。

### 3.7 单机 traceId 的边界：跨线程就断了

这是**阶段 6 会遇到的真问题**，值得现在就理解。

当前实现依赖 `ThreadLocal`，所以：

| 场景 | traceId 是否传递 | 原因 |
| --- | --- | --- |
| 同步 Controller → Service → Mapper | ✅ | 同一个线程 |
| `@Async` 方法 | ❌ | 换了线程，MDC 丢了 |
| 线程池提交任务 | ❌ | 同上 |
| `CompletableFuture.supplyAsync` | ❌ | 同上 |
| 定时任务 `@Scheduled` | ❌ | 本来就没有请求上下文，`current()` 返回 `-` |

**这就是阶段 6「异步生成图片」会踩的坑**：任务在线程池里跑，日志里的 traceId 全是 `-`，出问题根本串不起来。

**三种解法**（按投入产出排序）：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 手动传递 | 把 traceId 作为参数传给任务，任务里手动 `MDC.put` | 简单，但要改方法签名 |
| 包装 `Runnable` | 写一个 `MdcRunnable`，在 `run()` 前后 `put`/`remove` | 线程池复用的标准做法 |
| `TaskDecorator` | Spring 的 `ThreadPoolTaskExecutor` 支持装饰器，统一包装 | **推荐**，一处配置全局生效 |

`TaskDecorator` 的写法（阶段 6 会用到）：

```java
executor.setTaskDecorator(runnable -> {
    Map<String, String> contextMap = MDC.getCopyOfContextMap();
    return () -> {
        if (contextMap != null) MDC.setContextMap(contextMap);
        try {
            runnable.run();
        } finally {
            MDC.clear();
        }
    };
});
```

**再往上就是分布式追踪**：多个服务之间传递 traceId 需要协议约定（W3C Trace Context 用 `traceparent` header），采集和展示需要 SkyWalking / Zipkin / Jaeger。Spring Boot 3 的官方方案是 **Micrometer Tracing**（替代 Spring Cloud Sleuth）。

**面试可以这样讲**：「当前是单机请求级 traceId，基于 MDC + Filter，够用且成本低；如果是微服务架构，我会换成 Micrometer Tracing + OpenTelemetry，通过 `traceparent` header 跨服务传递，后端接 Zipkin 做可视化。」

## 四、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 实现方式 | Servlet Filter | 最早执行，能覆盖整个请求生命周期 | 拦截器——进不了 DispatcherServlet 之前的日志 |
| Filter 基类 | `OncePerRequestFilter` | 防 forward/include 重复执行 | 裸 `Filter`——traceId 会被删两次 |
| 优先级 | `HIGHEST_PRECEDENCE` | 保证先于 Security 和业务日志 | 默认顺序——Security 日志可能不带 traceId |
| 上游透传 | 有 header 就复用 | 支持网关/多服务串联 | 无条件新生成——链路断裂 |
| 格式校验 | **未做** | 阶段 0 简化 | 生产应加 32 位十六进制白名单 |
| 存储位置 | MDC（ThreadLocal） | 日志框架原生支持，零侵入 | 方法参数逐层传——污染签名 |
| 清理时机 | `finally` | 保证异常时也清理 | 方法末尾——异常时不执行 |
| 响应回写 | 响应头 `X-Trace-Id` | 用户能拿到 | 只放响应体——下载接口拿不到 |
| 跨线程 | **未处理** | 阶段 6 再加 `TaskDecorator` | 现在就加——还没有异步场景 |

## 五、面试考察点

### 基础题

**Q1：你这个 traceId 是干什么的，怎么实现的？**

答题要点：
- 每个 HTTP 请求分配唯一 ID，写进 MDC，日志 pattern 里用 `%X{traceId}` 带出来
- 同时回写响应头 `X-Trace-Id`，用户报错时能提供
- 用 `OncePerRequestFilter` 实现，优先级最高，`finally` 里 `remove` 防串号和内存泄漏
- 上游有 header 就复用，支持网关串联

**Q2：MDC 底层是什么？**

答题要点：
- SLF4J 的 Mapped Diagnostic Context，底层是 `ThreadLocal<Map<String, String>>`
- 线程隔离，所以天然按请求隔离
- 日志框架在输出时从当前线程的 MDC 里取值

**Q3：Filter 和 Interceptor 的区别？为什么用 Filter？**

答题要点：

| | Filter | Interceptor |
| --- | --- | --- |
| 规范 | Servlet 规范 | Spring MVC 规范 |
| 执行位置 | DispatcherServlet **之前** | DispatcherServlet **内部**，Handler 前后 |
| 能拿到什么 | `ServletRequest` / `ServletResponse` | `HandlerMethod`（知道调的是哪个 Controller 方法） |
| 异常能否被 `@ControllerAdvice` 捕获 | **不能** | 能 |
| 适用 | 编码、CORS、traceId、鉴权 | 权限注解、日志记录、参数预处理 |

traceId 要在最早时机生成、且要覆盖静态资源等非 Controller 请求，所以用 Filter。

### 进阶题

**Q4：`ThreadLocal` 为什么会内存泄漏？**

答题要点：
- `ThreadLocalMap` 的 Entry 继承 `WeakReference<ThreadLocal>`，key 是弱引用，value 是强引用
- ThreadLocal 对象被回收后，key 变成 null，但 value 还被 Entry 强引用着
- 线程池的线程不销毁，这些「key 为 null 的 entry」就一直留着
- 解决：用完必须 `remove()`，放在 `finally` 里

**Q5：异步任务里 traceId 会丢吗？怎么解决？**

答题要点：
- 会。MDC 是 ThreadLocal，切线程就没了
- 现象：线程池里的日志 traceId 是 `-`
- 解决：`TaskDecorator` 在提交任务时捕获 `MDC.getCopyOfContextMap()`，在任务线程里 `setContextMap` 恢复，任务结束 `clear`
- 更彻底：Micrometer Tracing + OpenTelemetry，用 `Context` 传播

**Q6：`OncePerRequestFilter` 解决什么问题？**

答题要点：
- 请求 forward/include 时，Filter 会被重复触发
- 它用 `request.setAttribute` 打标记，保证一次请求只执行一次
- 对本项目：避免 `MDC.remove` 被提前执行导致后半段日志丢 traceId

**Q7：为什么 `@Order` 用 `HIGHEST_PRECEDENCE` 而不是随便一个负数？**

答题要点：
- Spring Security 过滤器链默认 order 是 `-100`
- 要保证 traceId 在安全过滤器**之前**生成，否则认证失败的日志不带 traceId
- `Integer.MIN_VALUE` 是最稳妥的「我第一个」表达

### 陷阱题

**Q8：客户端自己传一个 `X-Trace-Id` 会怎样？有什么风险？**

答题要点：
- 当前实现**直接信任**，会用它作为本次请求的 traceId
- 风险一：日志注入（传 `\n` 伪造日志行）
- 风险二：伪造 traceId 污染日志，干扰排障
- 正确做法：正则校验 32 位十六进制，不合法就重新生成

**Q9：多实例部署时，traceId 能串起整个调用链吗？**

答题要点：
- 不能。单机 traceId 只在当前实例的日志里有效
- 跨服务需要协议传递（W3C `traceparent` header）
- 需要采集 + 存储 + 可视化：SkyWalking / Zipkin / Jaeger
- Spring Boot 3 用 Micrometer Tracing + `OtelPropagator`

**Q10：`%X{traceId:-}` 里 `:-` 是什么意思？**

答题要点：
- Logback 的默认值语法，`:-` 后面跟默认值
- 这里是空字符串，MDC 没值时输出空
- 如果不写，MDC 没值时会输出 `traceId_IS_UNDEFINED`

## 六、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 忘记 `MDC.remove` | 日志 traceId 串到别的请求 | 线程池复用 | 放 `finally` |
| 用裸 `Filter` | forward 时 traceId 丢失 | 重复执行导致提前 remove | 用 `OncePerRequestFilter` |
| 优先级不是最高 | Security 日志没有 traceId | Security 过滤器先执行了 | `HIGHEST_PRECEDENCE` |
| 无条件生成新 traceId | 网关传来的链路断裂 | 覆盖了上游值 | 先读 header |
| 异步任务里 traceId 丢失 | 日志全是 `-` | ThreadLocal 不跨线程 | `TaskDecorator` |
| 响应头没暴露给前端 | 浏览器 JS 读不到 `X-Trace-Id` | CORS 的 `exposedHeaders` 没配 | 见 [08 篇](./08-CORS跨域.md) |

> 最后一条是真实关联：`WebMvcConfig` 里配了 `.exposedHeaders("X-Trace-Id")`，不配的话浏览器同源策略会让 JS 读不到这个响应头，前端就拿不到 traceId 展示了。
