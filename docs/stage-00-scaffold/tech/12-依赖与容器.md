# 12 · 依赖与容器

> 对应源码：`pom.xml`、`docker-compose.yml`

## 一、一句话定位

`pom.xml` 决定了「代码能编译成什么」，`docker-compose.yml` 决定了「本地依赖怎么跑起来」。

前者面试问的是 **Maven 依赖机制**（starter、作用域、冲突仲裁），后者问的是 **容器编排**（健康检查、命名卷、端口映射）。

```xml
<parent>
    <groupId>org.springframework.boot</groupId>

<groupId>com.infinitecanvas</groupId>
```

## 三、逐段拆解

### 3.1 `spring-boot-starter-parent` 提供了什么

这是**所有脚手架的起点**，面试问「为什么继承它」要能说出四件事：

| 它提供的东西 | 具体内容 |
| --- | --- |
| **依赖版本仲裁** | 200+ 个常用依赖的版本在 `dependencyManagement` 里定好，自己引入时不写 `<version>` |
| **Maven 插件默认配置** | `spring-boot-maven-plugin` 的 repackage 目标、`maven-compiler-plugin` 的编码和版本 |
| **资源过滤** | `application.yml` 里的 `@project.version@` 能被替换成实际版本 |
| **`java.version` 属性** | 改一个属性就统一了编译版本 |

**它和 `spring-boot-dependencies` 的区别**（**高频面试题**）：

```xml
<!-- 写法 A：继承 parent（当前） -->
<parent>
    <artifactId>spring-boot-starter-parent</artifactId>
    <version>3.3.5</version>
</parent>

<!-- 写法 B：import BOM -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <artifactId>spring-boot-dependencies</artifactId>
            <version>3.3.5</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

| | `starter-parent` | `dependencies`（BOM） |
| --- | --- | --- |
| 依赖版本仲裁 | ✅ | ✅ |
| 插件默认配置 | ✅ | ❌ |
| 资源过滤（`@...@`） | ✅ | ❌ |
| 能否有自己的 parent | ❌ **单继承限制** | ✅ 可以继承公司的 parent |

**什么时候必须用 BOM**：公司有统一的 `company-parent`，Maven 不支持多继承，这时只能在 `dependencyManagement` 里 `import` Spring Boot 的 BOM。

**本项目用 parent**：单模块学习项目，没有公司 parent 的约束，parent 更省事。

### 3.2 `mybatis-plus-spring-boot3-starter` 的版本后缀很关键

```xml
<artifactId>mybatis-plus-spring-boot3-starter</artifactId>
<version>3.5.7</version>
```

**必须要带 `spring-boot3`**。

MyBatis-Plus 有三个 starter 坐标：

| 坐标 | 适用 | Boot 3 下会怎样 |
| --- | --- | --- |
| `mybatis-plus-boot-starter` | Boot 1.x / 2.x | **启动失败**（依赖 `javax`） |
| **`mybatis-plus-spring-boot3-starter`**（当前） | Boot 3.x | ✅ 正常 |
| `mybatis-plus-spring-boot3-starter` + `mybatis-plus-jsqlparser` | 3.5.9+ 需要额外引入 | 分页插件依赖它 |

> **3.5.9 之后的注意点**：MyBatis-Plus 3.5.9 开始把 `jsqlparser` 拆成独立依赖，用分页插件必须额外引 `mybatis-plus-jsqlparser`。本项目是 3.5.7，还没这个问题——**升级版本时要注意**。

**这就是「版本不是越新越好」的典型例子**：新版本拆包、改坐标、改包名，往往意味着你要改配置。

### 3.3 `mysql-connector-j` 的 `runtime` 作用域

```xml
<dependency>
    <groupId>com.mysql</groupId>
    <artifactId>mysql-connector-j</artifactId>
    <scope>runtime</scope>
</dependency>
```

**四个作用域对比**（**面试必考**）：

| 作用域 | 编译期 | 运行期 | 测试期 | 打进最终包 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| `compile`（默认） | ✅ | ✅ | ✅ | ✅ | 业务代码直接用的库 |
| **`runtime`**（当前） | ❌ | ✅ | ✅ | ✅ | **驱动、日志实现** |
| `provided` | ✅ | ❌ | ✅ | ❌ | Servlet API、Lombok（编译期需要，运行时容器提供） |
| `test` | ❌ | ❌ | ✅ | ❌ | JUnit、Mockito |

**为什么 MySQL 驱动用 `runtime`**：

代码里**没有任何一处 `import com.mysql.cj.jdbc.Driver`**——驱动是靠 JDBC 的 SPI 机制（`META-INF/services/java.sql.Driver`）被自动发现的。编译期不需要它，运行期必须有，所以是 `runtime`。

**好处**：如果有人不小心在代码里直接依赖了 MySQL 驱动的内部类，编译期就会报错，避免耦合到具体实现。

**`provided` 的经典例子是 Lombok**——但它这里用的是 `optional`：

```xml
<dependency>
    <groupId>org.projectlombok</groupId>
    <artifactId>lombok</artifactId>
    <optional>true</optional>
</dependency>
```

**`optional` 是另一套机制**（不是作用域），含义是「**不传递给下游依赖**」。如果别人把本项目当依赖引入，不会被迫也引入 Lombok。

配合 `spring-boot-maven-plugin` 里的排除：

```xml
<configuration>
    <excludes>
        <exclude>
            <groupId>org.projectlombok</groupId>
            <artifactId>lombok</artifactId>
        </exclude>
    </excludes>
</configuration>
```

**这是为了让 Lombok 不打进最终的 fat jar**：Lombok 只是编译期注解处理器，运行时完全不需要（注解已经变成字节码了）。不打进去能让 jar 小几百 KB。

**`commons-pool2` 为什么要单独引**：

```xml
<dependency>
    <groupId>org.apache.commons</groupId>
    <artifactId>commons-pool2</artifactId>
</dependency>
```

`spring-boot-starter-data-redis` **不包含**它。配了 `spring.data.redis.lettuce.pool.*` 但没有这个依赖，启动报：

```
java.lang.ClassNotFoundException: org.apache.commons.pool2.impl.GenericObjectPoolConfig
```

这是很常见的坑（详见 [07 篇](./07-Redis配置.md) 3.6）。

### 3.4 依赖冲突怎么仲裁

**Maven 的两条规则**（面试高频）：

| 规则 | 说明 |
| --- | --- |
| **路径最短优先** | 直接依赖 > 传递依赖（层级少的赢） |
| **第一声明优先** | 路径长度相同时，`pom.xml` 里**先声明**的赢 |

**本项目可能出现的冲突场景**：

`spring-boot-starter-web` 会传递引入 `jackson-databind`（比如 2.17.x）。如果手动引了一个 `jackson-databind:2.15`，**直接依赖路径更短，会覆盖 Spring Boot 仲裁的版本**，可能导致兼容问题。

**排查命令**：

```bash
# 看某个依赖的完整来源树
mvn dependency:tree -Dincludes=com.fasterxml.jackson.core

# 看所有冲突（同一 artifact 出现多个版本）
mvn dependency:tree -Dverbose | grep "omitted for conflict"
```

**`<exclusion>` 的用法**（阶段 1 可能用到：排除 Spring Security 默认的用户名密码日志）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-logging</artifactId>
        </exclusion>
    </exclusions>
</dependency>
```

### 3.5 为什么 `properties` 里单独定义了两个版本号

```xml
<properties>
    <mybatis-plus.version>3.5.7</mybatis-plus.version>
    <springdoc.version>2.6.0</springdoc.version>
</properties>
```

这两个依赖**不在 Spring Boot 的版本仲裁范围内**（不是 Boot 官方维护的），所以必须自己指定版本。

**用 `<properties>` 而不是直接写在 `<version>` 里的好处**：多个依赖共用同一个版本时，改一处即可。比如以后加 `mybatis-plus-jsqlparser`，也是 `${mybatis-plus.version}`。

**版本选择的依据**：

| 依赖 | 版本 | 依据 |
| --- | --- | --- |
| MyBatis-Plus | 3.5.7 | 3.5.9+ 要额外引 `jsqlparser`，3.5.7 更省事 |
| SpringDoc | 2.6.0 | 2.6.x 对应 Spring Boot 3.3 系列 |

**SpringDoc 版本必须和 Boot 对齐**：版本不匹配会出现 UI 白屏、`NoSuchMethodError`、文档不生成等问题。对应关系大致是：

| Spring Boot | SpringDoc |
| --- | --- |
| 3.0.x | 2.0.x ~ 2.1.x |
| 3.1.x | 2.2.x |
| 3.2.x | 2.3.x ~ 2.4.x |
| **3.3.x** | **2.5.x ~ 2.6.x** |
| 3.4.x | 2.7.x+ |

### 3.6 `spring-boot-maven-plugin` 干了什么

```xml
<plugin>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-maven-plugin</artifactId>
</plugin>
```

**核心功能是 `repackage`**：把普通 jar 重新打包成**可执行 fat jar**。

**普通 jar 的结构**：

```
canvas-server.jar
└── com/infinitecanvas/...
```

**repackage 后的结构**：

```
canvas-server.jar
├── META-INF/
│   └── MANIFEST.MF          ← Main-Class: JarLauncher
├── BOOT-INF/
│   ├── classes/             ← 你的代码
│   └── lib/                 ← 所有依赖 jar
└── org/springframework/boot/loader/   ← 启动器
```

**为什么能 `java -jar` 直接跑**：

`Main-Class` 不是你的 `CanvasApplication`，而是 `JarLauncher`。它负责：

1. 创建自定义的 `LaunchedURLClassLoader`
2. 把 `BOOT-INF/lib/` 下的所有 jar 加进 classpath
3. 反射调用 `Start-Class`（MANIFEST 里记录的真实主类）

**面试可讲**：「Spring Boot 的 fat jar 不是把依赖解压合并，而是**嵌套 jar**——用自定义 ClassLoader 加载 `BOOT-INF/lib/` 里的 jar。这样才能避免同名类冲突和 `META-INF` 覆盖。」

**`mvn spring-boot:run` 走的是另一条路**：直接 fork 一个 JVM 跑 `main` 方法，classpath 是本地仓库的 jar，**不经过 repackage**。所以开发时改代码生效快，但和生产 jar 的类加载方式不同。

## 四、docker-compose.yml

```yaml
services:
  mysql:
    image: mysql:8.0
    container_name: canvas-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: infinite_canvas
      TZ: Asia/Shanghai
    command:
      - --character-set-server=utf8mb4
      - --collation-server=utf8mb4_0900_ai_ci
    ports:
      - "3307:3306"
    volumes:
      - canvas-mysql-data:/var/lib/mysql
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-proot"]
      interval: 10s
      timeout: 5s
      retries: 10

  redis:
    image: redis:7-alpine
    container_name: canvas-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "6380:6379"
    volumes:
      - canvas-redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 10

volumes:
  canvas-mysql-data:
  canvas-redis-data:
```

### 4.1 端口映射 `3307:3306`

```
"宿主机端口:容器内端口"
```

**为什么是 3307**：本机 3306 已经有 MySQL 8.0 在跑，直接映射 3306 会冲突：

```
Error: Bind for 0.0.0.0:3306 failed: port is already allocated
```

**代价**：`application-dev.yml` 里的 JDBC URL 必须写 3307。**这两个文件是耦合的**，改端口要同时改。

**一个容易搞混的点**：

```yaml
ports:
  - "3307:3306"
```

- **左边**是宿主机（你的 Windows）
- **右边**是容器内部

所以容器里的 MySQL 还是监听 3306，只是宿主机用 3307 转发过去。**容器之间互相访问时用容器端口**（3306），不是 3307。

### 4.2 `MYSQL_DATABASE` 自动建库

```yaml
environment:
  MYSQL_DATABASE: infinite_canvas
```

MySQL 官方镜像启动时，如果这个变量存在，会：

1. 创建数据库 `infinite_canvas`
2. 用 `utf8mb4` 字符集（配合下面的 `--character-set-server`）
3. 把 root 用户的权限授予这个库

**这就是为什么不需要手动执行 `CREATE DATABASE`**——之前文档里那段手动建库的 SQL 已经不需要了。

**`MYSQL_ROOT_PASSWORD: root` 的风险**：只在本地容器用，不对外暴露（端口只映射到 127.0.0.1 的 3307……严格说是 `0.0.0.0:3307`，**同局域网的其他机器能访问**）。

**真要安全的话**：

```yaml
ports:
  - "127.0.0.1:3307:3306"   # 只绑本地回环
```

**本项目没这么做**：本地学习环境，且 3307 不常用，风险可接受。**生产环境绝不能这样**。

### 4.3 `TZ: Asia/Shanghai` 与字符集

```yaml
environment:
  TZ: Asia/Shanghai
command:
  - --character-set-server=utf8mb4
  - --collation-server=utf8mb4_0900_ai_ci
```

**`TZ` 解决什么**：容器默认 UTC。如果不设，`SELECT NOW()` 返回的时间比北京时间少 8 小时。

**实测验证**：

```bash
docker exec canvas-mysql mysql -uroot -proot -e "SELECT @@version, @@character_set_server, @@time_zone;"
# 8.0.46   utf8mb4   SYSTEM
```

`time_zone` 是 `SYSTEM`，表示跟随容器系统时区——容器设了 `TZ=Asia/Shanghai`，所以实际是东八区。

**字符集为什么必须显式指定**：

| 配置 | 不配的后果 |
| --- | --- |
| `utf8mb4` | MySQL 8 默认就是 `utf8mb4`，但显式写防止被镜像版本变更影响 |
| `utf8mb4_0900_ai_ci` | 8.0 的默认排序规则，大小写不敏感、重音不敏感 |

**为什么不用 `utf8`**：MySQL 的 `utf8` 是**阉割版**（最多 3 字节），存不了 emoji 和部分生僻字（4 字节）。`utf8mb4` 才是完整的 UTF-8。

**这个坑很经典**：用 `utf8` 建表，用户输入 emoji 直接报 `Incorrect string value: '\xF0\x9F...'`。

### 4.4 健康检查：`healthcheck`

```yaml
healthcheck:
  test: ["CMD", "mysqladmin", "ping", "-h", "127.0.0.1", "-uroot", "-proot"]
  interval: 10s
  timeout: 5s
  retries: 10
```

| 参数 | 含义 |
| --- | --- |
| `test` | 执行什么命令判断健康 |
| `interval` | 每 10 秒检查一次 |
| `timeout` | 单次检查超过 5 秒算失败 |
| `retries` | 连续失败 10 次才标记 `unhealthy` |

**为什么 MySQL 用 `mysqladmin ping` 而不是 `mysql -e "SELECT 1"`**：

`mysqladmin ping` 是**最轻量**的存活检测（只看服务端能否响应握手），不需要建立完整会话。而且 MySQL 镜像**自带** `mysqladmin`，不用额外装。

**注意 `-h 127.0.0.1` 不能省**：不指定 host 时，`mysqladmin` 可能尝试走 Unix socket，在某些镜像版本里 socket 还没就绪会误报。

**健康检查的价值**：

```bash
docker compose ps
# NAME           STATUS
# canvas-mysql   Up 2 minutes (healthy)     ← 这个 (healthy)
# canvas-redis   Up 2 minutes (health: starting)
```

**没有它的话**：容器 `Up` 不代表服务可用。MySQL 初始化数据目录要 20~40 秒，这期间容器是 `Up` 但连不上——应用启动太早就会报 `Communications link failure`。

**实测数据**：本项目 MySQL 容器从启动到 `healthy` 约 **25 秒**。

**阶段 8 的做法**：应用容器用 `depends_on` + `condition: service_healthy`，保证中间件就绪再启动：

```yaml
canvas-server:
  depends_on:
    mysql:
      condition: service_healthy
    redis:
      condition: service_healthy
```

**这个特性在 Compose 里是有版本要求的**：`condition: service_healthy` 需要 Compose v2.1+ 才在 `docker compose`（非 swarm）里生效。当前环境是 v2.35.1，支持。

### 4.5 命名卷与数据持久化

```yaml
volumes:
  - canvas-mysql-data:/var/lib/mysql
```

```yaml
volumes:
  canvas-mysql-data:
  canvas-redis-data:
```

**三种挂载方式对比**：

| 类型 | 写法 | 数据位置 | 适用 |
| --- | --- | --- | --- |
| **命名卷**（当前） | `canvas-mysql-data:/var/lib/mysql` | Docker 管理的目录（`/var/lib/docker/volumes/...`） | **数据库**（推荐） |
| 绑定挂载 | `./data:/var/lib/mysql` | 项目目录下，可见 | 配置文件、日志、需要直接看的数据 |
| 匿名卷 | `/var/lib/mysql` | Docker 随机命名 | 临时数据（不推荐） |

**为什么数据库用命名卷而不是绑定挂载**：

- 绑定挂载在 Windows 上有**文件权限和换行符问题**，MySQL 容易起不来
- 命名卷由 Docker 管理，性能更好（不经过 Windows 文件系统转换层）
- 备份/迁移用 `docker run --rm -v` 更规范

**命名卷的名字规则**：

```
{compose项目名}_{卷名}
```

本项目：`canvas-java_canvas-mysql-data`

**项目名默认是目录名**。这就是为什么把工程从 `infinite-canvas-main/canvas-java` 移到 `D:\project\canvas-java` 后，**卷还能继续用**——两次的目录名都叫 `canvas-java`。

**如果需要显式指定项目名**：

```yaml
name: canvas-java    # Compose 顶层字段，覆盖目录名推断
```

**这个细节面试可以聊**：「Compose 的项目名决定卷和网络的前缀，默认取目录名。改动目录名会导致卷名变化，看起来就像『数据丢了』——实际上旧卷还在，只是没被挂载。」

### 4.6 `restart: unless-stopped`

| 值 | 行为 |
| --- | --- |
| `no`（默认） | 不自动重启 |
| `always` | 总是重启（包括手动停止后 Docker 重启） |
| **`unless-stopped`**（当前） | 除手动停止外都重启 |
| `on-failure` | 非 0 退出码才重启 |

**`unless-stopped` 的好处**：Docker Desktop 重启后，容器自动恢复；但你手动 `docker compose stop` 的容器不会被莫名其妙拉起来。

**这对开发体验很重要**：Docker Desktop 每次开机要手动启动，启动后容器自动恢复，不用再执行 `docker compose up -d`。

## 五、镜像拉取的现实问题

这部分是**实测经验**，写进面试可以体现「真踩过坑」。

### 5.1 国内的拉取困境

**实测耗时**：

| 镜像 | 大小 | 耗时 |
| --- | --- | --- |
| `redis:7-alpine` | 39.6MB | 约 5 分钟 |
| `mysql:8.0` | 约 600MB | **15 分 40 秒** |

**过程中的现象**：

```
a63160a5eda1: Retrying in 8 seconds
a63160a5eda1: Retrying in 7 seconds
...
```

**关键认知**：`Retrying` **不是失败**，是某一层下载中断后自动重试。**只要层 ID 相同，重试会复用已下载的部分**——中途 `Ctrl+C` 才会真的白等。

### 5.2 加速器的存活检测

`daemon.json` 里配的镜像源不一定都活着。检测方法：

```bash
for m in docker.1panel.live docker.m.daocloud.io docker.1ms.run dockerproxy.com; do
  echo "$m -> $(curl -s -o /dev/null -w '%{http_code}' --max-time 8 https://$m/v2/)"
done
```

**结果解读**：

| 返回码 | 含义 |
| --- | --- |
| `200` | 完全可用 |
| `401` | **也正常**——服务活着，只是需要 token 认证 |
| `000` | 连接失败，**已失效** |

**实测结果**：

```
docker.1panel.live      -> 200   ✅ 可用
docker.m.daocloud.io    -> 401   ✅ 可用（需 token）
docker.1ms.run          -> 401   ✅ 可用
dockerproxy.com         -> 000   ❌ 已失效
docke.nju.edu.cn        -> 000   ❌ 已失效
hub.rat.dev             -> 000   ❌ 已失效
```

**为什么大部分都死了**：2024 年后国内大量公共镜像加速器关闭了公开服务。**这就是为什么拉取这么慢**——能用的几个在限速。

### 5.3 拉取卡住时的三步排查

```bash
# ① 看镜像到底下来没有
docker images | grep -E "mysql|redis"

# ② 单独拉一个，看真实进度（compose 会吞掉进度条）
docker pull mysql:8.0

# ③ 测加速器存活
for m in ...; do curl ...; done
```

**第 ② 步的关键**：`docker compose up -d` **不显示拉取进度**，会让人以为卡死。单独 `docker pull` 能看到每一层的百分比和速度。

### 5.4 完全拉不动的备用方案

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 换镜像源 | 试 `docker.1ms.run/library/mysql:8.0` 全限定名 | 需要几次尝试 |
| 离线导入 | 别人导出 `docker save`，你 `docker load` | 需要另一台机器 |
| 用本机已装服务 | 直接连本机 MySQL 3306 / Memurai 6379 | 要改配置，且 root 密码未知 |
| 云数据库 | 阿里云 RDS 免费试用 | 要联网，有成本 |

**本项目最终用的是第一种 + 耐心等待**。

## 六、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| parent | `spring-boot-starter-parent` | 依赖仲裁 + 插件配置一步到位 | import BOM——需要兼容公司 parent |
| MP starter | `spring-boot3-starter` | Boot 3 唯一可用 | 普通 starter——`javax` 不兼容 |
| MP 版本 | 3.5.7 | 避开 3.5.9+ 的 jsqlparser 拆包 | 最新版——要额外引依赖 |
| MySQL 驱动 | `runtime` | 代码不直接 import，靠 SPI 加载 | `compile`——可能耦合内部类 |
| Lombok | `optional` + 打包排除 | 编译期工具，运行期不需要 | 默认——jar 变大 |
| 中间件端口 | 3307 / 6380 | 避开本机已有服务 | 3306 / 6379——冲突 |
| 数据持久化 | 命名卷 | Windows 上权限问题少，性能好 | 绑定挂载——MySQL 可能起不来 |
| 健康检查 | 双向都配 | 避免应用启动早于中间件就绪 | 不配——启动顺序靠人工把握 |
| 重启策略 | `unless-stopped` | Docker 重启后自动恢复 | `always`——手动停止的也被拉起来 |

## 七、面试考察点

### 基础题

**Q1：`spring-boot-starter-parent` 和 `spring-boot-dependencies` 有什么区别？**

答题要点：
- `parent`：依赖版本仲裁 + **Maven 插件默认配置** + 资源过滤（`@...@`），但**只能单继承**
- `dependencies`（BOM）：只有版本仲裁，通过 `dependencyManagement` + `import` 引入
- 公司有统一 parent 时只能用 BOM，因为 Maven 不支持多继承

**Q2：Maven 的四种依赖作用域？**

答题要点：

| 作用域 | 编译 | 运行 | 打包 | 例子 |
| --- | --- | --- | --- | --- |
| `compile` | ✅ | ✅ | ✅ | 业务依赖 |
| `runtime` | ❌ | ✅ | ✅ | MySQL 驱动 |
| `provided` | ✅ | ❌ | ❌ | Servlet API |
| `test` | ❌ | ❌ | ❌ | JUnit |

**Q3：什么是 starter？**

答题要点：
- 一个「依赖聚合 + 自动配置」的组合包
- `starter` 本身通常只有 `pom.xml`（引入一组依赖），自动配置类在同名的 `autoconfigure` 模块
- 用户加一个 starter 就获得「依赖 + 默认配置」，这是 Spring Boot 开箱即用的核心
- 例：`spring-boot-starter-web` = `spring-webmvc` + `tomcat` + `jackson` + 自动配置

### 进阶题

**Q4：Maven 依赖冲突的仲裁规则？**

答题要点：
- **路径最短优先**：直接依赖 > 一级传递 > 二级传递
- **第一声明优先**：路径长度相同时，`pom.xml` 里先声明的赢
- 排查：`mvn dependency:tree -Dverbose`
- 解决：`<exclusions>` 排除、`<dependencyManagement>` 锁定版本

**Q5：Spring Boot 的 fat jar 是怎么做到 `java -jar` 直接跑的？**

答题要点：
- `spring-boot-maven-plugin` 的 `repackage` 目标重新打包
- 结构：`BOOT-INF/classes`（业务代码）+ `BOOT-INF/lib`（依赖 jar 原样嵌套）+ 启动器
- `MANIFEST.MF` 的 `Main-Class` 是 `JarLauncher`，`Start-Class` 是真实主类
- `JarLauncher` 创建 `LaunchedURLClassLoader` 加载嵌套 jar
- **不是解压合并**，避免同名类和 `META-INF` 冲突

**Q6：`optional` 和 `provided` 有什么区别？**

答题要点：
- `provided`：**作用域**，编译期有、运行期由容器提供、不打包
- `optional`：**传递性控制**，不是作用域，表示「不传递给下游依赖」
- Lombok 用 `optional`：防止别人依赖本项目时也被迫引 Lombok

**Q7：`docker-compose` 的健康检查和 `depends_on` 怎么配合？**

答题要点：
- 只有 `healthcheck` 定义了，`depends_on` 才能用 `condition: service_healthy`
- 单纯 `depends_on`（不带 condition）只保证**启动顺序**，不保证**就绪**
- MySQL 初始化要 20~40 秒，容器 `Up` 但还连不上——这就是要用 healthcheck 的原因

### 陷阱题

**Q8：用了 `mybatis-plus-boot-starter`（不带 spring-boot3）会怎样？**

答题要点：
- 启动失败，`NoClassDefFoundError: javax/servlet/http/HttpServletRequest` 之类的错
- 因为 Boot 3 全部迁到了 `jakarta.*`
- 必须用 `mybatis-plus-spring-boot3-starter`
- 同理：SpringFox 也是这个原因不可用（见 [09 篇](./09-接口文档.md)）

**Q9：Compose 项目名改了，数据库数据会丢吗？**

答题要点：
- **不会丢**，但会「看起来丢了」
- 命名卷的真实名字是 `{项目名}_{卷名}`
- 项目名默认取目录名，改了目录名就会挂到一个新的空卷
- 旧卷还在，可以用 `docker volume ls` 找到，`docker run -v` 挂载或改回去

**Q10：`ports: "3307:3306"` 里容器互相访问用哪个端口？**

答题要点：
- 容器之间用**容器端口**（3306），通过服务名访问：`mysql:3306`
- `3307` 只是**宿主机**的映射，给容器外（你的 IDEA、Navicat）用的
- 所以应用跑在容器里时，JDBC URL 是 `mysql:3306`；跑在 IDEA 里时是 `127.0.0.1:3307`

## 八、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| MP starter 选错 | 启动 `javax` 类找不到 | Boot 3 需要 `spring-boot3` 版 | 换坐标 |
| SpringDoc 版本不匹配 | UI 白屏 / 文档为空 | 和 Boot 版本不配 | 按兼容表选 |
| 配了 Redis pool 没加 `commons-pool2` | `ClassNotFoundException` | starter 不含它 | 加依赖 |
| 端口 3306 冲突 | `port is already allocated` | 本机已有 MySQL | 改 3307 |
| 换了项目目录 | 数据「丢失」 | 卷名变了 | 改回目录名或显式 `name:` |
| 绑定挂载 MySQL | 容器起不来 | Windows 文件权限 | 用命名卷 |
| `utf8` 建表 | 存 emoji 报错 | `utf8` 只有 3 字节 | 用 `utf8mb4` |
| 容器 `Up` 就启动应用 | `Communications link failure` | MySQL 还没初始化完 | 等 `healthy` |
| 拉镜像 `Retrying` 就中断 | 前功尽弃 | 误以为失败 | 让它跑完，会续传 |
