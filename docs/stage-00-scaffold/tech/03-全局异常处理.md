# 03 · 全局异常处理

> 对应源码：`common/exception/BizException.java`、`common/exception/GlobalExceptionHandler.java`

## 一、一句话定位

`BizException` 是「业务上说不行了」的表达方式，`GlobalExceptionHandler` 是「所有异常的统一出口」。

这两个类解决的问题是：**让 Controller 里不出现 try/catch，同时保证任何异常进去、统一结构出来**。

## 二、完整代码

### BizException.java

```java
@Getter
public class BizException extends RuntimeException {

    private final ResultCode resultCode;

    public BizException(ResultCode resultCode) {
        super(resultCode.getMessage());
        this.resultCode = resultCode;
    }

    public BizException(ResultCode resultCode, String message) {
        super(message);
        this.resultCode = resultCode;
    }
}
```

### GlobalExceptionHandler.java

```java
@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BizException.class)
    public ResponseEntity<Result<Void>> handleBiz(BizException e) {
        log.warn("业务异常 code={} message={}", e.getResultCode().getCode(), e.getMessage());
        return build(e.getResultCode(), e.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<Result<Void>> handleInvalidArgument(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(error -> error.getField() + ": " + messageOf(error))
                .collect(Collectors.joining("; "));
        return build(ResultCode.BAD_REQUEST, message.isBlank() ? ResultCode.BAD_REQUEST.getMessage() : message);
    }

    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<Result<Void>> handleConstraint(ConstraintViolationException e) {
        return build(ResultCode.BAD_REQUEST, e.getMessage());
    }

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<Result<Void>> handleUnreadable(HttpMessageNotReadableException e) {
        log.warn("请求体解析失败: {}", e.getMessage());
        return build(ResultCode.BAD_REQUEST, "请求体格式错误");
    }

    @ExceptionHandler(NoResourceFoundException.class)
    public ResponseEntity<Result<Void>> handleNoResource(NoResourceFoundException e) {
        String path = e.getResourcePath();
        return build(ResultCode.NOT_FOUND, "接口不存在: " + (path.startsWith("/") ? path : "/" + path));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<Result<Void>> handleUnexpected(Exception e) {
        log.error("未处理异常", e);
        return build(ResultCode.INTERNAL_ERROR, ResultCode.INTERNAL_ERROR.getMessage());
    }

    private ResponseEntity<Result<Void>> build(ResultCode resultCode, String message) {
        return ResponseEntity.status(resultCode.getHttpStatus())
                .body(Result.<Void>fail(resultCode, message));
    }
}
```

## 三、逐段拆解

### 3.1 为什么 `BizException` 继承 `RuntimeException` 而不是 `Exception`

| | `RuntimeException`（当前） | `Exception` |
| --- | --- | --- |
| 是否强制 catch | 不用，**编译期不检查** | 必须 catch 或声明 throws |
| 事务回滚 | 默认回滚 | **默认不回滚**（需要 `@Transactional(rollbackFor = Exception.class)`） |
| 在 Service 里的写法 | 直接 `throw`，方法签名干净 | 每个方法签都要 `throws`，污染一整个调用链 |

**关键点：Spring 的 `@Transactional` 默认只对 `RuntimeException` 和 `Error` 回滚。**

这是面试高频陷阱：如果 `BizException extends Exception`，那么「先插入订单，再扣库存，库存不足抛异常」这个流程里，**订单不会回滚**，数据就脏了。除非显式写 `@Transactional(rollbackFor = Exception.class)`。

用 `RuntimeException` 就没有这个问题。

**延伸知识点**：业务异常该不该触发回滚？

有些团队会区分两种异常：`BizException`（可预期，如「用户名已存在」，不回滚）和 `SystemException`（不可预期，回滚）。实现方式是给异常加 `@Transactional(noRollbackFor = BizException.class)`。本项目阶段 1 之后如果遇到「业务校验需要回滚」的场景，会再细化。

### 3.2 为什么异常里要带 `ResultCode`

```java
private final ResultCode resultCode;
```

异常本身携带了「该翻译成哪个错误码」的信息，所以全局处理器不需要写一长串 `if (e instanceof XxxException)`：

```java
return build(e.getResultCode(), e.getMessage());   // 直接取
```

**对比常见写法**：

```java
// 很多项目的写法，用自定义 code
public class BizException extends RuntimeException {
    private int code;
    public BizException(int code, String message) { ... }
}

// 使用处
throw new BizException(40001, "用户名太短");
```

问题：`40001` 是魔法数字，写错没人拦。用 `ResultCode` 枚举就有编译期检查——`ResultCode.USERNAME_TOO_SHORT` 拼错了 IDEA 直接标红。

### 3.3 `@RestControllerAdvice` 到底做了什么

这个注解是组合：

```java
@ControllerAdvice          // 声明这是一个「全局增强器」，被组件扫描收集
@ResponseBody              // 方法返回值走 HttpMessageConverter 序列化成 JSON
```

`@ControllerAdvice` 的实现原理：

1. 容器启动时，`ControllerAdviceBean` 搜集所有带 `@ControllerAdvice` 的 Bean
2. `ExceptionHandlerExceptionResolver` 遍历这些 Bean，建立「异常类型 → 处理方法」的映射表
3. 请求处理过程中抛异常，`DispatcherServlet` 调用 `processHandlerException()`，交给解析器链
4. 解析器按「**最具体的异常类型优先**」匹配，找到方法后反射调用

**为什么它只对 Controller 层生效**：

拦截点在 `DispatcherServlet`。如果异常发生在**过滤器（Filter）**里，此时还没进 `DispatcherServlet`，全局处理器根本抓不到——这个坑见 3.6。

### 3.4 异常匹配顺序：为什么 `Exception.class` 放最后也能正确匹配

`handleUnexpected` 处理的是 `Exception.class`，理论上能匹配所有异常。但实际上 `BizException` 会走 `handleBiz`，不会走兜底。

规则是 **`ExceptionHandlerMethodResolver` 按「继承距离」排序**：先找异常类本身，找不到再找父类，`Exception` 是最顶层，永远最后被选中。

**如果两个处理器匹配优先级相同会怎样**：Spring 抛 `IllegalStateException: Ambiguous @ExceptionHandler method mapped for ...`，启动直接失败。所以不要写 `handleA(Exception)` 和 `handleB(RuntimeException)` 之外的重复层级。

**一个容易忽略的点**：如果有 `@ExceptionHandler(Throwable.class)`，它会比 `Exception.class` 更晚匹配（`Throwable` 是 `Exception` 的父类），但能捕获 `Error`（如 `OutOfMemoryError`）。本项目没加，因为 `Error` 属于 JVM 层面问题，捕获了也做不了什么。

### 3.5 五种异常的来源与处理差异

| 异常 | 什么时候抛 | 为什么要单独处理 | 处理方式 |
| --- | --- | --- | --- |
| `BizException` | 业务主动 `throw` | 可预期，不是故障 | `warn` 级别，用自带 code |
| `MethodArgumentNotValidException` | `@Valid` 校验 `@RequestBody` 失败 | 要把字段名和原因拼给前端 | 遍历 `FieldErrors` 拼接 |
| `ConstraintViolationException` | `@Validated` 校验方法参数（`@RequestParam` 上的约束）失败 | 和上面不是同一个异常类 | 直接用 `e.getMessage()` |
| `HttpMessageNotReadableException` | JSON 语法错误、类型不匹配、缺 body | 原始 message 会暴露类名（如 `Cannot deserialize value of type Long from String "abc"`） | 只回「请求体格式错误」 |
| `NoResourceFoundException` | **路径不存在**（Spring 6.1+ 新增） | 不处理会返回 Spring 默认的 `{"timestamp":...,"status":404,"error":"Not Found","path":...}`，破坏统一结构 | 翻译成 404 统一结构 |
| `Exception` | 其他一切 | 兜底 | `error` 级别 + 完整堆栈，回通用文案 |

#### 两个校验异常为什么不合并

```java
@ExceptionHandler(MethodArgumentNotValidException.class)   // @RequestBody + @Valid
@ExceptionHandler(ConstraintViolationException.class)      // @Validated + 方法参数
```

- `MethodArgumentNotValidException`：校验的是**对象**（`@RequestBody UserDTO dto`），`BindingResult` 里能拿到字段级错误
- `ConstraintViolationException`：校验的是**方法参数**（`@RequestParam @Min(1) int page`），异常里是 `ConstraintViolation` 集合

两者没有继承关系，必须分开处理。**这是阶段 1 做注册接口时立刻会遇到的**：`@RequestBody` 的 `@NotBlank` 走前者，`@RequestParam` 的 `@Min` 走后者。

#### `NoResourceFoundException` 的前导斜杠

```java
String path = e.getResourcePath();
return build(ResultCode.NOT_FOUND, "接口不存在: " + (path.startsWith("/") ? path : "/" + path));
```

`getResourcePath()` 返回的是 **`v1/not-exist`**，不带前导斜杠。这是实测发现的（第一次跑出来文案是「接口不存在: v1/not-exist」，看着别扭），所以补了 `startsWith` 判断。

**面试可以聊这个细节**：说明你是真的跑过、看过输出，而不是照抄教程。

### 3.6 最关键的坑：Filter 里的异常抓不到

这是 **60% 的候选人答不上来**的问题。

```
请求 → Filter 链 → DispatcherServlet → HandlerInterceptor → Controller
         ↑                                    ↑
    异常在这里抛，                        异常在这里抛，
    @ControllerAdvice 抓不到              @ControllerAdvice 能抓到
```

**为什么**：`@ControllerAdvice` 的异常处理挂在 `DispatcherServlet#processDispatchResult` 上，Filter 在它外面。

**本项目现在就有一个真实案例**：`TraceIdFilter`（见 [04 篇](./04-链路追踪.md)）。如果以后在里面加鉴权逻辑并抛异常，`GlobalExceptionHandler` **完全抓不到**，客户端会收到 Tomcat 默认的 HTML 错误页。

**三种解决办法**：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 在 Filter 内部自己写响应 | `response.setStatus(...)` + 手写 JSON | 简单粗暴，但和统一结构会不一致 |
| Filter 里 try-catch 后转发到 `/error` | `request.setAttribute(...)` + `RequestDispatcher.forward("/error")` | 需要配 `ErrorController` |
| **改用 `HandlerInterceptor`** | 拦截器在 `DispatcherServlet` 内部，异常能被统一处理 | 只做参数级、不涉及流的逻辑 |
| 阶段 1 的做法 | Spring Security 的 `AuthenticationEntryPoint` / `AccessDeniedHandler` 自己处理 | 认证授权专用 |

**阶段 1 引入 Spring Security 后要特别注意**：`401` / `403` 是 Security 过滤器链抛的，必须在 Security 配置里注册 `AuthenticationEntryPoint` 和 `AccessDeniedHandler` 才能返回统一结构。这是下一个阶段的重要工作项。

### 3.7 为什么未知异常不回显 `e.getMessage()`

```java
@ExceptionHandler(Exception.class)
public ResponseEntity<Result<Void>> handleUnexpected(Exception e) {
    log.error("未处理异常", e);                                  // 完整堆栈进日志
    return build(ResultCode.INTERNAL_ERROR, ResultCode.INTERNAL_ERROR.getMessage());  // 只回"服务暂时不可用"
}
```

**如果回显 `e.getMessage()` 会泄露什么**：

| 异常类型 | message 里包含 | 危害 |
| --- | --- | --- |
| `SQLException` | `Table 'infinite_canvas.t_user' doesn't exist` | 泄露**表名**、**库名** |
| `BadSqlGrammarException` | 完整 SQL 片段，有时带参数值 | 泄露**字段结构**、**数据** |
| `NullPointerException` | `Cannot invoke "com.xxx.UserService.get()" because "this.userService" is null` | 泄露**类名**、**包结构** |
| `ConnectException` | `Connection refused: /127.0.0.1:3307` | 泄露**内网地址**、**端口** |

这些都是 OWASP 里明确列出的**信息泄露（Information Disclosure）**风险。

**正确做法**：日志里留全部信息（`log.error("未处理异常", e)` 带堆栈），响应里只给通用文案 + traceId，让用户把 traceId 给你，你去日志里查。

**这也是 traceId 设计价值的另一个体现**——没有它，你就得在一堆 error 里猜是哪一个请求。

### 3.8 日志级别为什么这么分

| 异常 | 级别 | 理由 |
| --- | --- | --- |
| `BizException` | `warn` | 业务上说不行了，是**预期内**的流程分支。用 error 会让错误率监控失真 |
| 参数校验失败 | 不打日志或 `warn` | 同上，爬虫乱请求会有大量此类日志 |
| 请求体解析失败 | `warn` | 可能是客户端 bug，值得关注但不是服务故障 |
| 未知异常 | `error` + 堆栈 | 真正的故障，必须告警 |

**面试可以讲**：错误率告警的基线依赖日志级别的准确性。如果业务异常全打 error，线上 error 数量会高到告警无法配置——最后大家只能把告警关了，等于没有。

## 四、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 异常基类 | `RuntimeException` | 不污染方法签名 + `@Transactional` 默认回滚 | `Exception`——必须显式 `rollbackFor` |
| 错误码载体 | 枚举 `ResultCode` | 编译期检查 | int 常量——魔法数字 |
| 未知异常文案 | 通用文案 | 防信息泄露 | 回显 message——泄露表名和内网地址 |
| 日志级别 | 业务 warn / 未知 error | 保证错误率监控可用 | 全 error——告警失效 |
| 统一出口 | `@RestControllerAdvice` | 一处配置全局生效 | 每个 Controller 写 try/catch——重复且易漏 |
| 404 处理 | 抓 `NoResourceFoundException` | 保持统一结构 | 用 `ErrorController` 重写——更重 |
| 参数校验 | 两种异常分开处理 | 二者无继承关系 | 只处理一个——另一个会落到兜底返回 500 |

## 五、面试考察点

### 基础题

**Q1：`@ControllerAdvice` 和 `@RestControllerAdvice` 有什么区别？**

答题要点：
- `@RestControllerAdvice = @ControllerAdvice + @ResponseBody`
- 前者方法返回值会被当作视图名解析（需要 `ModelAndView` 或模板引擎）
- 后者返回值直接走 `HttpMessageConverter` 序列化成 JSON
- REST 接口一律用后者

**Q2：一个请求进来抛了异常，Spring 是怎么找到对应的处理方法？**

答题要点：
- `DispatcherServlet#processHandlerException()` 触发
- 遍历 `HandlerExceptionResolver` 链，`ExceptionHandlerExceptionResolver` 负责 `@ExceptionHandler`
- 它在启动时已经扫描了所有 `@ControllerAdvice` Bean，建立了「异常类型 → 方法」的映射
- 匹配规则：从异常类本身开始向上找父类，**最近的匹配优先**

**Q3：为什么要自定义 `BizException` 而不用 `IllegalArgumentException`？**

答题要点：
- 语义明确：业务规则不满足 vs 编程错误
- 能携带 `ResultCode`，直接翻译成正确的业务码
- 可以统一 `warn` 级别记录，和系统异常区分开
- `IllegalArgumentException` 通常是参数非法，容易被归到 400，无法细分

### 进阶题

**Q4：Filter 里抛异常，`@RestControllerAdvice` 能捕获吗？**

答题要点（**这道题能答好是加分项**）：
- 不能。`@ControllerAdvice` 的处理入口在 `DispatcherServlet` 内，Filter 在它外面
- 现象：客户端收到 Tomcat 默认错误页，破坏统一结构
- 解决：Filter 内部自己写响应 / 转发到 `/error` / 改用拦截器 / 认证授权用 `AuthenticationEntryPoint`

**Q5：`@ExceptionHandler(Exception.class)` 会不会把 Spring 自己的异常也吞掉，导致问题难排查？**

答题要点：
- 会捕获，但要看情况
- Spring MVC 的一些异常（如 `HttpRequestMethodNotSupportedException` 405）如果不单独处理，会被兜底成 500——**这是真实的坑**
- 正确做法：兜底里判断 `e instanceof ErrorResponse`，用它的 status；或者显式列出常见的 `ResponseStatusException` 子类

> 本项目阶段 0 没有单独处理 `HttpRequestMethodNotSupportedException`（405）和 `HttpMediaTypeNotSupportedException`（415），阶段 1 加接口时如果遇到会补上。

**Q6：为什么业务异常用 `warn` 而不是 `error`？**

答题要点：
- `error` 级别应该代表「需要人介入的故障」
- 业务异常（用户名已存在、余额不足）是**预期内的流程分支**，用 error 会让错误率指标失真
- 实际后果：告警阈值没法设，最后只能关掉告警

**Q7：未知异常不回显 message，那前端怎么知道具体哪里错了？**

答题要点：
- 前端拿 traceId，用户截图反馈
- 后端按 traceId 在日志里定位，能看到完整堆栈
- 开发环境可以放宽（用 `@Profile("dev")` 单独配置回显），生产必须关
- 这是「安全 > 便利」的典型取舍

### 陷阱题

**Q8：`@Transactional` 遇到 `BizException` 会回滚吗？如果业务异常不该回滚怎么办？**

答题要点：
- 会。`BizException extends RuntimeException`，Spring 默认对 `RuntimeException` 回滚
- 不该回滚时用 `@Transactional(noRollbackFor = BizException.class)`
- 反过来，如果异常继承 `Exception`，默认**不回滚**，必须 `rollbackFor = Exception.class`——这是最经典的丢数据事故

**Q9：同一异常被两个 `@ExceptionHandler` 匹配会怎样？**

答题要点：
- 按继承距离选择最近的，不会报错
- 只有当两个处理器「距离相同」时才会报 `Ambiguous @ExceptionHandler`
- 例：同时有 `handleA(RuntimeException)` 和 `handleB(IllegalStateException)`，抛 `IllegalStateException` 走 handlerB

**Q10：全局异常处理器本身抛异常会怎样？**

答题要点：
- 会传播到 `DispatcherServlet` 的上一层，最终由容器处理（Tomcat 错误页）
- 常见原因：处理器里调用了可能失败的服务（如查字典表）
- 所以异常处理器里要保持「无依赖」，只做结构转换

## 六、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| `BizException extends Exception` | 事务不回滚，数据脏 | `@Transactional` 默认只回滚 `RuntimeException` | 改继承 `RuntimeException` |
| 只处理 `MethodArgumentNotValidException` | `@RequestParam` 校验失败返回 500 | 参数级校验抛的是 `ConstraintViolationException` | 两个都加处理器 |
| 兜底回显 `e.getMessage()` | 响应里出现表名、SQL | 信息泄露 | 只回通用文案 |
| 所有异常打 `error` | 错误率指标虚高，告警无法配置 | 日志级别语义用错 | 业务异常用 `warn` |
| 只依赖 `@RestControllerAdvice` | Filter 异常返回 HTML | 处理入口在 DispatcherServlet 内 | Filter 自己处理 |
| 没处理 `NoResourceFoundException` | 404 返回 Spring 默认结构 | Spring 6.1 后路径不存在走这个异常 | 单独加处理器 |
| 405/415 落到兜底 | 返回 500 而非 405/415 | 没显式处理 | 阶段 1 补上 |
