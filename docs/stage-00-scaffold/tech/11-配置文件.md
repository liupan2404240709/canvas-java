# 11 · 配置文件

> 对应源码：`resources/application.yml`、`resources/application-dev.yml`、`resources/logback-spring.xml`

## 一、一句话定位

三个文件分别管：**应用行为**（端口、路径前缀、框架参数）、**环境差异**（数据库地址账号）、**日志输出**（格式、滚动、traceId）。

配置项是「不需要写代码就能改变行为」的地方，也是最容易出事故的地方——**面试问配置文件，本质是问「你知不知道这些参数改了会怎样」**。

## 三、逐段拆解

### 3.1 `server.port: 8081` 与 `context-path: /api`

```yaml
server:
  port: 8081
  servlet:
    context-path: /api
```

**为什么是 8081 不是 8080**：开发机上 8080 被另一个 Spring Boot 项目占了。**这是环境约束，不是技术选择**——部署到服务器时改回 8080 即可（改配置不改代码）。

**`context-path` 的价值**：

```
设置前：http://127.0.0.1:8081/v1/health
设置后：http://127.0.0.1:8081/api/v1/health
```

配合 `ApiPath.V1 = "/v1"`，Controller 上一行：

```java
@RequestMapping(ApiPath.V1 + "/health")   // → /api/v1/health
```

**好处**：
1. **前缀只配一次**。不用在每个 `@RequestMapping` 上写 `/api`
2. **Nginx 转发好写**。`location /api/ { proxy_pass http://backend; }` 一条规则覆盖所有接口
3. **前后端路径规划清晰**。`/api/*` 是后端，其他路径可以留给静态资源

**代价（必须知道）**：
- Swagger 地址变成 `/api/swagger-ui.html`（第一次访问 404 就是这么来的）
- 所有接口测试的 URL 都要带 `/api`
- 如果将来用 Nginx 再代理一层，要注意**前缀是否重复**（`proxy_pass` 结尾有没有 `/` 差别巨大）

**一个常见的坑**：

```nginx
# 情况 A：转发后路径是 /api/api/v1/health  ← 前缀重复
location /api/ {
    proxy_pass http://backend;
}

# 情况 B：转发后路径是 /api/v1/health  ← 正确
location /api/ {
    proxy_pass http://backend/api/;
}
```

因为后端本身有 `/api` 前缀，Nginx 的 `location /api/` 匹配到之后，如果 `proxy_pass` 不带路径，会把完整路径原样转发（`/api/v1/health`），后端也认这个路径——**情况 A 其实是对的**。但如果 `location /` 加 `proxy_pass http://backend/api/`，就会造成 `/api/api/`。

**结论**：这类前缀叠加问题，调试时**先看 Nginx 的 access log 里转发的实际路径**，比猜快得多。

### 3.2 `spring.profiles.active: dev`

```yaml
spring:
  profiles:
    active: dev
```

**作用**：额外加载 `application-dev.yml`，且其中的配置**覆盖** `application.yml` 的同名项。

**加载顺序**（后面的覆盖前面的）：

```
application.yml → application-dev.yml
```

**profile 的多种激活方式**（优先级从高到低）：

| 方式 | 写法 | 适用 |
| --- | --- | --- |
| 命令行参数 | `--spring.profiles.active=prod` | 临时切换 |
| 环境变量 | `SPRING_PROFILES_ACTIVE=prod` | **容器部署（最常用）** |
| `application.yml` | `profiles.active: dev` | 本地开发默认值 |
| JVM 参数 | `-Dspring.profiles.active=prod` | 传统部署 |

**注意**：把它写在 `application.yml` 里意味着「默认 dev」——**打包成镜像时要靠环境变量覆盖**，否则生产环境会连到开发库。这是很常见的部署事故。

**阶段 8 的做法**：

```dockerfile
ENV SPRING_PROFILES_ACTIVE=prod
```

### 3.3 `jackson` 两个配置（详见 [06 篇](./06-JSON序列化.md)）

```yaml
jackson:
  time-zone: GMT+8
  default-property-inclusion: non_null
```

| 配置 | 作用 | 注意 |
| --- | --- | --- |
| `time-zone` | `Date` / `Instant` 的序列化时区 | **对 `LocalDateTime` 无效** |
| `default-property-inclusion: non_null` | null 字段不输出 | 前端 TypeScript 要声明可选 |

**这里故意没有 `date-format`**：阶段 0 写过，实测对 `LocalDateTime` 无效，已删掉避免误导（详见 06 篇 3.1）。

### 3.4 `multipart` 上传限制

```yaml
servlet:
  multipart:
    max-file-size: 20MB      # 单个文件
    max-request-size: 64MB   # 整个请求（含多个文件 + 表单字段）
```

**这两个参数的区别**：

| 参数 | 限制对象 | 超限时的报错 |
| --- | --- | --- |
| `max-file-size` | **一个** `MultipartFile` | `FileSizeLimitExceededException` |
| `max-request-size` | **整个** multipart 请求 | `SizeLimitExceededException` |

**为什么 `max-request-size` 要大于 `max-file-size`**：一次上传 3 个 20MB 的图片，总大小 60MB，单个文件都没超，但请求总量超了就会失败。64MB 允许「3 个 20MB 文件 + 一些表单字段」。

**阶段 3 会用到**：素材库上传图片。到时候要考虑：
- 图片实际大小分布（AI 生成的图可能 2~8MB）
- 超出限制时的错误提示（现在是 `MaxUploadSizeExceededException`，会被全局处理器兜底成 500，**文案不友好，阶段 3 要单独处理**）

> 按项目规范，「大小限制」属于会改变实际行为的边界值，阶段 3 落地前会再确认一次默认值。

### 3.5 MyBatis-Plus 全局配置

```yaml
mybatis-plus:
  configuration:
    map-underscore-to-camel-case: true      # 下划线转驼峰
  global-config:
    banner: false                            # 不打印 MP 的 banner
    db-config:
      id-type: assign_id                     # 雪花 ID
      logic-delete-field: deleted            # 逻辑删除字段名
      logic-delete-value: 1                  # 已删除
      logic-not-delete-value: 0              # 未删除
```

#### `map-underscore-to-camel-case: true`

数据库 `created_at` → Java `createdAt`。**这是 MyBatis 最重要的一个配置**，不开启的话所有下划线字段都映射不上，全是 null。

MyBatis-Plus 默认就是 `true`，这里显式写出来是为了**让人一眼看到，避免被误改**。

#### `id-type: assign_id`（雪花算法）

| 策略 | 说明 | 问题 |
| --- | --- | --- |
| `AUTO` | 数据库自增 | 分库分表后冲突；ID 可枚举（爬虫能遍历） |
| `INPUT` | 手动赋值 | 每处都要写 |
| `ASSIGN_ID`（当前） | 雪花算法，19 位 Long | **前端 JS 精度丢失**（见 [02 篇](./02-统一响应契约.md) 3.7） |
| `ASSIGN_UUID` | 32 位字符串 | 无序，B+ 树插入性能差 |

**雪花 ID 的结构**（64 bit）：

```
0 | 41 bit 时间戳 | 10 bit 机器 ID | 12 bit 序列号
```

- 41 位时间戳：可用 69 年
- 10 位机器 ID：支持 1024 个节点
- 12 位序列号：单节点每毫秒 4096 个

**优点**：趋势递增（对 B+ 树友好）、本地生成不依赖数据库、分布式不冲突。
**缺点**：19 位 Long 超过 JS 安全整数（2^53），**必须转 String 传输**。

#### 逻辑删除的三个参数

```yaml
logic-delete-field: deleted
logic-delete-value: 1
logic-not-delete-value: 0
```

配了之后，MyBatis-Plus 自动改写 SQL：

```sql
-- deleteById(1) 实际执行
UPDATE t_canvas SET deleted = 1 WHERE id = 1 AND deleted = 0

-- selectById(1) 实际执行
SELECT * FROM t_canvas WHERE id = 1 AND deleted = 0

-- selectList(...) 实际执行
SELECT * FROM t_canvas WHERE deleted = 0 AND ...
```

**逻辑删除的好处**：
- 数据可恢复
- 保留历史（审计、统计）
- 外键引用不会断

**坏处**：
- 表越来越大（需要定期归档）
- **唯一索引会失效**：`UNIQUE KEY(name)` 上，删掉 `name='a'` 后无法再插入 `name='a'`（因为旧记录还在，只是 `deleted=1`）
- 需要配合「带 `deleted` 的唯一索引」：`UNIQUE KEY(name, deleted)`

**这个坑阶段 2 建表时一定会遇到**（画布名称、用户名可能要求唯一），到时候用 `UNIQUE KEY(uk_name, deleted)` 解决。

### 3.6 `app.version` 与 `app.cors`

```yaml
app:
  version: 0.0.1
  cors:
    allowed-origins: http://localhost:5173,http://localhost:4173
```

**自定义配置放在 `app:` 下**——不要塞进 `spring:` 里，避免和框架配置混淆，也避免升级时冲突。

**`allowed-origins` 用逗号分隔的字符串，注入到 `String[]`**：

```java
@Value("${app.cors.allowed-origins}")
private String[] allowedOrigins;
```

Spring 会自动按逗号拆分。**注意**：如果某个 origin 本身含逗号（不可能，但理论上），这种写法会出错——所以生产级配置更适合用 YAML 列表：

```yaml
app:
  cors:
    allowed-origins:
      - http://localhost:5173
      - http://localhost:4173
```

两种都能注入到 `String[]`。列表写法更清晰，阶段 1 改配置结构时可以换。

### 4.1 JDBC URL 的六个参数

```
jdbc:mysql://127.0.0.1:3307/infinite_canvas
  ?useUnicode=true
  &characterEncoding=utf8
  &serverTimezone=Asia/Shanghai
  &useSSL=false
  &allowPublicKeyRetrieval=true
  &rewriteBatchedStatements=true
```

| 参数 | 作用 | 不配的后果 |
| --- | --- | --- |
| `useUnicode=true` + `characterEncoding=utf8` | 指定字符集 | 中文乱码 |
| `serverTimezone=Asia/Shanghai` | 声明服务端时区 | **时间差 8 小时**；MySQL 8 驱动不配会报 `The server time zone value ... is unrecognized` |
| `useSSL=false` | 关闭 SSL | 本地自签证书导致连接失败 + 一堆警告 |
| `allowPublicKeyRetrieval=true` | 允许获取公钥 | MySQL 8 用 `caching_sha2_password` 认证时会报 `Public Key Retrieval is not allowed` |
| `rewriteBatchedStatements=true` | **批量插入优化** | 批量插入性能差 10 倍以上 |

**`rewriteBatchedStatements` 值得单独说**（面试高频）：

**不开时**：`insertBatch` 1000 条 = 发 1000 次网络往返。

**开启后**：驱动把多条 `INSERT` 改写成一条：

```sql
INSERT INTO t VALUES (1,'a'),(2,'b'),(3,'c'),...
```

**性能差距**：1000 条插入，不开约 3~5 秒，开了约 0.1 秒——**差 30 倍以上**。

**注意**：它只对 `INSERT` 和 `UPDATE` 生效，且要求 SQL 结构相同（MyBatis-Plus 的 `saveBatch` 满足）。

### 4.2 HikariCP 五个参数（面试必考）

```yaml
hikari:
  pool-name: CanvasHikariPool
  minimum-idle: 5
  maximum-pool-size: 10
  connection-timeout: 3000
  idle-timeout: 600000
  max-lifetime: 1800000
```

| 参数 | 值 | 含义 | 调错的影响 |
| --- | --- | --- | --- |
| `pool-name` | `CanvasHikariPool` | 连接池名字 | 只影响日志可读性，多数据源时必须区分 |
| `minimum-idle` | 5 | 最小空闲连接数 | 太小：突发流量要临时建连接，慢 |
| `maximum-pool-size` | 10 | **最大连接数** | **太大：数据库连接数打满**；太小：请求排队 |
| `connection-timeout` | 3000ms | **从池里拿连接的最长等待** | 超时抛 `SQLTransientConnectionException` |
| `idle-timeout` | 600000ms（10min） | 空闲连接多久被回收 | 必须 < `max-lifetime` |
| `max-lifetime` | 1800000ms（30min） | 连接最长存活时间 | **必须小于数据库的 `wait_timeout`** |

#### 为什么 `max-lifetime` 必须小于 MySQL 的 `wait_timeout`

MySQL 默认 `wait_timeout = 28800` 秒（8 小时）——空闲 8 小时后服务端主动断开连接。

如果 HikariCP 的连接比这个活得久，就会出现：

```
应用从池里拿了一个"看起来正常"的连接
→ 实际服务端已经断开
→ 执行 SQL 报：Communications link failure / Connection reset
```

**这就是「长时间无请求后，第一个请求必然报错」的经典故障**。

HikariCP 官方建议：`max-lifetime` 比 `wait_timeout` **小 30 秒以上**。本项目配 30 分钟，MySQL 默认 8 小时，安全。

#### `connection-timeout: 3000` 的意义

健康检查接口里：

```json
"db": {"status":"DOWN","latencyMs":3001,"error":"Connection is not available, request timed out after 3000ms."}
```

3001ms 说明是**连接池拿不到连接**（数据库挂了或池被打满），不是 SQL 慢。这个值决定了**故障时请求等多久才失败**——3000ms 是「用户能忍」和「不让请求堆死」的折中。

#### `maximum-pool-size: 10` 够不够

HikariCP 官方给的公式：

```
connections = ((core_count * 2) + effective_spindle_count)
```

4 核机器 → 约 10 个连接。**连接数不是越大越好**——连接是数据库的稀缺资源，池太大反而因为上下文切换变慢。

当前 10 个，对学习项目够用。生产环境要按实际 QPS 和 SQL 耗时算：

```
需要的连接数 ≈ QPS × 平均SQL耗时(秒)
例：100 QPS × 0.01s = 1 个连接（理论值）
实际给 5~10 倍冗余
```

### 4.3 Redis 端口 6380 与连接池

```yaml
data:
  redis:
    host: 127.0.0.1
    port: 6380      # ← 容器映射端口
    database: 0
    timeout: 3s
    lettuce:
      pool:
        max-active: 16
        max-idle: 8
        min-idle: 2
        max-wait: 1s
```

**为什么是 6380**：本机 6379 是 Memurai（另一个 Redis 兼容服务），容器映射到 6380 避开冲突。

**`timeout: 3s`**：命令执行超时，不是连接超时。设置后避免 Redis 卡住导致请求一直挂着。

**`max-wait: 1s`**：从池里拿连接的最长等待，比 `timeout` 短——拿不到连接应该快速失败，而不是等 3 秒。

**`database: 0`**：Redis 有 16 个逻辑库（0~15），不同项目可以隔离。**注意 Redis Cluster 不支持多 database**，只能有 0。

## 五、logback-spring.xml

```xml
<configuration>
    <property name="LOG_HOME" value="${LOG_HOME:-logs}"/>
    <property name="PATTERN"
              value="%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId:-}] %logger{36} - %msg%n"/>

    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>${PATTERN}</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <appender name="FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_HOME}/canvas-server.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>${LOG_HOME}/canvas-server.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
            <maxFileSize>50MB</maxFileSize>
            <maxHistory>14</maxHistory>
            <totalSizeCap>1GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>${PATTERN}</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="CONSOLE"/>
        <appender-ref ref="FILE"/>
    </root>
</configuration>
```

### 5.1 为什么叫 `logback-spring.xml` 而不是 `logback.xml`

| 文件名 | 能力 |
| --- | --- |
| `logback.xml` | Logback **自己**先加载，此时 Spring 环境还没准备好 |
| **`logback-spring.xml`**（当前） | 由 **Spring Boot** 加载，支持 `<springProfile>`、`<springProperty>`、读取 `application.yml` |

**实际差别**：

```xml
<!-- logback.xml 里不能用（会报错或失效） -->
<springProfile name="dev">
    <root level="DEBUG"/>
</springProfile>

<!-- logback-spring.xml 里可以，按 profile 切日志级别 -->
```

**本项目现在没用到 profile 切换日志级别**，但阶段 8 会有：开发环境 DEBUG、生产 INFO。用 `logback-spring.xml` 就不用改代码。

### 5.2 `%X{traceId:-}` 与 04 篇的呼应

```
%d{yyyy-MM-dd HH:mm:ss.SSS} %-5level [%thread] [%X{traceId:-}] %logger{36} - %msg%n
```

拆开：

| 占位符 | 输出 | 示例 |
| --- | --- | --- |
| `%d{...}` | 时间 | `2026-11-12 20:00:00.123` |
| `%-5level` | 级别，左对齐 5 位 | `INFO ` / `ERROR` |
| `%thread` | 线程名 | `http-nio-8081-exec-1` |
| **`%X{traceId:-}`** | **MDC 里的 traceId，没有则空** | `cec6d4180e3f4878a2...` |
| `%logger{36}` | 类名，超 36 字符缩写 | `c.i.c.s.HealthService` |
| `%msg` | 日志内容 | |
| `%n` | 换行 | |

**`%logger{36}` 的缩写规则**：从左边开始缩，保留最右边的部分（因为右边最能标识类）。`com.infinitecanvas.canvas.service.HealthService` → `c.i.c.s.HealthService`。

**`%X{traceId:-}` 的 `:-`**：Logback 的默认值语法。不写的话，MDC 里没有 traceId 时输出 `traceId_IS_UNDEFINED`——很难看。

**这就是 [04 篇](./04-链路追踪.md) 里 `MDC.put` 的最终消费者**。整条链路：

```
TraceIdFilter 生成 → MDC.put → logback 的 %X 读取 → 日志行
```

### 5.3 `${LOG_HOME:-logs}` 环境变量占位符

```xml
<property name="LOG_HOME" value="${LOG_HOME:-logs}"/>
```

**含义**：优先读环境变量 `LOG_HOME`，没有就用相对路径 `logs`。

**为什么要可配置**：容器部署时日志目录往往要挂载到宿主机卷：

```yaml
# docker-compose.yml
volumes:
  - ./logs:/app/logs
environment:
  LOG_HOME: /app/logs
```

如果硬编码 `logs`，容器里的路径和宿主机对不上，日志就丢了。

**注意语法**：`${VAR:-default}` 是 Logback 的默认值语法（Shell 风格），不是 Spring 的 `${VAR:default}`（单冒号）。

### 5.4 滚动策略：`SizeAndTimeBasedRollingPolicy`

```xml
<fileNamePattern>${LOG_HOME}/canvas-server.%d{yyyy-MM-dd}.%i.log</fileNamePattern>
<maxFileSize>50MB</maxFileSize>
<maxHistory>14</maxHistory>
<totalSizeCap>1GB</totalSizeCap>
```

**这是「按时间 + 按大小」双维度滚动**：

| 参数 | 值 | 含义 |
| --- | --- | --- |
| `%d{yyyy-MM-dd}` | 按天 | 每天一个新文件 |
| `%i` | 序号 | **同一天内**超过 50MB 就递增（`.0`、`.1`、`.2`） |
| `maxFileSize` | 50MB | 单个文件上限 |
| `maxHistory` | 14 | 保留 14 天 |
| `totalSizeCap` | 1GB | **所有日志文件总量上限**，超了从最老的删 |

**为什么三个限制都要有**：

| 只配 `maxHistory` | 只配 `totalSizeCap` | 都配（当前） |
| --- | --- | --- |
| 某天日志暴涨，14 天内可能占几十 G | 保留天数不确定，排查历史问题找不到 | 天数 + 总量双保险 |

**`totalSizeCap` 的一个坑**：它必须大于 `maxFileSize`，否则会不停删文件。而且它的清理是「按天粒度」的——不会为了省 1MB 去删半个文件。

**实际文件命名**：

```
logs/
├── canvas-server.log                    ← 当前正在写的
├── canvas-server.2026-11-11.0.log       ← 昨天第 1 个
├── canvas-server.2026-11-11.1.log       ← 昨天第 2 个（超过 50MB 了）
└── canvas-server.2026-11-12.0.log       ← 今天
```

**注意 `canvas-server.log` 是「当前活动文件」**，不带日期。`tail -f` 追这个文件即可——滚动时 Logback 会自动切换到新文件，`tail -f` 能跟上（因为它按 inode 追）。

### 5.5 `<root level="INFO">` 与包级日志级别

```xml
<root level="INFO">
```

全局 INFO。而 `application.yml` 里：

```yaml
logging:
  level:
    com.infinitecanvas.canvas: info
```

**两者的关系**：

| 配置位置 | 作用 | 优先级 |
| --- | --- | --- |
| `logback-spring.xml` 的 `<root>` | 全局默认级别 + 输出目标 | 基础 |
| `application.yml` 的 `logging.level` | 按包覆盖级别 | **更高**（Spring Boot 会把 yml 配置应用到 Logback） |

**为什么两个都写**：`<root>` 里必须配 appender（输出到哪），`logging.level` 用来精确控制某个包的级别。

阶段 2 会有这样的需求：

```yaml
logging:
  level:
    com.infinitecanvas.canvas: info
    com.infinitecanvas.canvas.mapper: debug   # 只看 SQL
```

**注意 `mybatis-plus.configuration.log-impl: StdOutImpl`** 现在配的是「直接打印到控制台」——它**不走 Logback**，所以日志文件里没有 SQL。阶段 2 要改成：

```yaml
mybatis-plus:
  configuration:
    log-impl: org.apache.ibatis.logging.slf4j.Slf4jImpl
```

这样 SQL 才会进日志文件，也才会带上 traceId。

## 六、配置优先级的完整顺序

面试常问「配置从哪来、谁覆盖谁」。Spring Boot 2.4+ 的顺序（**后面的覆盖前面的**）：

```
1. 默认值（SpringApplication 里硬编码的）
2. @PropertySource 注解
3. Config Data（application.yml 等）
4. RandomValuePropertySource
5. 操作系统环境变量
6. Java 系统属性（-Dkey=value）
7. JNDI（java:comp/env）
8. ServletContext 初始化参数
9. ServletConfig 初始化参数
10. SPRING_APPLICATION_JSON
11. 命令行参数（--key=value）
12. 测试中的 @TestPropertySource
13. 测试中的 properties 属性
14. DevTools 全局设置
```

**日常只需要记住三条**：

```
命令行参数  >  环境变量  >  application-{profile}.yml  >  application.yml
```

**验证方法**（本项目实测过的一个坑）：

```bash
# 本会话的沙箱环境里有个 SERVER__PORT=51021
# 它被 Spring 当成 server.port，覆盖了 yml 里的 8081
env | grep SERVER__PORT
SERVER__PORT=51021        # ← 双下划线会被转成 server.port

# 解决：启动时去掉这个变量
env -u SERVER__PORT mvn spring-boot:run
```

**这是「环境变量覆盖配置文件」的一个真实案例**——Spring Boot 的**松散绑定**规则会把 `SERVER__PORT` 规范化为 `server.port`（双下划线表示层级分隔）。

**面试可以聊**：「配置不生效时，先确认有没有环境变量或命令行参数覆盖了它。可以用 `/actuator/env` 端点看某个配置项的最终来源（`propertySources` 会标出是哪一层提供的）。」

## 七、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 配置文件格式 | YAML | 层级清晰，支持列表 | properties——层级靠点号，长配置难读 |
| 端口 | 8081 | 避开本机已占用的 8080 | 8080——冲突 |
| 路径前缀 | `context-path: /api` | 配一次全局生效 | 每个 Controller 写 `/api`——易漏 |
| 环境隔离 | `application-dev.yml` | 数据库等差异集中 | 一份配置改来改去——易提交错 |
| 默认 profile | `dev`（yml 里） | 本地开箱即用 | 不给默认——每次要指定 |
| 日志文件 | `logback-spring.xml` | 支持 profile 和 Spring 属性 | `logback.xml`——不能用 `<springProfile>` |
| 滚动策略 | 时间 + 大小 | 双保险 | 只按时间——单日暴涨占满磁盘 |
| 连接池 | HikariCP（Boot 默认） | 性能最好的 Java 连接池 | Druid——监控功能强但更重 |

## 八、面试考察点

### 基础题

**Q1：Spring Boot 配置的优先级顺序？**

答题要点（记三条就够）：
```
命令行参数 > 环境变量 > application-{profile}.yml > application.yml
```
完整版还有 JNDI、系统属性、`@PropertySource` 等，但日常排查记住这三条。

**Q2：`context-path` 和 `@RequestMapping("/api")` 有什么区别？**

答题要点：
- `context-path` 是 Servlet 容器级别的，配置一次全局生效，且**影响所有路径**（包括 Swagger、Actuator）
- `@RequestMapping` 是 Spring MVC 级别，只影响那个 Controller
- 前者改一处就行，后者每个类都要写，容易漏

**Q3：HikariCP 的 `max-lifetime` 为什么要小于 MySQL 的 `wait_timeout`？**

答题要点（**高频**）：
- MySQL 空闲超过 `wait_timeout`（默认 8 小时）会主动断开连接
- 如果连接池的连接比这个活得久，池里会有「服务端已断开但客户端不知道」的死连接
- 用的时候报 `Communications link failure`
- 官方建议 `max-lifetime` 比 `wait_timeout` 小 30 秒以上

**Q4：`connection-timeout` 和 `socketTimeout` 有什么区别？**

答题要点：
- `connection-timeout`：**从连接池拿连接**的最长等待，超时抛 `SQLTransientConnectionException`
- `socketTimeout`：**SQL 执行**的网络读超时（JDBC URL 参数）
- 前者是「排队拿号」，后者是「办事太慢」

### 进阶题

**Q5：`rewriteBatchedStatements` 为什么能提升批量插入性能？**

答题要点：
- 不开：驱动把 `addBatch()` 的每条 SQL 单独发（1000 条 = 1000 次往返）
- 开启：改写成 `INSERT INTO t VALUES (...),(...),(...)` 一次发送
- 性能差 30 倍以上（实测 1000 条约 5s → 0.1s）
- 注意：要求 SQL 结构完全相同，且只对 INSERT/UPDATE 生效

**Q6：逻辑删除会给唯一索引带来什么问题？**

答题要点：
- `UNIQUE KEY(name)` 上，`name='a'` 软删除后（`deleted=1`）记录还在表里
- 再插入 `name='a'` 会**唯一键冲突**
- 解法：唯一索引带上 `deleted` 字段 → `UNIQUE KEY(uk_name, deleted)`
- 注意：这样只能允许「一条未删除 + 一条已删除」，多次软删同一名字还是冲突
- 彻底方案：`deleted` 存删除时间戳（`0` 表示未删，其他值为删除时刻），保证唯一

**Q7：`logback-spring.xml` 和 `logback.xml` 的区别？**

答题要点：
- `logback.xml`：Logback 原生加载，此时 Spring 环境未就绪
- `logback-spring.xml`：Spring Boot 加载，支持 `<springProfile>`、`<springProperty>`
- 要用 profile 区分日志级别必须用后者

**Q8：`maxHistory` 和 `totalSizeCap` 分别管什么？**

答题要点：
- `maxHistory`：按**天**保留，超过 14 天删
- `totalSizeCap`：按**总大小**限制，超过 1GB 从最老的删
- 只配前者：单日日志暴涨可能占几十 G
- 只配后者：保留天数不确定，排查历史问题找不到

### 陷阱题

**Q9：我改了 `application.yml` 的端口，重启还是原来的端口，为什么？**

答题要点（四个排查方向）：
1. **环境变量覆盖**（`SERVER_PORT` / `SERVER__PORT`）
2. 命令行参数 `--server.port=xxx`
3. IDEA 的 Run Configuration 里配了 VM 参数 `-Dserver.port=xxx`
4. 改了 `application-dev.yml` 但没重启 / 改的是 `target/classes` 里的副本

用 `/actuator/env/server.port` 查看最终生效值和来源。

**Q10：`spring.profiles.active: dev` 写在 `application.yml` 里有什么风险？**

答题要点：
- 打包成镜像后，如果没设环境变量，生产环境会用 `dev` profile
- 结果：连到开发数据库、Swagger 开着、日志级别是 DEBUG
- 正确做法：yml 里不写死，部署时用 `SPRING_PROFILES_ACTIVE` 环境变量指定

**Q11：`useSSL=false` 生产环境能用吗？**

答题要点：
- **不能**。本地开发关 SSL 是为了省事（自签证书麻烦）
- 生产环境数据库跨网络必须开 SSL，否则密码和数据明文传输
- 云数据库（RDS）通常强制 SSL
- 本项目现在只连本地容器，`useSSL=false` 可以；阶段 8 上云前要改

## 九、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 端口被环境变量覆盖 | 改了 yml 不生效 | 环境变量优先级更高 | `echo $SERVER_PORT` 排查 |
| 漏了 `serverTimezone` | 时间差 8 小时 | 驱动默认 UTC | 显式写 `Asia/Shanghai` |
| 没开 `rewriteBatchedStatements` | 批量插入极慢 | 每条单独发 | 加 URL 参数 |
| `max-lifetime` > `wait_timeout` | 偶发 `Communications link failure` | 连接被服务端断开 | 调小 `max-lifetime` |
| Swagger 404 | 漏了 `/api` | `context-path` | 用 `/api/swagger-ui.html` |
| `logback.xml` 里用 `<springProfile>` | 标签不生效 | 文件名不对 | 改 `logback-spring.xml` |
| `StdOutImpl` 打 SQL | 日志文件里没有 SQL | 不走 Logback | 改 `Slf4jImpl` |
| 逻辑删除 + 唯一索引 | 删除后无法重建同名 | 旧记录还在 | 唯一索引带 `deleted` |
