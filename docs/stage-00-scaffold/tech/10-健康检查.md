# 10 · 健康检查

> 对应源码：`controller/HealthController.java`、`service/HealthService.java`、`vo/HealthVO.java`

## 一、一句话定位

这三个文件是**唯一的一组完整业务代码**（Controller + Service + VO），也是后面所有模块的模板。

它同时是一个「活文档」：跑起来就能验证「工程骨架搭对了没有」——MySQL 通了没、Redis 通了没、统一响应生效没、traceId 有没有。

## 二、完整代码

### HealthController.java

```java
@Tag(name = "系统")
@RestController
@RequestMapping(ApiPath.V1 + "/health")
@RequiredArgsConstructor
public class HealthController {

    private final HealthService healthService;

    @Operation(summary = "健康检查", description = "依次探测 MySQL 与 Redis，并返回各自耗时")
    @GetMapping
    public Result<HealthVO> health() {
        return Result.ok(healthService.check());
    }
}
```

### HealthService.java

```java
@Slf4j
@Service
@RequiredArgsConstructor
public class HealthService {

    private final JdbcTemplate jdbcTemplate;
    private final StringRedisTemplate stringRedisTemplate;

    @Value("${spring.application.name}")
    private String appName;

    @Value("${app.version:unknown}")
    private String version;

    public HealthVO check() {
        HealthVO.Component db = probe(() -> jdbcTemplate.queryForObject("SELECT 1", Integer.class));
        HealthVO.Component redis = probe(() -> stringRedisTemplate.execute((RedisCallback<String>) RedisConnection::ping));
        boolean allUp = "UP".equals(db.status()) && "UP".equals(redis.status());
        return new HealthVO(appName, version, allUp ? "UP" : "DOWN", db, redis, LocalDateTime.now());
    }

    private HealthVO.Component probe(Callable<?> action) {
        long start = System.nanoTime();
        try {
            action.call();
            return HealthVO.Component.up(elapsedMs(start));
        } catch (Exception e) {
            log.warn("健康检查失败: {}", e.getMessage());
            return HealthVO.Component.down(elapsedMs(start), e.getMessage());
        }
    }

    private long elapsedMs(long startNano) {
        return (System.nanoTime() - startNano) / 1_000_000;
    }
}
```

### HealthVO.java

```java
public record HealthVO(String app, String version, String status,
                       Component db, Component redis, LocalDateTime checkedAt) {

    public record Component(String status, long latencyMs, String error) {

        public static Component up(long latencyMs) {
            return new Component("UP", latencyMs, null);
        }

        public static Component down(long latencyMs, String error) {
            return new Component("DOWN", latencyMs, error);
        }
    }
}
```

## 三、逐段拆解

### 3.1 三层各自只干一件事

| 层 | 类 | 职责 | **不该做什么** |
| --- | --- | --- | --- |
| Controller | `HealthController` | 接收请求、调用 Service、包装成 `Result` | 不写业务逻辑、不 try/catch、不直接调 Mapper |
| Service | `HealthService` | 探测逻辑、状态判定、异常收口 | 不关心 HTTP、不返回 `ResponseEntity` |
| VO | `HealthVO` | 出参结构 | 不含任何逻辑（除了静态工厂） |

**为什么 Controller 里没有 `try/catch`**：

```java
public Result<HealthVO> health() {
    return Result.ok(healthService.check());
}
```

只有两行。因为异常由 `GlobalExceptionHandler` 统一处理（见 [03 篇](./03-全局异常处理.md)），Controller 不需要操心。

**这是分层的核心价值**：Controller 足够薄，一眼能看出「这个接口做了什么、返回什么」。

**对比常见的坏味道**：

```java
// ❌ 业务逻辑塞在 Controller
@GetMapping
public Result<HealthVO> health() {
    try {
        Integer r = jdbcTemplate.queryForObject("SELECT 1", Integer.class);
        // ... 20 行业务
    } catch (Exception e) {
        // ... 10 行错误处理
    }
}
```

问题：无法复用（定时任务也要探测怎么办）、无法单测（要起 HTTP 环境）、越写越乱。

### 3.2 用 `Callable` 收口探测逻辑

这是本阶段最值得学的一个技巧。

**要探测两个组件，最直觉的写法是复制粘贴**：

```java
// ❌ 重复代码
long start = System.nanoTime();
HealthVO.Component db;
try {
    jdbcTemplate.queryForObject("SELECT 1", Integer.class);
    db = HealthVO.Component.up(elapsed(System.nanoTime() - start));
} catch (Exception e) {
    db = HealthVO.Component.down(elapsed(...), e.getMessage());
}

start = System.nanoTime();
HealthVO.Component redis;
try {
    stringRedisTemplate.execute(...);
    redis = HealthVO.Component.up(...);
} catch (Exception e) {
    redis = HealthVO.Component.down(...);
}
```

两个组件还好，将来加到 5 个（MySQL、Redis、MinIO、外部 API、消息队列）就是 5 段几乎一样的代码。

**当前写法**：

```java
private HealthVO.Component probe(Callable<?> action) {
    long start = System.nanoTime();
    try {
        action.call();
        return HealthVO.Component.up(elapsedMs(start));
    } catch (Exception e) {
        log.warn("健康检查失败: {}", e.getMessage());
        return HealthVO.Component.down(elapsedMs(start), e.getMessage());
    }
}
```

调用处变成一行：

```java
HealthVO.Component db = probe(() -> jdbcTemplate.queryForObject("SELECT 1", Integer.class));
HealthVO.Component redis = probe(() -> stringRedisTemplate.execute(...));
```

**为什么用 `Callable` 而不是 `Runnable`**：

| | `Runnable` | `Callable<V>` |
| --- | --- | --- |
| 有返回值 | ❌ | ✅ |
| 能抛受检异常 | ❌ | ✅ `throws Exception` |
| 用在哪 | `new Thread(...)` | 线程池 `submit()` |

`Callable.call()` 声明了 `throws Exception`，所以 `probe` 里的 `catch (Exception e)` 能捕获**受检异常**。如果用 `Runnable`，lambda 里抛受检异常编译不过。

**这个模式的名字**：**模板方法 + 回调**。把「固定流程」（计时、try-catch、构造结果）抽出来，把「可变部分」（具体探测动作）作为参数传入。

**面试可以讲**：「我用了 `Callable` 把『计时 + 异常捕获 + 结果封装』的模板逻辑收口，新增探针只需一行 lambda。这是策略模式的一种轻量实现，避免了 `if-else` 或重复的 try-catch。」

### 3.3 为什么用 `System.nanoTime()` 而不是 `currentTimeMillis()`

```java
private long elapsedMs(long startNano) {
    return (System.nanoTime() - startNano) / 1_000_000;
}
```

| | `currentTimeMillis()` | `nanoTime()` |
| --- | --- | --- |
| 语义 | **墙上时钟**（wall clock），返回从 1970-01-01 起的毫秒数 | **单调时钟**（monotonic），只用于测量时间间隔 |
| 会被改吗 | **会**。NTP 校时、用户手动改时间都会让它跳变 | 不会，单调递增 |
| 适合 | 记录「现在几点」 | **测量耗时** |
| 精度 | 毫秒 | 纳秒（实际精度取决于平台） |

**用 `currentTimeMillis` 测耗时的典型 bug**：

```java
long start = System.currentTimeMillis();
// ... 执行了 100ms
// 期间 NTP 校时把系统时间往前调了 1 秒
long cost = System.currentTimeMillis() - start;   // 结果是 -900，负数耗时
```

**结论**：测耗时一律用 `nanoTime`，记录时刻用 `currentTimeMillis` / `Instant.now()`。

**除以 `1_000_000` 为什么用下划线**：Java 7 的数字字面量分隔符，等价于 `1000000`，但不容易数错零。

### 3.4 探针用的具体 API

#### MySQL：`jdbcTemplate.queryForObject("SELECT 1", Integer.class)`

**为什么用 `JdbcTemplate` 而不是 Mapper**：

- 阶段 0 还没有 Mapper，也不该为了健康检查造一个
- `SELECT 1` 是最轻量的探针：不碰任何业务表，验证的是「连接可用」而不是「表存在」

**为什么不查 `SELECT 1 FROM DUAL`**：MySQL 支持 `SELECT 1`（Oracle 才必须带 `FROM DUAL`）。

**`JdbcTemplate` 是哪来的**：`spring-boot-starter-jdbc` 的 `DataSourceAutoConfiguration` 自动注册了 `JdbcTemplate` Bean。虽然 `pom.xml` 里没有显式引入 `starter-jdbc`，但 `mybatis-plus-spring-boot3-starter` 传递依赖了它。

#### Redis：`stringRedisTemplate.execute((RedisCallback<String>) RedisConnection::ping)`

```java
stringRedisTemplate.execute((RedisCallback<String>) RedisConnection::ping)
```

拆开看：

- `execute(RedisCallback<T>)`：拿到**底层连接**做操作，比 `opsForXxx()` 更底层
- `RedisConnection::ping`：方法引用，等价于 `conn -> conn.ping()`
- `(RedisCallback<String>)`：**必须有这个强转**，否则编译器无法确定重载

**为什么不用 `connectionFactory.getConnection().ping()`**：

那个写法要自己关连接：

```java
RedisConnection conn = factory.getConnection();
try {
    conn.ping();
} finally {
    conn.close();   // ← 忘了就连接泄漏
}
```

`execute(callback)` 内部帮你管理了获取和释放。

**为什么不用 `stringRedisTemplate.hasKey("xxx")`**：那会验证「key 存在」而不是「连接可用」，语义不对，而且要挑一个不存在的 key，很别扭。

**`PING` 是 Redis 的原生命令**，返回 `PONG`，是最标准的连通性测试。

**这里用 `StringRedisTemplate` 而不是自定义的 `RedisTemplate<String, Object>`**：`PING` 不涉及对象序列化，用最简单的就行（见 [07 篇](./07-Redis配置.md)）。

### 3.5 组件状态的三个字段

```java
public record Component(String status, long latencyMs, String error)
```

| 字段 | 值 | 设计意图 |
| --- | --- | --- |
| `status` | `UP` / `DOWN` | 用字符串而不是 boolean，和 Spring Boot Actuator 的约定一致（阶段 8 对接时不用改） |
| `latencyMs` | 毫秒数 | **失败时也记录**——能区分「连不上（3s 超时）」和「连上了但慢（800ms）」 |
| `error` | 失败原因 / null | 成功时是 null，配合 `non_null` 配置不会出现在 JSON 里 |

**为什么 `latencyMs` 失败时也要记**：这是一个很实用的设计。

```
"db": {"status":"DOWN","latencyMs":3001,"error":"Connection timed out"}
```

3001ms 说明是**超时**（HikariCP 的 `connection-timeout` 配的是 3000）。

```
"db": {"status":"DOWN","latencyMs":2,"error":"Access denied for user 'root'"}
```

2ms 说明是**认证失败**——网络通、服务在，只是密码错了。

**两个都是 DOWN，但排查方向完全不同**。这就是记录耗时的价值。

### 3.6 为什么整体 DOWN 还返回 HTTP 200

这是**刻意的设计**，也是面试可以聊的点。

```java
public Result<HealthVO> health() {
    return Result.ok(healthService.check());   // 永远 200
}
```

DOWN 时返回体是：

```json
{"code":0,"data":{"status":"DOWN","db":{"status":"DOWN",...}}}
```

**HTTP 状态码还是 200，`code` 还是 0**。

**理由**：

| 视角 | 解读 |
| --- | --- |
| 语义 | 「健康检查这个接口被成功执行了」是事实，200 正确；「依赖挂了」是**结果内容**，不是「接口失败」 |
| 可观测性 | 探测工具拿到 200 + body，能看到**具体哪个组件挂了、耗时多少**；如果返回 503，很多工具只看状态码，丢掉 body |
| 区分度 | 「服务进程死了」返回不了任何东西（连接拒绝）；「服务活着但依赖故障」能返回详细诊断——这两者必须能区分开 |

**什么时候该返回 503**：

阶段 8 接入 Spring Boot Actuator 后，`/actuator/health` 的行为是：

- 有 `HealthIndicator` 报 DOWN 时，返回 **HTTP 503**
- 这是给 **Kubernetes / 负载均衡** 用的：它们只看状态码，503 就把这个实例摘掉，不再转发流量

**两者的分工**：

| 端点 | 状态码 | 谁在用 |
| --- | --- | --- |
| `/api/v1/health`（当前） | 永远 200 | 人、监控面板、快速自检 |
| `/actuator/health`（阶段 8） | UP→200 / DOWN→503 | K8s、Nginx、负载均衡 |

**面试答题要点**：「自定义健康接口返回 200 是为了保留诊断信息，给人和监控看；标准化的 503 给负载均衡做摘流决策，两者不冲突，都保留。」

### 3.7 `@Value` 注入的两个细节

```java
@Value("${spring.application.name}")
private String appName;

@Value("${app.version:unknown}")
private String version;
```

**`:` 后面是默认值**。

| 写法 | 配置不存在时 |
| --- | --- |
| `@Value("${app.version}")` | **启动失败**：`Could not resolve placeholder 'app.version'` |
| `@Value("${app.version:unknown}")` | 注入 `unknown`，正常启动 |

**为什么 `appName` 不给默认值**：`spring.application.name` 是必填的（日志、链路追踪、注册中心都依赖它），配漏了应该立刻启动失败，而不是悄悄变成 `unknown`。

**为什么 `version` 给默认值**：版本号是辅助信息，缺了不影响服务运行，用 `unknown` 兜底更稳。

**这个取舍可以讲**：「必填配置不给默认值，让问题在启动时暴露；可选的辅助配置给默认值，避免因为一个非关键配置起不来。」

### 3.8 `@RequiredArgsConstructor` 构造器注入

```java
@RequiredArgsConstructor
public class HealthService {
    private final JdbcTemplate jdbcTemplate;
    private final StringRedisTemplate stringRedisTemplate;
}
```

Lombok 生成：

```java
public HealthService(JdbcTemplate jdbcTemplate, StringRedisTemplate stringRedisTemplate) {
    this.jdbcTemplate = jdbcTemplate;
    this.stringRedisTemplate = stringRedisTemplate;
}
```

Spring 4.3+ 后，**单构造器不需要 `@Autowired`**，自动注入。

**为什么用构造器注入而不是字段注入**：

| | 构造器注入（当前） | 字段注入 `@Autowired` |
| --- | --- | --- |
| 不可变性 | `final`，创建后不可改 | 可变，任何人能改 |
| 空指针风险 | 构造时就保证非 null | 可能因为漏注入而 NPE |
| 循环依赖 | **启动就报错**（好事，早发现） | 能启动但运行时报错/死循环 |
| 单元测试 | 直接 `new HealthService(mock1, mock2)` | 必须起 Spring 容器或用反射 |
| 依赖过多时 | 构造器参数爆炸（**信号：这个类职责太多**） | 看不出来 |

**Spring 官方明确推荐构造器注入**，IDEA 也会对字段注入报警告。

**面试可以讲**：「构造器注入让依赖不可变、测试友好，而且依赖太多时构造器会变得很长，这本身就是『该类违反单一职责』的提醒——字段注入会掩盖这个问题。」

### 3.9 为什么用 `@Value` 而不是 `@ConfigurationProperties`

```java
@Value("${app.version}")
private String version;
```

| | `@Value` | `@ConfigurationProperties` |
| --- | --- | --- |
| 适用 | 一两个散装配置 | 一组相关配置（如整个 `app.cors`） |
| 类型安全 | 弱（字符串拼接、`${}` 表达式） | 强（绑定到 POJO，支持嵌套、校验） |
| 松散绑定 | 不支持 | 支持（`app-name` / `appName` / `APP_NAME`） |
| 校验 | 不方便 | 可以加 `@Validated` + `@NotNull` |

**本项目的选择**：`appName` 和 `version` 是两个不相关的散装配置，用 `@Value` 够了。

**但 `app.cors.allowed-origins` 用 `@Value` 注入 `String[]` 就有点勉强**（`WebMvcConfig` 里那个），将来配置项多了会改成 `@ConfigurationProperties(prefix = "app")`。

## 四、设计决策

| 决策 | 选择 | 理由 | 替代方案与代价 |
| --- | --- | --- | --- |
| 探针收口 | `Callable` + `probe()` | 新增组件只加一行 | 每个组件写一遍 try-catch——重复 |
| 计时 | `nanoTime()` | 单调，不受系统时间调整影响 | `currentTimeMillis()`——可能算出负数 |
| MySQL 探针 | `SELECT 1` | 最轻量，不依赖业务表 | 查业务表——表没建就误报 |
| Redis 探针 | 原生 `PING` | 标准连通性测试 | `hasKey`——语义不对 |
| DOWN 时状态码 | **200** | 保留诊断信息 | 503——监控工具可能丢掉 body |
| 状态值 | 字符串 `UP`/`DOWN` | 对齐 Actuator 约定，阶段 8 无缝 | boolean——表达不了 DEGRADED |
| 依赖注入 | 构造器（`@RequiredArgsConstructor`） | 不可变、测试友好 | 字段注入——可变、掩盖依赖过多 |
| 配置注入 | `@Value` + 默认值 | 散装配置够用 | `@ConfigurationProperties`——此处过度设计 |

## 五、面试考察点

### 基础题

**Q1：健康检查接口应该检查什么？**

答题要点：
- 不只是「进程活着」，要检查**关键依赖**：数据库、缓存、外部服务
- 探针要轻量（`SELECT 1`、`PING`），不能查业务表、不能跑复杂 SQL
- 要能区分「服务死了」（连不上）和「依赖故障」（能返回详细诊断）
- 要记录耗时，区分超时和快速失败

**Q2：为什么 `Controller` 里没有 `try/catch`？**

答题要点：
- 异常统一由 `@RestControllerAdvice` 处理
- Controller 只做「接参 → 调 Service → 包装响应」
- 好处：代码薄、可复用、可单测

**Q3：`@RequiredArgsConstructor` 和 `@Autowired` 字段注入的区别？**

答题要点：
- 构造器注入：`final` 不可变、启动时保证注入、循环依赖立即报错、单测可直接 new
- 字段注入：可变、可能漏注入、循环依赖启动时能过但运行时报错、单测要起容器
- Spring 官方推荐构造器注入；依赖过多时构造器变长，刚好暴露「职责过多」

**Q4：`System.nanoTime()` 和 `currentTimeMillis()` 的区别？**

答题要点：
- `nanoTime`：**单调时钟**，只用于测间隔，不受系统时间调整影响
- `currentTimeMillis`：墙上时钟，会被 NTP 校时影响，测耗时可能出现负数
- 测耗时用前者，记录时刻用后者

### 进阶题

**Q5：健康检查返回 503 还是 200？**

答题要点（**这题答好很加分**）：
- 自定义接口返回 200：保留 body 里的诊断信息，给人看
- Actuator 的 `/actuator/health` 返回 503：给 K8s / 负载均衡做摘流决策
- 两者不冲突，都保留，用途不同
- 关键区分：**「服务进程挂了」根本返回不了东西，「服务活着但依赖故障」能返回详细诊断**

**Q6：K8s 的 liveness 和 readiness 探针有什么区别？**

答题要点：
- **liveness**（存活）：失败就**重启容器**。用于检测死锁、OOM 卡死。检查要极轻量（只看进程），不能依赖外部服务——否则数据库抖动会导致全部 Pod 被重启
- **readiness**（就绪）：失败就**从 Service 摘流**（不转发流量），不重启。用于检测依赖是否就绪
- 所以：liveness 查「我还能不能工作」，readiness 查「我现在能不能接客」
- **本项目的 `/api/v1/health` 适合做 readiness**，不适合做 liveness

**Q7：为什么 `probe()` 用 `Callable` 而不是 `Runnable`？**

答题要点：
- `Callable.call()` 声明 `throws Exception`，可以捕获受检异常
- `Runnable.run()` 不能抛受检异常，lambda 里写可能抛异常的调用编译不过
- 虽然本场景两个探针抛的都是非受检异常，但用 `Callable` 更通用

### 陷阱题

**Q8：健康检查接口会不会被滥用导致数据库压力？**

答题要点：
- 会。如果监控每 5 秒探测一次，`SELECT 1` 会一直占一个连接
- 缓解：`SELECT 1` 极轻量，但仍会消耗连接池连接（HikariCP 最大 10 个）
- 更好的方式：缓存探测结果（如 5 秒内复用），或用 Actuator 的 `HealthIndicator` + 缓存
- **不要**用业务查询做探针（如 `SELECT COUNT(*) FROM t_canvas`）——那是真的压力

**Q9：`@Value("${app.version:unknown}")` 里的默认值什么时候生效？**

答题要点：
- 配置项完全不存在时生效
- 配置项存在但值为空字符串时**不生效**（注入空串）
- 这是容易误解的点：`app.version:` （yaml 里空值）注入的是 null 或空串，不是 `unknown`

## 六、常见坑

| 坑 | 现象 | 原因 | 处理 |
| --- | --- | --- | --- |
| 用 `currentTimeMillis` 测耗时 | 偶尔出现负数耗时 | 系统时间被调整 | 用 `nanoTime` |
| 探针查业务表 | 表没建就报 DOWN | 依赖了不该依赖的东西 | 用 `SELECT 1` |
| 探针太重 | 监控压力大 | 查 COUNT / 复杂 SQL | 轻量探针 + 结果缓存 |
| 忘记强转 `RedisCallback` | 编译报「方法引用不明确」 | `execute` 有多个重载 | `(RedisCallback<String>)` |
| 连接没关 | 连接池耗尽 | 手动 `getConnection()` 忘了 `close` | 用 `execute(callback)` |
| 必填配置给了默认值 | 配漏了不报错，问题延后暴露 | `:unknown` 兜底 | 必填项不给默认值 |
| liveness 依赖数据库 | 数据库抖动导致全部重启 | 探针语义用错 | liveness 只看进程 |
